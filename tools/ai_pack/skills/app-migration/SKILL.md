# 业务程序迁移与复刻规范（以 C# 等强类型业务为主）

适用一切"把现有成熟程序（C#、Web、系统级软件）复刻迁移到 Zan"或"以现有产品为 UX 参照做同族新工具"的场景。核心目标是把返工从"事后发现"挪到"事前确认"，以最小代价产出高保真、纯正原生的 Zan 程序。

## 一、第一纪律：复刻，不创造、不阉割

1. **功能完整度 1:1 对齐**：
   - 动作：原版所有可见的按钮、窗口、菜单、右键项、快捷键、异常提示语、错误码均须完整复刻。
   - 为什么：任何自作主张判定"这个大概没用"并省掉的细节，都会在验收期被彻底打回；每一个凭空自创的控件与交互都会增加用户的认知与迁移成本。
   - 适用边界：允许排版现代化升级（如绝对坐标改弹性流式），但业务功能点与交互分支禁止阉割或自造。
2. **原版业务口径与缺陷原样保留**：
   - 动作：原版算法的循环边界、判断口径、字段取值、数据落盘路径（配置/缓存/DB）必须与原版严格一致。
   - 为什么：迁移者的首要职责是消除行为偏差；若擅自“纠错”，后续对照排查时行为基线会彻底断裂。存疑之处先挂账记录，代码先保持行为等价。

## 二、双账本先行机制（未对齐，不编码）

1. **结构与页面映射账本**：
   - 开工前盘点全部窗体/控制器/模块，建立 `原文件 (如 FormA.cs) ↔ 新文件 (src/.../FormA.zan)` 账本。
   - 新文件头部第一行注释显式声明对应原版类名，方便差距审计与调用追溯。
2. **Schema 与协议契约账本**：
   - 实体字段命名直接照搬底层 DB 或接口原始命名（含大小写），中文仅作为界面展示文案。
   - 严禁在迁移过程中自造中间层别名（如将 `creativeName` 擅改改写为 `title`），第二套命名会导致每次对接接口都必须做二次翻译，迅速失去维护性。

## 三、语义照原版，写法归 Zan（摒弃源语言思维包袱）

1. **严禁平行数组，强制“一行一实体”**：
   - 动作：原版若存在多个 `List<string>` 靠下标隐式对齐的旧代码，迁移到 Zan 必须合并为统一的强类型实体类（`class RowItem { ... }`）。
   - 为什么：平行数组极易因为某列缺失或排序引发静默串行，且无法复用标准表格排序/筛选组件；实体是对接真实数据的前提。
2. **标准库能力优先，严禁手搓影子库**：
   - 动作：实现任何能力前，先用 `zan_api_search` / `zan_example` 查验；只要标准库已有（如网络请求、JSON 编解码、加密哈希、容器集合、异步定时器），严禁在应用层手写底层轮子。
   - 为什么：手造影子库不仅质量缺乏保障，还会带来维护割裂，导致后续维护者重复踩坑。

## 四、C# 业务迁移核心映射规范

1. **类型系统与容器映射**：
   - `class` / `record` $\rightarrow$ Zan `class`，显式强类型字段，存取与加工分离。
   - `List<T>` / `Dictionary<K,V>` / `HashSet<T>` $\rightarrow$ Zan 标准库 `List<T>` / `Map<K,V>` / `Set<T>`。
   - `async Task<T>` $\rightarrow$ Zan `async` 异步函数。
2. **内存模型差异（CLR GC $\rightarrow$ Zan ARC）**：
   - 引用拓扑：父对象（窗口、全局控制器）持有子对象强引用；子对象反向引用父级必须声明为弱引用（`weak`）。
   - 事件解绑纪律：长生命周期的全局事件、通知中心、单例若订阅了短生命周期视图的方法，视图销毁时必须显式解绑。Zan 采用引用计数，遗漏解绑会导致委托强持有该视图，引发 ARC 内存泄漏。
3. **UI 窗体迁移（WinForms/WPF $\rightarrow$ Zan Gui）**：
   - 结构提取前置：先精读原版 `.Designer.cs` 或 XAML，提炼控件树层次与真实事件处理器，禁止盲目看截图抠坐标。
   - 绝对坐标淘汰：彻底弃用 `Point(x, y)` 绝对排版，改用 `Row`、`Column`、`Flex`、`Grow()` 等弹性容器；组件尺寸统一使用系统标准设计 Token。
   - 数据驱动解耦：严禁为了取业务数据而读取 `txtAge.Text`；控件只做展示和输入交互，所有计算必须依托强类型 `PageState` / `Model` 实体。
4. **数据访问与持久层（EF Core/Dapper $\rightarrow$ Zan Data）**：
   - 剥离 EF Core 的隐式行为：移除庞大的上下文跟踪（ChangeTracker）与惰性加载（Lazy Loading），所有查询明确显式化，避免 N+1 慢查询。
   - 遵循三级状态放置：瞬时交互在内存、高频热数据进缓存、事实数据进持久层。

## 五、精读核对四要素（消灭返工在动笔前）

在把 C# 的一个业务方法或事件处理器移植到 Zan 之前，先精读原版对应代码，核对以下四件事：
1. **作用的数据字段名**：从原版 schema/定义处确认字段拼写，不凭记忆猜。
2. **操作的目标行集合**：明确是作用于**勾选集（CheckedRows）**还是**当前激活行（CurrentRow）**。
3. **循环的粒度与层次**：明确是一组执行一次，还是逐行逐项执行一次。
4. **判断所用的数据集合**：明确过滤或校验是对**未过滤的全集**还是**已过滤的子集**计算。

## 六、闭环验证与协作纪律

1. **单模块/单窗体即时编译，严禁积压**：
   - 每写完一个实体或页面，立即执行编译：
     ```bash
     zanc <file.zan> --auto-stdlib -o _scratch/verify.exe
     ```
   - 严禁连续改写多个页面却不编译验证一次；编译阻塞时立即停下排查，严禁在未验证状态下继续铺展代码。
2. **算法探针断言先行**：
   - 涉及费率计算、加密算法、报文解析等纯逻辑，在 `_scratch/probe.zan` 中编写单测断言，确保与原版 C# 运算结果逐字节一致。
3. **验证即提交**：
   - 单个模块或窗体编译且冒烟通过后，立即执行 `git commit`（例：`feat(migration): 还原客户管理列表与筛选交互`），不让工作区堆积未提交的半成品。

## 七、逐位一致移植（确定性引擎/仿真/协议栈专用）

当目标是「与原实现**比特级一致**」（游戏引擎确定性模拟、协议栈、编解码、
加密、定点数仿真）时，第三节的"语义照原版"要升级为**逐位照原版**，并额外
遵守以下纪律。这类目标不是"用户可见行为一致"，而是**中间值也一致**。

### 7.1 对照床是唯一真值来源，不许凭读代码"想"出结果

- 动作：把原实现**原样编译成可运行的对照床**（直接 `#include` 真实头文件，
  零转写），让它在合成输入上吐出逐帧/逐步的数值 trace；Zan 侧吐同格式 trace，
  两者 `diff` 必须**逐字节为空**。
- 为什么：数值移植的错误几乎全是"我以为源码是这么算的"。对照床把"想"变成
  "看"，而且一次 diff 就能定位到第一处偏差的帧与字段，比人肉比对快几个数量级。
- 边界：对照床必须**直接包含原实现**，不得手抄一份——手抄那份就是新的漂移源。
  合成数据要够小但覆盖到被移植的路径（空指针/边界/无分支都要能跑）。

### 7.2 场景必须参数化，且两侧共用同一份场景描述

- 动作：把"初始状态"抽成场景描述（位置、目标、参数），**两侧解析同一字符串**，
  对拍脚本遍历全部内置场景。
- 为什么：单场景通过不代表移植对；交叉点、边界、互挤、掉头、静止这些边界
  路径各自暴露不同的语义错误。共用同一份描述杜绝"两边场景其实不同"的假一致。
- 边界：场景描述的**解析代码在两侧各写一遍**（语言不同），但**格式与取值必须
  一一对应**，改一处就要改另一处；发现不一致时优先怀疑解析差异而不是算法。

### 7.3 数值语义要落到"位"，不是落到"数学意义"

- 动作：定点数/宽整型/浮点的每个运算都要确认四件事：**中间量的位宽**、
  **舍入方向**、**溢出是否回绕**、**符号/无符号视图是否改变结果**。
  同一数学意义的两个写法（`x/2` 与 `x>>1`、`a/2u` 与 `a/2`）在位级可能差一位。
- 为什么：这类偏差不会崩程序，只会让结果慢慢偏，最后以"数字不对"的形式
  暴露，定位成本极高。
- 边界：特别核对**字面量后缀与构造函数是否等价**（如 `12_fp8` 与
  `fp8::integer(12)` 差一个移位因子）、**无符号视图下的除法**、
  **复合赋值与二元运算的截断差异**（前者调 `wrap()`、后者不调）。

### 7.4 容器/迭代顺序属于语义

- 动作：原实现里"插入到哪一端/哪一位置"的规则要照抄，包括看起来不重要的
  索引位置；每帧遍历顺序若影响结果，trace 里按原顺序输出。
- 为什么：确定性模拟里，遍历顺序决定谁先动、谁先被挤开，顺序一改结果就分叉。
- 边界：注意"插入到开头"与"插入到第 1 个位置"是**两回事**，后者常被误读成头插。

### 7.5 共享状态机（RNG 等）的调用序列就是状态

- 动作：所有推进全局状态的调用（随机数、累加器、事件队列）按**原顺序**复刻，
  并把"调用次数/最终状态"写进对拍输出的审计行。
- 为什么：少一次或多一次调用，之后所有数值全错，而且症状出现在很远的地方。
- 边界：审计行本身也要两侧同格式，否则"只有审计行不同"会被当成假阳性而忽略。

### 7.6 编译器缺陷要上报，不许绕路

- 动作：移植中撞到语言/编译器缺陷（重载没走、语法不支持）时，做**最小复现
  探针**，登记到语言仓库的缺陷台账（含现象、根因、方向、影响面），**并在移植
  侧用文档化的替代写法**，同时在代码注释里写明"这是编译器缺陷，不是设计选择"。
- 为什么：绕路会让缺陷永远留在编译器里；把绕路写清楚，至少下一个人知道这是
  债而不是规范。
- 边界：绕路只允许是**语义等价且局部**的（改用一个方法调用），不允许是
  "把整个算法重写成另一种风格"——那种会让对拍失去意义。
