# 编译器前端解析、绑定与语义检查契约

## 1. 扩展方法候选筛选与重载评分

- **接收者兼容性双向同步**：
  扩展方法的接收者兼容性判定必须同时应用于候选筛选（Filtering）与重载评分（Scoring）。当具体类实现接口、派生接口继承基础接口时，非泛型接口扩展方法应当能够被调用。
- **评分优先级准则**：
  ① 精确类型匹配（Exact Type Match）优于接口兼容匹配；
  ② 接口兼容匹配优于未受约束的裸类型参数（Type Parameter）。
- **泛型接口实参区分**：
  单纯通过符号层次遍历 `implements` 无法区分泛型实参（例如 `I<int>` 与 `I<string>`），必须保留完整的泛型类型实例化匹配路径，防止误匹配或漏匹配。

## 2. 语法解析器（Parser）分派契约

- **变量声明探测（`looks_like_var_decl`）**：
  在解析歧义位置（如泛型调用 vs 比较运算、局部变量声明 vs 表达式）时，前瞻分派必须严格核验类型指示符与后续标识符。
- **类型位置的节点分类**：
  语法树中位于类型位置（如字段类型、返回类型、泛型实参、局部变量类型）的标识符是 `AST_TYPE_REF`，而非通用的表达式标识符 `AST_IDENTIFIER`。后续 Binder 和 Checker 遍历时必须区分节点语义，严禁将类型引用降级为变量查找。

## 3. 调用形状与静态性判断

- **接收者槽位与静态性强相关**：
  在发射调用指令时，调用形状的接收者参数槽必须严格根据目标方法是否为静态方法来确定。实例方法必须提供有效的 `this` 接收者指针；静态方法和纯函数不得占用接收者槽位。
- **属性访问静态与实例区分**：
  访问属性时，若属性声明为 static，禁止通过实例接收者直接读写；反之实例属性必须绑定至有效实例对象，防止语义层绕过导致 IRGen 阶段解引用空接收者指针。

## 4. 闭包捕获与控制流分析

- **捕获变量而不是捕获值快照**：
  Lambda 表达式和局部函数捕获外部局部变量时，捕获的是变量的存储单元（Cell），以便在闭包内外实现共享修改。对闭包对象的保活必须遵循引用计数协议。
- **可空分析穿透复合控制流**：
  在进行可空性检查（Nullability Check）和空值守卫扫描时，静态分析必须穿透 `lock` 等同步块语句，同时核验锁体内外表达式与返回语句，避免误报合法的空值守卫逻辑。
## 5. 命名空间解析与包依赖（nsresolve）

- **只有 `using` 能解析包内类型，限定名不行**：
  同一命名空间树在 `stdlib/` 与 `packages/` 下各有提供者时，
  `System.Data.DataFrame`（限定名）报 `undefined type`，
  `using System.Data;` 后写 `DataFrame` 才行。
  但 `stdlib/` 下的限定名**可以**用（`System.Text.StringBuilder` 正常）。
  - 坑出处：写包间桥接时误以为限定名能省掉 `using`，结果编译不过，
    一度以为桥必须放在使用方包里。
  - 动作：跨包引用一律用 `using`，别赌限定名。
- **`using <命名空间>;` 是"整棵命名空间树"级加载，不是按文件**：
  `using System.Data;` 会把 `Zan.Data`（12 个顶层文件，含
  `DbValues` → `System.Data.Orm` → `System.Data.Sqlite`）与
  `Zan.DataFrame` 一起拉进来。编译单元数会从 12 涨到 33。
  - 注意这只是**源码**被拉进来（`SqliteConnector` 这类类型可解析）；
    原生驱动（`sqlite3`）是 `--publish` 时按 `driver.manifest` 打包的，
    普通编译不链。
  - 判定依赖代价的方法：拿"只用某命名空间"的最小程序编译，看
    `Compiled N files` 的 N。
- **依赖方向要用编译单元数定量，不能凭直觉**：
  实测 `Gui.Component.Chart` 依赖 `System.Data` 只多 19 个单元
  （337 → 356）；反向让 `System.Data` 依赖图表要多 297 个。
  - 判定：把桥放在**消费方**包（图表侧），让基础包不感知上层。
- **同一命名空间树可被多个包提供**：`using System.Data;` 同时命中
  `Zan.Data` 与 `Zan.DataFrame`，类型名冲突会在 checker 期报
  `undefined type`（不是重载歧义）。新增类型前要确认该命名空间下
  其它包没有同名类。
- **`ZANPKG_MISSING namespace=...` 是警告不是错误**：
  缺 `System/Text/Json`、`Gui/Styling` 等子命名空间时仍能编译通过
  （子命名空间按需加载），但对应能力不可用。看到这行要确认
  缺的是不是自己依赖的能力。

## 6. 前端模糊测试的 harness 纪律

- **harness 必须和被测程序一样预留大栈**：编译 fuzz harness 时带上与 `zanc`
  一致的栈预留（Windows MSVC 目标：`-Xlinker /STACK:33554432`；GNU ld：
  `-Wl,--stack,33554432`）。
  - 坑出处：不带时 harness 用的是进程默认 1MB 栈，**约 50 层括号嵌套就爆栈**，
    1560 个变异体里 23 个报 stack-overflow，看着像编译器有内存缺陷；实际上解析器
    有 `ZAN_PARSER_MAX_EXPR_DEPTH=512` 守卫（`src/compiler/parser.c:1573`），
    真 `zanc` 上同样的输入报的是 "expression nesting too deep (max 512)"。
  - 判定：肇事输入原样喂给真 `zanc`——真程序给诊断而 harness 崩，是 harness 的
    栈配置问题；真 `zanc` 也崩才是产品缺陷。
- **先拿 artifact 再下结论**：libFuzzer 把肇事输入写在 `-artifact_prefix` 指定的
  目录；先拿那个文件单点复现，再判断是产品缺陷还是 harness 假阳性。
- **Windows 下 ASan 是动态库**：`clang_rt.asan_dynamic-<arch>.dll` 必须与宿主架构
  一致（x64 机器拷 aarch64 的会得到 0xC0000135 DLL 找不到），并放在 harness
  可执行文件旁边或加入 PATH。
- 现成入口：`tests/fuzz/fuzz_frontend.c`（libFuzzer 入口，覆盖
  lexer/parser/nsresolve/binder/checker）+ `scripts/fuzz_frontend.ps1`
  （编译 + 播种语料 + 跑 + 收集 artifact）。

## 7. 前缀运算符表：两个后端必须逐项对齐（差分门抓不到语法层的分叉）

- **坑（2026-10-21 实测）**：C 宿主的解析器前缀表达式表少了一个 `+`
  （一元正号），自举侧一直有。于是 `+x` 在 C 宿主是**解析期**报错
  （`unexpected token '+'`），在自举侧照常编译。两个后端在**语法层**就分叉了，
  而差分门**全程绿灯**：差分门比的是程序 stdout，而这个用例在 C 宿主侧根本
  编译不过 → 连 conformance 套件都进不去，差分门自然无从比对。
  - 同一类分叉还有一种更隐蔽的形态：**一边派发重载、一边恒等返回**。
    实测类上的一元 `operator +`：C 宿主派发重载（输出 6/8/10），自举后端
    原样返回操作数（输出 5/7/9）——差分门同样看不见。
- **动作**：给任一后端增删改**运算符、关键字、字面量后缀**时，必须逐项对照
  另一后端的同一张表（前缀表达式集合、中缀运算符集合、类型关键字表），
  两边的表**一起改**。这类"语法表"目前**没有任何自动门**——差分门、conformance
  套件都是建立在"宿主能编译"这个前提上的，语法层分叉天然在它们的视野外。
- **口径**：差分门只能钉住"两边都能编译的程序输出一致"。**语法层**的分叉要
  另外钉：把两端口径一致的形态写成 conformance 用例并进差分门用例清单
  （例：`unary_plus`）；口径**不一致**的形态（例：类上的一元 `operator +`
  重载）**不要**进清单——那会把分叉钉成"两边一致"，改登记成自举缺口，
  免得差分门给假绿灯。
- **排查法**：两后端对同一程序的结论不同时，先分清是"一边编译失败"还是
  "输出不同"：前者是语法/检查层分叉（差分门看不见），后者才是降级层分叉
  （差分门能看见）。

## 8. `type_error` 哨兵**不发诊断**——返回它之前必须自己报

- **坑（2026-10-21 实测）**：checker's 一元运算分支对非数值操作数只
  `return c->binder->type_error`，而这个哨兵**本身不发诊断** → 错误一路漏进
  irgen：`-"x"` 造出对字符串指针的整数减法（LLVM 校验失败："Integer arithmetic
  operators only work with integral types"），`~"x"` 更是把编译器自己打崩
  （0xC0000005）。二元路径早就有 "cannot apply operator to 'X' and 'Y'"，
  一元这边只是漏了同款判定。
- **动作**：任何"类型不对就返回 `type_error`"的分支，必须在返回**之前**自己
  发一条诊断；哨兵只负责让后续阶段别再往下算，不负责报错。自举侧没有
  `type_error` 这个概念，检查器要么放行、要么自己报——两边都要落到"自己报"。
- **口径**：一元算术（`-` / `+` / `~`）的操作数 = 数值（char 与二元算术同口径，
  也算数值）或类 / 结构体（走重载路径）；类型参数与 `type_error` 不报——前者
  会在实例化时被具体类型替换，后者已经有别的诊断在报。
- **`!` 是另一条口径（2026-10-21 实测）**：一元 `!` 的操作数必须是 **bool**，与
  二元 `&&` / `||` 的 "both operands must be bool" 同口径，**不是"数值即可"**。
  坑在 `!` 打在非 bool 上**不产生非法 IR**——生成的是 `icmp eq <指针>, 0`，
  合法但语义荒唐（恒假），差分门与 conformance 全绿。措辞：
  `cannot apply unary '!' to 'X': the operand must be a bool`。
- **`!` 不像 `-` / `+` / `~` 那样只查原始类型名**：宿主没有 `operator !`，
  一元 `!` **没有重载路径**，所以类实例跟字符串一样非法（要一起报）；反过来，
  `bool?` 也不是 bool（宿主自己的二元 `&&` / `||` 也不接受可空 bool），要报。
  豁免只有两条：`type_error`（宿主）与**类型参数**（两边都得放行，实例化时才
  知道具体类型）。自举侧对应的两个细节：可空标志在类型节点的 `op == 1` 上，
  类型参数用 `binder.IsTypeParam(name)` 判——**别用 `IsPrimitive` 过滤**，
  那会把类实例整个放过，两端口径就分叉了。
- **改口径前先量存量**：`!` 的历史用法比一元算术宽（C 风格的 `!someInt` 会全量
  报错）。先全仓扫 `!\s*[A-Za-z_]` 看命中量，再决定是改代码还是放宽口径。
  实测：59 包全量扫描只命中 2 处真·误用——`Zan.Mvc` 的 `!force`（`force` 是 int
  字段，改成 `force == 0` 语义等价）与 `stdlib` `RandomExt.zan` 的 `!items`
  （`items` 是 `List<T>`，改成 `items == null`）。其余 5000+ 命中都是 bool。
- **跨后端**：这条检查必须**两个后端同一次落地**——自举侧的检查器补同样的判定
  与**同样的措辞**，再用 reject 用例把两边的措辞钉住
  （`tests/selfhost/reject_cases.txt` 的 `名字|||自举措辞|||宿主措辞` 三段式）。
  只改一边，差分门看不到（它比的是程序输出，不是诊断），但用户会拿到两套
  不同的错误信息。

## 9. 语言能力缺口要堵在**编译期**——`new T()` 这类"没有构造入口"的形态

- **坑（2026-10-21 实测）**：`class Maker<T> { T Make() { return new T(); } }`
  编译通过、运行期交出 **null**，第一次成员访问就崩进程（0xC0000005）。根因：
  类型参数没有构造入口，irgen 的 new 分支**既没报错也没生成构造调用**，只是把
  "未初始化的引用"返回了——静默错值，测试完全看不见。
- **动作**：这类"语言当前做不到"的事，检查器要**编译期报错**，别让运行期交出
  半个值。措辞 `cannot instantiate a type parameter 'T'`，两个后端同一次落地、
  同一句措辞，用 reject 用例钉住。语言真要支持"按类型参数造对象"，得先有约束
  系统（C# 的 `new()` 约束）——在那之前，**诚实的报错比静默的 null 强**。
- **分清两种形态**：`new T()`（标量）与 `new T[n]`（数组）**不是一回事**。
  数组的元素类型在实例化时被替换，路径是通的（实测 `T[] buf = new T[3]`
  正常），一刀切禁掉会打断合法代码。判据：宿主侧 `is_array` 为真时类型已被包成
  `TYPE_ARRAY`，类型参数判定自然不触发；自举侧 `NewExpr` 节点的 `ival == 1`
  是数组形态（`ival == 2` 是集合初始化式）。
- **推广**：凡是"宿主侧返回了一个半成品值"的分支，都是同一种病——检查器要在
  编译期把语义缺口堵住，而不是让运行期交出 null / 0 / 野指针。

## 10. 数组的元素类型是**另一个**节点——每个遍历器都要下钻 `array_element`

- **AST 形状**：`T[]` 在语法树里是**两层**——解析器把元素类型包进一个**合成的**
  `AST_TYPE_REF`（`parser.c` 的 `parse_type` 收尾处），合成节点持有数组标志，
  **元素本体挂在 `array_element` 指针上**（`ast.h` 的 `type_ref.array_element`）。
  合成节点上的 `name` 只是元素名字的一份**拷贝**。
- **坑（2026-10-21 实测，A469）**：名字解析阶段（`nsresolve.c` 的 `nr_walk`）
  原来只走 `type_args`，**不下钻 `array_element`** → 元素节点的名字从没被改写过。
  于是限定名元素类型（`Outer.Inner[]`）保留着点号原样，绑定期的
  `scope_find("Outer.Inner")` 查不到（嵌套类型不是作用域符号）→
  `undefined type 'Outer.Inner'`。同一个类型写成普通引用（`Outer.Inner x`）却
  正常——因为那条路径上的节点**是**被解析阶段改写过的那个。
  - 动作：遍历 `AST_TYPE_REF` 时，除了 `type_args` 还要走 `array_element`
    （元素节点自己也可能是包装节点——`T[][]` 是两层包装，递归即可）。
  - 顺带：元素节点与包装节点**同名**，所以 "ambiguous type" 这类诊断只能报
    一次——包装节点报，元素节点解析时把歧义检查静默掉（否则同一条诊断出现
    两遍）。解析阶段是**改写名字**的地方，遍历器不下钻 = 名字永远不被改写。
- **自查口径**：凡是"限定名在普通位置能用、在数组位置报 undefined type"的
  现象，先查那个位置的遍历器有没有下钻到元素节点。

## 11. 声明前瞻（`looks_like_var_decl`）：类型名的三种形态与 `?` / `[]` 后缀

- **类型名有三种 token 形态，各走各的规则**：声明前瞻里
  1. **关键字类型**（`string` / `int` / `bool` …）→ 关键字分支，**根本不看 `?`**，
     所以 `string?[]` 天生能过；
  2. **简单标识符**（`Encoding`）→ `TK_IDENT` / `TK_QUESTION` 分支；
  3. **限定名**（`System.Text.Encoding`）→ `TK_DOT` 分支。

  改前瞻必须**三处一起核**，否则会留下"简单名能写、限定名不能写"的洞。
- **真正的分界线是"两个维度"，不是一个**：实测（A479）`T?` 与 `T?[]`、
  简单名与限定名是**两个正交维度**——`Encoding? e` 能写、`Encoding?[] a` 不能写；
  `System.Text.Encoding? e` 不能写、`System.Text.Encoding?[] a` 不能写。
  只拿一两条探针就下结论会把边界记错（坑出处：A479 台账初版把它写成
  "简单名 vs 限定名"，实测真正的差别是「`?` 后是否跟 `[]`」**加上**「是否限定名」）。
- **`T?[]` 与 `cond ? [1,2] : x` 的分辨**：秩后缀的方括号里**只允许空白与逗号**，
  数组字面量里有表达式 → 靠这一条把"可空数组"和"三元里的数组字面量"分开。
- **限定名分支必须收紧到"标识符 + `;` 或 `=`"**：否则 `A.B ? c : d` 这种
  **限定名开头的三元表达式**会被当成声明，声明解析器会把 `?` 当成三元问号
  吃掉，后面一路报 `expected ':'`。
- **`?` 后跟 `?.` / `??` 不是类型后缀**：`TK_QUESTION` 分支要继续排除 `?` 与 `.`
  （`a?.b` / `a ?? b` 是表达式）。
- **教训**：前瞻这类"读几个 token 猜意图"的代码，**边界要拿矩阵测**。
  探针只覆盖你想得到的形态，矩阵才暴露真正的分界线——而且前瞻改动波及
  **全仓每个以标识符开头的语句**，回归面远大于看上去。
