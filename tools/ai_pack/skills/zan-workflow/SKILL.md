# 版本提交与任务管理规范

## 一、提交信息格式

```
<scope>: <一句话说清结果>（关键编号/上下文）
```

- **scope 用小写领域词**：compiler、runtime、irgen、checker、gui、game、
  server、css、gen、skills、docs、tasks……一个提交只属于一个 scope；
  跨领域的大改动拆提交。
- **冒号后写"做了什么结果"**，不写"修改了 xx 文件"——读 log 的人要的是
  结果。附关键影响："修 Split/ToArray 静默写坏数组槽" 比 "修 bug" 可查。
- **正文补充三点**（空一行后）：为什么改（根因）、怎么验证的
  （测试档/探针结果）、遗留了什么（未修项去 TASKS.md）。
- 反面：`update`、`fix`、`修改若干文件`、把五个领域塞进一个提交。

## 二、提交纪律

- **验证过即提交**：一轮改动测试通过就 commit，不把已完成的工作攒在
  工作树里——并发会话的 stash/checkout 会无声覆盖它。
- **一次提交一个完整意图**：功能+它的测试+它的 skill 沉淀同一提交；
  不把无关在途文件顺手带进去（提交前 `git status` 逐项确认）。
- **提交一律带路径限定**：`git commit -m ... -- <本次任务路径>`，不用无参数
  的 `git commit`。为什么：commit 提交的是整个索引，不是"我刚 add 的那几个"——
  共享工作树上其他会话已 `git add` 的在途文件会被一起卷进一个不相干信息的
  提交（实测发生过：一个功能提交把另一会话暂存的十几个文件全带上了）。
  **`-F <message文件>` 形式同样危险**——它是"提交整个索引"，不是"提交我 add 的"；
  带文件名的提交信息更容易让人以为已经限定了范围。
  发现混入且**确认 HEAD 仍是自己的提交**时：`git reset --soft HEAD~1`
  后按路径重交，他人暂存内容原样保留在索引里。
- **移动 / 重命名的提交，pathspec 要同时列旧路径和新路径**：
  `git commit -- <新路径>` 只提交**匹配 pathspec** 的条目，而重命名在索引里是
  "旧路径删除 + 新路径新增"两条——pathspec 只匹配到新增那条，**删除被漏掉**。
  症状：提交后本地看着对（工作区只有新路径），仓库里新旧两份文件并存，
  远程会多出一份旧文件。
  为什么：pathspec 的语义是"提交这些路径的当前状态"，不是"提交这一组改动"。
  边界：任何 `git mv` / 改名 / 移目录的提交。做法：pathspec 同时给旧路径与
  新路径（`git commit -- <旧> <新>`），提交后用 `git show --name-status` 核对
  出现 `R100`（纯重命名）而不是 `A` 加一条残留的 `D`。
  坑出处：一次"把九个文件归入子目录"的提交踩到——首次提交只带进新文件，
  旧文件仍是索引里的待删状态，`git status` 显示 `D` 才知道漏了。
- **`reset --soft HEAD~1` 前必须重新核对 `git log -1` 是不是自己的提交**：
  并发会话随时可能在你"发现混入"和"动手拆提交"之间往主分支上再落一个
  提交并推送——此时 `HEAD~1` 拆掉的是**别人的**提交，你的路径限定重交还会
  因"相对 HEAD 无变化"静默不提交，别人的提交变成悬空、只剩索引里那份增量。
  坑出处（实测）：拆混入时并发会话的提交恰好落在自己提交之上
  且已推送，`reset --soft HEAD~1` 拆掉了它。补救无损：对方的增量本就还在
  索引里，`git reset --soft origin/main`（或拆掉的提交哈希）即恢复原状——
  软重置只动 ref，不碰索引和工作树，别人的在途文件毫发无损。- **提交消息文件别用共享目录里的通用名，提交前逐字校验首行**：
  - 动作：`-F <message文件>` 的文件要放在**本会话专属**的名字下（如
    `zan_dir_input_msg.txt`），并在提交前**逐字校验首行**是不是本轮那条；
    提交后用 `git show -1 --stat` 核对"消息 ↔ 内容"配套。
  - 理由：`_scratch/` 是多会话共享的，`commit_msg.txt` 这类通用名会被别的
    会话覆盖——`git commit -F` 于是把你的改动挂在**别人的消息**下。实测
    （2026-10-21）：一个 9 文件的提交顶着另一会话的
    "feat(pkg): Game.Data 补齐 legend 的用法…" 消息，内容对、消息错。
  - 边界：改消息用 `git commit --amend`，**amend 前必须先确认 `git log -1`
    还是自己的提交**——并发会话随时会往主分支上再落一个提交，那次就差点把
    同事的提交消息改掉。消息确实错了但 HEAD 已不是自己的提交时，用
    `git commit-tree` 按原树 + 原父 + 原消息重建两个提交，再
    `git update-ref` 原子移动分支（索引与工作树都不动）。
  判定口诀：拆提交前先 `git log -1 --format=%h` 对哈希；哈希不是自己的就
  千万别 reset，改走 `git revert` 自己那部分或与对方会话确认。
- **污染的提交已经推送出去时，用 plumbing 重建 + `--force-with-lease` 强推**：
  此时 `reset --soft` 会拆掉别人叠在上面的提交（见上条），不能硬来。配方
  （全程不动工作树与真实索引，别人的暂存状态毫发无损）：
  ① 临时索引 `GIT_INDEX_FILE=<scratch>/idx`；`git read-tree <父提交>` 后
  `git add -- <自己的路径>`、`git write-tree` → `git commit-tree <tree> -p <父> -F <msg>`
  得到纯净提交；② 别人的提交用 `git merge-tree --write-tree --merge-base=<父>
  <纯净提交> <对方提交>` 得到合并树（不需要工作树，也不会把对方"顺带改的"
  文件算进你的提交——**注意 merge-tree 会把对方提交里相对父提交的所有改动
  都算进去**，要剔除就得自己用 `git update-index --cacheinfo` 定点回填
  父提交版本）；③ `git commit-tree <合并树> -p <纯净提交> -F <对方原信息>`
  → `git update-ref refs/heads/main <新提交> <旧提交>`（CAS，失败说明期间有人
  动过主分支，重来）；④ `git push --force-with-lease=refs/heads/main:<旧提交>`
  强推。坑出处（实测）：功能提交把另一会话暂存的 30 个文件卷进来，对方随后
  又在上面落了一个提交并推送；`reset --soft HEAD~1` 拆掉了对方的提交，最后按
  上述配方重建两条提交并强推修正，远端与本地归零。
- **PowerShell 里 `git diff --name-only` 的每行可能带 `\r`**：路径原样传给
  后续 git 命令会报 `fatal: Not a valid object name <路径>`——**且不中断
  脚本**（git 的 stderr 无缓冲、stdout 有缓冲，输出顺序还会骗人，看起来像
  另一个命令报的错）。路径一律先 `-replace "`r",""` 再用；批量循环里逐条
  校验 `$LASTEXITCODE` 与"预期成功条数"，否则会静默地一个都没改（实测
  30 个文件全被判成"不存在"而全被删出索引）。
- **同文件两方都改时，路径限定 add 仍会卷入对方 hunk——按 blob 定点暂存**：
  `git add <路径>` 是整文件粒度，对方在同一文件里未提交的 hunk 会一起进索引。
  配方：工作树保持双方叠加不动，取 `git cat-file -p <父提交>:<路径>`（原始
  字节）重放自己的变换，`git hash-object -w --stdin` 写 blob 后
  `git update-index --cacheinfo <mode>,<sha>,<路径>` 定点暂存——提交里只有
  自己的改动，对方的 hunk 留在工作树等他们自己提交。配套两条：① 提交后
  归属用 blob 等式核验——逐文件 `git rev-parse <提交>:<路径>` 对照预期内容
  的 hash 全等；grep 差集审计既会误报也会漏报（实测同一份 diff，grep 报
  数百可疑、blob 全等证明 0 混入）。② Windows `core.autocrlf=true` 下
  `git add` 的行尾过滤会把整文件重写成噪声 diff（LF/CRLF 翻转让 1337 行
  变 7308 行），脚本管道取 blob 内容也会被掺入 `\r`——一律 `git cat-file -p`
  原始字节，写入索引走 hash-object 绕过过滤器。坑出处（Mvc
  自限定重构实测）：16 个文件与并发会话的 Dao 解耦改动同文件交叠，路径
  限定提交仍混入对方 hunk，按上述配方拆出重交；首个提交还因行尾归一化
  全文件重写，`reset --soft` 后以 blob 重放修正。
- **提交信息诚实**：测试失败就说失败并写明；跳过的步骤写明；
  不写"完全验证通过"这种没跑过的结论。
- 禁止 `git add -A` 盲加；禁止把构建产物、日志、临时探针提交进库。
- 历史只前进：不 revert 别人的提交来"解决问题"，修根因向前修；
  回滚是决定不是调试手段。

- **Windows 目录级 git mv 被 Permission denied 拒绝时逐子目录移动**：目录改名
  需要目录句柄独占，任何进程把它当 CWD / 资源管理器开着它 / 索引器扫它都会拒绝，
  而子目录/文件的改名只需各自句柄空闲——`for d in ...; git mv stdlib/X pkg/src/X`
  逐项执行，锁定项报错重试即可，最后 rmdir 空壳。踩坑（整包 Gui 拆分）：
  目录级 `git mv stdlib/Gui packages/Zan.Gui/src/Gui` 连续三次 Permission denied
  （当时无 zanc 进程），逐 17 个子目录移动全部成功。

- **搬移带驱动束的包，`git add` 会被 .gitignore 静默拦截**：*.dll/*.so/*.dylib
  是全局通配忽略且无 drivers 例外，整目录 `git add packages/X` 不报错但二进制
  全部不入库——推送后才发现 HEAD 缺 lua54.dll（Zan.Scripting 实测，
  靠 Zan.Data libpq.dll 已入库作对照才定位）。搬完 `git ls-files`/status 逐文件
  比对，二进制逐个 `git add -f`；文本驱动束（driver.manifest/bundle stub/def）
  不受影响。附带坑：Windows 检出（core.symlinks=false）重加 symlink 会退化成
  100644 文本文件，Linux 侧拿到假 so——用
  `git update-index --add --cacheinfo 120000,<blob>,<路径>` 恢复链接语义。

- **重建提交态二进制产物前，先核对编译闭包的 git status**：共享工作树上
  另一会话未提交的源码编辑会被重建直接烤进产物——发出去的二进制里是别人
  的半成品，而"产物提交时间新于源提交"的陈旧判定还显得一切正常。重建
  驱动/交叉对象等提交态产物前，把编译闭包源逐个过 `git status --short`；
  有 ' M' 行就等落库再建，或 `git worktree add` 检出干净 HEAD 在旁路重建。
  坑出处（/04 两连）：平台驱动 dll 从并行会话在途的源码编出并入
  staging——当时自己的 status 检查带 grep 过滤把 ' M' 行滤没，复核才发现
  并撤销；次日十四件交叉运行时对象同型拦截（闭包内三个源文件在途，缓建）。
  反向坑同日验证：日期判陈旧≠内容陈旧——那十四件重编后与提交态字节全同
  （判定只看提交时间会虚报），动手重建前先做字节裁定（重建比对），
  字节同=现役零提交，别把日期账当真账清。

- **私有 index 提交：暂存与提交之间 HEAD 可能被推进 → 提交会静默回退别人的改动**：
  共享工作树上"只提交我自己的路径"要用私有 index（`GIT_INDEX_FILE` +
  `read-tree HEAD`），但**暂存**与**提交**之间 HEAD 可能被并行会话推进；此时
  提交出去的树 = 旧 HEAD + 你的改动，它会把新 HEAD 上别人的提交**整块顶掉**
  ——症状是你的提交的 `--stat` 里多出几个你根本没碰过的文件（显示为删除）。
  - 坑出处：私有 index 在旧 HEAD 上暂存，提交前并行会话落下一笔提交（给两个
    文档副本加 27 行），我的提交把那 27 行整段顶掉。提交尚未推送，用
    `commit-tree` + `update-ref` 原子重建才没造成损失。
  - 动作：**提交前按当前 HEAD 重新 `read-tree` 再暂存**；或者用
    `git commit-tree <tree> -p <当前 HEAD> -F <msg>` + `git update-ref
    refs/heads/main <new> <old>` 原子重建（更新前校验 HEAD 未变）。重建后必须
    核对两件事：`git diff --name-status <父> <新>` 里只有你的文件，且**没有**
    别人的文件被顶掉。
  - 附带坑：**用 `Copy-Item` 还原源码会保留旧的 mtime**，构建系统认为目标文件
    已经是最新 → 链出来的二进制其实还是旧代码。还原后要么改 `LastWriteTime`，
    要么强制重编，并**用一个探针复验产物确实含新行为**。

- **公共 index 会被别的会话填满:`git commit` 提交的是整个 index,不只是你 add 的**。
  共享工作树上另一个会话 `git add` 后没马上提交,它的暂存就躺在**同一个**
  index 里;你 `git add` 自己的文件再 `git commit`(不带 pathspec),
  会把对方的暂存一起提交——内容不会丢,但归属错乱(你提交里出现
  你根本没碰过的文件)。
  - 动作:**提交前先 `git diff --cached --name-only` 复核 index 列表**;
    出现不属于你的路径就别直接提交,改用私有 index
    (`GIT_INDEX_FILE` + `read-tree HEAD`)只提交自己的路径。
    提交完再 `git show --stat <sha>` 核一遍带进去的文件。
  - 坑出处(2026-10-21):提交"体检脚本修正"时把并行会话暂存的
    `packages/Zan.Jobs/`、`docs/ECOSYSTEM_ROADMAP.md` 等一并带进
    b0961ed37。已核实历史连续、无删除项、内容完整(没顶掉别人的提交),
    并已用 `session send` 通知相关会话"照常提交即可"。
  - 配套的坑:**提交前不复核 index,就等于替别人提交**——尤其在
    `git add` 与 `git commit` 之间还有别的会话在动同一个工作树时。
- **提交后把自己的路径从共享 index 里摘干净**：共享 index 里可能存着你**已提交
  路径的"提交前旧内容"**（私有 index 提交、或并行会话动过索引之后）——下一次
  `git commit` 会把这几条路径按旧内容再提交一遍，等于把你刚提交的功能 revert
  回去。症状：`git status` 里自己的文件是 `MM`，且 `git diff --cached` 看到的
  是自己改动的**反向**。
  - 动作：提交后立刻 `git reset HEAD -- <自己的路径>`（把 index 同步到 HEAD，
    不动工作区）；私有 index 提交后同样要 reset——共享 index 里你的路径还停
    在提交前。reset 前先用 `git diff HEAD --stat -- <路径>` 确认工作区内容
    是对的（要 reset 的是 index，不是工作区）。
  - 坑出处：属性协议提交之后，自己的 5 个路径在共享 index 里是提交前的旧内容；
    `git diff --cached` 显示自己刚提交的改动被反向撤销。后续任何提交若不先
    reset，那 5 个文件都会被按旧内容提交——功能"凭空变回去"。发现时工作区内容
    是对的，reset 一下即修好。
- **判"这条红灯是不是我造成的"：先比 exe 与源文件的时间戳**。共享工作树里
  别的会话改了编译器源码并**重新链接了 `build/zanc.exe`**，你随后跑测试看到
  的行为就**包含他们未提交的改动**——红灯可能是他们的，不是你的。
  - 动作：比 `build/zanc.exe` 与被改源文件的 mtime——exe 更新 ⇒ exe 里含
    未提交改动；再用 `git status` 确认那个文件确实在途。判完再决定是自己的
    锅还是别人的。
  - 坑出处：清掉 GUI 包里的 97 处无效 `using` 后跑受影响用例，一个输入框
    用例红了（golden 写 `ex unknown 0`、实际输出 `ex unknown false`）。查下来
    是并发会话**未提交**的改动（让 `Convert.ToString(bool)` 改渲染
    "true"/"false"），`zanc.exe` 比该文件新两分钟——那条 golden 要跟着他们
    那条线一起更新。没查时间戳就改 golden，等于替别人的在途改动背锅，还可能
    把 golden 改成错的方向。
## 三、任务台账（TASKS.md）：挂账有据，清账移单

- **台账只记两类**：未修缺陷（编号+一句话现象+根因线索+复现探针位置）、
  未开工的结构性任务。台账是"当前欠什么"的清单，**不是工作历史**——
  清单越长，AI 与人检索有效信息的成本越高，本身就是干扰。
- **挂账**：新缺陷一行一条；编号稳定不复用（作废的号留 `[-]` 与原因）。
- **挂账"编译器回归"前的三步对照**（误诊教训）：把
  "示例/项目编译失败"定性为主线回归前——① 查项目 README 与构建脚本的
  文档调用形态，照抄重试：多单元项目各有受支持形态（全文件清单、
  包源+跨项目数据文件、.html 设计稿必须是第一个编译输入——GenForm 从
  它合成窗口与控件字段，漏了报一片 undeclared identifier）；② 用 dist
  发布快照工具链跑同一调用对照——同样失败=从来如此，不是回归；
  ③ 编译通过后跑运行时自检（html_gallery 启动即打
  `SELFTEST fails=N of 86` 逐组件机检）——编译过≠装配对，正是走完
  这三步才发现真问题（kind 改名漏同步示例断言）。
- **修复必须同族扫尾**（深度审计实证四处同型漏网）：单点修复/
  加固落定后，grep 同型模式收尾，验收口径是"同族零残留"而非"本点修复绿"
  ——① 同函数的其它调用形态（修了 `+` 拼接丢内嵌 NUL，字符串插值是同族
  漏网）；② 拷贝粘贴的姊妹实现（给读侧加了 512MB 载荷上限，四处复制粘贴
  的写侧扩容循环全部漏网）；③ 读侧/写侧、编码/解码的成对面（读侧加固批
  不带写侧）；④ 平台矩阵的姊妹目标（修了一个平台的驱动依赖，姊妹平台的
  驱动缺 payload 同型存在）。不同族扫尾 = 下一轮审计重新发现一遍。
- **结单（清账三件套）**：缺陷修复闭环 = 修代码 + conformance 用例 +
  台账闭账，三件同一提交。闭账动作不是打勾，是**把条目移出未完成清单**：
  已完成条目压缩为一行摘要（`A7-5 ✅ 一句话结论 + 用例名`），
  排查过程、根因分析原文进提交正文，不在台账保留多行记录。
- **定期平账**：台账累积到可见的体积（或按轮次）全量复核一次——
  实际已完成仍标未完成的翻转状态、重复编号合并、被推翻的结论移入
  "已撤回的结论"、已完成章节整体压缩。复核结果（哪些批量关闭）
  在台账头部记一行，不写流水。
- **台账不做日记**：过程细节、排查流水只进提交正文或 skill；
  结论被推翻时改正文并在文末留撤回记录，不静默修改。

## 四、会话卫生（探针与产物的建立、清理标准）

散落的调试产物是可复现污染——实测一个项目的暂存目录能堆到数十 GB、
几千个条目，同一个探针复制出几十份。纪律如下：

**建立（写探针前）：**
- **一个会话一个目录**：所有探针/截图/日志/中间产物放
  `<项目约定的暂存目录>/<本轮主题>/`，禁止散落在源码树、仓库根、
  build 目录或用户目录——产物落到哪取决于命令的当前工作目录，
  **每条命令显式给绝对输出路径**，不依赖隐式 CWD。
- **探针文件用固定名，修改迭代而非复制**：复用固定名（如 `probe.zan`、
  `dbg.exe`）原地覆盖；"再存一份旧的"就是复制扩散的起点。
  版本历史与任务台账承担"保留旧状态"的职责，暂存目录不承担。
- **构建产物只落在构建输出目录或暂存目录**：编译输出一律指向这两个
  位置之一，不写进源码树。

**清理（每轮收尾的清场动作）：**
- 会话结束：删本轮暂存子目录（或至少删可再生的产物文件），
  源码树 `git status` 无游离文件。
- **确要长驻的（SDK、工具链、对照基线）**：目录里放一行 README.md
  写明是什么、怎么再获取——有 README 的条目按约定跳过清理脚本。
- 大体积清理由清理脚本兜底（按最久未动时间整条删除，dry-run 默认、
  显式确认才真删）；跑它的时机是暂存目录涨到数 GB，而不是等磁盘满。

**交付说明只写用户要关心的**：结果、验证证据、影响面、遗留项；
调试中间产物的路径不进交付说明，只进提交正文（如属必要）。

## 五、CI 黑腿排查定式（push 后 workflow 不落地/腿变红时）

- 判"腿没跑"还是"腿跑了挂"：先看 job 的 steps 时间线——2 秒即终、零 step = 没
  跑；真跑了才有编译/测试日志。坑出处：额度耗尽期把 "completed failure" 误读成
  workflow 坏，连修三天方向全错。
- 没跑的原因看 check-run 注解（GET /repos/{o}/{r}/check-runs/{job_id}/annotations）：
  "not started because an Actions budget is preventing further use" = 私有仓
  Actions 额度耗尽（免费 2000 分钟/月，macOS 腿 10× 计费，一次全腿实跑即烧完；
  run 会永远 queued，六腿包括 ubuntu 全体不动）。根治=转公开或提额，账期重置日期
  只有仓库设置页可见，API 拿不到。
- bot 回写是否落地看 API commits（GET /repos/{o}/{r}/commits）而不是本地
  origin/main——网络差时本地远端 ref 是陈旧的，会把"已回写"看成"没回写"。
  workflow_dispatch 手动触发不等于 push 事件：带 `github.event_name == 'push'`
  条件的回写步骤在 dispatch 下按设计跳过，产物只进 artifact。
- 环境镜像漂移会让昨天绿的步今天红（包管理器镜像剥掉 base 内置工具、编译器
  大版本升级改变默认产物落点、setup 步安装清单缺包），且后一步的坑会遮住前
  一步的：修一个红点要等下一次实跑暴露下一个，逐层剥。

## 六、版本号

- 面向发布（对外可见的行为变化/API 新增）才动版本文件；
  内部修复不动。版本变更单独提交或随主功能提交，不夹带无关改动。
