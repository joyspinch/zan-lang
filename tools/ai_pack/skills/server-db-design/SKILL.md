# 服务端 DB 专属数据层细则

通用思想（存取与加工分离、4 字节定长、主记录窄+大字段按键拆分、
派生数写时维护、状态三级放置、键控聚合）见 `data-modeling` skill，
本文件只写 SQL 数据库场景特有的落地细节。

## 一、JOIN 为什么不进 DB

- JOIN 让 buffer pool 命中率被大字段拖垮、让索引选择变复杂、
  让表间耦合从代码挪进无法版本化的查询计划里。
  定长窄表全在缓存里，`WHERE id IN (...)` 等价于内存 hash 拼装，代价远小于 JOIN 扫描。
- 落地形态：第一遍查询只取主表索引 id 列（带过滤排序限量），
  第二遍 `id IN (...)` 取整行，内存按原序拼装。
- 边界：这不是"拉全表到内存再聚合"——等值过滤、排序、LIMIT 必须留在 SQL
  （有索引支撑的），内存只做拼装+格式化。

## 二、分页与深翻页

- 两段式：第一遍只查 id 列（排序+分页），第二遍按 id 取全列，内存保持原序。
- 深页码（超过总页一半）反向取再反转集合，避免 `LIMIT 100000,20` 的扫过式代价。
- COUNT 只数索引列，不数 `*`。

## 三、索引与行宽

- 二级索引叶子带主键，主表行宽直接决定索引页能放多少行；
  窄表的列表扫描/计数/分页全是索引内覆盖扫描。
- 每表标配：自增主键 id、create_at/update_at（int Unix 秒）、status、
  is_delete（逻辑删除，数据访问层默认注入 is_delete=0）。
- 纯定长小表（任务队列位、秒级状态）可考虑 MEMORY/固定行格式，
  把"定长槽位"推到极致。

## 四、MySQL 类型细则

- 布尔/状态/枚举一律 `int unsigned`，不用 tinyint/smallint。
- 金额/比率/坐标定标成整数（分、固定标度），不用 decimal/float。
- 时间一律 `int unsigned` Unix 秒，不用 datetime。
- 超范围大数（外部平台 id、累计成交额）用 `bigint unsigned`。
- varchar 留给真正的短文本（标题、名字）；正文类长文本进 1:1 副表。

## 五、缓存旁路（cache-aside）写法

- 先写库，**同一调用内同步写缓存**（批量 MSet），
  不允许"写库后异步过期"造成的读旧窗口，除非业务明确容忍并注明。
- 缓存键前缀集中为常量（挂在实体模型上），禁止散落的字符串拼接键。
- 瞬时状态（限流/互斥/统计计数）不进缓存层也不进 DB，
  用进程内共享结构（内存表/原子计数），互斥锁带超时自动解锁。

## 六、慢查询治理

- 任何 SQL 超阈值（如 1s）自动落慢查询日志；按 SQL 指纹
  （参数归一化后的 hash）聚合耗时与次数——优化有靶子，不靠猜。
- 连接经池化封装：借出-归还-异常回收收在数据层基类，
  断线按错误消息白名单（gone away / killed / lost）识别并重试一次。

## 七、买断/领取的并发互斥：条件更新 CAS

- 「先 SELECT 看状态、再 UPDATE 改状态」两步在并发下必然双花
  （两人买走同一挂单、领走同一奖励）。抢占必须是一条条件 UPDATE：
  `UPDATE ... SET 占位 WHERE id=? AND 状态仍=原值`，以 affected 行数判胜负，
  败者明确报"刚被别人抢走"。
- 占位值不能是"另一个正向合法值"：把卖家 id 改写成买家 id 时，该行仍满足
  "在售"过滤（sellerId>0 一类），顺序双买照样发生。占位要让该行**退出**
  在售/可领过滤集（如取负数作已售标记，列表只取正值）。
- e2e 必须有并发用例：N 个买家同抢一件，断言恰好一人成功；
  探针谓词用目标回复的独有形状，宽谓词（"有 ok 即中"）会被心跳回复误命中。

## 八、评审补充（SQL 场景，在 data-modeling 七条之上）

1. 列表接口是单表索引查询 + 内存拼装吗？有没有混进 JOIN/子查询/函数计算？
2. 分页是两段式吗？深页反向了吗？COUNT 数的是索引列吗？
3. 缓存是同步双写吗？键集中管理吗？
4. 慢查询有指纹聚合统计吗？连接池化了吗？

## 九、CodeFirst 只建缺表，不补缺列

- `SyncStructureAllAsync`（CodeFirst 全量同步）**只创建缺失的表**，对已
  存在的表不校验也不补列——模型加字段后启动即 `UPDATE 旧表.新列`，会撞
  "no such column" 直接崩掉进程。补列必须显式
  `DbSchema.MigrateAsync(db, table, List<DbColumnDef>)`
  （`DbColumnDef.Of(name, kind)`），列落位后再做数据回填。
- 迁移与回填都要幂等：这段代码每次启动都跑，重复执行必须是无害 no-op
  （列已存在跳过；回填只更 `WHERE col IS NULL` 的行）。
- SQLite 的 `PRAGMA journal_mode/synchronous` 是"赋值并回显新值"的语句，
  `ExecuteAsync` 对返回行的语句会抛 "the statement returned rows"——
  必须用 `QueryAsync` 读掉结果集。
