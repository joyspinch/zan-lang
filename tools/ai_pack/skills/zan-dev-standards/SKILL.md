# Zan 开发规范总纲

定位：给 AI 的可落地标准。每条规则都是"动作 + 为什么"，不含项目流水。
领域细则：GUI 排版见 gui-design；游戏帧循环见 game-dev；服务端架构见
server-dev-standards；数据建模见 data-modeling；SQL 细则见 server-db-design；
版本提交/任务台账/会话卫生见 zan-workflow。

## 一、开发工作流（固定闭环）

1. **定向**：明确改的是哪一层（编译器/stdlib/模板/应用代码），读相邻同类的
   现有代码作为风格与写法基准。
2. **查证后再写**：不确定的 API 用符号索引（zan_api_search/lookup_symbol）
   查到签名再落笔，禁止凭印象造接口。
3. **编译-运行-验证**：`zanc <file.zan> --auto-stdlib -o out` 后必须运行
   并观察输出；"编译过了"不是完成标准。
4. **改编译器/stdlib 必须带 conformance 用例**（`tests/conformance/`），
   并跑受影响的最窄测试档；探针只算预检，不算验证。
5. **修根因，不绕行**：Zan 代码失败若源于编译器/runtime 缺陷，去修编译器，
   禁止把业务代码改写成绕开缺陷的形状。
6. **动包的公共 API 前全仓查消费方，grep 必须含项目模板与示例目录**：包内
   类型被模板与服务端样例跨包消费是常态（CSV 合并成包，两份旧
   `Csv` 共 8 处消费方，其中 4 处在模板里，漏一处 = 模板验收门红）。改 GUI/
   基础库公共 API 同理——一次异步化重构给模板写了不存在的 `Form.Close`，
   模板自此编译不过，直到模板门复跑才暴露。删除/搬家包文件、
   改公共 API 之后跑一遍"编译全部项目模板"的验收测试收口。
7. **禁止手搓简化版复刻仓库验收脚手架**（脚手架脚本这类）：模板占位符内容
   替换、入口文件重命名、manifest 键解析、target 分支参数，少搬一步就是整批
   假阳性（复刻缺占位符替换与入口逻辑，19 个模板假红空转一轮，
   真失败只有 1 个漏网消费方）。能直接跑现成验收测试就直接跑；复刻仅用于
   定位单模板问题，且必须对照原脚本逐行搬齐。

8. **跨平台模板不固化开发机目标，实例配置以用户选择为准**：通用模板省略
   固定平台；创建项目时按键覆盖用户显式选择，不能只在键缺失时追加，也不能
   依赖图标等可选资源是否存在。未选择时按宿主 OS 与架构回退；读取平台只解析
   对应字段，禁止全文搜平台名。模板复制曾保留 Windows 默认值吞掉向导选择，
   而本机编译仍通过；验证必须断言生成的配置，并覆盖已有键、缺失键和多平台。
   模板自带的 zan.proj 同理要参数化：写死的 `name=` 会被发布管线读走当产物名
   （gui-workbench 实案：项目叫别的名字，发布出来还是模板名）；模板里的死键
   （`auto_stdlib` 全仓无消费方）与手搓平台 API（kernel32 设环境变量在非
   Windows 静默失效，stdlib 已有跨平台对应物时必须换）都是同族债。

9. **跨平台基础能力在库内统一，宿主系统不决定应用目标**：先查已有门面，缺后端
   时补库；公共参数和返回类型不能随平台变化，应用侧不为同一能力复制系统调用。
   为什么：信号量句柄曾在 Windows 返回 nint、POSIX 返回 string，使用者被迫写
   平台分支；统一为不参与 ARC 的句柄后，同一用例可直接在两端编译运行。
10. **跨平台回归验证语义，不复制宿主金样**：覆盖 Unicode、空格、系统工具缺失
    和平台合法的文件名；启动成功只证明 exec/系统处理器被启动，不证明目标完成。
    为什么：反斜杠在 POSIX 是合法文件名字符，Windows 金样会误报；双 fork 只等
    中间子进程会把最终 exec 失败误报成功。交叉编译与目标实机运行分开报告。
11. **新增 cmake 脚本的循环用 `foreach(... RANGE ...)`，不要用 `for(... RANGE ...)`**：
    工具链是 CMake 4.x 时，`for()` 在脚本模式下不再解析（报 "Flow control
    statements are not properly nested" 或 "Unknown CMake command for"），
    `foreach(RANGE)` 在各版本都能用。
    为什么：`for()` 的报错指向 `endforeach()`，看起来像"括号没配平"，实际是命令
    本身不可用，排查方向完全会被带偏。
## 二、工程师认知与交互纪律（讲人话、重实效、拒绝机械报幕）

1. **单次读取与上下文信任（禁止反刍读取）**：
   - 工具调用已知或已读到的代码/结构默认完全记住；严禁对同一文件的同一片段反复 `read_file`。
   - 修改代码遵循「grep定位 -> 紧凑读20~50行上下文 -> 直接edit -> 窄档测试闭环」，禁止大范围通读无关代码。
   - 编辑后不要为了“确认写进去了没有”而二次回读，工具自会报错或校验。
2. **人类对话风格（讲人话、重实效、拒绝机械报幕）**：
   - 彻底摒弃公文式汇报、虚词套话、报幕前缀（如“一句话交代动作：”、“正在执行：”等）与自问自答式的过程流水账。
   - 工具调用非必要不发空话，直奔执行；仅在方向切换或关键耗时操作前简短自然说明，严禁给发言套用固定口头禅或句式模板。
   - 最终回复直接给结论：“改了哪、为什么、验证结果”。
   - 遇技术分歧像老手同事一样给出明确推荐与利弊，不抛出冗长选择清单反问人类。
3. **带着工程假设破局（主动推进而非原地打转）**：
   - 面对报错或新需求，基于架构直觉形成 1~2 个最可能的假设并以最小代价验证，不盲目漫游全仓。
   - 验证过即自动提交，不堆积未提交的工作区变动。

## 三、代码规范

- **GUI 与游戏排版及实体建模统一规范（Flex + Float 单轨化，废除双轨与旧式 Dock）**：
  ① 界面与游戏 HUD 排版模型归一：全面收敛为 `Flow`（参与父级 Flex 弹性盒主轴与交叉轴伸缩、间距 Gap）与 `Float`（脱离文档流绝对/浮动摆位，结合九宫格 Anchor 锚点对齐自适应分辨率）；彻底淘汰传统桌面切边式 Dock 停靠算法与独立的游戏绝对像素画布；
  ② 游戏 UI 本质即 GUI 皮肤化：游戏世界视口（`GameViewport`）作为 GUI 控件树中的内容节点，上层 HUD、背包、血条、技能栏直接复用标准 GUI 控件（`Button`/`ProgressBar`/`Panel`/`Flex`），视觉差异纯粹通过 CSS 类、主题贴图与九宫格边框（Border-Image）实现；
  ③ 实体强类型与 Enum 规范：高频渲染、设计器文档模型与动作分发全面采用强类型实体（如 `SceneActionBinding`、`FieldPositionMode`、`SceneAnchor`）替代动态弱类型字典或通用 `JsonValue` 解包，彻底根除高频帧循环中的哈希查找与堆内存浪费；`JsonValue` 仅作为磁盘持久化边缘的序列化载体。
- **Zan.Gui 界面禁止自绘**（源码 `packages/Zan.Gui/src/Gui`），全部用标准库控件与布局原语完成。
- **GUI 控件的样式解析与类型身份只有一条路**：
  ① **样式解析走基类入口**：控件解析自己的外观用 `Control.Box(app)` /
     `BoxState(app, state)`；借用别的类型的外观用
     `ResolveStyleAs(app, type, cls, state)`；**部件表面**（列表行、树行、
     滚动条轨道、弹层、分割线）用 `BareBox(app, type, state)` 取**裸基线**
     ——裸基线不带本控件的 Class、不带 id、不套行内覆盖：套上会串味
     （列表写成 `.primary` 就把每一行都染成主色）。控件实例方法里直调
     `Style.Of` / `Style.Full` 一律算违规（门禁：组件契约审计脚本的
     R4 规则）；静态 helper 没有 `this`，解析显式的（类型, 类）组合
     不算违规。
  ② **内联 style（`SetProp("style", ...)`）分两半**：视觉键（背景/颜色/
     圆角）在**解析时重放**进样式盒，控件上不留第二份副本——替换原文后
     旧值不留残影；布局键（width/height/pad/gap）**必须即时落控件**——
     样式盒里的 width 只影响画出来的那张面，撑不开控件的槽位，漏了这一段
     就是"写了等于没写"（坑出处：内联通道改成"解析时重放"时把布局键
     一起丢了，`style="width:88px"` 失效，回归用例 `gui_field_style` 变红）。
  ③ **控件的 kind 名单三处副本要对得上**：运行期重建注册表
     （`ControlBootstrap.Names` + 各族 bootstrap）、编译期限定名单
     （`GenForm.IsStdWidgetKind` / `IsHmiKind`）、控件自己声明的 `Kind()`。
     少一处就出两种症状：按 kind 重建拿到 null，或生成代码发裸名、用户
     项目的同名全局类压过 stdlib（坑出处：`Row`/`Spacer`/`FormGroup`/
     `FormItem`/`Modal`/`Drawer` 在注册表里却不在编译期名单）。
- **窗口程序开发铁律：UI 线程专职渲染与事件派发，业务/IO/计算绝对异步解耦非阻塞**：
  ① **职责唯一性约束**：UI 线程（主事件消息泵）核心使命是保持 60/120Hz 丝滑响应，只负责系统输入事件分发与界面排版绘制（Layout -> Paint -> Present），单次事件或帧处理耗时红线严禁超过 2ms；
  ② **严禁同步阻塞反模式**：严禁在 UI 线程直接执行网络通信（HTTP/WebSocket）、磁盘文件大读写、数据库 SQL 执行、大 JSON/XML 解析、图像解码、重 CPU 计算或同步 `Sleep`；
  ③ **架构解耦三段式**：立即响应反馈（UI 立即置灰/挂起 Loading，<1ms 放行） -> 后台非阻塞执行（Worker/Thread/Task.Run，纯内存隔离，严禁直接读写 UI 控件） -> `App.Post` 封送回传（唤醒消息泵，在 UI 线程统一排空回调回填数据并触发 `needsRedraw`）；
  ④ **生命周期与协同取消**：后台作业必须挂接 `CancellationToken` 或取消标志，窗口关闭或请求作废时即刻终止，杜绝野回调污染。
- **Win32 资源所有权必须分开记账，程序默认图标取自身 exe**：
  ① **系统共享图标不能销毁**：`LoadIcon(0, IDI_APPLICATION)` 这类是系统资源，
     `DestroyIcon` 它等于销毁别人的东西；而 `LoadImage`（从 .ico 文件加载）、
     `ExtractIconEx` / `SHGetFileInfo`（取文件自带图标）得到的图标**由调用方
     负责 `DestroyIcon`**；
  ② 全局句柄（托盘图标、窗口图标）用"**谁创建谁销毁 + 显式 owned 标记**"
     记账，退出路径统一回收：凭感觉无条件销毁会误杀系统资源，漏销毁则每
     进程泄漏 GDI 对象；
  ③ **默认图标取程序自身的 exe**（`Environment.ProcessPath` + stdlib 的
     `FileInfoEx.Icon`），不要退回系统通用图标——编译器生成的 exe 内嵌了
     默认图标资源，用户用 `--icon` 指定的图标也走同一条路，托盘/窗口因此
     显示的就是程序自己的图标；
  ④ 异步初始化的全局资源（如托盘图标在专用线程上装载）必须在**调用方
     返回前就绪**（在调用线程上装载），否则调用方读到的是半初始化状态；
  ⑤ 判定"图标是不是程序自己的"要**比像素**、不能比句柄：两次
     `ExtractIconEx` 拿到的是**两个不同的 HICON 对象**（同一张图），
     句柄不等不代表图标错；栅格化后逐字节比才是判据（`GetIconInfo` +
     `GetDIBits`，头要用 BITMAPV4 + BI_BITFIELDS 才拿得到 alpha 通道）。
- 组件写法与同目录既有组件保持一致：命名、事件命名、state 管理同构。
- 注释只写代码看不出来的约束与"为什么"；不复述代码、不写日期流水、
  不写"本轮修改了什么"。
- 常量收拢：魔法数进常量；字段名引用 schema 生成物或常量，不散落裸字符串。
- 资源（图片/字体/大 JSON）走内嵌或声明式引用，不在业务代码里手写路径拼接。
- **高频基础数据热路径杜绝逐字符/堆分配循环**：
  ① 文本解码（`Encoding.UTF8.GetString`）优先利用 `bytes.IsAscii` AVX2 向量化探测，纯 ASCII 直通单次 `memcpy` 投影；十六进制编解码（`ToHexString`）禁止在循环体内使用 `Substring` + `StringBuilder`，必须单次预分配 `byte[]` 配合 16 字节字符常数表直接位运算寻址写入；图像像素批量处理（`ImageBuffer`）全面废除浮点乘除与逐点函数调用，统一采用定点数移位（如灰度加权 `(B*29 + G*150 + R*77) >> 8`）与向量化批处理；
  ② 子串检索与前缀后缀匹配全面对接编译器原生机器指令 `s.IndexOf(needle, from)` / `s.LastIndexOf` / `s.StartsWith` / `s.EndsWith`，彻底杜绝手写 `while (i + n <= h) { if (hay.Substring(i, n) == needle) ... }` 反模式（消灭千万级临时堆分配与 ARC 记账，实测提升 49 倍）；
  ③ 字符码点判断与十进制数字解析统一使用原生只读单周期字节索引 `s[i] & 255`，严禁通过 `NativeMemory.Alloc(8)` 写入再 Span 取首字节释放的堆外分配反模式，严禁逐位 `Substring(i, 1)`；
  ④ 文本转义、分词与模板解析统一采用分块游标切片（Window Chunking），无特殊字符时直通返回原始字符串（0 堆申请），含特殊字符时以区间切片追加，消灭逐字节碎片分配；字典键值查询优先使用 `vars.ContainsKey(key)` 与 `TryGetValue`，严禁遍历 `vars.Keys` 数组造成 $O(N)$ 性能降级；
  ⑤ GUI 与游戏高频渲染循环严禁闭包委托与多重 Span 重复构造：`YSortLayer` 等空间与深度排序结构采用紧凑索引直接访问（`GetSortedEntityId`）替代 `ForEachSorted` 委托闭包，消灭每帧闭包分配；`SpriteBatch.Add` 复用单一 `Span<float>` 实例完成 8 浮点装填；富文本与代码高亮词法探测（`CodeEditor.InSet/ContainsSub`、`Markdown` 行内解析、`ChatView.MdStrip`）全面直通原生 `IndexOf` 与分块游标区间切片；
  ⑥ 网络与通讯协议热路径（WebSocket、Redis RESP、HTTP 流）全面采用 AVX2/SSE2 向量化与 NativeMemory 零堆分配加速：WebSocket 数据帧 4 字节掩码在广播构造 64/128/256 位宽掩码向量后通过 `Vector256.Xor` / `Vector128.Xor` 单指令处理 32/16 字节，非对齐尾部按 4 字节整数步进异或；Redis RESP 文本行协议与 WebSocket HTTP 握手终止符（`\r\n` / `\r\n\r\n`）采用带界限限制的 `MemoryExtensions.IndexOf`（AVX2 `Equals` + `ExtractMostSignificantBits` + `TrailingZeroCount`）实现单周期 32 字节跳跃定位，杜绝逐字节标量比对与越界脏读；缓冲区扩容与搬移严禁使用 `for` 循环逐字节赋值，统一调用直接对接 libc `memmove`/`memcpy` 的 `NativeMemory.Copy` 与 `NativeMemory.PutString`。
- **ZanWeb/Mvc 视图 CSP 纪律（`[security].csp` 开启后 `style-src 'self'` 拦内联）**：
  `style=""` 属性、`<style>` 块、`onclick=` 内联 handler、JS 里 innerHTML 拼进的
  style 属性全会被拦；CSSOM 赋值（`el.style.width=`）不受限。视图写法：th/td 列宽用
  `width="N"` 表现属性；组合样式进 admin.css「视图去内联工具类」或语义类；模板条件
  样式把 `{{#if}}` 搬进 class（`class="chatrow{{#if mine}} mine{{/if}}"`）；动态百分比
  宽高用 `data-w`/`data-h` 交 admin.js 统一 CSSOM 回填；页面脚本一律外链 `/static/js/`
  并 `defer`。（坑出处：框架与模板视图两次全量清扫九百余处内联样式；动态宽高与
  tooltip 色点两种 CSSOM 形态实机验证。）
- **杜绝手拼 JSON 字符串与手拼 SQL 拼接（严禁裸字符串拼接与简陋的 Replace 引号）**：
  ① JSON 序列化一律使用标准库 `System.Json.JsonValue` 构建器（`PutStr/PutInt/PutDouble/PutBool/PutNull/PutJson` 与 `Append`），字符串成员经原生转义安全处理特殊字符（引号、反斜杠、控制字符 `\n`/`\r`/`\t`），杜绝因换行或引号破坏 JSON 报文语法；嵌套片段利用 `PutJson`/`AppendJson` 原生嵌入，禁止通过文本剪裁与字符串拼接嵌入；
  ② 数据库非查询/查询/聚合操作一律使用参数化 API（`DbParams` 与 `?` 占位符），禁止手写拼接 `Quote` 单引号或裸拼接变量（如 `"WHERE slot=" + key`），杜绝 SQL 注入漏洞并复用数据库预编译执行计划；
  ③ 实体持久化与业务数据访问优先使用原生 ORM 表达式与模型映射（`Select<T>` / `Insert<T>` / `Update<T>` / `Delete<T>` / `DbTable.Of`），通过 lambda 强类型表达式（如 `a => a.slot == slot`）或类型化查询链，由编译器与 ORM 生成层自动完成列名白名单核验、类型绑定与参数化，从架构根源上根除手写裸 SQL 字符串的脆弱性。
- **ORM 条件只有值自带原语，裸 SQL 片段是生成代码专属**。用户面条件一律
  `WhereEq/WhereGe/WhereLe/WhereIn/WhereLikeAny`（列名经实体元数据校验，
  值全部参数化绑定）与类型化 lambda（`ids.Contains(a.id)` 降级为参数化
  IN；空列表恒假，不会生成非法 `IN `）；列表筛选收集成 `List<OrmCond>`
  后 `WhereConds(conds)` 一口吞（多列 LIKE 用 `|` 分组 OR）。批量更新/
  删除走 `DbTable.Of(conn, "表").Query.WhereIn(...).ExecuteUpdateAsync(...)`
  （列名过 RequireIdent 白名单）。`W("片段")+InI(...)` 这类片段/参数分离
  写法已整体删除，只以 `__` 前缀（`__Frag/__Pi/...`）存在于编译器生成代码
  里，手写代码不可见；要给查询链接名字仍用门面根
  `__DbQ_Post sel = __DbBind.Q_Post(conn);`（裸赋值 `this.Post` 编译不过）。
  坑出处：片段+参数靠位置配对，编译器查不出错位，历史上实烂三处
  （根治，值自带后错位不可能发生）。
- **Zan.Web 菜单是显式选择（GenRoute 约定），别靠描述"顺便"进侧栏**。进
  管理菜单只认显式标注：`[Custom(IsMenu = true)]`（类级或动作级，图标/权限
  同写在那一处）、`[Menu]`、`[AdminAction(IsMenu = true)]`；类级
  `[Description]` 只做文档与标题回退，**不会**让控制器进菜单。非根动作
  没有方法级显式标注一律不进——类级菜单配置只作用于根动作。方法层显式
  标注永远赢过类级默认（两层合并类先方法后）。坑出处：登录/健康检查这类
  有描述的公开端点曾被类描述隐式默认刷进侧栏，而监控类控制器的非根动作
  上已标注的 `[Custom(IsMenu=true)]` 又被反向吞掉（GenRoute
  改约定后两端同时修复，一致性用例锁定）。
- **把专用特性换成通用名值对时，构造默认值不会跟着走——默认值要迁到消费方**。
  `[Custom(...)]` 早期是带构造参数的专用特性（`icon = "mdi:antenna"` 这类默认），
  泛化成 `CustomAttribute(name, value)` 后按 key 存值，"某个 key 的默认值"就
  没有位置了：没写该 key 的调用方拿到空串。症状是"某几条记录少一个字段、
  显式写了的却正常"。修法：默认值落到**唯一消费方**（菜单图标 → `MenuBuilder`
  的 `defaultIcon` 兜底），别塞回特性。用 `git log -S '<默认值字面量>' -- <路径>`
  能定位它在哪次重构里丢的。坑出处：菜单一致性用例期望 `mdi:antenna`，
  一次纯文件规范化重构把默认值吃掉后该用例一直红。
- **安全策略变更后，用例要把"意图"显式写出来，而不是改基准迁就实现**。
  fail-closed 类策略（未声明授权的端点一律要求登录）落地时，原来"隐式公开"的
  端点会变成需要登录；此时正确修法是让用例/调用方**显式声明**公开（如
  `[Custom(Authorization = CustomAuthorization.None)]`），保住用例原本要覆盖的
  语义；直接把基准改成新行为等于悄悄删掉这条覆盖。判断口径：基准是契约，
  策略变更属有意决策 → 改调用方让它显式合规；实现跑偏 → 改实现。
  坑出处：菜单一致性用例的匿名用户从"看到首页"变成"看到 0 条"，两条症状
  （icon 丢失 + 匿名 0 条）根因完全不同，别当成一个 bug 一起修。
- **"降级/回退"这类安全口径按主流实现的判据写，别把"容器存在"当"条目存在"**。
  例：X.509 主机名校验里"是否允许回退到 Subject CN"的判据是 **SAN 里有 dNSName
  条目**（RFC 6125 §6.4.4），不是"SAN 扩展存在"；用后者会把"SAN 里只放
  email/URI"的证书也拒掉。同一族的第二个坑：**CN 是任意字符串标识符**
  （`Zan Test CA` 带空格），不是 DNS 名，套 LDH 域名规范化会直接判否——
  主流实现（Go `crypto/x509`、Java `HostnameChecker`）在 CN 不是合法主机名模式时
  退化为大小写不敏感的精确比对，而不是拒绝。坑出处：X.509 一致性用例的
  "Fallback to CN when no SAN" 一直红，根因是实现与自带注释矛盾。
- **"grep 不到类型定义"≠"类型不存在"：先看同名文件是不是空壳**。批量清理
  机械注释 / 规范化文件名的重构可能把一个类型的**内容**冲掉，只留下
  `using` + `namespace` 的空壳文件——文件在，类型没了，`grep 'class X'`
  什么也搜不到，很容易误判成"仓库里根本没有这个 API"。判定顺序：先按文件
  名找（同名 .zan 在不在），再看内容（是不是只有壳），最后才下"未实现"的
  结论。这类残骸的修法是**按标准补齐真实实现**（例如 HTTP/2 错误码按
  RFC 9113 §7 补 `Http2Error`），不是给用例补个桩类型——桩会让用例测一个
  假实现。坑出处：HTTP/2 帧编解码其实早已落地，缺的只是被冲成空壳的
  `Http2Error`，而当时的登记把整条 HTTP/2 API 记成了"根本不存在"。
- **控件自带菜单要接宿主能力，走"宿主项 + 命令回吐"通道，别在宿主里另画一套菜单**。
  控件（如代码编辑器）自己画右键菜单时，宿主（IDE）级能力（格式化文档/重命名/
  LSP 代码动作）不能在宿主里再画一个菜单顶上去：宿主禁自绘，且两套菜单会同时
  开、互相打架。正确形状是——控件留一段**宿主段位**（如 `action >= 100`）供宿主
  注入菜单项，宿主项带**命令名**；控件点选后把命令名写进自己的命令槽，宿主每帧
  用 `TakeCommand()` 取走（取一次即清空）。控件不认识命令语义，宿主只落地命令，
  两边都不越界。判断口径：菜单归谁画，能力就以"项 + 命令"挂进谁的菜单。
  坑出处：给代码编辑区补右键菜单时，IDE 侧曾冒出"另画一套"的冲动，走控件既有
  `ctxCmd`/`TakeCommand()` 通道后一次做对。
- **语言事实三则（CRUD 声明化实机踩出）**：① `protected`
  是**仅子类可见**——同包同命名空间的协作类也访问不到（`Crud` 访问
  `AdminController` 的 `Can/Note/Saved` 直接编译错）。包内协作面要么
  放开为默认公开（如 Note/Saved 这类通用应答/审计），要么像
  `Screen(canUpdate, canDelete)` 那样由子类调用方取好掩码再当参数传；
  ② 关键字不能当标识符——`where`（lambda 语法）与 `set`/`get`（属性
  访问器语法）都是保留字：`where` 做变量名报 `unexpected token` 一串，
  `DbValues set` 参数把整段方法解析炸成上百条级联错（各改名实修）；
  另 `StringBuilder.Append` 返回 void，`sb.Append(x).ToString` 链式
  取值编译不过，必须拆两条语句；
  ③ async 方法同一表达式里 await 前不得再求值带副作用的调用
  （`this.Ctx.path` 要先赋局部变量），编译期强制；
  ④ **不支持嵌套类**：类里面不能再声明类。实体类型一个文件一个类
  （同包约定：辅助实体拆成独立文件，同命名空间内跨文件引用）。想在同一处
  看全就放同一命名空间的不同文件。
- **语言事实第四则（全站假死排查踩出）**：`virtual` 在派生类
  里是**新开槽位**（隐藏基类实现），不是覆盖——挂接框架生命周期钩子
  （请求前后清理这类）必须写 `override`。曾把控制器基类的请求钩子声明
  成 `virtual`：框架经基类静态类型的槽位派发，新槽位永远打不中，跑的
  是基类空实现——每请求借出的资源从此不还，池扩张到上限后全部挂满
  超时，全站 503/无响应（客户端只见偶发失败）；而 `base.` 这类静态
  引用仍能打中新槽位，半通半不通最迷惑。排查定式：资源池借还计数
  失配 + 钩子首行日志打不出来 = 槽位没接上。SDK 新版编译器对该形状
  直接告警（`--deny-warnings` 可升级为编译失败），合法重载与真
  override 不误报。
- **语言事实第五则（XML DOM 包首日踩出）**：① 包命名空间按
  using 拉取：`packages/*` 里的类型必须先 `using System.Xml;`（对应的
  包命名空间）才入编，漏 using 直接报 `undefined type 'XmlNode'` 且不
  指向缺 using——新包首次使用先补 using 再排查别的（与 stdlib 按需拉入
  同一门槛，包从 packages/ 发现根扫描）；② 可空返回值不得链式解引用：
  checker 强制（`'RootElement' can return null; accessing ... faults at
  runtime`），既有代码惯例是存局部变量判空，无 `?.` 使用先例、别臆测其
  形态；深层取值逐层存局部判空，同根多条断言用 `if (x != null) {}` 包住
  整段，测试探针尤其常用。
- **语言事实第六则（Zan.Toml 包首日踩出）**：① `JsonValue.At(i)`
  是**数组专属**——对象上调 `At(i)` 直取数组底层的 `items[i]`，对象该列表
  恒空，无边界检查直接段崩（编译期查不出）；对象遍历配对用
  `KeyAt(i)`/`ValAt(i)`，`Count` 两种形态通用；② 无序格式的往返相等
  **必须按键集合深度比，不能比 ToJson 原文**——写出器把行内对象键合法地
  挪进 `[表头]` 区块，同层键序变化是语义不变的（TOML 表无序），拿 JSON
  文本判等会误报失败：递归 `Eqv(a,b)`（对象逐 KeyAt 查 Has+ValAt 递归、
  数组按序递归、标量按类型比）才是正确闸门。
- **语言事实第七则（Zan.Protobuf/Zan.MsgPack 首日踩出）**：
  ① 数值类型只有 `int`/`long`/`double`/`bool`——没有 `float`，也没有
  `sbyte`/`short` 有符号小整型：32 位浮点字段做不了（当文档化取舍写进
  README），小整型符号扩展手工算（`v >= 128 → v - 256`），别臆测类型
  存在；② IEEE-754 位型互转没有 reinterpret，配方是复用归一化构造
  （**±∞/NaN 必须先收口**——归一化循环对非有限值永不终止）+
  逐位累加解码（各项 2^(b-52) 恰可表示、和精确）；解码侧造 ±∞/NaN 用
  `2^1024` 溢出与 `inf - inf`，**不能拿特殊位型递归自造**（位型
  仍是特殊值，无限递归）；③ 判 NaN 用 `x != x`，判 ±∞ 用
  `x > 1e308` / `x < -1e308`——`x == x` 对 ∞ 恒真，照 NaN 惯用法写
  会误报失败。
- **语言事实第八则（Zan.Yaml 首日踩出）**：① 同类里
  **static 方法调用实例方法不报检查器错**，直到 LLVM verification 才炸
  （`Operand is null`，指向被调函数的 this 实参）——报错不提示
  "static 调实例"，纯帮助类小函数一开始就 `static` 化（`JsonValue`
  伴随 helper 如 `HexDigit`）；② 字符串转义集合有限：`\b`/`\f` 是
  编译错（invalid escape sequence），要控制字符用
  `Encoding.Utf8FromCodePoint(8)`（退格）/`(12)`（换页）落；③
  `while (true)` **合法**（stdlib TaskJoin/ByteBuffer/JsonTape 都在
  用）——别凭"语言不支持"把循环改写成标志位绕路（此前会话曾这样
  误绕，证伪撤案）；④ 可空返回链式取成员（`Get.Get`）检查器
  强制"先落地局部 + 判空"，测试代码给一个永非 null 的哨兵 helper
  （缺失返 `NewNull`）一次消音全部链式断言。
- **语言事实第九则（深审修复批连踩两次）**：转出型 `byte[]` 的
  `Length` 含尾随 NUL 槽——`ByteBuffer.ToBytes`、hex/字符串转字节这类 API 产出的
  数组比"逻辑数据"多 1 个收尾 0 字节（既有契约，bytebuffer_bounds 金样钉死）。
  拿 `.Length` 当数据长度喂底层（实例：RSA hex 密钥按字节数传参）会多传一个 0
  而被拒或错算；真实长度用写入/转换时记下的 n 传递，不反查数组。
- **语言事实第十则（异步调度与高并发进程/同步原语重构踩出）**：
  ① `Task.Run(Action/delegate)` 下发给 Worker Pool 时必须生成独立堆帧
  （TaskActionFrame）并绑定 `zan_co_ready`，不能在当前调用线程同步 invoke；
  ② 跨线程运行的委托闭包记录必须通过 `emit_closure_retain/release` 保活，
  完成后写入 DONE 原子状态并唤醒 awaiter，不能直接返回 0；
  ③ 进程启动严禁直接调用系统的 `popen/system` 拼接裸命令，必须提供直接调用
  `CreateProcessW` / `execve` 并进行参数转义的 argv[] 机制，以杜绝命令注入；
  ④ 同步原语 Mutex 应优先使用用户态轻量化 `SRWLOCK` / `futex`，避免进入内核态
  创建具名或匿名内核互斥体造成的调度与争用开销；
  ⑤ 异步解耦必须彻底独立于 UI/渲染帧：UI 线程专职负责事件分发与绘制，后台任务与 I/O
  完成后通过 `App.Post` + 线程级 `Wake` 唤醒 UI 消息泵排空回调，严禁后台计算依赖渲染循环推进；
  跨线程/协程结果传递与协作取消统一使用 `TaskCompletionSource<T>` 与 `CancellationToken` 原语。
- **语言事实第十一则（游戏存档迁移连踩两次）**：
  `JsonValue` 对象上 `Put(key, value)` 对**已存在的键是追加重复键**（序列化
  产出两份同名键，读档端 `Get` 只见其一、`Count` 虚高），`Set(key, value)`
  才是**原位替换**——改写从旧档剥出来的字段（如给 buildings 列表元素剥
  旧字段、裁 researched 长度后写回）必须用 `Set`；数组元素没有原位写，要
  重建数组再 `Set` 整个键。踩坑实锤：探针证明 `Put` 后对象含两个同名
  `"list"` 键（Count 4→Set 后 3），存档迁移测试两次因 `Put` 写回被
  Require 拒收。

- **文本格式包的 BOM 防线（Yaml/Toml/Xml 跨平台审计踩出）**：
  文件读取 API 已在文件层剥 UTF-8 BOM，但 `Parse(src)` 收网络报文/
  内嵌资源时没有这层兜底——Windows 工具产出的文本常带 EF BB BF，不剥
  首键/首标签带隐形字节或报"expected <"。任何文本格式解析器的 Parse
  入口自己剥一次 BOM（三字节判定 + Substring(3)），一致性测试加
  BOM+CRLF 向量锁行为；换行侧在切行层吃掉 CRLF/孤立 CR，写出恒 `\n`。
- **标记类消毒器：实体要解、协议要清、输出要转义**（坑出处：HTML 消毒器
  落地）：三处漏一处就能被绕过——
  ① **属性值里的实体必须解码**：只解文本不解属性，`href="javascript&colon;…"`
  会被当成"没有协议名的相对地址"放过去，浏览器却是当 `javascript:` 执行的；
  ② **判协议前按浏览器的规则清 URL**：去掉制表/换行（`java&#9;script:` 就是
  这么绕过去的）、去掉首尾空白与控制字符，再看协议名；
  ③ **输出端转义才是最后一道闸**：文本转义 `& < >`，属性值转义 `& < > "`；
  标签白名单之外，默认"连内容一起丢"（script/style/iframe 的代码留在正文
  里没意义），而不是只丢标签。
- **stdlib 的"静默空操作"比崩溃更难查**：删错了列表（对象的值列表 vs 数组的
  元素列表）时，调用方看不到任何报错——元素还在，一切"看起来正常"。
  同族的坑是**偏移量写死**：扫描从 `from` 开始，起点却写成常量 1，
  from>0 时读到错位的数字（`{"x":-7}` 被读成 0、`[1,-2]` 被读成 -1）。
  为什么：这两个坑都不抛异常，只会悄悄给出错的数，等到上层用错数据出
  问题时，早就查不到源头了。**做法**：凡是"按下标改容器"与"从 from 扫到
  to"的代码，逐行核对用的是不是同一份数据；测试里既要断言结果，也要
  断言"没动的地方真没动"。
- **写进文档的语法要逐条对账实现，边界条件单独测**：JSONPath 的"逗号并接"写
  进了类注释与 README，实现却漏了，是 conformance 第一次跑就暴露的；同一次
  里 JSON Pointer 的切分循环写成 `while (i <= n)`，探针直接挂死才暴露。
  **做法**：每条语法配一条用例（含"该不匹配时就是不匹配"的负例）；切分/扫描
  类代码按"空输入 / 只有一个元素 / 最后一个元素 / 越界"四种形态各写一次；
  循环条件里的 `<=` 与 `<` 要对着"最后一个元素的下标"手算一遍；探针要带
  超时跑，挂住就是死循环而不是"慢"。
- **声明驱动的 CRUD 定式（ListPage/Crud 落地）**：一屏一个
  `ScreenDef` 静态声明（列 Col/Tag/Flag、行内操作 Ops、筛选、工具栏、
  `Table/EditFields` 写白名单），渲染 `Screen` 整段产出 screenHtml
  （视图只剩壳），通用写动作走 `Crud.Field/Batch/Delete`（白名单+
  Gen.Safe 双保险+`?` 占位符，行级授权由调用方预检 allowed 集合，
  越权与不存在同答 404），`Crud.Conf` 同一声明投影 adminUI conf 契约。
  新屏别再手写表格 HTML 与格式化帮静态方法；业务语义（会话失效、
  关联清理）留在屏内动作，通用动作只对声明的主表负责。
- **堆外密码学实现的三坑（stdlib Pbkdf2 首日踩出）**：① 内层消息
  缓冲必须按 `max(saltLen+4, 32)` 分配——PBKDF2 的 U 链从第二轮起
  消息是 32 字节摘要，按"盐+块序号"尺寸分配会在盐短、c≥2 时
  span 越界；② 每轮算完 U 必须把 U 回写外层缓冲的消息位，只留下
  内层摘要 ih 会让下一轮错拿 ih（链静默变错）；③ 最小对拍集必须含
  c=1 与 c≥2、短盐与 >64B 长键、dkLen≤32 与 >32 分块——c=1 与
  单块向量对上述两类 bug 全都测不出来（RFC 7914 形状
  向量 + Hmac.Compute 对拍双保险锁进 tests/conformance/pbkdf2）。
- **动态加载系统 C API 时逐参数对照目标 SDK 头文件**：函数指针不得凭
  印象省略“编码类型”等中间参数；Crypt32 的 `CertAddEncodedCertificateToStore`
  曾少声明一参，编译和链接都通过，却在首次加入证书时进入系统 DLL 后
  崩溃。对负面策略做多次调用并在崩溃时取原生回溯；Windows SDK 结构
  成员还受头文件宏与版本控制，限时字段不可用时用缓存-only 策略失败
  关闭并明确互通限制，不能改成无界网络查询。
- **异常面 catch 裁决 taxonomy（全量裁决沉淀）**：代码里合法的 catch 只有
  五类，写时注释必须能对号入座——① 传播/包裹/重抛（边界换异常类型，
  或清理后原样重抛）；② 合法错误值契约（探针读可选资源，缺席即常态
  返回默认值；TryX/bool/null/Failure 契约，doc 写明"失败返回什么"）；
  ③ 进程/后台循环边界记日志继续（请求→500、后台循环不因一轮失败而
  死）；④ don't-mask 清理（回滚/释放自身失败不得覆盖原始异常，空 catch
  是常态但注释写明不变式）；⑤ 设计内护栏（每帧 guard、日志终端汇"无处
  可报"）。唯一禁令：**无注释裸吞**。why：审计曾把"61 处 catch 仅 6 处
  重抛"当软着陆证据，全量逐处读上下文后 122 处真实站点全部合法——
  grep 口径不是吞点口径，探针/契约/边界天然占多数；裁决时还要把"静默
  丢根因"（catch 转 null/默认值且不留任何诊断，如池借出 null 无日志）
  与真吞点区分开单独挂账。

- **取消 IO 的顺序是置位、唤醒、确认结束、关闭**：取消通知可能早于 reactor
  注册，须在取消状态下重复唤醒，保留描述符到 await 完成；停用并排空迟到
  回调后才允许 close/reuse。显式 stopped 状态禁止 Accept 自动重开。
  为什么：空闲 accept 停止竞态会挂住关闭流程，迟到通知会误伤复用句柄；
  POSIX 监听 socket 的 shutdown 不等于取消，仍分配的 fd 上 fatal errno
  不能按 IsOpen 重试，errno 应在 syscall 后立即保存到局部。Windows
  取消/复用及真实多进程关闭已验证；POSIX 此次仅静态复核，不冒称实测。
- **注销后台回调不等于生命周期排空**：进程退出前 await `Timer.StopAsync`，
  等已选回调和最后一个共享泵结束；同步 `Stop` 仍供回调自停。临时批次
  放同步 helper，返回时释放，不跨后台 Sleep；完成标志须在这些引用释放后发布。
  为什么：Start/Stop 最小探针五次泄漏临时列表，后台泵还撞上全局析构；
  排空修正后五次及周期/自停/重启回归均无泄漏。取消回调只捕获独立状态，
  不捕获持有该 Timer 的 owner，避免 owner→timer→callback→owner 环。
- **ARC 子助手不要强持有所有者**：构建时短暂传入 owner，勿保存反向字段。
  为什么：集合持有搜索助手、助手持有集合会把图和倒排表留住，Close 资源
  不会破环；移除反向引用后重开/检索回归通过泄漏检查。验收须检查 stdout/
  stderr 的 `memory leak detected`，报告不保证非零退出码，不能只看 exit 0。
- **树形结构不要存父指针——ARC 收不掉引用环**：命令树 / AST / 配置树 / DOM 这类
  "父持有子、子又指回父"的结构，在 ARC 下成环，引用计数永远降不到 0，
  进程退出时被泄漏检查报成"仍可达"（症状是 `memory leak detected: N
  object(s) still reachable`，点名 `List<...>` 之类容器）。
  **做法**：要"从根到自己"的路径就**存路径字符串**（挂到父上时算好），
  或存下标/id；**要真回父节点就用 `weak` 字段**（`public weak Node parent;`，
  父被回收后读到 null，语义正好）。**"存祖先链"不是办法**——链里装的是
  父节点的强引用，父→子(children) + 子→链→父 照样成环。
  **验收**：这类用例要跑带 `--check-leaks` 的变体（普通跑是绿的，泄漏只
  在变体里看得见）。
  坑出处：CLI 命令树最初让命令节点存 `parent` 指针，命令树整体成环
  → conformance 报 22 个对象仍可达；改成存 `path` 字符串后归零。
  同一个坑在 HTML DOM 上又踩了一次：祖先链 `List<父节点>` 是强引用，
  98 个节点连带 497 个对象（每个节点两份 chain 列表）在退出时报泄漏，
  换成 `weak` 父指针后归零。

- **原生模块拆分先写所有权与内容版本契约**：借用像素须注明有效期、
  行 stride 的单位和 alpha 格式；接收方要长期持有就用自己的分配器 COPY，
  不跨独立 CRT 释放。GPU 缓存按内容 serial 更新，不按指针/句柄判断；
  临时 surface view 不缓存。坑出处：sprite 同 key 重烘焙保留句柄、瞬时
  view 复用同一地址，只有新 serial 或强制重传才能画出新内容；回归要
  同时覆盖 padded stride、驱逐重载和稳定句柄换像素。
- **CPU/GPU 往返要验证方向与提交顺序**：top-down CPU 像素上传到
  bottom-up framebuffer 时翻转行，readback 做对称变换；dirty shadow
  首次未初始化时不得比较。坑出处：恢复 CPU 快照后的下一批 GPU 绘图
  暴露上下倒置，单独 draw/readback 却通过。用无中间读回的
  2D→batch→snapshot/restore→batch→2D 顺序断言像素；只测单项图元不够。

- **门面/物理双层对象：物理实例绝不能回填管理器回引用，配置在发放时下沉拷贝**。
  连接池、事务包装这类"门面 + 物理"结构里，门面判定字段（如
  `client.pool != null`）往往就是命令路由开关——给池建的物理连接回绑
  `pool`，它自己的第一条命令（连验活 PING 都算）就会被门面语义重新路由进
  `pool.Acquire`，递归开连直接挂死，且没有任何编译期/诊断提示。正确做法：
  池级钩子（序列化器、事件、超时）在开连时**拷贝**到物理对象上，池与物理
  对象之间保持单向引用。边界：发放即快照，之后改池级钩子只影响新开对象，
  需在注释里写明。坑出处：回绑写法表现为"第一条命令挂死、开连例程被递归
  进入两次"，分阶段打印（enter/connected/wired/ping ok）一击定位——
  async 挂死先怀疑命令被二次路由，别急着怀疑编译器。
- **IDE 运行与发布编译参数解耦（调试挂满诊断，发布绝不挂隔离区）**：
  IDE 本地调试/F5 运行统一走 `-g --arc-guard --check-leaks --strict-runtime`，
  把野指针/悬垂指针和生命周期错乱当场转成受控断言 / `0xDEAD0000DEAD0000` 崩溃，
  避免内存破坏（0xC0000005）串到远端分配器深处才爆；但部署/发布产物
  （`--publish` 或 `-g --no-arc-guard --no-check-leaks`）严禁启用 `--arc-guard`
  与 `--check-leaks`，因为死块隔离区只吞不吐会导致长期运行的服务或桌面端 RSS
  无界膨胀；工程级 `strictMemory` 开关仅作用于本地非发布运行，绝不穿透覆盖发布配置。
  坑出处：历史构建中本地 F5 与发布共用一套标志，导致部署产物因 quarantine
  积累常驻内存，或调试时缺 guard 让 UAF 沦为偶发难以复现的 0xC0000005。
- **原生栅格化与 Blit 裁剪必须做 64 位整数防溢出**：
  在计算目标裁剪右界和下界时，`dx + dw` 和 `dy + dh` 若直接用 32 位 `int` 相加，
  当坐标处于极端区间（如 `INT_MAX` 附近的平移或越界拖拽）会发生 signed integer
  overflow（UBSan 报警），导致边界反转或崩溃；计算外包围盒右下坐标必须显式强转为
  `(long long)dx + (long long)dw` 再与 clip 区间取最小值。坑出处：渲染器 Blit
  在大坐标渲染时触碰 UBSan 符号溢出断言。
- **Windows Clang 下开启 ASan 与崩溃捕获冲突规避**：
  在 Windows x64 下用 Clang 开启 AddressSanitizer 时，若涉及 `__builtin_setjmp`，
  须带 `-mllvm -asan-realign-stack=16`，防止 ASan 32 字节栈重对齐与 Win64 SEH unwind
  展开要求（16 字节对齐）冲突导致 `offset is not a multiple of 16`；同时运行时异常捕获器
  （VEH）在检测到 `__SANITIZE_ADDRESS__` 或 `__has_feature(address_sanitizer)` 时必须跳过安装，
  避免进程在 CRT 析构（`__asan_unregister_globals`）退出时被 VEH 二次拦截并在未初始化的
  stdio 上 `fopen` 发生二次 access violation。
- **AI 管线三件套的定式（`System.Ai`）**：
  ① **失败用返回值不用异常**：网络失败是常态（超时、断网、5xx），
  `Complete` 返回 `null` + `client.lastError` 给出可读原因，比抛异常顺手——
  调用方不必到处包 try/catch，也不会漏掉一个异常分支。
  ② **嵌入响应按 `index` 归位，不靠数组顺序**：协议里有 `index` 字段，靠
  顺序是典型的错位 bug 来源（某个网关重排了数组，向量就全对不上号，而且
  **不报错**——只是检索结果莫名其妙）。维度不一致直接报错，**不截断和稀泥**
  （截断会让相似度算错且错得隐蔽）。
  ③ **token 估算必须单一口径**：切块用的 `TokenCost` 与客户端用的
  `EstimateTokens` 是同一把尺子。两处口径不一致会让"切出来说每块 100
  token，一算却是 25"——这类 bug 不报错，只是账单与限流全错。
  ④ **POST 补全默认不重试**（`maxAttempts=1`）：补全没有幂等键，重试可能
  重复计费。5xx 与网络错误才重试（指数退避，上限 2 秒）；4xx 不重试。
  ⑤ **不内置模型价格**：价格会变，内置就是内置一份会过期的谎言。单价表
  由调用方传；估算是估算，要标出来。
  ⑥ **混合检索用 RRF 而不是分数加权**：向量的距离（1 - cos_sim，0~2）与
  BM25 的分数（无上界）**不在同一量纲**，加权求和必须先归一化，而归一化
  方式（min-max？z-score？按查询内分布？）每种都有坑且对查询敏感。RRF 只看
  **排名**不看分数（`score(d) = Σ 1/(k + rank_i(d))`，k=60 取自原论文），
  对量纲完全免疫。两路原始排名与分数都保留在命中实体上，要自己加权时可用。
  ⑦ **依赖用子命名空间而不是包根**：AI 管线依赖
  `System.Data.ZanDb`（HNSW 索引，17 个编译单元）与 `System.Text`
  （BM25，37 个）——**不拖 ORM 与 sqlite 驱动**（那些在 `System.Data` 根与
  `System.Data.Orm` 下）。实测编译单元数是判断依赖代价的硬指标。
  ⑧ **`double` → `float` 的转换代价要实测再写文档**：向量索引用 `float[]`
  （单精度，因为索引常驻内存、量大），embedding 服务返回 `double`。实测
  分量相对误差约 1e-8、余弦偏差约 1e-9，对检索排序没有可观察影响——但要
  与服务端原始向量逐位一致时**不能经过这层**。
  ⑨ **动手前先查"平台是不是已经有了"**：数据库**原生**就有向量索引
  （HNSW）、混合检索（用的就是同一个 RRF 公式 `1/(61+i)`）、检查点与世代
  机制、从源文档重建索引。自己在应用层拼一套 HNSW+BM25 是**重复造
  轮子**，而且丢掉了事务一致性。坑出处：AI 管线先做了内存版向量存储，
  写持久化版时才发现数据库早已把整条路铺好了。
  ⑩ **自己拼的索引没有锁 = 不支持并发写**：HNSW 的 `Add` 改三个共享结构
  且**无锁**，并发写会撕裂图结构（不是"结果不准"，是内存结构损坏）。
  数据库那侧靠读写锁串行化写，索引变更走 journal + 检查点，与文档写入
  同事务。**应用层拼的索引要么自己加锁，要么明说"单写者"**——别让调用方
  以为它能并发用。
  ⑪ **两个后端做同一件事，语义必须对齐并断言**：内存版与持久化版都用
  RRF（k=60）、都返回同一个命中实体，但**光"看起来一样"不够**——conformance
  要有一条断言比两边的融合分数**逐位相等**。否则从内存切到持久化，检索
  结果会悄悄变样，而没人会发现。
  ⑫ **远端写的 request id：一个 id 只能配一个请求，重试才复用它**：
  服务端按 id **绑定请求指纹**——同一个 id 配不同的请求体会被判
  `id_conflict`（不是静默覆盖，也不是当成两次独立写入）。所以：
  ① 一次操作里有多个不同请求时**各自派生 id**（实测：建文本索引与向量
  索引共用一个 id，第二次被拒 `id_conflict`，连带向量索引没建成、检索
  报"search index does not exist"——**错误信息指向症状而不是根因**，
  排查时先看第一个失败的请求）；② 同一个请求**重试时用同一个 id**，
  这才是幂等（服务端按 id 去重，网络超时后重试不会写重）——所以 id 要
  在重试循环**外面**取一次。

- **远端协议封装：解析响应要看信封结构，不看结果字段**：远端响应是
  `{v, id, ok, revision, result|error}` 的信封，`result` 才是载荷，
  `error` 是 `{code, message}`。判成功要读 `ok` 而不是看 `result` 存不
  在——**失败时 `result` 也可能有值**（比如空数组），只看 `result != null`
  会把失败当成功。
- **起服务端的用例必须 await 停止方法，否则 leakcheck 报泄漏**：
  `RequestStop()` 只是**请求**停止（置标志）；`await StopAsync()` 才会
  停监听、排空在途连接、关掉数据库。少 await 一步，退出时一堆对象仍
  可达 → leakcheck 报几百个对象泄漏，而**直接跑程序是过的**（只有
  leakcheck 变体带 `--check-leaks` 才看得见）。坑出处：远端检索器
  conformance 用 `RequestStop()` 收尾，leakcheck 变体报"515 object(s)
  still reachable"，换成 `await StopAsync()` 即净。
- **leakcheck 变体的失败要重跑一次再下结论**：并行跑时可能撞端口或
  撞 Windows 的 AV 短暂占文件（`STATUS_SHARING_VIOLATION`），表现是
  "单跑绿、并行红"。但**别用它当借口**——先看泄漏报告里点名的分配点
  （`file.zan:LINE`），那才是根因。

- **编排层要抽象存储后端，就抽接口而不是加参数**：编排层原来只认内存
  档的检索器，接本地/远端档就得绕开编排层自己拼提示词——那等于没有
  编排层。抽两个契约：
  ① **读侧接口要同时有同步与协程两版**：本地档（文件 + 内存索引）没有
  IO 等待，同步更直白；远端档**必须**协程（阻塞会停掉 worker 的事件
  循环，把并发限制在 worker 数量上）。**异步专属的后端，同步方法要
  明确报错**（抛异常），不能悄悄阻塞——后者伪装成"能用"，实际把并发
  能力废掉了。仓库先例：协程化的 MySQL 驱动，其同步接口直接抛。
  ② **写侧接口的 id 由后端分配**：数据库的 id 是服务端在事务内发的；
  让调用方给 id 就得"先查最大 id 再 +1"——那是竞态（两个进程同时写
  会撞 id）。接口返回**后端分配的 id 列表**。
  ③ **检索器与写入器必须来自同一个后端**——写进 A 库、从 B 库读是配
  错了。接口能同时声明同步与协程两套方法（委托做不到：一个委托只有
  一个签名），所以这里用接口而不是传委托。
  坑出处：AI 编排层绑死内存档 → 抽 `IRetriever` / `IIndexWriter`。

- **每次请求新建 `HttpClient` = 每个请求泄漏一条 keep-alive 连接**：
  `HttpClient` 内部有连接池，每次新建等于每次丢掉池子里的连接——连接
  被服务端留着，客户端这边已经把它丢了。leakcheck 的症状很典型：
  "N 个 TcpClient / HttpRequest / ByteBuffer 泄漏"（N = 请求数）。
  正确做法：**按端点复用**（连接池是按 host/port 建的，换端点就得换客
  户端，所以按端点规范化串做键缓存），并给客户端加 `Close()` 关掉
  全部。坑出处：AI 客户端每次 `PostJson` 新建 `HttpClient` 且从不关 →
  leakcheck 报"每个请求一个 TcpClient 泄漏"。**同款代码在 Web 框架的
  AI 模块里也有**（同一个坑，两处）。

- **增强层失败要降级，不能拖垮主流程**：像重排这种"锦上添花"的层，
  失败时**降级继续**（用未增强的结果），而不是让整个请求失败。降级的
  失败原因要**单独记**（`rerankError`），与主流程的 `lastError` 分开
  ——两者语义不同："主流程失败了" vs "主流程成功了但没增强"。降级时
  还要**把结果裁回主流程期望的规模**（宽召回 50 条 → 降级后取 topK），
  否则降级路径会把宽候选集直接塞进提示词。
  坑出处：重排降级后忘了裁剪，20 条候选全进了提示词。

- **不同来源的分数不能混**：重排服务的分数（0~1 或无上界 logit，各家
  不同）与 RRF 分数**不同量纲**。要融合就用 **RRF**（只看排名不看分
  数，量纲免疫）；要用原始分数就**各自存各自的字段**，别塞进同一个
  字段——混在一起下游没法比，而且"看起来能用"。
  重排改变了顺序，就让**顺序**表达重排的结论。

- **重排后文本必须跟着命中一起重排**：顺序变了之后**不能按位置取文本**
  ——位置变了，文本和命中就对不上，而且**不报错**，只是答案里混进了
  别的块（错位 bug 最常见也最难发现的形态）。要按 **id** 找回对应文本。

- **让模型打分用行号协议，不用 JSON**：模型吐 JSON 的失败率不低（多一
  个引号就废一次调用）。让模型回"编号 空格 分数"再解析，容忍格式噪
  音。解析要**容错**：只认能解析出的行，认不出的**跳过**（不猜、不硬
  套）——少几条参与打分比整批报废强。
  坑出处：`LlmReranker` 用行号协议，conformance 专门验"部分行解析不
  出来时其余仍可用"。

- **起 HTTP 服务的用例：`Stop()` 之后要等在途连接收尾**：
  `server.Stop()` 只停监听，**已在服务中的连接还在跑**——不等就退出，
  leakcheck 会报连接、请求、缓冲区一串泄漏。标准收尾：`Stop()` 之后
  `for (int w = 0; w < 20; w = w + 1) { await Task.Delay(10); }`。
  另一个要点：起服务用 `Task.Spawn(server.Start())`（`Start()` 是
  `async void`，直接调会立刻返回，端口还没监听起来）。
  坑出处：重排 conformance 起初 `ai.Start()` 后直接跑、`Stop()` 后直接
  退，leakcheck 报 13 个对象泄漏、arcguard 报 `null reference`。

- **Zan 的 `List<T>` 没有 `RemoveRange`**（只有 `Add`/`AddRange`/`Insert`/
  `RemoveAt`/`Clear`/`Contains`/`IndexOf`/`LastIndexOf`/`Reverse`/
  `ToArray`）——要删一段就循环 `RemoveAt(i)`。`List.Count` 是**属性**不是
  方法（`list.Count()` 编译不过，报 "is a property, not a method"）。
  成员表在编译器的 `builtin_api.c` 的 `members_list`。

- **一条消息/一条记录有两个字段时，用实体不用 `List<string[]>`**：
  `List<string[]>` 就是"靠下标对齐的平行数组"——谁也不知道 `[0]` 是角色
  还是内容，而且**长度不受检查**（写成三个元素的数组编译器不报错，运
  行时读到越界才炸）。用 `AiMessage { role, content }` 这样的实体。
  坑出处：AI 客户端的 `CompleteMessages(List<string[]>)` → 改成
  `List<AiMessage>`。

- **会话历史要按"轮"裁，不按"条"裁**：一轮 = 一条用户消息 + 一条助手
  消息（成对）。裁到一半（一半提问没回答）上下文就是断的——模型看到
  "我上一轮问了什么"却没有"我上一轮得到什么"，容易重复提问、答非所问。
  超预算整轮丢，从最老的开始。
  配套两条边界：**当前轮不裁**（最后一条还没助手回答的用户消息正在进
  行中，裁了就丢了当前提问）；**至少留最新一轮**（预算小到装不下一轮
  时宁可超预算也不清空历史——有历史总比没历史好）。
  坑出处：会话记忆的 `Trim` 第一版把"进行中的半轮"和"完整轮"混为
  一谈，裁出来的历史断成两截（conformance 抓到）。

- **当前指令不参与历史裁剪**：系统提示（人设、规则、格式要求）不是
  "历史"，它是**当前指令**——裁掉了模型就变了个人格、忘了规矩。裁剪
  只动系统提示之后的部分。

- **多轮上下文里，历史不进检索只进提示词**：检索只用**当前问题**——历
  史里的旧问题对当前问题没有帮助，混进去会拉偏召回。失败时**不写历
  史**——写进去会让下一轮带着一条失败的问题，模型以为自己问过而没得到
  答案。

- **列存的缺失值用掩码位表达，不用哨兵值**（坑出处：补 DataFrame 缺失值
  处理）：列存是强类型的 `List<long>`/`List<double>`/`List<string>`，格子里
  **总有值**，所以"这行没填"与"这行填了 0"**分不开**。
  ① **不用 `0` 当哨兵**：`0` 与 `""` 都是合法值，混为一谈后两种情况的
  处理方式常常相反（前者该 drop，后者该保留）。pandas 的 `NaN` 好使是因为
  double 有专门的 NaN 位；Zan 列存是强类型的、没有 NaN 语义，所以要用
  **独立的布尔掩码**（与值列表等长，空 = 该列无缺失，不占额外内存）。
  ② **空字段不参与类型推断**：否则 `1,,3` 被推成 Str，数字列退化成文本列；
  整列全空 → Str。
  ③ **写入即"有值"**：写非空值清掉缺失标记，写空串到 Int/Float 列**重新**
  置为缺失。两者必须对称，否则出现"值是 3 但标记仍缺失"的自相矛盾状态。
  ④ **聚合跳过缺失**（求和/均值/最值），不是当 0；全列无有效值返回 0.0
  而不是 NaN——NaN 会顺着下游的平均再平均，污染出一片垃圾。要区分"没有
  有效值"与"有效值恰好是 0"，另给一个有效值计数。
  ⑤ **带小数的填充值要先升型再填**：往 Int 列填均值 1.5 会被截成 1，
  **静默算错**（同一个坑在窗口均值上踩过一次）。所以填小数前把列升成 Float。
  ⑥ **掩码随数据流传播**：任何"复制行"的新表（`Filter`/`Copy`/`SortBy`/
  `Concat`/重采样）都要带走掩码，否则一趟变换就丢了缺失信息。
  ⑦ **掩码按需增长**：只在"掩码为空"时补齐是不够的——追加第二个缺失格
  时掩码不跟着长就越界。正确做法是标记第 row 格时把掩码补齐到 row+1。
- **AI 辅助工具链与包生态韧性（永远暴露、自动回退、缺包自愈）**：
  ① MCP 工具注册必须去条件化：核心工具（`zan_api_search`, `zan_lookup_symbol`,
  `zan_list_members`, `zan_example`）严禁因为项目目录缺少 `.zanmap` 离线文件
  就拒绝注册向 AI 隐藏，必须始终暴露，调用时自动向 `knowledge/` 或 SDK
  源码兜底；② 面向终端发布必须包含 `packages-catalog.json` 与 `pkg_*` 工具族
  （`pkg_list_installed`, `pkg_search`, `pkg_install`），遇到 `namespace not found`
  时由 AI 反向映射并自动安装，而非盲猜重写；③ 编译器内建 `zanc --api <symbol>`
  命令行直达查询，确保即使无 MCP 环境，AI 也能通过单行命令拿到真实类型与方法签名。

- **设置面板接入定式（Game.Foundation 三件套）**：
  一个项目要"有设置"，不重写存盘与档位计算，只写三样：
  ① **声明**：`GameSettings` 里声明选项（`AddBool`/`AddIntChoice`/`AddOption`）；
     离散档位用 `AddIntChoice`（`AddInt` 按 min..max 枚举会摊出几十档，按钮
     组没法用）。
  ② **档位逻辑**：`SettingsModel` 把声明翻译成"一行几个档、当前第几档"，
     选档写回 + 存盘。**视图各项目自绘**（美术风格不同），但这段易错的
     逻辑只有一份。
  ③ **接线**：HTML 设计稿里档位按钮的 id 与事件名统一取
     `opt_<键>_<值>`（如 `opt_aiDiff_hard`）——按语义而不是按行号，增删
     选项不会让按钮与行错位；场景类遍历 `SettingsModel` 生成同名事件。
  ④ **高亮必须 class 驱动**：视觉属性写进 `<style>` 的 `.opt` / `.opt.on`，
     行内 style 只留几何（行内 style 在 HTML 构建器里会合成 `.zgen-N` 规则，
     会把 class 高亮压掉，详见 gui-design skill）。状态类用
     `SetClassIn("optstate on", on ? "on" : "")`——group 里必须带上要清除的
     状态类，否则取消高亮时清不掉。
  ⑤ **落盘要跑两遍**：设置只在内存里 = 没有设置。测试用例首跑写、次跑
     （新进程）读回断言，两遍的值必须不同（首跑默认值、次跑上次写的值）。
  坑出处：五个项目接设置时，高亮不生效的根因是"行内 style 压过 class"
  （实为没写那条 class 规则），`SetClassIn` 的 group 不含状态类会留下脏 class。

## 三、验证纪律（实机/无头通用）

### 改了共享底座文件，验证面要自己收窄（验证范围沉淀）

- **受影响面分析工具对共享底座文件算出的 ctest 命中面会大到不可跑**：改 HTTP
  客户端传输层那种被几十个包消费的底座文件，它给出的命中是 **1181 条**（正则
  `^conformance_` 全量），照着跑就是一次 tier 级的长跑，违反"日常只跑 target
  化测试"。**做法**：把命中面按域自己收窄再跑——改 HTTP 传输层就跑
  http/https/net/web/security-http/ws 族的用例（本次 55 条，约 4 分钟），既有
  同族用例兜底，又有新增用例定点。改完只跑新增的那条是不够的：共享函数（如
  重定向判定函数）的签名/语义改动会打到**别的**通道（本次改了重定向重放函数
  的签名，文本通道与字节通道两处调用点都要跟着变）。
- **共享树里别的用例红了，先归因再动手**：本次同族跑出某个 Web API 文档用例
  红，diff 是布尔渲染从 `1/0` 变成 `true/false`——来自**另一个会话未提交的
  编译器表达式生成文件**（那段 diff 明确在发射 `"true"`/`"false"` 字面量）。
  这类红不是本次改动造成的，**不要去"顺手修好"**：那是别人的在途改动，回退它
  就踩了"禁止回退"那条。做法是：在交付说明里写清归因（哪个文件、哪段 diff、
  为什么与本次无关），自己的用例单独跑绿作证。
- **动手前先查 skill 再写代码**：`base` 是 Zan 保留字（skill 里早有一条），
  本次写重定向地址解析函数时用了 `string base = ...` 当局部变量，编译直接报
  "reserved word"，白费一轮构建。保留字清单在 skill 的代码规范一节。

### 探针测量与脚本改文件的三条硬纪律（排查沉淀）

- **测"超期/耗时"先核对单位与减数**：耗时量是微秒、延时参数是毫秒，`raw - delayMs` 少乘 1000 会把 0.5ms 真超期算成 50ms 假超期（一轮"2× 回归"查了两轮调度器，结果是自己探针的单位错）。测超期一律 `raw - delayMs * 1000`。
- **Stopwatch.GetMilliseconds/GetMicroseconds 是静态单调钟读数（墙钟），不是流逝时间**：拿来当 elapsed 用会打出 1 亿毫秒级的数（实案：探针打出 `build=102483857ms`，误判为计时器坏了）。测流逝要么 `Stopwatch.GetMicroseconds` 前后两次相减，要么 `StartNew` + `ElapsedMilliseconds`。
- **trace 打点必须带绝对时刻，成对相对量串不成时间线**：`late_us` 只能回答"迟了几多"，回答不了"第几段路迟的"；push/fire/park/slept 各打点带运行时单调钟绝对值，一轮就能定位迟滞在停车原语还是派发路径。
- **脚本批量改文件必须读原文→逐处断言命中→写回→复验大小**：`open(p,"w").write(变量.replace(...))` 里变量不是文件内容时写出 0 字节（两个运行时源文件被截断的实案）；写完大小不对就停，别继续跑。

### 流式/增量的判定要靠握手，不要靠时间阈值（增量交付验证沉淀）

- **判"是不是真流式"必须用确定性握手，不能用"回调早于响应结束"这种时间阈值**：
  服务端发完第一帧后**等客户端确认收到**才发第二帧。缓冲式客户端的确认
  永远到不了（它要等整条响应收完才回调），服务端等超时 → 用例直接看到
  "没增量"。这样判定是二值的，不受机器快慢影响。
  坑：先用"回调时间戳 < 响应结束时间戳"当判据，缓冲实现**也会通过**
  （它只是晚了几百毫秒而已），阈值一放宽就漏判；而握手版对缓冲实现
  是**必败**的。
- **握手要防死等**：服务端等确认要有**截止时间**，到点就记超时并继续
  发后续帧（否则缓冲实现的用例会挂死，而不是失败）。
- **"等没等"这类二值事实只卡下界**：断言"耗时 >= 阈值"（跳过等待必然
  低于下界，真等了必然不低于），不要断言"耗时 <= 阈值"（慢机器上必 flaky）。
- **带超时的等待原语，其返回值不能用来区分"等到信号"与"看门狗超时"**
  ——它两种情况都返回 true，调用方必须**复查谓词**（比如受互斥量保护的
  计数器）。误用会让用例把"超时"当成"已确认"，判据整个失效。
- **golden 里写死了跨线程的输出顺序 = 非确定用例**：服务端回调跑在 IO
  线程、客户端跑在协程里，两行 stdout 谁先落地是**不确定的**；golden 一
  旦把那个顺序写死，用例就变成概率性失败（实测 6 次挂 2 次）。
  症状很有迷惑性——"随机挂、重跑又好了"，很容易被当成产品缺陷去查。
  **修法不是调顺序碰运气，而是建立真实的先后关系**：让被等待的那一方
  signal 一扇门，另一方等门开了再打那行。这样顺序由协议保证
  （握手完成必然早于连接回报），不是运气。
  怎么认出这类用例：把测试二进制**连跑 8~20 次**，比对每次输出——不一致
  就是它。写个扫描脚本对每个用例跑 N 次比 md5，是找出全仓 flaky 用例的
  省时办法。**扫描脚本本身要先自检**：拿一个每次输出随机的假用例跑一遍，
  脚本必须报出"不稳定"；采样之间的哈希要有分隔符（空格），否则多个哈希
  连成一坨，数出来永远只有 1 种——脚本就会永远报"没有 flaky 的"，是个
  假阴性。
- **写死端口的用例，同一份跑两遍就会自己撞自己**：第二个实例 bind 失败，
  但它的客户端连上了**第一个实例**的服务器——收到的是别人准备的数据，
  断言失败。症状极像产品 bug（"协议实现读错了 TID"），其实是两个进程抢
  一个端口。端口按 PID 派生（`基础端口 + ProcessId % N`），并发实例各占
  各的。
  改之前先确认**跨用例**有没有重用的端口：grep 出所有 `127.0.0.1", 端口`
  的写法，统计每个端口出现在**几个不同文件**里。跨文件重用才会让 ctest
  并行跑不同用例时撞；只在自己文件里重复的，只有"同一用例跑两份"才撞。
- **把"静默不做事"改成"真的做事"（比如让等待真的等）之后，要复测并发下的
  表现**：新行为可能**占住线程**。等待从"跳过"变成"真等"是对的，但同步休眠
  会占住 worker 线程，调度器在该线程上的其它协程要等它结束才能派发。
  测法：起 N 个协程各带定时器，主协程进同步等待，看**别的协程的定时器是
  否按时**。多 worker（默认）不受影响；**单 worker 下会明显推迟**（实测
  200ms 的定时器被拖到 550ms）。这类"占住线程"是同步上下文的固有代价，
  但要**量化并登记**，不能默认它无害。
  **复现时把同步等待放在 async 协程内部**——放在 `Main` 里复现不了：`Main`
  跑在主线程上，不是 worker，占的是主线程，worker 池照常派发，看不出差别。
  只有"在协程里同步睡"才会占住 worker。
  **解法不是加诊断，是让同步等待泵调度器**：把一次长睡拆成**按下一个定时器
  截止时间切片**的等待，每片醒来做两件事——派发到期定时器（把协程标记成
  就绪并入队），**再亲自把就绪的协程跑起来**。第二步不能少：派发只让
  协程"就绪"，没人执行它它照样不跑；单 worker 下唯一的 worker 正卡在
  这次等待里，等待者自己得顶上 worker 的活。改完实测 200ms 的定时器从
  503ms 回到 204ms，而同步等待本身照样等满 500ms。
  两条断言分开写：**上界**用"先后关系"（同步等待刚结束时定时器到没到）——
  顺序是二值事实，不受机器快慢影响；**下界**用"等了 >= 阈值"守住"静默
  跳过等待"那个老 bug 不退化。
- **让等待者"自己顶上 worker 的活"= 在协程内部嵌套跑别的任务**：这会让
  `co_run` 出现**嵌套**（外层 co_run → 协程 step → 同步等待 → co_run
  内层）。嵌套会踩掉 worker 的**每任务状态**——典型是 `w->cur`：内层
  co_run 把它设成自己的帧、跑完清成 NULL，外层的 `w->cur` 就没了。
  而 `zan_co_ready` 判断"是不是自己唤醒自己"靠的正是
  `(sw->cur == frame)`：命中挂 `CO_SELFQ`（重排走环尾 = 真让出），没命中
  当普通唤醒塞进 **LIFO cell**（下一个就跑自己 = 没让出）。于是外层协程
  的 `await Task.Yield()` 变成**空转**：自唤醒被误判成普通唤醒，抢到
  LIFO cell 又立刻自己跑，排队的协程全被压住。
  **症状**：让出语义静默失效，单看"任务都跑完了"完全正常，只有对照
  "让出前排队的任务有没有插进来跑过"才看得出来。
  **教训**：worker 上的**每任务状态**（`cur` / 抢占配额起点等）在嵌套运行
  时必须**保存并恢复**，不能靠"内层跑完清成 NULL"蒙混——内层不知道外层
  还在栈上。改这类调度代码要问一句"我新加的这条路径会不会嵌套调用
  调度器本身"。
  **测法**：让外层协程在同步等待里制造嵌套，等嵌套结束后 `await
  Task.Yield()`，然后看**排队中的任务在 Yield 返回前跑没跑过**——二值
  事实，不受机器快慢影响。断言要卡"有没有跑过"而不是具体数字。
- **"等一个协程跑完"不能只自旋等标志**：根驱动 await（非 async 方法里
  await 一个 async 调用，编译器分配子帧后让当前线程把它驱动到完成）走
  `zan_co_sched_run_until`，它原来**只自旋等 `done` 标志**，指望别的线程
  去跑子协程。子协程是 `co_submit` 提交的，而 `co_submit` **从 worker 线程
  提交时把任务塞进调用者自己那个 worker 的 LIFO 槽**（`w->lifo`）——别的
  worker 偷不到（`co_steal` 偷的是别人的队列，不偷 lifo 槽）。当前 worker
  正卡在自旋里，压根没机会去取那个槽：子协程永远跑不起来，`done` 永远不
  置位——**死锁**。
  **症状**：worker 数越多越不靠谱（实测 1/2/4/8 全卡），因为**没有任何
  worker 会去取那个 LIFO 槽**；只有"主线程调"是好的（主线程没有自己的
  队列，子协程会被 worker 跑掉）。所以**症状依赖调用上下文**，从
  `Main` 里测完全发现不了——必须在协程内部调。
  **解法**：等候期间**自己顶上 worker 的活**（就地取就绪任务跑起来），
  和上面那条同步等待是同一个思路。**主线程进来时没有自己的队列，保持
  自旋是对的**（子协程会被别的 worker 跑掉）——所以判据是"当前是不是
  worker 线程"，不能一刀切。
  **教训**：凡是"**等别的协程完成**"的路径，都要问一句"**我等的那个协程
  会被谁来跑**"。调度器里的任务分派不是全局公平的——从 worker 提交的任务
  进的是**那一个 worker 的本地队列**，别人拿不到。
- **"await 能不能放在非 async 方法里"判据是"目标要不要真挂起"，不是
  "外层方法是不是 async"**：非 async 方法里的 await 有两大类——
  **能同步降级**的（普通值原样求值、async 调用走根驱动、`Task.Delay`
  同步休眠、`Task.JoinWait` 事件汇合、`Task.Yield` 退化成空操作）语义
  都**正确**；**必须真挂起**的（`Gate.Park` 与 `Socket.*` 那一族）要把恢复
  函数挂到协程帧的状态槽上，没有帧就无路可走。
  按"外层是不是 async"一刀切报错会**误伤**前面那五大类（连已提交的
  `async_sync_delay` 用例都编不过），而且会造成**宿主与自举分叉**——
  自举侧检查器明写 "an 'await' in a *synchronous* method is fine
  ... Only the *operand* has to be a coroutine frame"。
  **判据要在降级处（代码生成）判，不是在检查器判**：代码生成 逐个给 `Gate.Park` /
  `Socket.*` 报"only supported inside an async method"，措辞更准，**名单
  只有一份、不会和检查器走偏**。检查器再抄一份名单就是两处漂移的根源。
  **副作用**：非 async 方法里的 `await Task.Yield()` 会退化成空操作——这
  是**对的**（同步上下文里没有协程可让出），别当成"静默丢语义"去报错。
- **增量解析的"半行缓冲"要在流结束时**补处理**剩下的那半行**：按行切分的
  协议（SSE / HTTP chunked / TCP 行协议）里，最后一块数据**常常不以分隔符
  收尾**——对端发了最后一条消息就走，没有理由再补一个换行。解析器只在
  遇到分隔符时处理行，流结束时缓冲区里剩下的那半行就被**静默丢掉**：
  流正常结束（无错误、无异常）、内容却少一截。
  症状很有欺骗性——"结果少了最后一截，但一切看起来都成功"，很容易被
  当成对端的问题或测试数据的问题。收尾处把残留缓冲按完整的一条处理。
  配一条用例：服务端最后一帧**故意不带换行**，断言内容完整。
- **消费增量数据用事件驱动的 `Take`，不要用「取一下 + 睡一下」的轮询**：
  轮询版（`while (true) { 取; 没数据就 sleep 40ms; }`）有两个代价：每个
  分片的到达延迟最多一个轮询周期；整条流期间一直在白醒（一次长回答 =
  几十次空转）。事件驱动版（挂在事件门上，写入或 Abort 唤醒）**有数据
  才醒**。
  迁移时注意**取消路径**：轮询版每个周期都会检查取消标志，事件驱动版挂着
  的时候不会——所以底层必须能被外部**唤醒**（`Abort()` 要 signal 事件门），
  否则取消会永久等待。
  配套用例要钉住三件事：有数据才醒（挂起不空转）、**增量**（分批写 →
  消费者醒 ≥2 次，攒完一次给不算增量）、Abort 能唤醒挂着的消费者。
- **逐帧解析外部数据时，解析函数会抛异常还是返回 null——先查清楚再调**：
  仓库里 `JsonValue.Parse` 遇坏 JSON 是**抛** `JsonException`（不是返回
  null）。逐帧解析的代码若直接调它，一个畸形帧就**炸掉整条流**——用户
  看到的是"功能崩了"，而不是"这一帧没认出来"。而"跳过这一帧、继续下一
  帧"才是这类协议该有的行为。逐帧解析处一律包 try/catch。
  这条坑在同一个功能里往往**同时存在**三个形态（抛异常 / 静默跳过 /
  收尾丢半行），修的时候要一次看全，别只修撞见的那一个。
- **同一个协议解析逻辑在多处重复时，改一处要找出全部**：AI 客户端与
  Web 框架各有一份 SSE 解析（AI 客户端内部两个入口现已共用一个内核，
  跨包仍是两份）。修好一份不代表另一份也好了——同样的三个
  缺陷在两边都存在，只是被各自的用例覆盖与否不同。找齐的方式是搜协议
  关键词（`data:` / `SseSink` / `event-stream`），不是搜类名。
- **「解析外部输入」不只指上游响应，**客户端**传来的字段同样算**：
  请求体、路径参数、表单字段、历史记录——都是不可信输入。JSON 解析函数
  遇坏输入抛异常时，调用方没接住就是 **500 + 栈回溯**，而不是一句
  "这一项没认出来"。
  典型坑：代码里明明写着 `if (root == null) { return "内容无法解析"; }`——
  意图写得清清楚楚，但解析函数是**抛**异常的，这行判断**根本走不到**，
  异常先跑了。看到"解析失败"的分支时，回头确认解析函数到底返回 null
  还是抛异常。
  排查手法：grep 出所有解析调用，逐个看**输入来源**——凡是来自
  网络/客户端/文件的，外面都得包 try/catch。

### 自己做 SSE 流：生产端的最小配方与失败语义（流式实现沉淀）

- **在 Zan 里做真流式，配方是三件套**（网络包自带，不用自己写 socket）：
  1. `SseSink sink = SseSink.ToMemory();` —— 内存 sink，带事件门；
  2. `long producer = Task.Spawn(http.PostSseToSinkAsync(path, body, sink));`
     —— 传输在后台跑，响应体**边到边**写进 sink；
  3. 消费侧 `SseDelivery d = await sink.TakeCo();` —— 有数据才醒，不轮询。

  `PostSseToSinkAsync` **不抛异常**，失败写进 sink 的结果标记
  （`sink.Attempt()`）：正常是 `"ok"`，失败是 `"err: ..."`——非 2xx 是
  `"err: HTTP 404: <错误正文摘要>"`，对端提前关是 `"err: connection closed"`，
  空闲超时是 `"err: timeout"`，消费者主动放弃是 `"err: cancelled"`。
  所以调用方**必须自己判前缀**：`Attempt().StartsWith("err:")` 才是失败。
- **"消费者主动放弃"与"上游失败"在标记里长得不一样，要分开处理**：
  `sink.Abort()` 之后传输层必然报 `"err: cancelled"`——那是**我们自己**
  叫停的，报成错误会让调用方以为流挂了。判据是"调用方是不是主动叫停的"，
  不是标记文本。
- **释放 sink 要等 producer 结束**：`SseSink.Dispose()` 会销毁互斥量，而
  producer 可能还在往 sink 里写（中止上游后它要等传输层才发现）。提前
  Dispose = 写入打到已释放的互斥量上，是崩溃不是泄漏。等不到就**别释放**
  （漏一个句柄好过崩）。
- **流式协议的失败语义通常与非流式不同**：非流式失败就返回 null；流式可能
  **只拿到一半**（上游报错、连接被掐断、调用方叫停）。半截内容是**已经
  付过费的**（token 已花掉），丢掉它等于让用户白等白花钱——所以流式的
  结果对象**永远存在**，失败原因放在结果里（`error` 字段），而不是"返回
  null"。写契约时要把这两种语义**分别写清楚**，别让调用方猜。
- **LLM 流的工具参数是分片到达的**（OpenAI 兼容：`delta.tool_calls[].
  function.arguments`；Anthropic：`content_block_delta` 的
  `input_json_delta.partial_json`）。拼装要**按服务方给的序号归位**
  （`index`），**不能靠到达顺序**——服务方完全可能先发第 2 个工具的片段。
  参数片段是 JSON 文本的片段，拼完才是完整 JSON。
- **用量在流里可能分几帧发**（Anthropic：输入 token 在 `message_start`，
  输出 token 在 `message_delta`）——收到用量帧要**合并**，覆盖会把先到的
  那一半抹掉。

### 几何检测：单次测量有偏，要按整簇聚合并用稳健统计（图像/定位类算法沉淀）

- **斜切图形的"特征中点"不等于几何中心**：方块沿任意方向切一条线，弦**不
  关于垂足对称**（只有过中心的切线才对称）——切线偏 h 时中点会**线性漂移**，
  速率正好是 tanθ。所以"扫一行取中点"这种单次测量必然有偏（实测 15° 时相邻
  行之间就漂 1px，几行下来偏了半个模块以上）。**要按整簇命中聚合并取稳健
  统计**：能命中的那些行关于中心行对称，聚合值才落在真位置。
- **聚类的键要用"多模态配对后的点"，不能用单一维度的特征**：两个不同目标
  可能共享同一个维度的取值（两个定位图形的 x 完全相同，相隔十几个模块），
  单维度聚类会把它们并成一簇——症状是"该分开的目标分不开，中心算成两者
  中点"。
- **稳健统计不是可选项**：簇里一定会混进"长得像但不是"的假命中（数据区的
  巧合图案），平均值被拉偏一两个单位（实测把一个特征点拉偏 11px，直接导致
  采样全错），**中位数对少量离群值免疫**。
- **比例类的特征量要从"差"里取，不要从"被测段"反推**：被测段的长度会随
  切线位置缩短（偏心 h 处短 2h·tanθ），而嵌套结构的"差"（外圈减内圈）不随之
  变化——容差要按**不变的那个量**算，否则偏心的行会被误判成不合格。
- **"量出来的视在尺寸"要显式换算回真实尺寸**：图上量到的边长是被放大过的
  视在值（弦长放大 1/max(|cosθ|,|sinθ|) 倍），不换算会让尺度相关的推算
  （版本、容量、格子数）整条偏掉——不换算的后果不是"差一点"，而是**整类
  角度直接判错**。

### 诊断数据（账单 / 日志 / 外部表格）要有格式契约，解析必须自己校验（剖析类工具沉淀）

- **格式是契约，写端与读端共用一份定义**：采集端和解析端引**同一个**定义
  （同一个类 / 同一个常量表），格式一改两边一起改。格式各写一套的必然漂移：
  写端改了小数位或加了字段，读端还按老格式解析，症状是"偶尔有帧解析不出来"，
  极难定位。契约至少定死：前缀、字段顺序无关性、必填字段、数值格式、非法字符集。
- **未知字段忽略，不要报错（前向兼容）**：格式以后一定要加字段；旧解析器遇到
  不认识的 key 就崩，等于每次加字段都要同时升级所有读者。解析器只认自己要的
  key，其余跳过。
- **坏行跳过并计数，不要让整份数据作废**：账单 / 日志是往 stdout 打的，混着
  游戏自己的输出是常态，某一行的数值写坏也常见。解析分三档——不是本格式的行
  **忽略**；是本格式但坏了的**跳过并计数**（给出 `skipped` 与第一个错误码）；
  好行照常解析。一份账单里有一行坏了，不该让整份账单作废。
- **数值解析自己严格校验，别拿 `Convert.ToDouble` 当校验**：它对 `"abc"` 静默返回
  0（不抛异常），坏输入会被当成"值就是 0"——诊断数据里一个写坏的值变成"0 毫秒"
  而不是"这一行坏了"，把排序和统计整个带偏。诊断数据里**错的值比没有值更坏**：
  人会照着假数据去优化。严格校验失败就判失败，由调用方决定"跳过"还是"报错"。
- **报告里的数字固定小数位**：默认的 `double.ToString()` 给的是最短往返表示
  （16.666666666666668），位数随值漂——golden 逐字比对每次都飘，diff 全是噪声。
  自己按"四舍五入到 N 位 + 补零"打，输出才稳定可回归。
- **分位数用最近秩，不用插值**：`p = ceil(q × n)` 的那个样本。插值出来的 p95 是
  "某个不存在的帧"的虚构耗时，看报告的人会去找那一帧；最近秩给的是**真实出现过
  的样本**。
- **热点按累计量排，不按单次最慢排**：单次最慢常常是一次异常（首帧资源加载、
  GC），它不告诉你"每帧都在花时间的是谁"；累计量才是每帧都要付的税。另外，
  **整体热点与"超预算帧里的元凶"常常不是同一个分段**——前者是稳定开销，后者才是
  玩家感觉卡的原因，要分开给。
- **"没被任何分段记到的时间"要单独报出来**：`total - 各分段之和`。这个数大就说明
  **有代码没插桩**——全部分段都很快但整帧很慢，答案通常就在这个差值里；不单独
  报，读者会一直以为"插桩已经覆盖了全部时间"。
- **开关型插桩：关着时调用点是空操作**：环境变量门控的剖析走廊，关闭状态下
  `Begin/End` 全是空操作，调用方**不必**写 `if (enabled)`——每个分段写一遍条件，
  漏一个就插桩不一致，账单对不上，而且这种漏是看不出来的（少一个分段，报告仍然
  "正常"，只是少了点数据）。

### 调试 / 覆盖层工具：数据与绘制分层（调试工具沉淀）

- **先算"行"，再画"控件"**：调试工具的判据从来不是像素，而是"哪一行被标成超预算、
  占比算得对不对"。所以先把数据算成**行模型**（label / value / share / 标志位），
  绘制层只负责把行摆成控件。反过来先画控件再抽逻辑，判据就被绑死在 GUI 上——
  既没法无头断言，也没法拿同一份数据出别的呈现。
- **只有绘制层依赖 GUI，数据层不碰**：数据层的源文件不引用 GUI 命名空间，
  判定器才能在无头环境里直接断言行模型；绘制壳薄到只剩"一行 → 一个控件"，
  两份实现不会各走各的。坑出处：帧剖析覆盖层工具的十个文件里只有面板文件碰 GUI。
- **同一份行模型要有无 GUI 的等价呈现**：同一批行要能同时变成面板和纯文本，
  这样 CI / 日志里能逐字比对"这一帧到底报告了什么"，而不是只能靠人眼看截图。
- **排序要确定**：调试工具的输出顺序不能飘——主键相同时按 id 升序兜底，降序只
  翻转主键。顺序一飘，同一份数据两次输出就不一样，diff 全是噪声。

### 3D 渲染：先算后画，判据不绑像素（渲染管线沉淀）

- **渲染决策全在"计划层"算完，绘制层只负责提交**：相机矩阵、世界矩阵、视锥
  剔除、CPU 光照、排序、批次分组全在计划层；绘制层拿到的是一份"绘制项列表"，
  只负责装批提交。反过来先画再抽逻辑，判据就被绑死在画布上——既没法无头断言，
  也没法拿同一份决策出别的呈现（离屏渲染 / 录像 / 回归比对）。
- **矩阵只用一套，别造第三套**：生态里 4x4 矩阵只有"列向量"与"行向量"两套，
  渲染管线吃的是列向量那套。两套之间差一个转置，混用时错的是**布局**（平移在
  第几列、缩放作用在哪），症状是"场景停在原点"或"旋转对但缩放串了"，而公式
  本身一点没错——**这类 bug 读公式读不出来，只能靠断言钉住**。
- **CPU 侧的模型要先能独立验证**：GPU 后端把光照写死成固定键光时，材质与多光源
  就在 CPU 上算，算完当每实例 tint 传进去。代价是画面变成"CPU 着色 × 固定键光"
  两层叠加——但**至少材质与光照参数真的进了画面**，且可以在无头环境里逐条断言
  （面朝光更亮、点光随距离衰减、聚光锥角内外有别）。
- **帧内零分配是渲染热路径的硬要求**：绘制项、矩阵、排序缓冲全部复用——绘制项
  回收进池子，矩阵按递归深度预分配，排序用包内自带的归并排序。通用库里的排序
  函数每次调用都新分配一组数组，放在每帧重建的路径上就是纯 GC 压力。
- **剔除与排序的计数要暴露出来**：计划层要能报"本帧考虑了多少个、被剔掉多少个"
  ——没有这两个数，剔除逻辑坏了（把该画的剔了）只能靠肉眼发现画面少东西。

### 刚体求解器：接触流形与支撑函数的几何陷阱（动力学引擎沉淀）

- **面-面接触必须多接触点，单点一定不稳**：滑动摩擦作用在质心下方，会产生
  一个"把盒子掀翻"的力矩；单点的法向冲量没法在接触面内重新分配来抵抗它，
  盒子会越滑越歪，法向冲量被"分离速度"吃掉，最后沉进地里。要做 SAT + 面裁剪
  （参考面 / 入射面，Sutherland-Hodgman 裁 4 个侧面），面-面接触出 4 个点。
  这是 Box2D / Bullet 稳定堆叠的同一个机制，不是可选的"高级特性"。
- **支撑 / 极值函数在方向分量为 0 时必须取面中心，不能取端点**：盒子的支撑点
  沿某方向取极值时，那个方向的零分量对应的是**整条边**，取边上的哪一点都对，
  但必须取**边中点**（分量为 0）。取成 `+半长`（端点）会把接触点挪到盒角，
  力臂瞬间大三个数量级，有效质量算出来差 1200 倍——症状是物体"穿过"地面，
  而支撑函数本身看起来完全合理。
- **支撑方向要先转到局部系再挑符号**：世界方向直接拿去和局部半长比符号，
  物体转过姿态后支撑点会挑错面，SAT 的最小穿透轴因此算错。
- **接触对要规范化顺序（按 id 或稳定键）再进表**：宽相的排序每帧都可能变
  （SAP 按 minX 排），两个刚体位置互换后，同一对会建出**两个方向相反**的
  接触对象——同一对刚体被解两次，两条法线还互相打架。规范化（低 id → 高 id）
  之后接触键唯一，法线方向恒定。
- **数值断言要对着解析解比，不要只验"没炸"**：摩擦减速度 `μ·g`、滑行距离
  `v²/(2μg)`、反弹高度 `e²·h`——这些都有闭式解。只验"物体还在动、没飞出去"
  会漏掉成倍的偏差（实测：单点接触版本摩擦减速度只有理论值的 1/16，物体照样
  "看起来在动"，但完全不符合物理）。

### 协议实现：自对拍守不住"两边都算错同一个东西"（协议 / 线格式沉淀）

- **同一个包两端的自对拍测试，只能守住内部一致性**：客户端与服务端如果
  **错在同一个字节布局上**（比如都少算一个消息号、都不带长度前缀），自对拍
  照样全绿。协议实现必须另配**真实互通验证**——对端要是**第三方实现**。
  把两端塞进同一进程（内存管道 + 线程）只是让测试跑得方便，**代码还是同一
  份**，照样守不住。
- **互通验证查出来的东西要固化成"已知答案测试"，定值来自第三方的字节布局**：
  把对端算出来的定值钉进 conformance，"少一个长度前缀 / 少一个消息号"这类
  规则才被真正锁住。只在互通脚本里断言一次，等于没锁。
- **长度前缀与"多包一层"是协议实现最常见的两处字节级错误**：变长整数
  （mpint 之类）在 RFC 里常常写成"存储为 string"，意思是**带 4 字节长度
  前缀**；结构体字段常写成"string 装着子结构"，少包一层照样能解析出**长度
  正确的垃圾**。这两种错误都不报"格式错"，只报"验签失败"或"第一个包解不开"，
  报错完全指不到原因。
- **同一个概念只能有一个编码器**：包里一旦出现第二份编码（比如一份 mpint
  带前缀、一份不带），调用方迟早挑错，症状是"某个方向的密钥 / 哈希全不一样"。
  编码器收口到一个，调用方只传原始值。
- **对端的实现顺序未必符合 RFC**：客户端"下一条必须是应答"这种假设，会把
  对端**先发来的数据**当成"应答不对"直接报错；请求 / 命令的结束判据要取
  RFC 指名的那个信号（比如 exit-status），不是"等对端关连接"——不少实现
  发完就不关了。
- **AEAD 的 nonce 计数器初值通常不是 0**：它是密钥派生出来的 IV 的一部分，
  按 RFC "每次调用之后递增"使用。把初值当 0，握手全程看着正常，**第一个
  加密包就解不开**。
- **断言原始线路内容时，"读到某标记为止"的标记不能与响应头撞车**：HTTP 的
  分块结束块是 `0\r\n\r\n`，而服务端的 `Server: <产品>/1.0\r\n\r\n` 这一行
  **本身就含 `0\r\n\r\n`**。用单段标记做"读到结束块为止"，会在响应头处就
  停下，症状是"正文一段都没发出来"——实际正文早就发完了。标记要带上
  前导 CRLF（`\r\n0\r\n\r\n`），要求它前面不是版本号里的字符。
- **线路上的正文是被分帧隔开的，连续正文只能在解码后的响应里查**：分块
  线路是 `5\r\nalpha\r\n4\r\nbeta\r\n`，原文里根本没有连续的 `alphabetagamma`；
  拿连续正文去查原始线路必然查不到。查原始线路要看**帧前缀**，查解码结果
  才看正文。
- **流式/分块响应的服务端分支条件是"用什么定界"，不是"有没有正文来源"**：
  空正文也必须走分块路径把**结束块**写出去。条件写成"有正文来源才走分块"，
  空正文就会退回普通发送路径——响应头声明了 chunked 却永远不发结束块，
  客户端一路挂到超时（症状是"请求不返回"，不是"响应格式错"）。

### 二进制格式解码器：位级语义靠对拍钉死，别靠移植（格式解析沉淀）

- **位级格式先用快语言写独立原型，对真实第三方数据逐字节对拍，再移植**：
  熵编码、位流、压缩这类"位序 + 表布局"的格式，机械移植会把读错的语义
  一起搬过去；而这类错误的症状是"长度正确、内容全错"，肉眼极难定位。
  用一种迭代快的语言（脚本）先写一份**独立**原型，拿**真实第三方产出**的
  数据逐字节对拍，语义钉死后再移植，纠错成本降一个数量级。参考实现源码
  用来确认格式细节（字段位宽、表铺法、结束标记），**不要转写成目标语言**。
  边界：规范明确但位级细节易错的格式才值得；语义简单的格式不必。
- **从缓冲区按位切字段必须显式掩码**：有符号整数的 `>>` 是**算术右移**
  （符号位会补下来），把一个 32 位字拆成多个字段时，不掩码的高字段会把
  符号位带进结果，表现为"尺寸字段算出负数"这种指不到原因的报错。每个
  字段都写成 `v >> k & mask`。
- **往表 / 缓冲里铺数据前，按最终尺寸重新分配**：复用"按另一个尺寸预分配"
  的数组去铺表是**越界写**，编译器不报错，症状是相邻内存被踩、数据随机
  错乱，排查成本极高。
- **校验条件逐条对照参考实现，别凭直觉加严**：自己加的"完整性检查"会把
  规范允许的输入判死——例如规范允许"权重为 0 的符号"（该符号不出现在码流
  里），而"符号数必须等于权重项数"这种形状检查会把它判成树损坏。每条
  检查都要能在参考实现里指出对应的那一行。
- **规范与参考实现冲突时以参考实现为准，并把瑕疵记进文档**：互通性由真实
  实现决定；不记录瑕疵，下一个人照着表格改回去就又坏了。

### 用例与环境解耦（内嵌资源、目录枚举与跨包引用）

- **内嵌资源的目录枚举按设计合并磁盘与内嵌**：内嵌根下的目录列表是
  「磁盘优先、内嵌补差」的并集（标准库 `System.IO.Directory` 的
  `MergeEmbed` / `EmbedChildren`），单文件发布后 `views/` 之类照样能枚举。
  所以**内嵌根名不能与运行目录里的真实目录同名**：conformance 用例的运行目录
  默认是仓库根（测试脚本的 `WORKDIR=tests/..`），仓库根上有真实的
  `assets/`（品牌素材），拿 "assets" 当内嵌根会让 `Directory.GetDirectories`
  数到 {brand, pack} 两个，断言 `Count == 1` 必红——而内嵌功能本身完全正确。
  做法：内嵌根取一个运行目录里不可能出现的名字（本次取 `embedfx`），或者只
  断言内嵌项本身、不对「内嵌+磁盘」的并集总数做等值断言。
- **先分清「语义」和「断言」再决定改哪边**：目录枚举的合并是设计，测试里的
  等值计数是假设。先确认用例量的到底是内嵌树还是并集，再决定是改测试还是改
  运行时；把设计的语义改掉去迁就一条脆弱断言，是拿产品能力换测试绿灯。
- **跨包引用类型必须显式 `using`，编译器不会替你想起来**：某个 SDK 包里
  `Aes.DecryptBlockEcb` 报 "'Aes' is not a known variable, type, or namespace"，
  缺的是 `using System.Security.Cryptography;`——内建成员表里登记过 "Aes"
  只说明编译器知道这个类型的成员签名，不代表它在你的文件里可见。同包的
  另一个文件早就写了那行 `using`，这类"同一个包里一半文件能编一半不能编"
  的报错，先比 `using` 行再怀疑编译器。
- **包与包之间没有依赖清单，A 包 `using` 了 B 包就等于废掉 A 的独立性**：
  `zan.pkg` 的 `dependencies` 段**当前没有任何包在用**（各包清单只有
  name/version/description/author/license）；编译期的可见性来自
  `zan_collect_package_source_roots()` 把**工程里所有**包源根并进来
  （`src/compiler/main.c`）。于是 A 包源码里 `using` 了 B 包的命名空间时，
  在"整仓一起用"（`--package-project zan-lang`、SDK 发布）下能编；一旦用户
  只装了 A 包，A 包自身就编不过。已有先例：`Zan.Ai` 依赖 `Zan.Net`、
  `Zan.Mvc` 依赖 `Zan.Data`。
  **对策**：给包加能力前先问「这个能力在 stdlib 里吗」——**stdlib 是所有包
  都看得见的底座**；非要跨包拿，就走注入（调用方传回调/策略），别让基础包
  硬依赖可选包；真需要共享就评估把最小必要的那部分下沉到 stdlib。
  坑出处：给 `Zan.Net` 接 HTTP 自动解压时，gzip/deflate 编解码器在
  `packages/Zan.IO/src/System/IO/Compression/`，`Zan.Net` 全树零引用；直接
  `using System.IO.Compression;` 就把网络包绑死在压缩包上，压缩包一旦不装，
  网络包连带编译不过。
  **落地形态**（HTTP 内容编码解码）：网络包只留一个注入点
  （`HttpClient.SetContentDecoder`），**实现放在压缩包里**（一个桥类把
  `Content-Encoding` 映射到本包的编解码），两边都不绑死；应用侧一行装配：
  `http.SetContentDecoder(System.IO.Compression.ContentCoding.Decode);`。
- **注入式能力"缺实现"时必须报错，绝不能把"没做"的结果当"做了"交出去**：
  没装解码器又碰上 `Content-Encoding: gzip` 的响应时，客户端要么**抛错**
  （说清缺的是什么），要么明确返回"未解码"标记——**不能默默把压缩字节
  当正文返回**：那样调用方拿到一堆乱码，却没有任何提示，排查时只会怀疑
  服务器。同理，**同一能力的各通道口径要一致**：内存通道解码了，落盘通道
  （下载）不解码的话，落下来的就是压缩过的文件——下载通道要么也解码，
  要么明确报错说"该响应带内容编码，本通道不解码"，不能留一个"看着下完
  了、其实解不开"的文件。
- **协议里"看起来一样"的两种线上形态要按规范判定，不能猜**：`deflate`
  在 HTTP 里有裸 DEFLATE 流和 zlib 包装（2 字节头 + 尾 adler32）两种，
  服务器两种都发过。按 zlib 头判定（`CM==8` 且 `(CMF<<8|FLG)%31==0`）
  决定要不要跳过那 2 字节；猜错就会解出一堆垃圾或直接失败。
- **同名类跨命名空间时，裸名按"成员命中"消歧，落在歧义上要显式限定**：编译器
  解析裸名的顺序是 当前命名空间 → 祖先命名空间 → **本文件**的 `using` →
  成员命中消歧 → 歧义诊断。同名类型多于一个时，`X.M` 这种成员访问先用"谁声明了
  M"筛候选，唯一命中就用它（`Window.GetTickMs()` 命中 `Gui.Backend.Window`）；
  仍然多命中就报 `ambiguous type 'X'; qualify it with its namespace`，这时只能
  写全限定名或调整 import。
  **导入按文件隔离**：别的文件 import 了什么跟你无关（修复前编译器把全工程的
  using 合并成一个列表，任何文件都能被别人的 import 改掉绑定——已修，结论在
  版本历史里）。
  对策不变但**理由变了**：用到哪个命名空间的类型就显式 import 哪个，既让歧义面
  变小也让意图清楚；但不要再把它当绕行手段——编译器已经不串味了。
  坑出处：卡牌游戏加上 `using Game.Cards;` 后 `Window` 绑不到
  `Gui.Backend.Window`（当时数据框包的 `System.Data.Window` 抢走了裸名，
  多个外部项目集体编不过）。
- **同名类在"全局命名空间 + using 包"时直接撞车（undefined type，不是绑错）**：
  项目里原本有个全局类 `DataRow`，迁移到包时又 `using 某包;` 引入包里同名
  的 `DataRow`，裸名 `DataRow` 就有两个候选，编译器**绑不了**，报 undefined
  type（不是"绑到另一个"）。**对策：迁移到包时把项目自研的同名类删掉**，
  别留"适配层"——适配层同样会撞。坑出处：某客户端迁数值表包时，自研的
  `DataRow` 与包里的同名类并存，报 127 个 undefined type，删掉自研类、
  改用包里的类型后一次过。
- **把棋类 AI 迁到共享搜索包时，终局分的口径要一起搬**：共享的 alpha-beta
  包对终局只给固定 `±Mate`——只说"谁赢"，不说"几步赢"。于是"一步将死"和
  "四步将死"同分，搜索按走法顺序随便挑一个，**AI 会选慢杀**。项目自己那份
  实现往往带距胜项（象棋旧实现是 `500000 + depth * 1000`），迁移时把这个项
  补进适配器的 `Evaluate()`：终局分 = `Mate - 已走层数`，并让**游戏侧接管
  终局判定**（含"无着可走"——象棋没有闷杀规则，无着可走就是被将死），否则那条
  固定 `-Mate` 的分支会和带层数的终局分打架。适配器还要把 `Evaluate()` 翻成
  **当前行棋方**视角（包的契约如此），并缓存合法着法列表——合法着法是搜索里
  最贵的一步，终局判定不能再算第二遍。坑出处：象棋项目迁共享搜索包后一度
  搜出"四步将死"，因为终局分没有距胜层数；补上后每层深度都先吃帅。
- **把棋类规则迁到共享包时,三样东西要一起搬**:① 规则语义(禁着/终局/数子口径);
  ② 状态所有权——劫点、停手计数、提子数只能有**一份真相**,放包里,游戏侧读包,
  别再留一份自己的字段(两份真相会在"某处忘了同步"时漂移);③ 表现层钩子——
  包里不碰像素,提子动画靠"包里返回被提子坐标"承接,特效仍由游戏播。
  同时要一条**无副作用试算**接口(`Probe` / `ProbeMove`):否则游戏侧 AI 会
  "存盘→临时落子→算气→还原",那既是两份真相,也是漏还原 ko/pass 计数的老坑。
  坑出处:围棋项目迁 `Game.Board.GoBoard` 时,自研的 `Group`/`TryPlay`/
  `TryPlayRaw`/`Probe`/`Score` 一并删掉改调包,AI 试算换成 `ProbeMove` 一次
  拿全(合法/提子/气数/块大小),项目侧净删 196 行。- **红灯先按层归因，编译错误会掩盖运行期行为**：一条 conformance 用例可能同时
  有编译期错误与运行期行为差异；先把编译错误清掉再重跑看运行期输出——本轮 22 条
  "编译失败"清掉可见性误伤后，有 3 条露出真正的运行期缺陷（X509 的 CN 回退口径、
  MVC 菜单 icon 落空、HTTP/2 帧 API 在仓库里根本不存在）。把编译错误当结论，
  红灯永远查不完。
- **用例要先判定环境能力再断言；"读不到"有两种，别混**。剪贴板、桌面会话这类
  能力在 CI 与 agent 机器上可能不可用，用例应先探测再用，不可用时打印 skip
  理由——否则它在任何无头机器上恒红，把真缺陷淹没在噪声里。但**"写成功、读回
  空"不等于"没有剪贴板"**：Windows 剪贴板是全局独占资源，两个进程同时开会被
  拒，撞上争用时"写"抢到了、"读"没抢到，读回来就是空串。**能力探针（能打开
  就是有）比"读一次看是不是空"可靠**，先量清是哪一种再下结论。坑出处：本轮把
  一次争用误判成"环境没有剪贴板"，登记成环境问题；后来同一会话实测剪贴板完全
  可用、8 条用例全绿，真缺陷（库层不重试）一直躺在"环境问题"里没人修。
- **Windows 全局独占资源（剪贴板）必须退避重试，不能一次失败就返回**。争用是
  瞬时的（复制/粘贴、剪贴板管理器、输入法取词），一次"写-读"往返要开关剪贴板
  十几次，撞上一次整条就红——用户看到的是"复制偶尔没反应"，测试看到的是"用例
  偶发红"。另外它的独占是**按窗口句柄**判的：持有者挂真实窗口（资源管理器/
  IDE 都是）时别人的 `OpenClipboard(NULL)` 会被拒，两边都传 NULL 则互不排斥
  ——所以"造争用"来验证重试时，持有方必须挂真实窗口句柄，否则根本撞不上。
- **红灯先定归属：僵尸基准（源码改了、基准没同步）不是这次改动造成的**。判定
  办法是比对**用例源码**与**基准 .out** 的最后改动时间——基准比源码旧，就是
  僵尸基准（用例加了输出行、基准没跟上），这条红灯在动手前就红着。坑出处：
  一条代码编辑器用例在改用例时加了 "diagnostics and minimap check ok" 输出，
  基准没同步，该用例一直红，差点被当成本次改动的回归。定完归属再决定补基准
  还是修实现，别把别人的锅背到自己改动上。

### IDE 内部逻辑的无头探针验证配方（模板打磨沉淀）

- **探针作 paths[0]，全量工程源一起编**：zanc 只给首个输入发 Main，探针文件带
  `static void Main` 放首位，后接入口的窗体文档与工程源清单响应文件
  （ZanIDE 工程即 `<build>/ide_files.rsp`，其中已含 Gui 包源码，改组件库
  同样被这把编译覆盖），即可在命令行无头驱动 IDE 内部任何静态方法
  （项目创建、向导数据投影这类），不必起窗口。
- **链接集照抄工程的 IDE 构建脚本**：`--no-arc-guard --no-check-leaks` +
  运行时归档（`--link-lib`）与内嵌资源对象（`--link-input`）+ 宿主平台的
  系统库；探针不要窗口子系统——console 子系统才吃得到 println 断言输出。
- **夹具走真文件，断言读回盘上字节**：给有文件副作用的函数（项目脚手架、
  导出器这类）喂临时目录下的真实输入树，事后把产物按字节读回断言
  （工程文件关键字段、忽略表、README 命令行），别在内存里 mock 文件系统。
- **App 级全窗控件用独立宿主探针驱动**（向导芯片实机验证）：
  WizardHost 这类宿主是独立顶层窗口、自带事件泵，主窗的 ZAN_UI_SCRIPT
  dump/clickid 够不到内部——别硬掰驱动，直接给控件搭一个
  `App.CreateDarkStage(标题, 宽, 高)` 探针宿主，帧循环里 `控件.Show(app)`，
  ZAN_UI_SCRIPT 就能在该窗口内 dump/clickid/截图。夹具坑：向导
  catSel/tplSel 必须同指一个模板——tplSel 会被钳回当前分类的可见集合，
  分类停错时右栏静默换模板、置灰判定全部落空。
- **外部截图进程先声明 DPI 感知**（同上）：PowerShell 默认不感知 DPI，
  GetWindowRect 被 OS 虚拟化，量出的矩形比真实窗口小，PrintWindow 的
  DC 跟着小——截图被裁角还以为窗口没建对。截图脚本开头调一次
  `SetProcessDpiAwarenessContext(-4)` 再量再抓。

### 编辑器智能感知：补全分层与片段展开（编辑器体感沉淀）

- **"客户端没声明能力"不等于功能不能用——先问这份能力由谁消费**：语言服务
  的片段候选（`insertTextFormat=2`）此前在宿主侧被整条丢弃，理由是"客户端未
  声明 snippetSupport，不能把占位符当普通文本插入"。真实分工是：占位符根本
  不该由客户端解析，而是由编辑器自己的片段引擎展开，协议里的 insertTextFormat
  只是"这段文本是模板"的标记。丢掉它 = 语言服务的片段模板从来没进过编辑器。
  这类"按能力丢弃"的分支不报错、只静默失效，必须逐条问"这份能力谁在消费"。
- **JSON-RPC 里没有 id 的消息是通知，不是非法消息**：响应分发只认有 id 的
  消息，诊断推送（publishDiagnostics）没有 id，于是整条被丢——诊断通道从上线
  起就没通过过。给协议层分流时必须同时给通知留出口，否则"看起来实现了"的推送
  永远到不了 UI。
- **片段占位符的位置不要记死偏移，用链式推进**：洞 i+1 的起点 = 洞 i 的终点
  + 两者之间那段固定文本。片段模式下用户只往洞里打字，固定文本不动，所以只要
  盯住当前洞的终点，后面的洞就跟着走。所有编辑原语（插入、退格、换行、删选区）
  都要同步当前洞的终点，否则"洞里打完字再 Tab"会跳错位。
- **片段模式下要压掉补全弹窗**：Tab 优先接受弹窗，弹窗一开洞就跳不动。VS 的
  做法是占位符内不弹补全；方向键移动光标 = 离开片段（光标一动，片段即结束）。
- **补全候选按种类分层要三层一起做**：种类权重（工程符号 > 关键字/片段）+
  收集顺序（同分时工程符号优先）+ 浏览模式（无前缀）按种类配额。片段必须排在
  关键字之前——同名时"片段"标签决定 Tab 是否展开模板。改完排序要把弹窗实机
  截图看一眼：分层是否真落到屏幕上，而不是只改了打分函数。
- **发布构建的 DCE 会掩盖成员缺失，开发模式全量编译也要过一遍**：`--publish`
  会删掉没人调用的死代码，某段死代码里调用了并不存在的方法，发布构建照样绿，
  只有开发模式（非发布）全量编译才红。症状往往被误读成"只能按发布模式编"。
  修法优先补作者预期的 API，而不是改他的调用点——调用点属于别人的功能。
- **错误列表要同时收"上次构建"与"IDE 实时分析"两类来源**：只有构建日志时，
  构建成功一次错误就全没了，打字冒出来的语法错根本进不来；VS 的 Error List
  收的是"当前工程所有已知问题"。合并时按 (文件, 行, 消息) 去重——同一处错误
  常被两个来源各报一条。
- **去重/排序的键必须归一化**：路径分隔符（`\` 与 `/` 混用）、行号（字符串比
  会让 "10" 排在 "9" 前面）都会让同一个东西算出两个键，顺序也被写法牵着走。
  路径先归一化再比，行号按数值比。
- **插入排序的移动条件是"别人比我大"**：写反了（写成"我比别人大"）不报错、
  只是顺序反了——小数据集上肉眼很难发现，务必用断言把顺序钉住。
  坑出处：错误列表按 (路径, 行) 排序时条件写反，实时诊断被排到了设计错误后面。
- **签名提示的重载要能逐条切（VS 的「◀ 2/3 ▶」）**：语言服务的 signatureHelp
  本来就返回**全部**重载（`signatures` + `activeSignature`），编辑器只取
  `activeSignature` 那一条 = 重载信息从协议层一路丢到 UI。签名条要显示
  「第 n/m 条」并给出切换入口（点浮层上的箭头 / Ctrl+Shift+Space），手动
  选择在整个调用期间保持、换一次调用才重置——否则用户看到的是"永远那一条"。
- **自动挑重载的口径必须与语言服务一致**：两边都取"第一个参数个数大于当前
  实参下标"的重载（LSP 的 activeSignature 同口径）。各挑各的会让签名文字与
  第二区的参数文档对不上（看着像另一个函数的说明）。
- **闭包里不能沿用外层的空值收窄**：`if (guard == null) { return; }` 的收窄
  不跨闭包边界，闭包里再取 `guard.snapshot` 会被空安全检查判红，整个 IDE
  构建不过。只读值（snapshot / 路径）提到闭包外捕获成局部量；要写回守卫
  对象的（`guard.semantic = result`）在闭包内自己再判一次空。
  坑出处：IDE 在 HEAD 上因此编译不过，9 处报错全在闭包里。

### 右键菜单与片段选择器（编辑器体感沉淀）

- **菜单放不下时按主流 IDE 口径降级，不要让最后几项点不到**：编辑器右键菜单是
  自绘浮层，高度随项数增长；窗口不够高时菜单一律被裁到窗口外，末尾的宿主项
  （格式化文档 / 重命名符号 / 快速操作和重构）永远点不到。降级顺序按"主流 IDE
  右键里本来就没有"排：先去掉「跳转到行…」「查找…」（它们属于编辑/转到菜单），
  再去掉次要编辑命令（复制行/删除行/多光标），最后合并连续分隔行。
  坑出处：补上"插入代码片段…/切换断点/折叠展开"后菜单高 673px，1080×720 的
  宿主窗口放不下，底部的宿主项整段点不到。
- **Ctrl+M 与 Enter 同码（Windows 都发 CR）**：折叠/展开快捷键必须靠修饰键区分，
  否则 Ctrl+M 会插入一个换行。编辑器里 `code == 13` 分支要先看 HasCtrl 再决定是
  换行还是折叠；Ctrl+Shift+M 靠 Shift 位区分"展开"。
- **片段模板表单一源化**：候选列表与展开逻辑都从同一张表取。两处各写一份必然
  走散——列得出却展不开（新增片段只加进列表、忘了加模板，Tab 展开就静默失败）。
  片段模板必须是本语言语法：插进去的代码要能直接编译，验证办法是把"填好洞"的
  展开结果整体编译一遍。
- **"只列片段"的选择器要有模式生命周期**：模式标志必须在弹窗关闭时清掉，否则
  之后的打字一直只列片段，看起来像补全坏了。判据用"弹窗是否开着"，打开选择器
  时先声明弹窗要开着（否则重建弹窗的入口会把它当"上一轮已结束"清掉）。
- **既有黄金输出锁定的行为不要顺手改**：普通补全里"Enter 接受片段只插入触发词、
  Tab 才展开模板"是既有契约，改动要连带改黄金输出；只在新场景（如片段选择器）
  放宽，那里插触发词本来就没有意义。
- **服务端片段库未必是本语言语法**：语言服务内置的片段（`string[] args`、
  `get => …`、`Task`）插进本语言代码编译不过。语言服务推送的片段走模板展开，
  但"插入代码片段…"这类浏览型入口要维护本地片段库并做编译验证。
- **行号槽右键是断点菜单，不是编辑菜单**（VS 口径）：点行号槽左键 = 切换断点，
  右键 = 断点菜单（切换/条件/删除全部）。这条菜单**不动光标**——断点只针对被点
  的那一行，光标留在原处。
- **一套浮层复用多种菜单，用"菜单模式"字段切换内容**：编辑器只有一套菜单浮层
  （打开/绘制/命中/派发），断点菜单与文本区主菜单共用它，靠一个模式字段决定
  "这次装哪份菜单项"。另起浮层就要把命中与绘制再写一遍。
- **宿主能力分段注入**：主菜单的宿主项（格式化/重命名/快速操作）与断点菜单的
  宿主项（条件断点）语义不同，各挂各的注入口（`SetHostCtxItems` /
  `SetHostBreakpointItems`），别塞进同一份列表再按名字过滤。

### 共享工作树里的"编译中间态"（并发会话的阻塞判定）

- **别人正在改编译器时，`packages/` 编译红多半是中间态，不是你的锅**：先定位
  第一个报错落在哪个包、哪一行，判断是"编译器的新诊断暴露了包代码的真缺陷"
  （要修包）还是"编译器改动还没收尾"（等）。别把时间花在替别人收尾上。
- **按依赖链找"还能验证的那块"**：包的编译只拉它真正引用的文件——编辑器包
  不引设计器与上传作业，就能在整仓红的当口照常编译与跑测试；设计器/宿主侧
  则必须等包恢复。
- **被阻塞的线要登记而不是硬上**：写进 `TASKS.md`（现象 / 现状 / 已想清的方向 /
  阻塞原因），恢复后按登记直接开工，不要在红着的树上堆改不动的代码。
- **Zan 坑：三元表达式直接当函数实参会报"无法解析为可调用"**：
  `EqInt("x", cond ? 0 : 1)` 编译不过（同样的三元写成 `cond >= 0 ? 1 : 0`
  反而能过——取决于前项的类型推断）。稳妥写法：先 `if/else` 落到一个 int 变量
  再传参。
  坑出处：写断点菜单的 UI 用例时踩到，报错指向调用点而不是三元本身。

### 共享资源冲突要"等"，不要"另开一份"（并发会话的串行纪律）

- **共享构建资源只有一个，用串行闸拿**：走仓库提供的构建脚本
  （`scripts/build.ps1`）与测试脚本（`scripts/test.ps1`），两者共用一把跨进程锁
  （`scripts/build_gate.ps1`）。**不要裸跑 `cmake --build build`**——它没有闸。
  看谁占着锁：`pwsh -File scripts/build_gate.ps1 -Status`。
- **拿不到就排队等，不要另建一棵构建树**。另建（`build_mine`、
  `build-zancprobe` 等）是用磁盘换隔离：几百 MB 到 2 GB 的重复构建，而且公共包
  一改副本就漂移——副本没有让共享状态消失，只是把它藏起来了，漂移照旧。
  **共享资源冲突时的正确动作是等，不是复制一份。**
  坑出处：一次 15 worker 并发，多出 2.7 GB 重复构建树 + 一个 247 MB 仓库副本
  （detached HEAD 停在旧 commit），而公共包仍旧不同步。
- **公共包不要用 worktree 副本**（`git worktree add` 出来的"干净副本"）：它与主
  仓库天然漂移，且并发开发应直接提交主分支、不建分支。直接用主仓库
  `packages/`，编译时 `--package-project <repo>`；确实要隔离就把 `packages/`
  **拷**进自己项目的 `build/` 目录（拷贝不参与 git，不会漂移到"另一个 commit"）。
  坑出处：worker 被指派对一个已被删除的公共包副本编译，它自建新副本顶上，
  从此用着停在旧 commit 的公共包。**副本会一次次被重建**——只要任务书还
  写着"用那份干净副本"，就有人再开一份（实测同一天被重建两次，一次停在
  落后 3 个提交的 commit，一次落后 4 个，11 秒建完）。任务书里写死主仓路径。
  **仓库外的 git worktree 副本一律不再建**（任何用途：公共包、A/B 对比、
  读源码）。要对比两个 commit：要么在**同一目录串行做两轮**，要么用
  `_scratch` 下的**普通目录拷贝**（不注册进主仓 worktree 列表、不参与 git）。
  理由就一条：从副本里读到的源码是**旧快照**，据此得出的结论可能是错的，
  而且它会让所有人顺着它去用旧公共包。
- **别把"事实"抄进任务书再分发给 N 个 worker**：抄错的事实会被放大 N 倍。
  任务书只写**目标与验收标准**；API/语义让每个 worker 自己读一次源码（10 行），
  比抄一份可能错的强。编译器源码永远比任务书权威。
  坑出处：任务书里"Gui 只在磁盘上找皮肤、没有内嵌兜底"被 15 份 worker 继承，
  而编译器源码（`src/compiler/main.c`）明确写着 zanc 会自动内嵌标准库皮肤基线
  （只有暂存的 `skins/` 含完整 base.css 替身时才跳过）。
- **能用断言钉住的行为，不要靠截图反推**。抓帧只用于"好不好看/像不像"这类断言
  不了的东西；且一次抓完、批量分析像素，别边抓边猜采样时序。
  坑出处：某任务为抓一个 40 帧红色闪光反复调采样间隔（0.12s→0.1s），296K
  token 花在代码逻辑里已写明的结论上——"分支走了 → 闪光计时器被赋值 → 闪光
  没画出来"，问题是渲染不是采样。
- **写像素断言前先把"不变量是什么"想清楚，方向别写反**：右对齐的语义是
  "锚点是文字右边界"，所以**换锚点时整块墨迹跟着平移**（左右缘一起动），
  而不是"右缘钉死不动"。一旦把断言写成"右缘不变"，用例立刻报
  `got -20 want 0`——是断言错了，不是实现错了。
  可观测的定义要选**与锚点无关**的那一个：右对齐 = 同一锚点下，比左对齐
  整块左移恰好一个文字宽度，换锚点时左右缘位移相同。
  坑出处：给右对齐文字 API 补 conformance 时踩的。
- **模板/技能里写了"怎么用"，不等于包里真有这个 API**：写用法的人不会顺手
  把实现补进包，于是模板引着一个**从未存在过**的方法，编译直接失败。落地前
  先查它到底有没有过：
  ```
  git log --all -S '<方法名>' -- packages/        # 空输出 = 从未存在（API 缺失）
  git log --all -S '<方法名>' -- packages/ | wc -l # 非空 = 查清楚是谁加的/删的
  ```
  缺失就在包里补（规则 10），并给新方法配一条 conformance 用例把语义钉住；
  顺手把模板/技能里的调用改成真实签名，别让下一批 worker 继续抄。
  坑出处：有一次提交同时引出了两个"只写用法没写实现"的包 API——两个 ship
  出去的模板都编译不过。
- **并发上限自己盯着**：会话数超过 3~4 个时，人和模型端点都开始互相拖累，
  且重复派发同一任务会白烧两份 token。派任务前先确认没有同题在跑。
  **同题重复派发的典型产物是"空壳会话"**——零消息、零产出，只烧 token 不干活；
  判据是会话列表里**标题相同**（同一父会话下），派发前扫一眼列表，发现同题
  就只留一份，已经开出来的空壳立刻归档。
  坑出处：一次 26 个 worker 子会话的并发里，有两个任务各被重复派发了一份，
  两个副本都是零消息空壳——纯白烧 token，还让"有几条任务在跑"更难数清。

- **调度器是并行的唯一入口**：`scripts/sched.ps1` 管三件事——**任务准入**
  （同题重复派发直接拒、并发超上限排队）、**共享资源锁**（租约 + 进程存活
  判定：持锁进程崩了锁自动失效、PID 被复用能认出来、别的进程也能替它
  解锁）、**副本自动回收**（过期租约 + 没人引用的仓库外 worktree 副本，
  删前先证明"内容已在主仓"）。
  - 派 worker 前：`pwsh -File scripts/sched.ps1 register -Title "<任务名>"`
    ——同题已在跑会直接拒（exit=2，点名是谁在跑），并发超上限排队（默认 4）。
    长任务 `heartbeat -Id <lease>` 续租，结束 `finish -Id <lease>`（顺手清掉
    它登记的副本）。派发前先 `status`。
  - 拿构建资源：`scripts/build.ps1` / `scripts/test.ps1` / **裸 ctest** 都走
    同一把锁。裸 ctest 也自动排队——钩子挂在 CMake 生成的 `CTestCustom.cmake`
    上（`scripts/ctest_gate.ps1`），谁跑都一样，绕不过去；`scripts/test.ps1`
    持锁在先再拉起 ctest 时，钩子认出"持锁者是 ctest 的祖先"，不重复加锁、
    也不提前解锁（否则父进程还在跑锁却没了）。
  - 坑出处：约束只写在 AGENTS.md 里必然被漏——裸跑一次 `ctest` 就漏了，所以
    把约束挂到 ctest 自己身上；副本靠"记得删"必然删不干净（worktree 副本被
    删两次又被重建两次），所以回收要自动 + **有证明才删**（干净 + HEAD 是
    main 的祖先才动，独有提交/未提交改动一律保留并报出来）。
- **共享工作树里提交自己的文件：临时索引 + 部分提交之后必须把真实索引刷回来**。
  做法：`$env:GIT_INDEX_FILE=<临时索引>` → `git read-tree HEAD` →
  `git add <自己的路径>` → `git commit -F <msg文件> -- <自己的路径>` →
  **把 `GIT_INDEX_FILE` 置回空** → `git add <自己的路径>`。
  原因：**部分提交（`git commit -- <paths>`）之后真实索引不会自动跟 HEAD 对齐**，
  索引里留的还是旧 blob，`git status` 显示 `MM`；下一个会话一提交，你的改动
  就"凭空消失"（别人以为是自己误删的）。所以刷回不是可选项。
  - **`git add` 可能失败，必须复核**：`fatal: unable to write new index file`
    是别人正在写索引时的真实报错（共享工作树里很常见）。失败那一刻
    `git status --porcelain` 会打出怪状态（同一路径既"已暂存删除"又"未跟踪"），
    过一会儿自愈。**别假设 add 成功**——刷回后立刻
    `git status --porcelain -- <路径>`，要求输出为空；不空就重跑 `git add`。
  - 提交消息文件放临时目录（`_scratch` 之类），用 `-F` 传（`-m` 必须在 `--`
    之前）。
  坑出处：给一个右对齐文字 API 补提交时 `git add` 被并发写索引打断，
    `git status` 一度显示 `D`/`??` 打架；只看提交是否成功就收工的话，
    真实索引会带着旧 blob 留在那儿。

### PowerShell 脚本协作的几个坑（脚本纪律）

- **租约/心跳的时间戳存 epoch 数字，别存 ISO 字符串**：`ConvertFrom-Json`
  会把 ISO 字符串转成 DateTime，再转回字符串就不是原来的字面量（时区还会
  被折一次）——比对必然失配，症状是"刚写的租约瞬间过期""持锁者明明活着却
  被判成已死"，于是什么都拦不住。epoch 秒/毫秒是数字，过 JSON 不变形。
- **命名参数只能用哈希表 splat**：`& $cmd @array` 是**纯位置**的，传
  `-Name` 会被当成位置参数，报"找不到接受该实参的位置参数"；要用
  `& $cmd @hashtable`。
- **`Start-Process -ArgumentList` 按空格拼接**：传
  `-Command "Start-Sleep -Seconds 120"` 会被拆成 pwsh 自己的参数，进程秒退
  ——于是"常驻持锁进程"当场死掉，锁被判成自动失效，测试看着像闸没生效。
  带空格的命令串用 `-EncodedCommand`（Base64，没有空格）。
- **`Write-Host` 走信息流（3），不是成功流**：抓脚本输出要 `*>&1`；只写
  `2>&1` 抓不到，脚本自测会"什么都没收到"却显示 PASS。
- **后台辅助进程要把 stdout/stderr 重定向到文件**：否则它攥着管道不放，
  调用方看着像卡死。

### 测试产物要收口，别散着堆（构建产物纪律）

- **一个用例 = 一条 ctest 条目 = 一个可执行文件**：conformance / 泄漏 / ARC
  三个结论共用同一份插桩产物（`build/cases/case_*.exe`），determinism 另立
  一条 `case_det_*`（它要比两次代码生成，只留一枚 stamp，不产 exe）。
  **别再把同一个源编成多个 exe**：孪生档的老写法是同一份源码编三遍
  （普通版 / `--check-leaks` / `--arc-guard`）跑三遍，一轮全量下来 3500+ 个
  exe、4700 个一次性文件，而每个程序本身只跑几毫秒——浪费全在重复编译与
  重复落盘上。合并的判据是"插桩版 stdout 与普通版逐字节相同"（插桩干净时
  不额外打印），所以一次运行能同时给三个结论。
  坑出处：泄漏报告打在 **stdout** 上，所以"故意泄漏"的用例不能拿插桩版比
  golden，得额外编一份未插桩的普通版（`PLAIN_OUT_EXE`）。
- **用例产物只有一个去处**：所有 conformance 用例的可执行文件都
  编到 `build/cases/`，`build/` 根只留真产物与工具链。新增用例时不要写回根
  目录，也不要另开目录。
  坑出处：几百轮测试之后 `build/` 根堆了 **1884 个一次性 exe / 6 GB**，真产物
  只剩 4 个；`ctest` 每跑一次还留一个 `LastTest.log.tmpXXXXXX`（37 个 / 3.7 MB）。
- **它是缓存，不是垃圾**：测试 harness 靠"源文件/编译器/标准库 stamp 没变就
  复用旧 exe"来加速，**全删等于每轮重编一千多个程序**。所以按**最近使用 +
  体积上限**清扫（仓库提供的清扫脚本的 `-KeepDays` / `-MaxCacheMB` 参数），
  热的工作集要保住，冷的才扔。
- **日志合并成一份**：`ctest` 的完整输出归档成 `build/test-out/<tier>-<时间>.log`，
  只留最近 5 份；别每个用例一个输出文件散在 `build/` 里。
- **`build/` 根不能按通配符删**：真工具链（链接器 `ld.lld.exe`、仓库自带的
  `repomap.exe` / `zan-mcp.exe` / `zanfmt.exe`…）也在那儿，按名字猜着删会踩到
  发布脚本。保留清单写死在清扫脚本里，每条都注明来源。
- **用例 exe 不是 cmake 编译产物**：它们没有同名 `.dir` 中间态，是 harness
  每次现场编译的，所以删掉安全、下次会重新生成。
  坑出处：曾以为"根目录那堆 exe 是构建产物，删了要重编一千多个程序"（其实是
  缓存），反过来"全留着"又让 build 涨到 10 GB——两头的直觉都是错的，判据是
  "有没有同名 `.dir` 中间态"。

### 改编译器的"行为口径"时，宿主、自举侧与 golden 是同一批交付（口径变更纪律）

- **改了输出的措辞或形状，三样必须同批改**：宿主实现（编译器本体）、自举侧实现
  （自举编译器）、conformance 的 golden（期望输出文件）。只改一样，对拍门必然红，
  而且红的方式会误导人。
- **对拍门红了先分类，再动手**：把宿主输出、自举输出、golden 三者两两比。
  - 宿主 == 自举、但都 != golden → **golden 过期**，按宿主输出更新 golden；
  - 宿主 != 自举 → **真分叉**，两边必须选一个口径统一（自举要照抄宿主）；
  - 三者都不同 → 先看宿主自己是不是也不对（"分叉"有时是宿主错了）。

  坑出处：改 bool 渲染口径（`"1"/"0"` → `"true"/"false"`）后 7 个对拍用例全红，
  逐个比对后 6 个是 golden 过期、1 个是宿主自己漏了一条路径——不分类就分头改，
  必然改错一半。
- **"自举要照抄宿主"的前提是宿主那一侧是对的——分叉时先判谁错，别机械照抄**：
  两侧行为不同，有三种可能：自举缺了守卫（照抄）、自举多了守卫（自举删）、
  **宿主自己算错了**（另立条目修宿主）。第三种最危险：照抄等于把一个缺陷
  复制成两份，还顺手把"哪边对"这件事也定反了。判据：**看语言语义**——同一个
  表达式按语言规则该是什么值，以那个为准；两个后端都不对时，以语言的为准，
  把它写成台账条目在错的那一侧修。
  坑出处：宿主把 `bool` 当**有符号**整数用（i1 符号扩展），于是
  `Convert.ToInt32(true)` = -1、`Math.Sqrt(true)` = NaN；而语言语义是 1
  （`bool` 转整数取 0/1，且 `bool` 没有到 double 的隐式转换）。自举侧原本
  给的是正确的 1，照抄反而会把对的一侧改错。
- **两端的守卫要落在各自的"分派入口"，且判据不同就别共用一张白名单**：
  补一条"这个类型不许进这条路径"的守卫时，先找这条路径上所有分支的**汇合
  点**，守卫下在那里一次覆盖全部；散在每个分支里各判一遍，漏一个分支就是
  一条漏网路径。而**判据**要看两端各自在判什么——一边判"降级后的值类型"、
  另一边判"静态类型"时，共用一张白名单会同时错两次（放行了不该放行的、
  拒掉了不该拒的）。
  坑出处：给自举后端补 `Math.*` / `Convert.To*` 的类型守卫时，宿主这两个
  入口的判据根本不同（前者判降级后的值类型、后者判静态类型白名单），
  照抄成一张表会让 `object` 在 `Convert.*` 被拒、在 `Math.*` 被放行。
- **判定"这个值是不是 bool"要看语义类型，不能看 LLVM 值的宽度**：泛型实例化的
  方法返回值（如宽结构体集合的 `Contains`）会被提升成 i64，按宽度判就掉进 itoa，
  渲染成 `"1"`——同一个 bool 在不同上下文里长得不一样（`"x" + b` → `"x1"`，
  而 `b.ToString()` → `"true"`）。C# 的口径是 true/false：宿主按语义类型判，
  自举侧按值类型判，两边必须同口径。
  坑出处：编译器的字符串转码入口只看 `LLVMGetIntTypeWidth(vt) == 1`，
  泛型集合方法返回的 bool 因此漏判，宿主说 `"1"` 而自举说 `"true"`。
  **修法**：宿主侧抽一个共用助手，按 `infer_expr_type` 的**语义类型**判
  （i1 直接用，宽化过的 i64 先 `icmp ne 0`），**四条取串路径全部改用它**——
  拼接、插值、`Convert.ToString`、标量 `ToString()`。踩坑点：修一条漏三条
  （"汇合点"只有一个）——凡是"把值转成字符串"的地方，判据统一走这一个助手，
  别在每个调用点各判一遍。
- **重写 golden 里的 bool：按**逐位**对齐，不是按词边界**。golden 一行里常常
  **连着好几个 bool**（`"plus=" + IsMatch() + IsMatch()` 渲染成 `"10"`，修好后
  是 `"truefalse"`），还可能**bool 与真数字混在一行**（`matrix.rt=m13b00` →
  `m13bfalse0`：第一个是 bool，第二个是数字）。按 `\b0\b|\b1\b` 这种词边界正则
  判，会把 `"10"` 当成一个数字而漏判。正确的判据是**联合 token 走查**：老侧拆
  成「字面量 / 0-1 数字」，新侧拆成「字面量 / true-false 词 / 数字」，两边
  **一对一**对齐——一个 bool 词恰好吃掉老侧一个数字（`true`←`1`、`false`←`0`），
  剩下的数字必须原样不动。
  坑出处：曾因词边界漏判，把 123 份并非 bool 的过期 golden 一起改了；后来又用
  同一判据把 11 份 golden 误判成"非 bool 改写"而全部打回，最后靠逐位走查才
  分出真改写 9 份。
- **"在受影响名单里"不等于"该改"——重写 golden 前先证明它真的受影响**：
  判据是**逐行**过"是不是 bool 渲染"的走查（上一条），不是"这个文件在
  受影响名单里"。实测有 `chart_axis_breaks` / `directory_paths` 被误列进去：
  里面的 `prct=1` 是百分比、`dirs=1` 是计数，**一个 bool 都没有**，重写只动了
  行尾。
- **重写 golden：按仓库原字节重建，别拿工作树直接提交**：仓库里有 golden 带着
  CR CR LF 行尾（历史产物，git 的 CRLF→LF 过滤器处理不了这种"双 CR"）。把它
  写成普通 LF 就等于把**行尾归一化**夹带进提交。正确做法：新 blob =
  **编译器实际输出的内容** + **仓库原行尾**，逐行拼接——只动该动的那些行，
  其余行保持原始字节。判据：重建后再跑一次"逐行是不是 bool 渲染"的走查，
  两者都过才提交。

### 阈值类测试（体积/行数/耗时预算）：基线会漂，量的是不是你要守的那个量（阈值纪律）

阈值测试最常见的两种误判，都不是"代码坏了"：

- **基线过期**：预算是一条按"某天的实测值 × 余量"定下的硬线，而被量的东西
  会随开发长大。2026-10-22 实测：发布体积预算的 `.text` 预算是 200,000、
  实测 199,752——只剩 248 B 余量。成因不是固定大表回来了，是这一个月运行时
  源码 +140 提交 / 净增 ~8.8K 行，运行时载荷整体长大（linux 侧 `.text`
  189,074 同步长高——两侧同步，可据此排除平台特有）。**阈值红先查基线是哪天
  定的、中间长了什么**，别急着改代码；确定是正常成长，就按"实测 × 余量"重新
  定基线，并把基线数写回文档（预算脚本的头注通常会写这条要求）。
- **量的不是你要守的那个量**：Windows publish 会把内置默认图标塞进 PE 的
  `.rsrc`（实测 106,360 B，占产物三成）——图标是**产品资产**，不是运行时载荷；
  这条预算的用途是抓固定大表回归 / 抓丢 `--gc-sections`，就该用 `--no-icon`
  量。同理，失败文案别把**当前实测值**印成 `"(baseline: …)"`——那样写读起来
  像"和基线一样却还超预算"，实则基线是另一个数；改成 `"(measured: …)"`。
- 两条推论：① 阈值测试的**判据文案必须与判据同源**（写死的计数、印出来的
  数、实际比的值要是同一个量），否则报错会把人带偏——一个 MVC 安装脚本曾写死
  源文件数 121（包已长到 163），报错却印 `163 -> 163`，看着像集合差异，其实是
  过期常量；改成按相对路径逐个核对，才既准又不会随包增长而过期。
  ② 阈值放宽后要**记下为什么放宽**（写进任务台账 / 文档），否则下一个会话只
  会看到"预算涨了"，查不出是正常成长还是回归。

### 链接器死代码消除：裸 .o 进链接行 = 整体载入，GC 对它无效（链接粒度纪律）

- **实测（2026-10-23）**：一份 hello world 发布产物 `.text` 199,752，其中运行时
  占 84%（167,488）。查"为什么瘦不下来"时走了弯路：先按"函数都可达"解释，又试
  "加 `-ffunction-sections` + `--gc-sections`"——实测 `.text` 几乎不变
  （199,736），于是**错误地**把"加编译开关这条路"记成了死路。
- **真根因**：运行时对象是**裸 `.o`** 直接进链接行，而**裸 `.o` 是整体载入，
  section GC 对它无效**（链接器没有"只取需要的成员"这一步——那是**归档**的
  行为）。同条件对照（同一 gcc、同一 `--gc-sections`）：
  | 链接方式 | 留下的硬件加速符号 | `.text` |
  |---|---|---|
  | 裸 `.o` 直接进链接行 | 63（全留） | 156,640 |
  | 打进静态库 `libcrypto.a` | **0** | **103,232** |
  | 裸 `.o` + `--gc-sections` + `-ffunction-sections` | 63（仍全留） | — |
- **处方因此换了**：不是加编译开关，而是**把可选子系统从"文本包含"改成
  "独立归档成员"**。具体形态：运行时里有一行 `#include "rt_hw_accel.c"`
  （4558 行硬件加速）——**文本包含** ⇒ 必然与宿主 TU 同体 ⇒ 必然整体进 .o ⇒
  每个程序都背整块 SHA/AES/AVX2。要拆成按特性的归档成员（sha / aes /
  sm3-sm4 / rsa / pixel / crc），链接行只给归档。端到端收益实测：hello world
  `.text` 200,728 → 147,320、file 244,476 → 180,836，
  **这块独占 53,408 B（26.6%）**。
- **交叉侧同因同解**（2026-10-23 复测）：交叉产物一样剪不掉——linux-x64
  交叉 hello world 里硬件加速符号 63 + AES 32 个全在，占 `.text` 约
  37,941 B（19.8%）；而交叉链接**本来就带 `--gc-sections`**（`ld.lld -static
  ... -s --gc-sections`）——**带了照样剪不掉**，正好反证根因是"裸 .o 整体
  载入"而不是"缺 GC 开关"。宿主与交叉因此是同一个修法。
- **推论 ①：文本包含 = 把一整个子系统焊进宿主 TU**。`#include "x.c"` 让链接
  粒度彻底失效——无论链接器多聪明，这个 TU 都得整体进产物。查体积时先 grep
  运行时里的 `#include ".*\.c"`，那几行就是最大的候选。
- **推论 ②：归档成员粒度 = 实际死代码消除的粒度**。把某子系统单独编成归档
  后，只要程序用到其中**任意一个**符号，整个归档成员（一个 .o）仍会被拉进来
  ⇒ 必须**按特性再切到成员粒度**，否则只是把体积挪个地方。
- **推论 ③：先问"链接器凭什么能剪掉它"**。`--gc-sections` 剪的是 **section**，
  而 section 级裁剪要 section 已被切细（`-ffunction-sections`）**且**该 section
  不在"整体载入"的路径上。任一条不满足，加多少编译开关都没用——这就是上一轮
  误判的来源：**"加了开关没变化"不等于"这条路没收益"**，可能只是没找到真正
  的杠杆。
- **推论 ④：`-fdata-sections` 在有 1.4 MB `.bss` 静态表的运行时里是地雷**
  （把 `.bss` 搬进 `.data`，发布产物 245 KB → 1.8 MB，×7.4，而 `.text` 纹丝不
  动）。它和 `-ffunction-sections` 一起上会掩盖真实效果，测体积收益时要分开
  测、一次只动一个变量。
- **推论 ⑤：数符号前先确认产物没被剥符号**（2026-10-22 踩到，差点报错结论）。
  发布模式会剥掉符号表，`nm --defined-only` 对剥过的二进制**一个符号都读不出
  来**——于是"按需拉取没生效"和"根本没链接进去"长得一模一样。实测：在剥符号
  产物上数硬件加速符号恒为 0，换成未发布产物才看见真相（hello 0 个 / 用到
  加密的程序 95 个）。**凡是靠数符号下结论的测量，一律用未发布产物**；体积
  测量相反——要的是发布形态（`.text`/文件大小），用发布产物。
- **推论 ⑥：归档成员与它替代的裸对象必须同代重出**。旧裸对象（内含该子系统）
  + 新归档 ⇒ 同一符号被定义两次，链接报重复符号；新裸对象 + 旧归档 ⇒ 缺符号。
  所以"拆成归档"**不是一个文件的改动，是一次成对的重新产出**（对象 + 归档 +
  配方 + 暂存 + 发布打包），漏一头就是坏链。
- **推论 ⑦：归档要排在被它替代的对象之后进链接行**。归档成员只为"**仍未定义**
  的符号"解引用；被替代对象若已定义同名符号，成员就不会被拉进来（无重复定
  义），反过来排则必然重复定义。链接行顺序是这类改动的一部分，不是细节。
- **落地后的实测收益**（2026-10-22 收口）：宿主发布 hello `.text` 199,752 →
  **146,344**（−53,408）；交叉 linux-x64 hello 189,074 → **137,458**
  （−51,616）。按需拉取在宿主/交叉/macOS/wasm32 上都成立（hello 0 个硬件加速
  符号，用到加密的程序 83~95 个）。验证要**端到端跑一次**（交叉产物实跑，
  SHA-256("abc") 要输出标准向量 `ba7816bf…15ad`），别只看符号数。
- **坑出处**：先花了两轮把"补 `-ffunction-sections`"当成死路写进任务台账和归
  档文档，根因是**实验做在裸 `.o` 上**；真杠杆（改归档）一测就见效。教训：
  **否定一条处方前，先确认实验条件覆盖了它的前提**。

### 交叉工具链的隐藏依赖：预编译对象比源码旧、musl 声明门、缺内建归档（交叉工具链纪律）

- **预编译对象会比源码旧很多，而"旧"不会自己报警**。交叉目标通常提交
  `.o`/`.a`（不带头文件），源码改了不重出，所有交叉构建就静默用旧代码。
  2026-10-22 实测：已提交的一个交叉定时器对象里**连崩溃兜底的 altstack
  代码都没有**（那功能是后来才加进头文件的），而过时检查没看那个头文件 ⇒
  没人发现。**过时段落要把"对象依赖的头文件"也算进源列表**，否则源改了对象
  不跟，过时检查永远绿。
- **配方在现代工具链下可能根本编不过——而提交的对象是旧工具链编的**。
  同一批配方在旧版 zig 编得出、新版编不出：musl 把 `sigaltstack` /
  `SS_DISABLE` 藏在 `_BSD_SOURCE/_XOPEN_SOURCE/_GNU_SOURCE` 后面，而配方用裸
  `-std=c11`（无特性宏）⇒ 交叉对象长期停在旧代码。修法有两条：① 源侧补声明
  （**注意 glibc 与 musl 的 `sigaltstack` 参数序相反**，glibc 侧照抄 musl 的
  原型会 conflicting types）；② 配方侧加特性宏（但 `_GNU_SOURCE` 会把
  `strerror_r` 换成 GNU 语义，**副作用比缺声明大**）。源侧补声明 + 只对 musl
  生效最稳。
- **交叉 sysroot 缺"编译器内建归档"会断在 128 位运算上**。用 `__int128` 除法
  的运行时代码需要 `__udivti3`/`__umodti3`（在 compiler-rt / libgcc 里）。
  一个目标的 sysroot 带 `libgcc.a`、另一个没有 ⇒ 后者任何用到十进制的交叉
  程序都链不过（`undefined symbol: __umodti3`）。补法：zig 自带
  `lib/compiler_rt/*.zig`（`udivti3.zig`/`umodti3.zig` 直接 `@export` 这两个符
  号），用 `zig build-lib -target <triple> -OReleaseFast` 编成归档塞进 sysroot；
  链接行里 sysroot 的 `libgcc.a` 是**存在才加**的，缺了就静默不链。
- **顺带一提**：发布链接带 `--gc-sections`，非发布链接不带 ⇒ 同一个缺符号问
  题，**发布版能过、调试版过不去**。别被"发布能跑"骗了。
- **坑出处**：一次交叉收口连踩三条——交叉 linux 程序链不过（缺十进制运行时对
  象）→ 补上后又链不过（缺 `__umodti3`）→ 再补内建才通。每一层都是"预编译产
  物比想象缺东西"，**交叉链接失败先查缺哪个对象/符号，别急着怀疑自己的改动**。


### IDE 工作面模型与停靠布局的坑（工作面两维化沉淀）

- **停靠宿主面板不要新开分组，做成同侧页签**：停靠组件的布局算法给"尺寸
  未具体化"的新分组只分最小高度（56px）——已有分组按持久化的 extent 吃掉
  整侧，新分组只剩一条缝（实测：右侧列底边一条 53px 的带子，会话面板那样
  窄没法用）。同一侧再开一个分组前先想清楚：需要大面积的宿主面板（会话、
  属性检查器）注册成同侧页签（newGroup=false）占满整列；真要独立分组就
  得先给它一个像样的 extent。
- **同一块控件树只能有一个宿主**：面板既住独立子窗口又住停靠面板时，两处
  渲染同一批控件 id，点击会落到另一个宿主上，状态回读也跑两遍。两个宿主
  必须互斥：开一个先收另一个（收窗口 / 关面板都要处理）。
- **停靠面板"开着"的判据是"当前看得见"不是"没关掉"**：同一分组里只显示
  活动页签，非活动面板的内容矩形被清成 0×0。按钮的点亮态与状态栏标识要读
  "看得见"，否则用户切到别的页签后按钮还亮着。
- **工作面状态尽量派生，别另设字段**：面板显隐本来就落在停靠布局文件里，
  开关就不必再写一份状态文件——两份状态会打架（面板被用户关掉，字段还说
  开着），多一个落盘文件多一处不同步。
- **IDE 本体可以用 UiDriver 驱动**（"UiDriver 只绑进程里第一个 App"那条限制
  对 IDE 不成立：IDE 就是第一个 App）：ZAN_UI_SCRIPT 给脚本、ZAN_UI_OUT 给
  输出目录，`keydown 65 3` / `keyup 65 3` 就是 Ctrl+Shift+A（mods 位：Ctrl=1
  Shift=2 Alt=4，keycode 用 Windows 虚拟键码；Ctrl+Shift+字母不产生控制
  字符，所以走按键抬起事件那条通道；该通道必须带上修饰键状态，否则
  组合键退化成裸键）。三条配套坑：① 注入的坐标是**客户区**
  像素，而画布 dump 的起点在自绘标题栏下方（+48px），点功能区页签要 +48；
  ② `dump pixels` 的 ZPX1 头部 24 字节（x,y,w,h,bpp 五个 u32 从偏移 4 起，
  w 在 12、h 在 16），像素是内存序 B,G,R,A，转图用现成脚本别手写；③ 脚本
  路径只传裸文件名，点击后至少等 1~2 秒再 dump。
- **改组合键行为必须走真实键盘验收，合成事件会掩盖"修饰键根本没送到
  上层"**：UiDriver / `InjectEvent` 的合成事件自带 mods 位，真机上的
  修饰键却是 Windows 消息带来的，两条路径不等价。Windows 键盘后端曾把
  WM_CHAR 与 WM_KEYUP 的修饰键固定记成 0，于是 IDE 一批组合键在真机上
  是坏的：Ctrl+Space（弹补全）、Shift+F12（查找引用）、Shift+F8、
  Ctrl+Shift+F/R/A/S、Ctrl+Alt+F、编辑器的 Shift+Tab 反缩进，全退化成
  裸键——而它们此前只被合成事件验证过，一直没暴露。
  **验收方法**：写一个探针窗口（Gui 后端），用 SendKeys 发真键，把每个
  键盘事件的 kind/code/mods 打出来（kind 4=按下、5=抬起、6=字符；code 是
  Windows 虚拟键码；mods 位 Ctrl=1 Shift=2 Alt=4），对着它看修饰键落在
  哪个事件上、值对不对。仓库内仓库自带的 `scripts\key_event_probe.ps1`
  就是这个探针（`-Combos "+{F12};^{ }"`）。
  坑出处：Windows 键盘修饰键丢失导致 IDE 组合键集体失效（2026-10）。

### GUI 保留树事件路径的真实点击验证（事件门控验证沉淀）

- **先分清事件通道，再声明"路径已被点击验证"**：控件事件是双通道。Button
  这类控件有专属 `UiEvent Click` 字段，处理器经重载的 AddByName 路由进专属
  字段，点击在 `Ui.Activate` 命中后 `Click.PostS(this)` 直发；`On.Fire(app,
  wid, this)` 只广播通用 hub（WidgetEvents），对 Button 永远空转——hub 里
  没有订阅者。走 hub 的是通用自动接线、直接 FireOn，以及复选框/下拉/输入框
  等控件的 hub 事件与 HTML 元素 data-on-click。把"点了 Button"当"hub 路径
  已验证"是假阳性（曾有性能门控提交的验证描述即含此错）；立即模式界面里
  `RegisterRect`+`ClickAvailable` 的几何热区（导航行这类）根本不是控件，
  点它等于什么事件路径都没碰。
- **hub 路径的探针夹具用"无专属字段、只订 hub"的控件**：Panel 订
  `root.On.Click`（Panel 没有专属 Click 字段，点击只能经通用分发到达），
  宿主用 ChildWindow 独立窗口。
- **ChildWindow 独立窗口探针配方**：子类 override `Title/Width/
  Height/ShowMaximize/IdBase`（同进程多窗 IdBase 分段防撞号），主流程
  `w.SetRoot(root, null); w.Wire; w.OpenStandalone;
  w.PumpStandaloneUntil(stop)`，stop 是 `delegate bool Xxx`、返回 true 停泵。
  驱动 `ZAN_UI_SCRIPT`：`wait 2500`（等首帧）/ `click x y`（保留树命中区
  客户区 1:1）/ `wait 800` / `quit`（兜底防点空挂死），断言读 stdout 的
  处理器输出。事件成员名以事件表源码为准（是 `Enter` 不是 `EnterS`——
  编不过先 grep 成员表再猜）。

- **截图必须锚定进程 PID、按窗口抓取**，禁止全屏抓图后肉眼找窗口——
  全屏抓到的是最前面的任意窗口（编辑器/旧实例），拿错误窗口的像素做判断
  会得出"程序坏了"或"修好了"的假结论。先记录启动 PID，再按 PID 枚举顶层窗口
  逐个抓取；抓不到目标窗口就重试，不要让工具猜。
- **UI 驱动用合成事件，不用真实 OS 点击**：driver 的 `clickid` 在点击时刻
  解析命中区中心并注入，天然免疫窗口框偏移。数字 hit id 顺序发号、控件
  增删即整体移位（曾在 ListView 拖动停摆、菜单滚动条跳跃上爆过），脚本
  别握数字号——用 `clickid @语义名`：驱动按**本帧命中区的语义标签**当场
  解析（后注册者=顶层优先），标签在就永远点得中。新控件注册命中区时用
  `RegisterRectL` 带上数据键标签（向导行/平台芯片已接，芯片标签=
  "linux-x64" 这类平台 id），没标签才退宿主 probe "id.<name>" 旧通道。
- **UiDriver 一次 click 注入的是 move+press+release 三个事件，一帧只消费一个**：
  注入后必须连喂 3 帧以上，press 与 release 才会分别落到帧里。少喂帧的现象极具
  误导性：右键"点了没反应"其实是 press 已生效（菜单已开）、release 还堵在队列里；
  再点一次时残留的 release 抢在新 press 前面，菜单项就永远点不中——看起来像
  "菜单不响应点击"，真因是节拍不是逻辑。修法：每次 `UiDriver.Exec` 之后固定
  喂 4~5 帧再断言。坑出处：代码编辑器右键菜单的实机回归，菜单已开但宿主项点
  不中，排查半天才发现是驱动事件节拍。
- **ZanWeb 模板实机核对坑清单**（ListPage/FormPage/视觉重绘验证起，每条都白折腾过一轮）：
  ① 静态资产挂在 `/static/*`（`StaticFiles.Mount(app, "/static", "wwwroot")`），
  curl `/js/x.js` 拿到的是 API 层 `{"code":"404"}` JSON——不是"服务了旧文件"，
  先核对 URL 再怀疑缓存；② 改 wwwroot 的 JS/CSS 必须同步升布局模板
  里的 `?v=N`：资产响应带 `Cache-Control: max-age=3600`，浏览器缓存键含查询串，
  只 reload 页面拿不到新 JS（新代码 "确认加载" 要看执行中的函数源码或版本参数），
  且版本号升级放在该轮资产编辑**全部完成之后**——先升 v 后再改 js，会以新版本号
  缓存旧内容，之后怎么刷新都是旧的（菜单图标不渲染即此故，再升一位才好）；
  ③ `app.exe start` 会 daemon 出脱离启动任务的 worker，杀后台任务杀不掉它——
  重建 exe 报 `Permission denied`、旧进程继续占端口继续服务旧视图，须
  `app.exe stop` **并按 netstat 确认监听端口 PID 已清**（stop 不干净时链接
  照样 Permission denied）；④ config/views/wwwroot 按进程工作目录
  相对读取，起服务必须 cd 到发布目录，且 views 改动要重启才生效（视图缓存）；
  ⑤ e2e 与手动实机核对共用临时沙箱目录时，e2e 收尾会按自己的端口重写
  甚至留下"无 config"状态——手动起服务报"未配置会话密钥"这类假故障，先重新
  生成沙箱 config 再查代码；⑥ `--publish` 不落盘 views/wwwroot——运行时
  从磁盘读，手动沙箱要自己把模板的 views/ wwwroot/ 拷进发布目录（e2e 也是
  copytree 布置的），漏了就是整页 `<!-- view not found -->`；
  ⑦ config `worker.daemon=false` 时 `app.exe restart` 会前台阻塞把脚本挂死——
  起服务用 `(app.exe start > boot.log 2>&1 &)`，别用裸 restart；⑧ 手动起的
  沙箱实例占着 e2e 的端口时，e2e 起服阶段不会报"端口占用"，而是对自己的
  数据目录跑断言、拿到空表 IndexError 之类的假故障——跑 e2e 前先按 netstat
  停掉自己的实例；⑨ e2e_mvc.py 不带 `--build` 会复用沙箱既有 app.exe——
  改完源码直接跑，旧断言全绿、新断言全挂（测的是旧二进制，exe mtime 早于
  改动），极像"功能写坏了"；改源后必须 `--build`，或先核对 exe 时间戳。
  另：e2e 末轮 forgot 流程会把 admin 密码重置为 `newpass-e2e-123`，手动

- **多进程服务的停机探针（Worker/RunCommand）**：`<app> start` 恒为
  master + worker 子进程（单进程捷径仅非 CLI 的裸 RunAll），HTTP 服务跑在
  子进程；start master、worker、stop 客户端**都会执行 Main**。证据标记必须
  **按 pid 分文件**——共享一个标记文件会被三个进程互相覆盖（读到的永远是
  最后写者，信号错乱难排查），子进程 stdout 可能被重定向、Console 断言会
  静默丢失；钩子内先 `await Task.Delay` 再落标记，可证明"被等待"而非
  fire-and-forget。排查停机路径先想"自己关的连接被自己当 master 之死"
  竞态（如 ChannelLoop 对 handoff 通道 EOF 无条件 exit(0)，把整个排空
  等待短路）。
- **多窗口/离屏事件分发中鼠标按下 blocker 必须严格判定几何（禁止 hitId < 0 一票否决）**：
  在多窗口/子窗口与离屏设计器交互中，`ApplyEvent` 在鼠标按下（`kind == 2`）时记录 `pressOnBlocker`，
  必须严格为 `hitId < 0 && hitTester.BlockerAt(mouseX, mouseY)`，绝不能写成 `hitId < 0`。
  设计器画布、未注册几何热区的面板或空白工作区点击时 `hitId < 0` 是常态，若无条件置位 `pressOnBlocker = true`，
  后续鼠标抬起（`kind == 3`）会误入阻挡逻辑清空 `clickTargetId = -1`，导致整窗/全 IDE 所有点击事件被全局吞噬静默瘫痪；
  同时 FocusManager 的 `PushIds(first)` 分配段必须与 `PushId(first)` 作用域栈同步绑定，确保即时模式控件的 ID 跨帧连续且完全隔离。
- **外壳非客户区行为用真实消息 + 显式泵断言**：双击标题栏、SC_MAXIMIZE
  这类 WndProc 路径，PostMessage 到真实 hwnd 再显式 PumpGuarded，消息在
  泵内同步派发，无 sleep、无时序依赖。两条坑：NC 双击的 wParam 必须是
  WM_NCHITTEST 的 HTCAPTION(2)——传 0（HTERROR）DefWindowProc 静默忽略，
  "双击被挡住"的断言是空洞的假绿；RunLoop 的帧体只在 needsRedraw 时跑，
  静止窗口上永不点火——场景别挂在帧体上，用 worker 线程发消息
  （PostMessageW/IsZoomed 线程安全）+ app.Post 回 UI 线程收尾
  （Post 契约即线程安全）。
- **GUI 客户端×服务端联调的实机冒烟定式**：客户端留
  `ZAN_<APP>_AUTOLOGIN="user:pass"` 环境缝（登录窗独立泵起手前预填并
  直走登录流，GUI e2e 复用同一缝）；断言优先取**服务端可观测痕迹**而
  不是读屏——客户端行为落 DB 的状态列直接 sqlite 断言（如"打开会话"
  必推进已读水位，>0 即证明打开链路真发生了）；「实时消息并入屏」用
  前后两张窗口截图**逐字节 diff** 判重绘发生（PNG 确定性编码，内容同
  则字节同），等待窗口给足——WS 建连与秒级轮询节拍都是秒级窗，3s 级
  等待会假阴，6s 起拍、不等再兜底重拍；启动带 `ZAN_GUI_OVERLAP=1`+
  `ZAN_GUI_LAYOUTLINT=1`+`ZAN_GUI_OVERLAP_LOG=<file>`，收尾断言日志空
  （重叠/尺寸自检零命中）。截图脚本按 PID+窗口类枚举取最大可见窗，
  `$pid` 是 PowerShell 保留自动变量，参数名不能叫 `$Pid`。
- **后台窗口不 present：截图 diff 断言前必须点击激活**：数据并入（甚
  至下载落盘回调都跑完）后，非前台窗口的呈现面停在上一个交互帧——实
  测合并后 7s 截图仍逐字节同，一次合成点击立即出新帧，纯 SetCursorPos
  hover 无效。所以「重绘发生」类断言的**每张**截图前注入一次中性点击
  （点在无控件画布上，纯泵帧），并用 SetWindowPos 把窗口钉到屏内固定
  位置再拍（默认布局偶尔比屏高，出屏窗口捕获几何不稳）。
- **`Directory.ReadPath` 不是 cwd 解析器**：它对 cwd 里已存在的路径回
  空串（「程序随附资源回落」语义——磁盘上有就用原路径），永远产不出
  绝对路径；要取绝对 cwd 用 `Directory.GetCurrentDirectory`（跨平
  台）。想用 ReadPath(".") 拿 cwd 的写法静默失效，极难察觉。
- **截图 diff 断言必须选「内容必然变化」的动作**：PNG 确定性编码下，
  「重拉同一份数据再渲染」的重绘字节与之前完全相同（重绘发生了但断言
  假阴）——重开同一个详情面板这类动作判不了重绘，改判开/关切换（收起
  必然少一块像素）或数据必然不同的两步。
- **Windows 控制台命令的 subprocess 捕获别用 `text=True`**：tasklist
  这类工具按系统码页（GBK）输出，UTF-8 reader 直接 UnicodeDecodeError
  崩线程；拿 bytes 自己按 `errors="replace"` 解码。
- **TLS（libssl/libcrypto）已无随库驱动**：stdlib 曾带的
  System/Security/Cryptography/drivers/ 目录已随 OpenSSL 驱动下线而删除，
  老资料"设 `ZAN_LIB_PATH` 指向该目录"的做法失效。`ZAN_LIB_PATH` 机制
  本身仍在（任意放导入库的目录，win 用 `;` 分隔，见 ZANC_CLI.md env 表）：
  需要真 TLS 时指向自备 OpenSSL 导入库目录，运行期把对应 DLL 摆到 exe 旁；
  Windows 下只携带不触发 TLS 的程序可直接链接——不可解析的非系统库会被
  自动桩化（调用时才报错），不再链接期失败。

- **GUI 测试合成驱动的“静止泵”永挂坑**（chatview_bubble/transfer/
  chart_stackedarea_aa 三测试在安静机器上集体挂死，同一二进制早晨有人用机器时全绿，
  cdb attach 抓栈定位）：`App.ProcessEvent` 在无挂起重绘、无动画截止、无待处理事件
  时走阻塞 `window.WaitEvent`（GetMessageW 无限等；空闲零 CPU 是产品正确语义，
  不要改成轮询）。测试帧与帧之间常处于静止，静止泵只能靠环境消息流（鼠标活动等）
  偶然喂活——机器一安静就必挂，且挂点随时序漂移，极难归因。定式：守卫帧体
  （FrameGuarded 的 body）末尾续订 `RequestAnimationFrame(16)`（spinner 的文档化
  模式，animNextMs 截止让泵走 ≤16ms 非阻塞等待），或泵前 `RequestRedraw`
  （datatable 系同款）；纯数据突变后必须请求重绘再泵。诊断抓
  `USER32!GetMessageW` 栈一锤定音。

### 帧预算与"未响应"的归因（GUI 性能排查）

- **"卡顿"与"窗口未响应"必须分家，两者的责任方不同**。Windows 判未响应 =
  UI 线程 5 秒不泵消息；渲染一帧十几毫秒，差两个数量级——**渲染慢只会掉帧，
  不会造成未响应**。分家的判据是 phase 分解：`ZAN_FRAME_PROF=1` 让 App 把每帧
  拆成 `bg/measure/arrange/tree/render/present` 写进 exe 同目录的
  `zan_frame_perf.log`（分段打点 + 像素计数；超预算的单帧**单独记一行**，均值
  看不见卡顿）。六个 phase 都正常却仍"未响应"，就是 UI 线程上的同步阻塞
  （项目层）：该抓栈，而不是调渲染参数。库层每帧成本的判据是 **slow16
  （>16.7ms 的帧数）而不是平均帧时**。
  坑出处：实测一个 IDE 的帧预算（CPU 后端、固定皮肤与固定夹具项目）共
  95 批 2850 帧，**只有 1 帧**超过 16.7ms，就是首帧 195ms（其中 ribbon
  107ms、玻璃模糊 2274kpx、全量混合 2885kpx）——离"未响应"的 5 秒差 25 倍，
  渲染**结构上不可能**造成未响应。**别把门禁口径当稳态均值读**：
  帧预算脚本的 `tree_ms`/`render_ms`/像素量取的是**最差批次**（`_max_tree`
  一类聚合），不是均值——同一份日志里 tree_ms 中位只有 4ms、最差批次
  12ms，"稳态 12.5~17.6ms 超预算 2 倍"这种读法会把布局误判成病根。
  看稳态要看 30 帧批次的分布（中位 + 慢帧计数），判卡顿看 slow16，判尖刺
  看日志里的 `spike whole_ms=...` 行（它带 `top=`/`mark=`/`scope=`，直接
  指出是哪棵子树、哪个标记最贵）。
- **自证工具：`Gui.Diagnostics.UiWatchdog`**（GUI 包的 `src/Gui/Diagnostics/`）。
  `Enter(name)` / `Exit()` 把可疑代码括起来，退出时超过阈值（默认 2000ms）才报
  `UIWATCHDOG stall stage=<name> blocked=<ms>ms`——**只有你自己括的区间才计时，
  空闲期零误报**；`FrameBegin()` / `FrameEnd()` 统计慢帧与最差帧。排查顺序：
  先整帧括一次（分清"渲染还是别的"），再细分到每一步（定位"卡在哪"）。
- **子窗渲染有单帧预算，但预算不是万能药——两个边界必须一起记**。子窗是在
  **主线程的主帧内同步渲染**的，单帧总时长 ≈ Σ(各子窗渲染)，子窗一多就能顶过
  Windows 的 5 秒未响应阈值（进程一直在跑、只是没泵消息）。库层为此给了
  `ChildWindows.SetRenderBudgetMs(ms)`（默认 50ms，0=不限）+ 轮转（推迟不饿死）
  + `SetSlowRenderWarnMs(ms)`（默认 200ms）/`SetSlowRenderSink(...)`，超阈值报
  `UIWATCHDOG stall stage=child-window blocked=<ms>ms title=<标题>`（与
  UiWatchdog 同一套 grep）。实测 20 个重子窗（每个绘制 30ms+）：单帧从 1482ms
  降到 62ms、17 个推迟，25 帧内每个子窗至少被画到 2 次。
  边界：① 预算只管"空闲泵"这条路径——子窗收到**自己的窗口事件**时会就地渲染
  一次（交互路径：用户点的那扇窗必须立刻出画），所以写断言要用**每帧增量**，
  绝对计数会被那次就地渲染串掉；② 预算切不开**单个**子窗自己的渲染，单个子窗
  就慢到秒级时靠耗时告警点名，不靠预算。
- **门禁"跳过"不是"通过"：条件不满足时门禁必须响**。帧预算门在表面尺寸与
  标定面不一致时输出 `FRAME_BUDGET_SKIPPED` 并**跳过全部毫秒断言**——本机
  1920x1230 vs 标定 1942x1286，于是 tree_ms 超预算 2 倍、像素量超 11 倍这些
  超标**从未被拦下**，门看起来一直是绿的。这类"条件不满足就跳过"的门禁要改成：
  跳过时打警告并把差异写进结论（或按比例缩放预算），否则它只在标定机上生效。
  坑出处：帧预算脚本的 surface 尺寸门。
- **判"窗口卡死"要看人眼所见：`PrintWindow` 对交换链窗口返回的是陈旧表面**。
  `PrintWindow`（含 `PW_RENDERFULLCONTENT`）向 D3D/交换链窗口要图时，拿到的是
  DWM 缓存的旧表面：实测一个活着的游戏程序，五个时点抓帧文件**字节级完全
  相同**，看上去"永远停在启动闪屏"；同期的桌面实拍（`Graphics.CopyFromScreen`
  抓窗口所在矩形，先 `SetForegroundWindow` 置前）显示程序早已进主菜单。
  **拿 PrintWindow 判死活会把活程序误判成卡死**——这类误判比查错方向更贵，
  它会让整条排查跑偏。判"活程序是否还在更新"的正确姿势：桌面实拍（人眼所见）
  ＋ 程序自身输出（启动阶段进度行等）交叉验证；`PrintWindow` 只适合抓静态内容。
  判"Windows 是否真的判它未响应"另有硬证据：逐拍采样
  `Get-Process | Select-Object Responding`（Windows 的判据是 UI 线程 5 秒不泵
  消息），不要靠"画面看着不动"下结论——画面不动和进程未响应是两件事。
- **性能基线文件是"某时刻某产物"的快照，引用前必须用当前产物重测**。工程目录
  里常见的帧耗时/构建耗时基线文件都是上一次跑某一版产物留下的：实测一个多窗口
  应用的帧耗时基线（写于旧产物、旧探针格式）显示 20 个子窗 509ms/帧，而同一
  探针在当前产物上重测只有 87ms/帧——6 倍差；直接引用旧基线会得出"开满子窗
  必然卡死"的错误结论。引用前先确认三件事：产物版本、探针口径（平均/最差/
  强制重绘）、机器规格；口径不同的两份数据不可比。基线过期比没有基线更危险，
  因为它带着数字，看起来可信。
- **"能跑 + 有存档 + 有设置 + 单文件发布"是基础设施门槛，不是游戏品质门槛**
  （坑出处：arena 等十个阶段一骨架项目——给占位骨架补上存档与设置，这四条
  立刻全绿，但它连玩家输入都没有、美术全是几何图形 + "TODO 位图"）。
  - 汇报游戏项目时**必须同时报美术资产数**（位图/音频），否则会把"可运行
    的原型"说成"游戏"；`scripts/audit_game_projects.ps1` 的 `art` 列与
    `PROTO` 标记就是干这个的：基础设施四口径全绿但 `art=0` → 原型。
  - 真游戏还要另过三关：① 真实位图资产（非几何图形）② 可玩的核心闭环
    （玩家有输入、有目标、有失败/成长）③ 音画反馈；存档里要有真正值得
    保存的东西（进度/解锁，而不是 `best=0`）。
  - 推论：**别把力气花在给骨架加功能上**。存档/设置这类地基该补（真游戏
    也要），但补完只是地基，别当成"达标"报喜——一个真样板胜过十个加了
    存档的骨架。
- **纯 Canvas 直绘的游戏接"存档 + 设置"有定式，别各写一遍**
  （arena 等十个阶段一骨架项目，坑出处）：
  - **存档**用包里的 `Game.Foundation.GameSaveStore`（原子写 + .bak 备份 +
    版本号），项目只写"这个游戏存哪几个字段"；存档目录用
    `%LOCALAPPDATA%/<游戏名>`，并让环境变量可覆盖（测试脚本靠它落在临时目录，
    不污染玩家机器）。
  - **设置**分两层：`GameSettings`（声明）+ `SettingsModel`（档位计算/校验/
    落盘）在包里；视图用包里的通用 `Game.Foundation.Gui.SettingsOverlay`
    （标准库控件搭的卡片：一行一个档位按钮组 + 关闭按钮），有自己美术风格的
    项目自绘视图、接口不变。**设置项必须真的影响玩法**，否则是摆设。
  - **接线三件套**：`form.Add(overlay.Root())` 挂载 → 每帧 `overlay.Tick()`
    （轮询按钮点击）→ 渲染顺序把控件树叠在直绘之上：
    `form.MeasureTree(app)` → `form.Arrange(...)` → `form.RenderTree(app)`，
    放在自己的 `Render()` 之后、`RenderChrome()` 之前。
  - **键盘开关必须判事件真的发生过**：条件里要有 `got == 1`（事件确实来
    了），否则会拿上一帧残留的键码反复开关——表现为"按一次闪一下"或根本
    开不了。
  - **落盘必须跑两遍验证**：第一遍写、第二遍是**新进程**读回（局数 1 → 2），
    只跑一遍看不出"写了但读不回"；断言要同时查日志行与存档文件存在。
  - 包 API 不要凭印象写：`Environment.GetCurrentDirectory()` 不存在（用
    `Directory.GetCurrentDirectory()`），`GameSaveStore.Save` 收 `JsonValue`
    （`JsonValue.NewObject()` + `PutInt`）——先读 .zan 确认真实签名。
- **牌面/图标类美术别逐张生成位图：底板位图 + 几何花纹**
  （坑出处：麻将的 34 种牌面——万筒条 ×1-9 加东南西北中發白）：
  - 底板（牌的质感与金边）用一张 AI 生成的位图，**花纹用画布原语画**：
    同心圆点阵＝筒、竹节＝条、汉字数字＋红「萬」＝万、单字＝字牌。几何花纹
    比 AI 生成的字形准得多（AI 画中文常糊），改起来也快，还省掉几十次生成。
  - AI 出的图**未必有 alpha 通道**（最新图像模型常不支持透明背景）→ 本地抠：
    背景是纯色时，从图边洪泛抠掉背景 + 裁边 + 缩放（PIL 十几行即可）。
  - 素材体量：位图先缩到**实际显示尺寸的 2 倍以内**再入库，别把原图直接
    带进仓库。
- **Zan 的保留字**：`base` / `out` / `where` 是关键字，**标识符不能以它们
  开头**——`baseKind` 会被切成 `base` + `Kind`，报的还是
  "expected ')', got 'base'" 这种看不懂的错。命名避开这三个词，撞了先改
  名字而不是换写法。
- **GuiHost 的无头冒烟：帧计数放 `Update()`，不要放 `Render()`**
  （坑出处：麻将的无头冒烟"跑满 90 帧就退出"）：宿主在**窗口不可见**时跳过
  整段渲染（`Render` 根本不调），帧计数停在 0 → 程序永远等不到退出，表现为
  "无头冒烟超时"。`Update` 在隐藏分支里照常调，计时/超时/收尾都放 `Update`；
  `Render` 只管画与抓帧。
- **共享工作树里公共包被别人改到半坏时，别等也别抢改**：用上面「冻结床」
  那套隔离法（把公共包解析根 `--package-project` 指向一棵**拷贝**出来的
  干净树）；**不要拿 `git worktree` 副本当隔离树**——副本与主仓天然漂移，
  公共包一改就落后（"公共包不要用 worktree 副本"那条同样适用：隔离靠拷贝，
  不靠 worktree）。坑出处：并行会话把某个 Gui 包文件改到引用了尚未声明的
  字段，整个树编译不过。
- **音效别每个项目各写一遍加载与降级**：公共包 `Game.Foundation.SfxBank`
  （游戏基础包）已经把三件事收好了——按名加载（磁盘优先 + 内嵌兜底）、
  按事件播放并限频、**没有音频设备时整库静默失效**（无头 CI/无声卡不崩不卡）。
  项目侧只留"这个游戏有哪些音效名、什么事件播哪个"，音效文件用 WAV、
  文件名与事件名同名。限频参数按事件给（连打/多敌人同帧触发会爆音）。
  坑出处：9 个游戏项目各写一遍加载逻辑，其中一个还漏了"没声卡"分支。
- **资产目录里有图 ≠ 画出来了**：体检要把"位图数"和"资产是否进渲染路径"
  分成两列（源码里出现图片路径字面量才算接上）。一条链必须走完：
  生成 → 抠 alpha → 缩放入库 → **进渲染路径** → 截图人眼验收。断在"入库"
  这一步的项目，运行时画面还是纯色块，但体检看着像有美术。
- **抠 alpha 用边缘连通洪泛，不是全图阈值**：主体内部也有暗部，全图按亮度
  抠会把角色的暗面一起抠穿；从图边洪泛只吃掉背景连通区。
- **跨树编译前先确认符号在目标树里存在**：公共包的改动没提交时，工作区
  里能读到的 API 在隔离树里可能还不存在（表现为"文档里有、编译说
  没有"）。裁源矩形取景用包里的便捷函数 `CDraw.BlitImageSrc`——**目标
  矩形走视口映射、源矩形按源图像素裁**，两组坐标单位不同，最容易搞错；
  底层是 `Canvas.BlitImage(key, dx, dy, dw, dh, sx, sy, sw, sh)`（源矩形
  在最后，`sw=0,sh=0` 是整幅）。别再各项目自己写一份 BlitSrc。
- **宿主标题栏压在内容区之上**：GUI 壳的 chrome 画在内容区顶部，HUD 与
  按钮要避开顶部一条（按窗口高度比例，实测约 48px），否则点不到、
  截图上像"文字被切了"。
- **原始生成图不入库**：1024² 的原图体积是入库素材的十倍以上，放进
  `build/` 这类已忽略目录并把生成脚本与提示词一并留下；入库的按**显示尺寸
  2 倍**缩放。仓库外项目目录常被安全策略禁止删除，临时产物只能落在项目
  内部已忽略的目录。
- **真游戏的三道关卡**（位图资产 / 可玩闭环 / 音画反馈）与其判据写在
  仓库自带的《真游戏标准》文档里；判断"这是游戏还是原型"按那把尺子，
  别按"能跑 + 有存档 + 有设置"判——那三条只说明程序是活的。
- **画布 blit 没有旋转、也没有水平翻转**：`Canvas.BlitImage` 只有源矩形
  （sx,sy,sw,sh），`Gui.SpriteBatch` 每精灵也只有位置/尺寸/源矩形/tint。
  所以"把角色转个方向"运行时做不到——朝向只能**离线预烘焙**成方向帧
  （俯视 16/24 角度精灵表，横版左右镜像帧），运行时按纯函数映射取帧。
  **只算朝向状态、渲染层根本不读它，等于没做**（横版角色"永远朝右"就是
  这么来的）；断言要钉住"逻辑朝向 → 取帧索引"的映射。
  旋转帧用「预乘 alpha → 旋转 → 反预乘」消黑边，旋转轴要与实体位置重合。
- **AI 出的大面积底板容易变成高频噪点**（看着脏、廉价）：地砖、地面、
  毡面、台面这类**大面积底板用程序化生成**（低频噪声 + 大块结构 + 缝隙 +
  局部斑驳 + 暗角），AI 只负责主体与小物件。纯色块底板同样不合格——
  底板要能看出材质与结构。
- **游戏 UI 要有自己的皮肤包**：引擎的 `skins/<name>/skin.css`（`:root`
  令牌 + 每控件规则 + 美术资源）+ `app.UseSkin(name)` 就是给这件事准备的。
  三个坑：① `UseSkin` 要在默认皮肤（`UseSkin("dark")`）**之后**调用，否则
  被盖回去；② 真正生效的圆角令牌是 `--border-radius-*`（Theme 字段名
  `borderRadiusSmall`），`--radius-*` 只在皮肤自己的规则里有效，两组都写；
  ③ **基线 `base.css` 不要手工拷**：编译器对引用 Gui 的程序自动把
  `Gui/skins` 整目录烤进 exe（内嵌兜底），运行时加载是**磁盘优先、
  内嵌兜底**。磁盘上再放一份 base.css 反而会盖住 exe 内嵌的新基线，
  "内嵌兜底到底生效没有"就永远测不出来。必须落磁盘的是**游戏自己的
  皮肤包**（`skins/<名>/skin.css`），它被内嵌过滤器排除在外。
- **HUD 控件宿主要负责排版**：`HudLayer.Render` 只 `RenderTree` 不
  `Measure/Arrange` 时，"根填满窗口 + 内部居中"的浮层整层是空的
  （Esc 打开等于没打开）。这一层已在公共包 `HudLayer` 修好（渲染前按
  客户区尺寸排版），项目侧**别再各抄一遍** Measure/Arrange；世界坐标的
  元素不要挂 HudLayer（挂了会按客户区重排）。
- **正面视角的素材做不出"侧身"帧**：角色原图是正面时，水平镜像只换边、
  换不出朝向。要让玩家一眼看出转向，得给主体加**不对称标记**（手里的
  提灯/独眼/背带）+ **朝向侧光池**（脚下光斑偏在朝的那边）。要真正的侧身
  帧只能用 AI 重出原图——重出要与既有美术风格对齐，否则风格会裂开。
- **UiDriver 的 `ZAN_UI_SCRIPT` 必须是绝对路径**：相对路径按进程工作目录
  解析，脚本路径找不到时驱动**静默不启动**——没有报错，画面停在主菜单，
  看起来像"游戏没进对局"。

### 通用绘制原语进包，游戏实现层只调包（绘制机制沉淀）

- **判据是"换个游戏还成立吗"**：成立就是公共机制。九宫格切图、裁源贴图、
  描边/投影文字这类东西一旦有两个项目各写一份，签名就会漂。实测多个游戏
  项目里 8 个各写了一份九宫格，签名漂成 8 种（有的收内存键、有的收路径；
  切角语义、目标过窄时怎么退化各不相同），描边文字 6 家各写一份（1 设备
  像素 / 1 逻辑像素 / 随字号加粗三套并存），裁源贴图 3 份样板——全部加起来
  约 270 处调用点。同一件事修一次 bug 要改 8~11 处。归公共包的 `Game.Kit`
  命名空间，项目只留**自己特有**的件（切角常量、牌面字形、终端等宽字）。
- **收进包时逐条对齐差异，不要抹平**：多份实现的差异点各有道理——描边偏移
  （1 设备像素 vs 1 逻辑像素 vs 随字号加粗）、投影偏移（有的 (1,2) 往右下）、
  源切角与目标切角的倍率（底板按 2 倍入库的，目标切角要折半）、切角取源
  路径还是内存键。包 API 用**重载**表达（7 参与"带 targetScale"的 8 参并存），
  而不是给每个项目造一个变体；实在表达不了的（参数序不同、inset 语义）才在
  项目侧适配。抹平成一种会让所有项目的观感一起变。
- **同族 API 的实参改写要括号感知，别用正则按逗号切**：实参里有嵌套括号
  （`Convert.ToString(x)`）、有换行、有字符串字面量。PowerShell 里 `[^,]+`
  **不跨行**，按逗号切的正则会把多行实参切错位置——症状是"改完参数顺序不对"
  而不是"匹配不上"。用括号配对扫描拿实参边界，只切掉要改的那一段文本、其余
  原样保留（把全部实参 join 回去会把多行调用压成一行，diff 全是噪音）。
- **文字量宽要换算回逻辑像素**：`Canvas.MeasureText` 给的是**设备**像素，
  而 HUD 布局写在**逻辑**坐标里——直接拿设备宽减半去居中，视口放大后文字
  会偏出中心、底板宽度会算错。公共包的 `CText.WidthPx` 做这个换算
  （`dev * 65536 / vpS`），居中/右对齐都走它。这类 bug 在 1:1 视口下看不出来，
  窗口一放大就现形，迁移时顺手清掉。
- **`"mem:"` 键不能当文件名读**：内嵌兜底解析出来的键形如 `mem:assets/x.png`，
  画布直接认，但 `File.ReadAllBytes("mem:...")` 抛 FileNotFoundException。
  公共包 `CDraw.BlitSource` 要先判 `IsMemKey` 再读盘；每个项目自己写一个
  `IsMemKey` 挡着，就是同一个坑每家补一次。
- 坑出处：一轮"把通用绘制原语收进包"的改造，11 个游戏项目逐个改、逐个跑
  四段测试（玩法断言 / 存档两遍 / 无头冒烟 / 皮肤自检），每改一个项目单独
  提交，公共包侧配两条 conformance（九宫格纯函数 + 像素钉；文字描边四向
  必宽 + 换锚点墨迹平移等距）。

## 四、经验沉淀纪律（skill 的准入标准）

- 沉淀的是**通用可落地的规则**：动作 + 理由 + 适用边界。三样缺一的
  不进 skill：没有"动作"的是感想，没有"理由"的是迷信，没有"边界"的是口号。
- **不带流水账**：日期编号、"本轮/本机/这个 demo"、一次性排查过程、
  具体文件路径——一律不进 skill 正文。教训先问"换个项目还成立吗"，
  不成立就扔。
- 被推翻的旧规则在同一提交里删除，skill 里不留"可能也对"的僵尸条目。
- 单个 skill 控制在约 300 行内：逐坑细节、长流程挪 `references/` 子文件，
  正文只留决策规则；description ≤2 行、只写真实触发场景。
- 机器专属内容（本机路径/尺寸/环境限制）写进项目文档或注释，永不进 skill。

## 五、避免制造垃圾（开发过程中的克制）

- **不加没被要求的抽象**：接口/配置项/泛型参数只在出现第二个消费者时引入。
- **不写没人读的文档**：注释、README、说明段落服务于"下一个改代码的人"，
  营销词、空话、复述代码的段落删掉。
- **不留一次性文件**：探针脚本用完删，日志/截图不进源码树，临时方案
  不"先这样"——临时方案没有转化计划就会变成永久垃圾。
- **重复即信号**：同一段逻辑出现第二遍就必须收拢（基类/工具函数/常量），
  第三遍就是债。
- **依赖最小化**：新外部依赖要有不可替代的理由；能 stdlib 解决的
  不引入第三方。

## 六、技术债清理（平台升级后回头维护代码）

平台（编译器/runtime/stdlib）每前进一格，昨天的高效写法今天就可能是
旧写法。**代码不会自己跟上平台——不维护就是技术债。**

- **债从哪来**：编译器能力升级后（新内建、新语法糖、缺陷修复、性能契约
  变化），旧代码里为绕过缺陷而生的写法立刻变成债——手写循环对应新内建、
  平行数组对应新字典、降级封装对应已修语义、死分支对应已失效的条件。
  功能没坏，所以没人改它；它只会在下一次变更时让正确修改变贵。
- **发现即挂账，修毕即结单**：看到"绕过写法/旧形态"的代码，立刻记入任务
  台账（编号+一句话+根因+探针位置）；修完把条目移出未完成清单，压缩为
  一行摘要——挂账与结单的完整纪律见 zan-workflow。
- **顺手修的范围**：改动所在文件内的旧写法顺手更新（同一提交）；
  跨文件的成片旧写法开专项（列表→逐条修→跑受影响测试档→闭账），
  不允许"这次先不动"无挂账通过。
- **清债顺序按毒性**：① 会误导后续开发的（死分支、假封装、误导性命名）
  ② 阻碍修 bug 的（绕过写法与根因修复冲突）③ 纯风格旧化的。
- **禁止新债**：提交里引入绕过写法必须有台账条目和转化计划；
  "临时方案"没有转化计划就是永久债。
- **平台升级是清债触发器**：编译器发新版/新内建落地时，扫一遍
  对应旧写法的重灾区（grep 已知旧模式），成片的立专项，零散的顺手改。

## 七、评审自查（每次交付前过一遍）

1. 工作流闭环完整吗？（编译→运行→验证→测试档→提交，见 `zan-workflow`）
2. 有没有绕过编译器缺陷的写法？有没有该进基类/常量的重复？
3. 截图/断言锚定 PID 与窗口了吗？判断基于探针还是基于"看了一眼"？
4. 本次新踩的坑，值得沉淀吗？按第四节标准过一遍，不合格不写。
5. 有没有制造垃圾？（无用抽象、没人读的文档、一次性文件、重复逻辑）
6. 本次引入或发现的旧写法，挂账了吗？（见第六节）
7. 删了该删的吗？（临时探针、废弃产物、被推翻的规则）

- **并行会话共享工作树时，编译验证用"冻结床"隔离在途噪声**（定式）：
  别的会话正把某个包/stdlib 文件改到语法破损的中间态时，直接用工作树工具链编译
  会看到与己无关的解析错误假象。隔离法：`git archive HEAD packages stdlib |
  tar -x` 解到独立临时目录，再拷入当前 zanc 与其运行时 obj 兄弟文件——包/stdlib
  发现跟 zanc **二进制位置**走，床内 zanc 只见 HEAD 冻结包，与工作树在途编辑完全
  解耦；tar 报 linux 驱动符号链接失败在 Windows 无碍。**zanc 必须连带
  捆绑件**：`ld.exe`、`ld.lld.exe`、`mingw/`（dllcrt2.o 等）拷到 zanc 同目录
  ——zanc 只找自己旁边的 ld.exe，缺了就静默回退 PATH 上的 ld（GNU-ABI 链接满屏
  undefined reference，档案里符号明明都在）。适合"要在别人施工时量出
  自己改动的真实基线"的场景（撞名定性、A/B 对照），日常验证仍走工作树。
