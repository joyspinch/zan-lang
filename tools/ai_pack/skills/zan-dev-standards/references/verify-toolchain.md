# 验证——工具链/链接/口径/阈值

> 从 verification.md 拆出：行为口径三端同批、阈值基线漂移、链接粒度、交叉工具链隐藏依赖。

### 改编译器的"行为口径"时，宿主、自举侧与 golden 是同一批交付（口径变更纪律）

- **改了输出的措辞或形状，三样必须同批改**：宿主实现（编译器本体）、自举侧实现
  （自举编译器）、conformance 的 golden（期望输出文件）。只改一样，对拍门必然红，
  而且红的方式会误导人。
- **stdlib/packages 是编译期物料，改完不用重建编译器**：包源码在每次编译按
  内容哈希缓存取用。改完包源码直接重编目标用例即生效——别把一个几秒的验证
  拖成几十分钟的全量重建；若"改了没生效"，先查缓存哈希变没变。反过来自举侧
  （自举编译器源码）只影响自举编译器，两边改的是不同的东西。
- **对拍门红了先分类，再动手**：把宿主输出、自举输出、golden 三者两两比。
  - 宿主 == 自举、但都 != golden → **golden 过期**，按宿主输出更新 golden；
  - 宿主 != 自举 → **真分叉**，两边必须选一个口径统一（自举要照抄宿主）；
  - 三者都不同 → 先看宿主自己是不是也不对（"分叉"有时是宿主错了）。

  坑出处：改 bool 渲染口径（`"1"/"0"` → `"true"/"false"`）后 7 个对拍用例全红，
  逐个比对后 6 个是 golden 过期、1 个是宿主自己漏了一条路径——不分类就分头改，
  必然改错一半。
- **"自举要照抄宿主"的前提是宿主那一侧是对的——分叉时先判谁错，别机械照抄**：
  两侧行为不同，有三种可能：自举缺了守卫（照抄）、自举多了守卫（自举删）、
  **宿主自己算错了**（另立条目修宿主）。第三种最危险：照抄等于把一个缺陷
  复制成两份，还顺手把"哪边对"这件事也定反了。判据：**看语言语义**——同一个
  表达式按语言规则该是什么值，以那个为准；两个后端都不对时，以语言的为准，
  把它写成台账条目在错的那一侧修。
  坑出处：宿主把 `bool` 当**有符号**整数用（i1 符号扩展），于是
  `Convert.ToInt32(true)` = -1、`Math.Sqrt(true)` = NaN；而语言语义是 1
  （`bool` 转整数取 0/1，且 `bool` 没有到 double 的隐式转换）。自举侧原本
  给的是正确的 1，照抄反而会把对的一侧改错。
- **两端的守卫要落在各自的"分派入口"，且判据不同就别共用一张白名单**：
  补一条"这个类型不许进这条路径"的守卫时，先找这条路径上所有分支的**汇合
  点**，守卫下在那里一次覆盖全部；散在每个分支里各判一遍，漏一个分支就是
  一条漏网路径。而**判据**要看两端各自在判什么——一边判"降级后的值类型"、
  另一边判"静态类型"时，共用一张白名单会同时错两次（放行了不该放行的、
  拒掉了不该拒的）。
  坑出处：给自举后端补 `Math.*` / `Convert.To*` 的类型守卫时，宿主这两个
  入口的判据根本不同（前者判降级后的值类型、后者判静态类型白名单），
  照抄成一张表会让 `object` 在 `Convert.*` 被拒、在 `Math.*` 被放行。
- **判定"这个值是不是 bool"要看语义类型，不能看 LLVM 值的宽度**：泛型实例化的
  方法返回值（如宽结构体集合的 `Contains`）会被提升成 i64，按宽度判就掉进 itoa，
  渲染成 `"1"`——同一个 bool 在不同上下文里长得不一样（`"x" + b` → `"x1"`，
  而 `b.ToString()` → `"true"`）。C# 的口径是 true/false：宿主按语义类型判，
  自举侧按值类型判，两边必须同口径。
  坑出处：编译器的字符串转码入口只看 `LLVMGetIntTypeWidth(vt) == 1`，
  泛型集合方法返回的 bool 因此漏判，宿主说 `"1"` 而自举说 `"true"`。
  **修法**：宿主侧抽一个共用助手，按 `infer_expr_type` 的**语义类型**判
  （i1 直接用，宽化过的 i64 先 `icmp ne 0`），**四条取串路径全部改用它**——
  拼接、插值、`Convert.ToString`、标量 `ToString()`。踩坑点：修一条漏三条
  （"汇合点"只有一个）——凡是"把值转成字符串"的地方，判据统一走这一个助手，
  别在每个调用点各判一遍。
- **重写 golden 里的 bool：按**逐位**对齐，不是按词边界**。golden 一行里常常
  **连着好几个 bool**（`"plus=" + IsMatch() + IsMatch()` 渲染成 `"10"`，修好后
  是 `"truefalse"`），还可能**bool 与真数字混在一行**（`matrix.rt=m13b00` →
  `m13bfalse0`：第一个是 bool，第二个是数字）。按 `\b0\b|\b1\b` 这种词边界正则
  判，会把 `"10"` 当成一个数字而漏判。正确的判据是**联合 token 走查**：老侧拆
  成「字面量 / 0-1 数字」，新侧拆成「字面量 / true-false 词 / 数字」，两边
  **一对一**对齐——一个 bool 词恰好吃掉老侧一个数字（`true`←`1`、`false`←`0`），
  剩下的数字必须原样不动。
  坑出处：曾因词边界漏判，把 123 份并非 bool 的过期 golden 一起改了；后来又用
  同一判据把 11 份 golden 误判成"非 bool 改写"而全部打回，最后靠逐位走查才
  分出真改写 9 份。
- **"在受影响名单里"不等于"该改"——重写 golden 前先证明它真的受影响**：
  判据是**逐行**过"是不是 bool 渲染"的走查（上一条），不是"这个文件在
  受影响名单里"。实测有 `chart_axis_breaks` / `directory_paths` 被误列进去：
  里面的 `prct=1` 是百分比、`dirs=1` 是计数，**一个 bool 都没有**，重写只动了
  行尾。
- **重写 golden：按仓库原字节重建，别拿工作树直接提交**：仓库里有 golden 带着
  CR CR LF 行尾（历史产物，git 的 CRLF→LF 过滤器处理不了这种"双 CR"）。把它
  写成普通 LF 就等于把**行尾归一化**夹带进提交。正确做法：新 blob =
  **编译器实际输出的内容** + **仓库原行尾**，逐行拼接——只动该动的那些行，
  其余行保持原始字节。判据：重建后再跑一次"逐行是不是 bool 渲染"的走查，
  两者都过才提交。


- **表达式"没有类型"时，错误会落在离病灶很远的地方——先给表达式补类型，别在
  兜底分支打补丁**：类型推断里凡是**没给某个表达式形态定类型**的，推断会退到
  **兜底分支**——二元运算退到左操作数、赋值退到目标槽。症状于是报在别处：
  条件表达式（`c ? a : b`）没有类型 → `int + (c ? "#s" : "#g")` 被定成 `int`
  → 报 "cannot convert 'int' to 'string' in initializer"，而真正的病灶是括号
  里的那一段。修法：给那个**表达式形态**补一条定型分支，别去改兜底分支——
  兜底分支是症状，改它会掩盖"这一类表达式一直没有类型"的事实，下一个没被
  覆盖的形态（`??`、短路 `&&`/`||` 的值、模式匹配的结果）会原地复发。
  找病灶的判据：**报错说的那个类型，是哪一步"猜"出来的**——左操作数、目标槽、
  第一个分支，是三个常见的猜测来源；顺着它们往回找，落在"根本没定型"的那段。
- **粗粒度类型模型里，"判不出就放过"好过"猜一个"**：自举侧的类型模型比宿主粗
  （没有 type kind，可空与数组秩的信息也不全），合并两支类型时**可能判不出共同
  类型**。这时返回**未知类型**（不报诊断）好过猜一个、或照抄宿主的报错措辞：
  猜一个 → 误拒宿主接受的程序，把差分门与自举固定点门一起弄红；照抄措辞 →
  自举说不出宿主那两个操作数的准确类型名，报错要么对不上、要么误导人。
  判据：**自举侧宁可漏报，不可误拒**——误拒会打断"自举编译自举源码"这条自指链，
  漏报只是少一条诊断。已知差异要**显式登记**（台账 + 差分门的 known-gaps
  机制），别让它停在"两边都以为对方是对的"的状态。
  坑出处：自举 checker 原先没给条件表达式定型，固定点门在 gen1→g2.ll 就断，
  自举编译器拒绝编译自举源码自己（宿主接受同一段代码）。

### 阈值类测试（体积/行数/耗时预算）：基线会漂，量的是不是你要守的那个量（阈值纪律）

阈值测试最常见的两种误判，都不是"代码坏了"：

- **基线过期**：预算是一条按"某天的实测值 × 余量"定下的硬线，而被量的东西
  会随开发长大。2026-10-22 实测：发布体积预算的 `.text` 预算是 200,000、
  实测 199,752——只剩 248 B 余量。成因不是固定大表回来了，是这一个月运行时
  源码 +140 提交 / 净增 ~8.8K 行，运行时载荷整体长大（linux 侧 `.text`
  189,074 同步长高——两侧同步，可据此排除平台特有）。**阈值红先查基线是哪天
  定的、中间长了什么**，别急着改代码；确定是正常成长，就按"实测 × 余量"重新
  定基线，并把基线数写回文档（预算脚本的头注通常会写这条要求）。
- **量的不是你要守的那个量**：Windows publish 会把内置默认图标塞进 PE 的
  `.rsrc`（实测 106,360 B，占产物三成）——图标是**产品资产**，不是运行时载荷；
  这条预算的用途是抓固定大表回归 / 抓丢 `--gc-sections`，就该用 `--no-icon`
  量。同理，失败文案别把**当前实测值**印成 `"(baseline: …)"`——那样写读起来
  像"和基线一样却还超预算"，实则基线是另一个数；改成 `"(measured: …)"`。
- 两条推论：① 阈值测试的**判据文案必须与判据同源**（写死的计数、印出来的
  数、实际比的值要是同一个量），否则报错会把人带偏——一个 MVC 安装脚本曾写死
  源文件数 121（包已长到 163），报错却印 `163 -> 163`，看着像集合差异，其实是
  过期常量；改成按相对路径逐个核对，才既准又不会随包增长而过期。
  ② 阈值放宽后要**记下为什么放宽**（写进任务台账 / 文档），否则下一个会话只
  会看到"预算涨了"，查不出是正常成长还是回归。

### 链接器死代码消除：裸 .o 进链接行 = 整体载入，GC 对它无效（链接粒度纪律）

- **实测（2026-10-23）**：一份 hello world 发布产物 `.text` 199,752，其中运行时
  占 84%（167,488）。查"为什么瘦不下来"时走了弯路：先按"函数都可达"解释，又试
  "加 `-ffunction-sections` + `--gc-sections`"——实测 `.text` 几乎不变
  （199,736），于是**错误地**把"加编译开关这条路"记成了死路。
- **真根因**：运行时对象是**裸 `.o`** 直接进链接行，而**裸 `.o` 是整体载入，
  section GC 对它无效**（链接器没有"只取需要的成员"这一步——那是**归档**的
  行为）。同条件对照（同一 gcc、同一 `--gc-sections`）：
  | 链接方式 | 留下的硬件加速符号 | `.text` |
  |---|---|---|
  | 裸 `.o` 直接进链接行 | 63（全留） | 156,640 |
  | 打进静态库 `libcrypto.a` | **0** | **103,232** |
  | 裸 `.o` + `--gc-sections` + `-ffunction-sections` | 63（仍全留） | — |
- **处方因此换了**：不是加编译开关，而是**把可选子系统从"文本包含"改成
  "独立归档成员"**。具体形态：运行时里有一行 `#include "rt_hw_accel.c"`
  （4558 行硬件加速）——**文本包含** ⇒ 必然与宿主 TU 同体 ⇒ 必然整体进 .o ⇒
  每个程序都背整块 SHA/AES/AVX2。要拆成按特性的归档成员（sha / aes /
  sm3-sm4 / rsa / pixel / crc），链接行只给归档。端到端收益实测：hello world
  `.text` 200,728 → 147,320、file 244,476 → 180,836，
  **这块独占 53,408 B（26.6%）**。
- **交叉侧同因同解**（2026-10-23 复测）：交叉产物一样剪不掉——linux-x64
  交叉 hello world 里硬件加速符号 63 + AES 32 个全在，占 `.text` 约
  37,941 B（19.8%）；而交叉链接**本来就带 `--gc-sections`**（`ld.lld -static
  ... -s --gc-sections`）——**带了照样剪不掉**，正好反证根因是"裸 .o 整体
  载入"而不是"缺 GC 开关"。宿主与交叉因此是同一个修法。
- **推论 ①（2026-10-23 更正）：文本包含 = 把一整个子系统焊进宿主 TU**。
  `#include "x.c"` 让链接粒度失效——这个 TU 的代码与宿主同生共死。查体积时
  先 grep 运行时里的 `#include ".*\.c"`，那几行就是最大的候选。
  **旧版本这里写的是"裸 `.o` 整体载入、section GC 对它无效"，这句是错的**：
  section GC 对**裸 `.o` 一样有效**（见 ⑨ 的实测），真正剪不掉的是
  **可达**的代码（分发表指着它、文本包含进来且被保留符号引用）。
- **推论 ②：归档成员粒度 = 实际死代码消除的粒度**。把某子系统单独编成归档
  后，只要程序用到其中**任意一个**符号，整个归档成员（一个 .o）仍会被拉进来
  ⇒ 必须**按特性再切到成员粒度**，否则只是把体积挪个地方。
- **推论 ③（2026-10-23 更正）：先问"链接器凭什么能剪掉它"**。`--gc-sections`
  剪的是 **section**，要剪得动得同时满足两条：该 TU **按函数分节**（编译时加
  `-ffunction-sections`），且被剪的函数**不可达**。上一轮把"`-ffunction-sections`
  无效"记成死路，是因为那批实验作用在 crypto 那个 TU 上——那里的 crypto
  函数**都可达**（宿主 TU 内的分发表指着它们），所以换成归档成员粒度才见效。
  **"加了开关没变化"不等于"这条路没收益"**，可能只是那个 TU 不满足前提。
- **推论 ④（2026-10-23 更正）：`-fdata-sections` 单独用是地雷，配着
  `-ffunction-sections` 用反而是帮手**。单独用会把 `.bss` 搬进 `.data` 而
  没有任何 GC 收益（发布产物 245 KB → 1.8 MB，`.text` 纹丝不动）；和
  `-ffunction-sections` 一起上时数据节也跟着可 GC。实测（见 ⑨）：只加
  `-ffunction-sections` 与再加上 `-fdata-sections` 的 `.text` 完全相同
  （48,495），`.bss` 反而是加了 `-fdata-sections` 的更小。测体积收益仍然
  要一次只动一个变量。
- **推论 ⑤：数符号前先确认产物没被剥符号**（2026-10-22 踩到，差点报错结论）。
  发布模式会剥掉符号表，`nm --defined-only` 对剥过的二进制**一个符号都读不出
  来**——于是"按需拉取没生效"和"根本没链接进去"长得一模一样。实测：在剥符号
  产物上数硬件加速符号恒为 0，换成未发布产物才看见真相（hello 0 个 / 用到
  加密的程序 95 个）。**凡是靠数符号下结论的测量，一律用未发布产物**；体积
  测量相反——要的是发布形态（`.text`/文件大小），用发布产物。
- **推论 ⑥：归档成员与它替代的裸对象必须同代重出**。旧裸对象（内含该子系统）
  + 新归档 ⇒ 同一符号被定义两次，链接报重复符号；新裸对象 + 旧归档 ⇒ 缺符号。
  所以"拆成归档"**不是一个文件的改动，是一次成对的重新产出**（对象 + 归档 +
  配方 + 暂存 + 发布打包），漏一头就是坏链。
- **推论 ⑦：归档要排在被它替代的对象之后进链接行**。归档成员只为"**仍未定义**
  的符号"解引用；被替代对象若已定义同名符号，成员就不会被拉进来（无重复定
  义），反过来排则必然重复定义。链接行顺序是这类改动的一部分，不是细节。
- **推论 ⑧：把子系统从"文本包含"改成"归档成员"，要普查所有**手写链接集**
  ——它们以前是**顺着文本包含**白捡符号的，摘走就断链（2026-10-22 踩到）。
  宿主侧编译器注入归档没问题，但**自举固定点门**的链接集是手搓的一组裸对象
  （RT_OBJS）：它编的定时器运行时文本包含着 crypto 运行时，于是白捡了整块
  `zan_hw_*`；crypto 一摘走，链接就报 7 个 LNK2019（zan_hw_sm3 /
  zan_hw_base64_encode|decode / zan_hw_sha1|256|512 / zan_cpu_feature）——
  自举编译器二进制本身会把标准库的 NativeMemory crypto 声明（Extern →
  `zan_hw_*`）拉进来，所以 gen2 的 IR 引用这些符号。
  判据：**"这个符号从哪来"要逐个问**，不能只看宿主链接行——凡是**不经过
  编译器本体的链接**（harness 脚本、交叉配方、IDE 打包、发布暂存）都自带
  一份链接集，改链接行成分时要一起改。
  修法：同一个 TU 用**那个链接集自己的编译器**再编一份（自举这边必须用
  驱动该链接的 clang——宿主的归档是宿主工具链编的，C 运行时可能不同，混链
  会坏）。
- **落地后的实测收益**（2026-10-22 收口）：宿主发布 hello `.text` 199,752 →
  **146,344**（−53,408）；交叉 linux-x64 hello 189,074 → **137,458**
  （−51,616）。按需拉取在宿主/交叉/macOS/wasm32 上都成立（hello 0 个硬件加速
  符号，用到加密的程序 83~95 个）。验证要**端到端跑一次**（交叉产物实跑，
  SHA-256("abc") 要输出标准向量 `ba7816bf…15ad`），别只看符号数。
- **⑨（2026-10-23 实测）运行时对象没按函数分节 = 链接期裁剪基本失效，
  这是比 crypto 归档更大的一个杠杆**：同样 6 个交叉运行时对象（同步/文件/
  十进制/定时器/嵌入资源/解压）+ 同一个 main + 同一条 `-Wl,--gc-sections`
  链接行，**只改编译开关**：
  | 运行时对象的编译选项 | `.text` |
  |---|---|
  | 现状（无分节） | 140,314 |
  | `-ffunction-sections` | **48,495（−65%）** |
  | `-ffunction-sections -fdata-sections` | 48,495 |
  各目标的运行时配方与宿主构建**都没有** `-ffunction-sections` ⇒ 发布产物里的
  运行时是"整块进"，空程序也要背走 io/同步/定时器/十进制的全部 `.text`。
  这条与 crypto 归档那条**互补不冲突**：归档解决"可达但不该在"的子系统，
  分节解决"不可达却整块进"的运行时。**两个杠杆都要用。**
- **⑩（2026-10-23 实测）发布产物体积的大头排序，标准库不在其中**：宿主
  hello 的发布产物 287,232 字节 = `.text` 146,432 + **`.rsrc` 106,496** +
  导入表/重定位/pdata 约 35 KB。那 106 KB 是**默认图标**——构建脚本把它编成
  字节数组进编译器，**每个 Windows exe 都带一份**，占发布体积 37%；编译器
  已有 `--no-icon` 开关。而标准库只占 **7,680 字节**：标准库源码 1.25 MB /
  171 个文件，但 `using System` + 一句 `Console.WriteLine` 的程序比空程序只多
  7,680 字节 `.text`（156,160 vs 148,480）——编译器只拉 `using` 到的命名
  空间，发布时再 `--gc-sections` 裁一遍。**查体积别去翻标准库。** 开发构建
  703,679 字节，多出的 416 KB 是 DWARF 调试信息（约 317 KB）与符号表。
- **坑出处**：先花了两轮把"补 `-ffunction-sections`"当成死路写进任务台账和归
  档文档，根因是**实验做在 crypto 那个 TU 上**（那里的函数**可达**，section GC
  天然剪不掉）；真杠杆（改归档）一测就见效。教训：**否定一条处方前，先确认
  实验条件覆盖了它的前提**——"换了 TU 再测一次"才是完整验证（⑨ 就是换 TU
  后的结果：同一条处方在运行时对象上值 65%）。

### 交叉工具链的隐藏依赖：预编译对象比源码旧、musl 声明门、缺内建归档（交叉工具链纪律）

- **预编译对象会比源码旧很多，而"旧"不会自己报警**。交叉目标通常提交
  `.o`/`.a`（不带头文件），源码改了不重出，所有交叉构建就静默用旧代码。
  2026-10-22 实测：已提交的一个交叉定时器对象里**连崩溃兜底的 altstack
  代码都没有**（那功能是后来才加进头文件的），而过时检查没看那个头文件 ⇒
  没人发现。**过时段落要把"对象依赖的头文件"也算进源列表**，否则源改了对象
  不跟，过时检查永远绿。
- **配方在现代工具链下可能根本编不过——而提交的对象是旧工具链编的**。
  同一批配方在旧版 zig 编得出、新版编不出：musl 把 `sigaltstack` /
  `SS_DISABLE` 藏在 `_BSD_SOURCE/_XOPEN_SOURCE/_GNU_SOURCE` 后面，而配方用裸
  `-std=c11`（无特性宏）⇒ 交叉对象长期停在旧代码。修法有两条：① 源侧补声明
  （**注意 glibc 与 musl 的 `sigaltstack` 参数序相反**，glibc 侧照抄 musl 的
  原型会 conflicting types）；② 配方侧加特性宏（但 `_GNU_SOURCE` 会把
  `strerror_r` 换成 GNU 语义，**副作用比缺声明大**）。源侧补声明 + 只对 musl
  生效最稳。
- **交叉 sysroot 缺"编译器内建归档"会断在 128 位运算上**。用 `__int128` 除法
  的运行时代码需要 `__udivti3`/`__umodti3`（在 compiler-rt / libgcc 里）。
  一个目标的 sysroot 带 `libgcc.a`、另一个没有 ⇒ 后者任何用到十进制的交叉
  程序都链不过（`undefined symbol: __umodti3`）。补法：zig 自带
  `lib/compiler_rt/*.zig`（`udivti3.zig`/`umodti3.zig` 直接 `@export` 这两个符
  号），用 `zig build-lib -target <triple> -OReleaseFast` 编成归档塞进 sysroot；
  链接行里 sysroot 的 `libgcc.a` 是**存在才加**的，缺了就静默不链。
- **顺带一提**：发布链接带 `--gc-sections`，非发布链接不带 ⇒ 同一个缺符号问
  题，**发布版能过、调试版过不去**。别被"发布能跑"骗了。
- **坑出处**：一次交叉收口连踩三条——交叉 linux 程序链不过（缺十进制运行时对
  象）→ 补上后又链不过（缺 `__umodti3`）→ 再补内建才通。每一层都是"预编译产
  物比想象缺东西"，**交叉链接失败先查缺哪个对象/符号，别急着怀疑自己的改动**。
- **对外 ABI 的形参一律用定宽类型**（`size_t` / `long` 是平台相关的）。编译器
  后端按语言侧的 `long`（**恒 64 位**）发调用，运行时若用 `size_t` 收，32 位
  目标上（wasm32）签名就错了：链接器只报一句 *function signature mismatch*
  的**警告**，**链接照过，模块运行时坏**。凡是"编译器调用、运行时实现"的入
  口，长度/容量都要写 `int64_t`。判据：**只要这个符号有一头是编译器生成的，
  就不能有平台相关的类型**。
- **同一目标的两个 arch 可能不是同一代对象**。实测一个 arch 的同步对象是重新
  产出过的、另一个还是旧版（缺一个 UI 线程符号）⇒ 前者绿、后者红，且红的那个
  报错看着像"驱动缺符号"，实则是对象比源码旧。**别假设同目录的对象同代**，
  逐个 arch 查 mtime 与符号。
- **"全绿"要按 (目标 × 特性) 的矩阵算，不是按目标算**。只跑普通控制台探针，
  就看不见：只吃 GUI 程序的移动目标、GUI 目标专属的运行时注入路径、以及 GUI
  才用到的运行时对象。扫交叉目标至少配三个探针：普通控制台 / 触发重运行时的
  特性（加密 / 十进制）/ GUI。
- **能力表别写死**。`--list-targets` 原先是静态表，把本机构建**发不了码**的目
  标也 advertise 出去（LLVM 没 RISC-V 后端时，`--target riscv64` 只得到一句
  笼统的 "code generation failed"）。按 **LLVM 自己的注册表**过滤，列表与能力
  对齐；`--target` 被拒时直接点名"这个构建没有该 triple 的后端"。
- **查 LLVM 能力前先注册后端**：`LLVMGetTargetFromTriple` 在后端没注册时对
  **所有** triple 都返回失败 ⇒ 查表会把全部目标判成不可用（比不过滤更糟）。
  注册函数要从发码那侧提成对外函数再调。
- **坑出处**：一次全目标扫描把上面六条全撞出来了——wasm32 的十进制入口签名
  错（链接过、运行坏）、一个 arch 的对象比源码旧、OHOS 的 GUI 目标缺 EGL/GLES
  （预编译驱动直连 GL，静态链接无处可解）、RISC-V 被广告成可用。**"逐个目标试
  一个程序"给不了"全绿"的结论，矩阵才给得了。**
- **"对象比源码旧"的根因通常不是"忘了重出一次"，是"没有会重出的机制"**。
  查的时候往上一层看：谁在重出？CI 覆盖了哪些目标？**没有一个 job 重建的目
  标，对象就必然停在旧代**，谁手跑一次就停在谁手跑的那天。补法是**接上 CI**
  （一条配方 + 一个 job），不是手搓一次了事。
- **配方产出 = CI 提交清单 = 过时检查的产物表 = CI 的触发路径，四处必须同一集合**
  。实测三处全漏过：CI 每次把归档与嵌入资源那两个对象编出来又丢掉（清单里没有）
  ，而**构建是绿的**；配方读的源没进 CI 的触发路径，改了也不触发重建。**加一条
  配方产物，三处同步加。**
- **CI 腿的检查步骤红了 = 整条腿静默停摆**。检查步骤排在提交步骤前面，一红
  job 就中止 ⇒ 对象永远停在旧代，而仓库里"腿停了"和"配方没产出"**长得一模一样**
  （都是旧对象）。实测：某个桌面平台的符号检查器从某天起就是红的（GUI 兼容对象
  开始 import 驱动符号，而检查器只认系统库与同目录对象）⇒ **一个月里没有任何该
  平台的对象被 CI 刷新过**，而流水线其余部分照常绿。**每加一个 CI 步骤都要问一
  句"它红了会挡住什么"**——检查步骤排在前面时最危险。
- **白名单要从产物里读，不要写死**。检查器把 GUI 驱动的导出符号写死成常量，驱
  动一加新入口就又变红——上面那条红灯就是这么来的。改成从驱动 dylib 的符号表里
  读，白名单就跟着产物走。
- **`continue-on-error` 是借来的，得还**。新接的 CI 腿第一次跑之前可以先挂上它
  （脚本从没被执行过，让它第一次就染红整条流水线不合理），但**第一次跑通之后就要
  摘掉**——一个永远不红的腿和没有腿没有区别。**腿接上之后要验证它真的跑过**：
  CI 提交出来的对象就是证据（实测某移动平台的原生工具链腿首次执行就成功，它提
  交的那批对象把一个架构的 GUI 交叉链接从红变绿）。
- **"这台机器补不了"是要查证的结论，不是印象**。判"本机缺 X、补不了"之前先把常
  见安装位置查一遍（`Program Files` / 用户目录 / SDK 目录），更稳妥的是**直接把那
  条配方跑一次**——脚本会自己点名缺哪个文件。实测：判"本机没有某个跨平台 SDK，驱
  动只能在别的机器上编"，实际那台机器就装着它（还自带目标平台的原生 SDK），一条
  配方跑通，顺带查出仓库里两个陈旧/缺失的驱动产物。**"补不了"写进台账之前，先
  用一次执行去证伪它。**
- **"只有用到某特性的程序才需要某个对象" ⇒ 这类缺失平时看不见**。某个平台的十
  进制运行时对象在配方 / 提交清单 / 过时表 / 仓库四处皆无，而普通控制台程序不用
  十进制 ⇒ 交叉扫描一片绿，直到有人交叉编译一个用到十进制的程序才炸（报的还是
  "运行时对象目录不存在"这种容易误判成环境问题的措辞）。**缺对象要按 (目标 × 特
  性) 逐格补，别按目标补。**
- **坑出处**：一次工具链收口里某个平台的腿同时中了两枪（十进制对象四处皆无 + 检
  查步骤自己红了一个月），两者叠在一起才让"该平台的对象停在旧代"看起来像"没人
  跑配方"。
- **空壳库比缺库更坏**。导不出任何符号的动态库占着位置，会让人以为"支持着这
  个目标"，而真正链接时只得到一串 undefined symbol。**要么放真库，要么不放**
  ——并且让链接在缺库时**直接点名缺哪个、去哪拷**。
- **静态链接模型装不下动态库依赖**。预编译的 GUI 驱动直连 EGL/GLES/FreeType
  ⇒ 静态 exe 链接**原理上**无解（不是配置问题）。此时正确做法是换链接形态
  （HAP 的 `--emit-lib`）或换驱动实现（运行时 dlopen），不是往链接行里塞假符号。
- **"保持最新"的门不能用提交日期，要用"所有权 + 触发路径"审计**（2026-10-23
  实测）。日期规则对 CI 托管的产物有两处硬伤：① **重建结果字节相同**时
  （只改注释级源码）仓库不变，产物的提交日期永远停在旧值 ⇒ 门会一直红，
  而且红得没有道理；② 检查 job checkout 的是 **push 本身**，刷新腿是之后
  才提交的 ⇒ 这个竞态是**结构性**的，再等也等不掉。改成只依赖仓库就能判定
  的审计：**每个产物是否在某条 CI 腿的 `git add -f` 清单里（谁重建它）、
  那条腿的 `paths:` 触发列表是否覆盖它的全部源码（源码一改它会不会重跑）**。
  审计当场抓出三处真缺口：有一条配方产出的 HAP 适配对象不在对应 job 的提交
  清单里（**CI 造完就扔**，仓库里那个还是旧代）；两个 workflow 的触发路径都
  漏了三个公共头/源文件（改这些源码，各目标的嵌入资源/解压对象静默停在旧代）。
  **"配方产出 = 提交清单 = 过时表 = 触发路径"四处必须同一集合——这条纪律
  现在有机器可查了，别再靠人记。**
- **产物"字节相同所以没提交"这件事本身要被承认**。自动刷新腿的语义是
  "重建 → 有差异才提交"⇒ 字节相同的那次**不留任何痕迹**，任何依赖提交历史
  的判据都会误报。判据要落在**内容**上（谁的腿负责、源码变没变），不落在
  **时间**上。
