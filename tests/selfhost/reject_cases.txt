# Programs the self-hosted compiler must refuse to compile.
#
# A reject case guards a fail-closed boundary: the self-hosted backend has
# to report a diagnostic instead of emitting IR it cannot lower (the C host
# may well accept the same program -- the point is that the self-host must
# not answer with a wrong value or with broken IR). The source lives next to
# this list in reject/<name>.zan.
#
# A line may pin the diagnostic: `name|||expected substring` (matched
# literally against the compiler's output). That way the case asserts the
# self-host refuses the program for the *intended* reason -- not for some
# later, unrelated one.
#
# A third field pins the C host's diagnostic as well:
# `name|||self-host substring|||host substring`. Such a case asserts that
# both compilers refuse the program with the *same wording* -- the self-host
# may not answer a program the host rejects with a diagnostic of its own.

# `await` of an operand that is not a coroutine frame: the lowering would
# read the frame's resume slot out of a non-frame address.
await_not_a_coroutine

# A call the self-hosted backend cannot lower (a C-host builtin it does not
# implement yet): the old lowering answered with the constant 0. The task
# handle family is lowered now (A419, plus Task.Cancel), so this case uses a
# task builtin that is still missing -- Task.IsCancellationRequested.
unsupported_builtin_call|||not supported by the self-hosted compiler yet

# A call whose receiver resolves to nothing: the old lowering evaluated the
# receiver into the constant 0 and answered the call with 0.
unresolved_call

# A task started from a lambda carries no result: using the handle as a
# Task<T> would release the action frame twice (the completion path reaps it
# and the reader reaps it again) -- a double free that aborts the process.
# The C host rejects this at compile time with the very same diagnostic
# (tests/diag/task_run_action_result_type.zan).
task_result_type|||cannot convert 'Task' to 'Task<int>' in initializer: a task started from a lambda/Action carries no result

# A type that does not exist: both compilers must refuse the program with
# the very same wording ("undefined type 'X'"), pointing at the type name.
undefined_type|||undefined type 'Undefined'|||undefined type 'Undefined'

# A built-in generic used with the wrong number of type arguments: the
# diagnostic has to read the same on both sides.
generic_arity|||using the generic type 'List' requires 1 type arguments (got 2)|||using the generic type 'List' requires 1 type arguments (got 2)

# A base type that does not exist: same wording on both sides, pointing at
# the base name.
undefined_base_type|||undefined base type 'Undefined'|||undefined base type 'Undefined'

# "ValueTask" is only a return-type spelling: the host's parser rewrites it
# for an async (or bodyless) method, and its binder does not know the name
# at all. A plain method that declares it is rejected on both sides.
valuetask_not_async|||undefined type 'ValueTask'|||undefined type 'ValueTask'

# A Task-shaped slot only accepts a task handle: a raw value there is not
# convertible. The target is spelled 'Task' (without the type arguments) --
# that spelling comes from the host's assignability check.
task_slot_raw_value|||cannot convert 'double' to 'Task' in initializer: no implicit conversion|||cannot convert 'double' to 'Task' in initializer: no implicit conversion

# The same rule on a return statement.
task_return_raw_value|||cannot convert 'int' to 'Task' in return statement: no implicit conversion|||cannot convert 'int' to 'Task' in return statement: no implicit conversion

# A unary minus on a string: the operand is neither numeric nor a type with
# a unary '-' overload. The self-host lowers it as `sub i64 0, <ptr>` --
# invalid IR -- and the C host used to answer the same program with an LLVM
# verifier error instead of a diagnostic. Both sides must refuse it with the
# same wording.
unary_on_string|||cannot apply unary '-' to 'string'|||cannot apply unary '-' to 'string'

# A unary `!` on a non-bool operand: the host's binary `&&` / `||` already
# require bool ("both operands must be bool"), the unary one did not -- so
# `!someString` silently became "compare the pointer with 0". Both sides
# must refuse it with the same wording.
unary_bang_string|||cannot apply unary '!' to 'string': the operand must be a bool|||cannot apply unary '!' to 'string': the operand must be a bool

# `!` has no operator-overload path (there is no `operator !`), so a class
# instance is just as wrong as a string -- the lowering would be "compare the
# reference with 0". Both sides must refuse it with the same wording.
unary_bang_class|||cannot apply unary '!' to 'Box': the operand must be a bool|||cannot apply unary '!' to 'Box': the operand must be a bool

# A type parameter cannot be instantiated: there is no constructor entry for
# it, so the compiler used to hand out a null reference and the first member
# access crashed the process. The array form `new T[n]` is legal (the element
# type is substituted at instantiation) and must stay legal.
new_type_param|||cannot instantiate a type parameter 'T'|||cannot instantiate a type parameter 'T'

# `await` inside a lambda in an async method: a lambda is not a coroutine, so
# the await has no frame of its own -- the lowering hung it on the enclosing
# coroutine's blocks (a br across functions) and the host answered with an
# LLVM verification failure instead of a diagnostic. Both sides must refuse it
# with the same wording.
await_in_lambda|||'await' inside a lambda is not supported: a lambda is not a coroutine|||'await' inside a lambda is not supported: a lambda is not a coroutine
# The general assignability check (A477): a value whose type cannot land in
# the target slot. The self-hosted checker used to have only the two
# Task-specific rules, so it compiled `int y = "hello";` and let the string
# pointer land in the int slot. Both sides must refuse it with the same
# wording.
implicit_conversion_string_to_int|||cannot convert 'string' to 'int' in initializer: no implicit conversion|||cannot convert 'string' to 'int' in initializer: no implicit conversion

# The same rule, another pair of types.
implicit_conversion_bool_to_int|||cannot convert 'bool' to 'int' in initializer: no implicit conversion|||cannot convert 'bool' to 'int' in initializer: no implicit conversion

# The same rule on the return path.
implicit_conversion_return|||cannot convert 'string' to 'int' in return statement: no implicit conversion|||cannot convert 'string' to 'int' in return statement: no implicit conversion

# The narrowing rule (A485): a float value in an integral slot. The host
# reports the narrowing diagnostic, not the general "no implicit conversion"
# one -- the self-host had to grow the same rule.
narrowing_double_to_int|||narrowing conversion from 'double' to 'int' in initializer needs an explicit cast (C# rules)|||narrowing conversion from 'double' to 'int' in initializer needs an explicit cast (C# rules)

# An integral constant that does not fit the target's range narrows as well
# (`byte b = 200;` is fine, `byte b = 300;` is not).
narrowing_const_overflow|||narrowing conversion from 'int' to 'byte' in initializer needs an explicit cast (C# rules)|||narrowing conversion from 'int' to 'byte' in initializer needs an explicit cast (C# rules)

# An enum slot is an integral slot: a float value narrows into it.
narrowing_to_enum|||narrowing conversion from 'double' to 'Color' in initializer needs an explicit cast (C# rules)|||narrowing conversion from 'double' to 'Color' in initializer needs an explicit cast (C# rules)

# The same rule on the return path.
narrowing_return|||narrowing conversion from 'double' to 'int' in return statement needs an explicit cast (C# rules)|||narrowing conversion from 'double' to 'int' in return statement needs an explicit cast (C# rules)
