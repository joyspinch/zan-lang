# Pixel metrics are strict budgets: the three-run spread was <= 0.1%, so a
# regression is a real regression.  Millisecond metrics are deliberately
# loose and machine-dependent; they only catch order-of-magnitude drift.
# first_blend_kpx and first_style_miss are strict anti-regression gates.
# Ratchet the values downward as work lands; they may only be lowered, never
# raised. B2 first step (project sources read in per-frame slices instead of
# all on the tab-switch frame) lowered render/worst/tree; the first frame is
# now 112-116 ms warm and 178 ms cold, so its budgets keep their headroom.
# The calibrated surface is part of the budget; lower it only with a new
# measurement. A surface mismatch skips the pixel gate.
#
# RECALIBRATED against the fixed fixture: run_frame_budget.cmake now runs the
# IDE with its own throwaway profile (skin=emerald, fixed panel sizes) and its
# own generated project, so the numbers no longer depend on whatever skin and
# layout the developer happens to have persisted in %APPDATA%\ZanIDE. The old
# pixel values came from an unknown wallpaper/glass configuration that no run
# could reproduce (the same build measured round_kpx 244 under the default skin
# and 1972 under emerald). Every pixel counter below is the value the fixed
# fixture measures, plus headroom; three runs agreed to the pixel.
# round_kpx is high because the emerald glass panels each fill a rounded rect
# over the whole panel (top rect 891 kpx alone): that overdraw is the next
# target, not something this gate should hide -- keep the value pinned so any
# further growth fails.
first_whole_ms=200
first_tree_ms=120
first_blend_kpx=3700
first_style_miss=300
# Ratcheted 2024 after the glass pipeline landed: the fixture profile is now
# pinned via ZAN_IDE_CONFIG_DIR (the IDE reads config beside its exe, so an
# %APPDATA%-only fixture used to be silently ignored and the gate measured
# whatever the developer's build carried), scroll strips crossing a glass
# panel widen the next frame's clip to the panel union instead of forcing a
# whole-window redo, and continuous scrolling defers panel re-blur to one
# settle refresh (App.NoteScrollDamage / BackdropDirtyIn / SettleGlassRefresh).
# Steady state measures blend 103-161, grad 86-115, restore 95-127,
# fill 96-128, total ~2150, partial 30/30. The last driver batch holds the
# forced `redraw full` pixel dumps and is excluded from steady-state stats.
blend_kpx=260
restore_kpx=220
fill_kpx=200
round_kpx=2100
grad_kpx=135
total_kpx=2500
style_resolve=650
style_miss=5
render_ms=10
worst_ms=20
tree_ms=8
surface_w=1942
surface_h=1286
# partial_min is a FLOOR, not a ceiling: every steady-state batch must keep at
# least this many of its 30 frames damage-clipped. Animation and state changes
# that go back to whole-window redraws show up here and nowhere else (the
# render_ms average hides them). Measured 30/30 once animation frames and the
# scroll paths declare their damage rects; raise it as work lands, never lower.
partial_min=28
# slow16 counts the frames in a batch that took longer than one 60 Hz budget
# (16.7 ms, rounded to >16). worst_ms reports the same number whether a batch
# dropped one frame or twelve, so the stutter the user feels needs its own
# ceiling. Measured 0 in every steady-state batch on the calibrated surface;
# 2 leaves room for a scheduler hiccup without letting real stutter through.
slow16_max=2
# Partial frames now carry the whole steady state (30/30), so their own cost
# needs a ceiling: render_ms and the pixel counters only ever see whole-window
# frames and read 0 when there are none. Measured 1.8-2.0 ms.
part_render_ms=4
