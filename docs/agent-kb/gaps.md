# 小助手要能独立做出项目：还缺什么

结论先说：缺的不是"更强的模型"，而是**可查询的事实、结构化的计划状态、自动的验证回路**。
下面每条给出：现状 → 缺口 → 落地形式（IDE 内置）。

## 1. 能力目录（"有没有现成的"）

- 现状：控件/组件/HMI/模板/标准库都在，但只能靠 grep 和记忆找；模板元数据刚刚才结构化。
- 缺口：一个可检索的能力目录——每个控件/组件/模板的用途、必填参数、示例位置、
  是否可被设计器摆放、依赖哪些驱动。
- 落地：知识图谱的"能力目录视图"（[knowledge-graph.md](knowledge-graph.md) P1），
  数据来自 LSP 索引 + `PropSpec`/`ControlFactory` + manifest + gallery 示例。

## 2. 影响范围计算（"改这个会动到谁"）

- 现状：改动范围靠人判断，容易漏掉引用点、测试和文档。
- 缺口：给定符号/文件，列出定义、引用、继承者、覆盖它的测试、描述它的文档。
- 落地：图谱的 `references/inherits/test_covers/doc_describes` 查询，直接产出任务的
  `impact[]`。

## 3. 结构化任务与计划状态

- 现状：计划存在于对话里，重启即丢；"哪一步验证过"没有记录。
- 缺口：可持久化、可续跑、可回溯的任务对象（字段见
  [agent-workflow.md](agent-workflow.md)）。
- 落地：IDE 侧任务面板 + 项目内存储（随项目走，可提交或忽略），与 AI 面板打通。

## 4. 自动验证回路

- 现状：编译/测试/构建都有脚本，但要人挑、人跑、人读输出。
- 缺口：改动 → **自动选层级** → 跑 → 结构化解析结果 → 失败自动喂回诊断上下文。
  规则已经明确（见 [testing.md](testing.md)），只是没自动化。
- 落地：IDE"验证"命令：按改动路径推层级（改 `src/compiler` → standard；改
  `stdlib/Gui` → standard + gallery；改 `templates` → e2e_pipeline），
  串行调度（避免共享 `zanc.exe` 与桌面资源冲突），把失败用例、诊断、日志直接
  变成可点击的结构化条目。

## 5. UI 端到端自动化（当前最大缺口）

- 现状：`scripts/shot_*.ps1`、`drive_ide.ps1`、`UiDriver`(`ZAN_UI_SCRIPT`) 已经能脚本化
  驱动，但没有成体系的用例集；窗体模板的 `.g.zan` 生成路径在无头测试里被 SKIP。
- 缺口：一组"新建项目 → 选模板 → 选尺寸 → 创建 → 编译 → 运行 → 截图比对"的可重复
  UI 用例；HMI 控件在真实窗口里的交互（报警、趋势推点、键盘输入）没有自动验证。
- 落地：把驱动脚本包成 IDE 内置的"UI 回归"任务 + 基线截图库（差异阈值比对）。

## 6. 需求 → 约束的显式建模

- 现状：程序模式、设备尺寸、扩展能力这些约束以前混在模板名里，用户和智能体都得靠猜。
- 已改善：manifest 现在有 `type/target/category/sizeable/size/shape/preview/sketch`，
  向导按"模式 / 结构 / 尺寸"三个维度分开表达。
- 仍缺：**扩展库/能力维度**（网络、数据库、WebView、HMI 驱动、串口、打印…）还没有
  结构化字段，也没有"勾选能力 → 自动加依赖与示例代码"的创建流程。
- 落地：manifest 加 `capabilities=` 字段 + 向导里的能力勾选 + 脚手架按勾选注入
  `zan.proj` 依赖与起步代码。

## 7. 错误知识的回流

- 现状：踩过的坑散落在提交信息和对话里。
- 缺口：按错误码/消息可检索的"已知问题 → 根因 → 修法 → 回归测试"库。
- 落地：帮助与反馈面板的本地诊断聚合（[diagnostics-reporting.md](diagnostics-reporting.md)）
  + 与 agent-kb 的案例条目互链。

## 8. 改动规约的机器可执行化

- 现状：规约写在 `AGENTS.md` 和本知识库里，靠自觉。
- 缺口：能自动检查的部分应该自动检查——仓库根是否干净、临时文件是否在 `_scratch/`、
  新诊断是否配了正反两个用例、改了模板是否跑了 e2e。
- 落地：IDE 提交前检查（可作为面板里的 checklist + 一键校验）。

## 优先级建议

1. 能力目录 + 影响范围（P1，立刻降低"猜"的成本）
2. 自动验证回路（P1，直接减少"能编过就说完成"）
3. 结构化任务状态（P2）
4. UI 端到端用例集（P2，当前证据链最薄的一环）
5. 能力/扩展库维度建模（P2，紧接向导这轮改动）
6. 帮助反馈 + 错误知识回流（P3，与服务端/市场一起）
