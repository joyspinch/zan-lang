# 智能体开发闭环：从需求到交付

> 目标不是"写出能编译的代码"，而是**每一步都留下可核对的证据**，出错时能定位到根因，
> 结束时项目和知识库都比开始时更清晰。

## 全流程

```text
1  需求输入            用户原话照抄存档，不要先解释成自己的话
2  识别类型与约束      程序模式(控制台/窗口/HMI/服务端/库) · 设备尺寸 · 目标平台 · 性能/离线约束
3  查能力目录          已有哪些模板/控件/组件/标准库能直接用（知识图谱 + project-map）
4  澄清               只问会改变实现的问题，一次问清，答案存档
5  影响范围            要改的文件清单 + 谁引用了它们（引用关系来自符号索引，不靠猜）
6  分步计划            每步可独立编译、可独立验证；标注每步的验证手段
7  小步实施            一步一改，不混合无关重构
8  自检               编译 → 目标层级测试 → 相关构建(gallery/IDE) → 需要时真实窗口
9  诊断定位            按 debugging-playbook：分层 → 最小探针 → 根因（禁止绕过）
10 根因修复 + 回归      修完必须有一个会失败的测试变绿
11 分层验证            smoke → standard/full（按范围）→ gallery/IDE → e2e_pipeline → UI
12 交付证据            改了什么 · 为什么 · 跑了哪些验证 · 结果 · 哪些没验证到
13 沉淀               更新知识索引/方法论；把这次的坑写成一条可检索的经验
```

**第 12 步的"哪些没验证到"是硬要求**：没跑到的路径要显式说出来（例如"窗体模板的
`.g.zan` 生成路径无头测试 SKIP，未在真实 IDE 里创建过"），不能用"已完成"糊过去。

## 每个任务必须持久化的字段

这是 IDE 侧"任务/计划"数据结构应存的内容（不是聊天记录，是结构化状态）：

| 字段 | 用途 |
| --- | --- |
| `requirement_raw` | 用户原话 |
| `clarifications[]` | 问题 + 回答 |
| `constraints` | 程序模式、设备尺寸、平台、性能、依赖限制 |
| `capability_matches[]` | 需求点 → 现成模板/控件/库（含来源文件） |
| `impact[]` | 受影响文件 + 命中理由（定义/引用/测试/文档） |
| `plan[]` | 步骤、状态(pending/doing/done/blocked)、验证手段 |
| `changes[]` | 每步的 diff 摘要 + commit |
| `verifications[]` | 命令、层级、结果、耗时、失败详情 |
| `unverified[]` | 明确未覆盖的路径 |
| `findings[]` | 定位到的根因、修法、加了哪个回归 |
| `knowledge_updates[]` | 沉淀去向（agent-kb 条目/图谱节点） |

有了这些字段，任务可**中断续跑**（重启后知道做到哪、哪步没验证），也可**回溯**
（为什么当初这么改）。

## 复用优先顺序

1. 现成**模板**（`templates/`）：整套项目骨架。
2. 现成**组件/控件**（`Gui/Component`、`Gui/Widget`、`Gui/Hmi`）。
3. 现成**标准库能力**（`System.Net`/`Data`/`Text`/`Web`…）。
4. 仓库里的**真实示例**（`examples/`，含完整游戏/业务项目）。
5. 都没有才新写；新写时优先放到能被复用的层（控件而不是页面内联）。

判断"有没有现成的"不靠记忆：用 IDE 的能力目录/知识图谱查
（见 [knowledge-graph.md](knowledge-graph.md)），查不到再 grep。

## 与用户交互的纪律

- 需求含糊时**先给方案再问**，不要只抛问题。
- 计划变更必须告知，不能悄悄改路线。
- 报告结论时区分"我验证过的"和"我推断的"。
- 失败照实说，附上定位到哪一步、下一步打算怎么做。
