# 构建缓存（设计提案）

> **状态**：进行中（2026-11-24）。台账 B-ID227。阶段 1 已落地（语义见
> [`ZANC_CLI.md`](ZANC_CLI.md) `--no-build-cache` 与 `ZAN_CACHE_*`）；阶段 2、3 为目标设计，落地前不为真。
> 当前实现段落的核实来源：`src/compiler/driver/main_frontend.c`、`main_codegen.c`、
> `src/compiler/emit/emit_target.c`、`src/compiler/optimizer.c`、`src/compiler/build_cache.cpp`。

## 1. 问题

zanc 是整程序编译器：每次构建都把拉入的 stdlib/packages 源码重新解析、生成 IR、
优化、出目标码。macOS arm64 实测（Release zanc，2026-11-24）：

| 程序 | 解析 | irgen | 优化 | 出目标码 | 墙钟 |
|---|---|---|---|---|---|
| hello（31 文件） | 0.16 s | 0.004 s | 0.10 s | 0.03 s | 0.28 s |
| gui_tabs（698 文件，12,645 个函数） | 0.8–2.4 s | 1.5–2.7 s | 5.6–8.1 s | 2.3–3.5 s | 10.9–16 s |

优化 + 出目标码占七成，且几乎全是没改过的库代码。

## 2. 为什么不做"每个包预编译成 .o + 接口文件"

C/C++ 式按包预编译与 Zan 的闭世界语义冲突，三处硬伤（当前实现）：

1. **闭世界按需发射**：库函数体发不发由整程序可达性决定（拉入过滤 `pi_*`、
   `prune`、`emit_target.c` 的 publish_instance_prune / reflect_demand / vslot demand）。
   预编译整包等于放弃剪枝，体积与链接时间都退化。
2. **泛型实例化**：`List<T>` 等库泛型对用户类型的实例只能在见到用户代码后生成，
   落在"库"里却随用户代码变。
3. **整程序事实入 IR**：反射需求表、去虚化依据的类层次、类型 ID，以及按计数器命名的
   私有常量（`@__zan.strlit.N`）。实测在 gui_tabs 的 `Main` 里加一行
   `Console.WriteLine`，未优化 IR 的 diff 有 25,530 行，绝大部分是库函数体里常量的改名。

所以**缓存只认结果、不重做决策**：键是闭世界、泛型、反射全部决定完之后的产物（模块
内容）的哈希，命中即"同样的输入以前算出过的同样的输出"。正确性不依赖缓存理解这些规则，
规则变了只影响命中率。

## 3. 阶段 1（已落地）：LLVM 后端记忆化

两张表，键都是 BLAKE3（上下文摘要 ‖ 阶段标签 ‖ 模块 bitcode）：

| 表 | 键里的模块 | 值 |
|---|---|---|
| optimize | 优化前模块（剪枝、分片之后） | 优化后 bitcode + 优化器 stderr 报告（命中时原样重放） |
| object | 交给后端的最终模块（桩、内嵌资源、section 之后） | 目标文件；并行切分时为 N 份，N 进键 |

- **上下文摘要**：格式版本、LLVM 版本、zanc 可执行文件路径 + 大小 + mtime（纳秒）、
  去掉 `-o`/`--emit-deps`/`--time` 取值后的全部命令行参数、排序后的全部 `ZAN_*`
  环境变量（缓存自身的三个除外）。对象表另加 TargetMachine 的三元组/CPU/特性/优化级/
  重定位/代码模型。宁可多失效，不可错命中。
- **为什么两张表**：优化之后、出目标码之前，链接阶段会按驱动文件是否存在给 DllImport 打桩、
  注入包清单内嵌资源（`main_codegen.c`），这些依赖磁盘状态，不在优化前模块里。
  两张表各自对纯函数求值，不需要追踪这些依赖。
- **确定性**：同一输入的 IR 逐字节一致（已核实）。但 bitcode writer 的输出还依赖内存中的
  历史（函数内符号表的哈希顺序、读回时被丢掉的属性），所以未命中路径存档后**改用读回的模块**
  继续，与下一次命中喂给后端的字节完全相同。存档模块的结构体类型去名：命中时模块读进 irgen
  的同一个 LLVMContext，同名类型会被改名成 `String.1`；优化之后没有按名字找类型的代码。
- **存储**：`$ZAN_CACHE_DIR/backend`，缺省为平台用户缓存目录（macOS
  `~/Library/Caches/zan/backend`，Linux `$XDG_CACHE_HOME` 或 `~/.cache`，Windows
  `%LOCALAPPDATA%`）。临时文件写好后改名入位，并发构建不会读到半截条目。用 LLVM `pruneCache` 清理，
  缺省为 20 分钟检查一次、7 天过期、上限 4 GiB，可用 `ZAN_CACHE_PRUNE` 覆盖。
- **关闭**：`--no-build-cache`、`ZAN_BUILD_CACHE=0`。`ZAN_DUMP_OPT_IR`、`ZAN_LLVM_ARGS`
  有旁路输出（IR 落盘、`-time-passes`），设置时自动关闭；`--emit-ir` 不走优化表（要保留类型名）。
- **效果**：重复构建跳过 LLVM 优化和后端，前端照跑；命中、未命中、关缓存三种构建的产物逐字节相同。
  实测数字记在落地提交的说明里。

## 4. 后续阶段（目标设计）

### 阶段 2：改了用户代码时库代码照样命中（按来源分区的 ThinLTO 后端缓存）

1. **内容命名**：私有常量（`__zan.strlit.N` 等）按内容哈希命名，或在分区内重编号，
   让用户代码的改动不波及库函数体的字节。这是命中率的前提，先单独落地并用 IR diff 验收：
   改一行用户代码，库函数的 diff 应为 0。
2. **按来源切分优化前模块**：函数按定义来源分组。用户源码一组，每个包一组；实参含用户类型的
   泛型实例归用户组。跨组引用的局部符号外部化（参照 `SplitModule`）。
3. **ThinLTO 后端**：每组带 summary 写 bitcode，用 `llvm::lto::LTO` + in-process
   ThinBackend + `localCache` 跑。LLVM 的缓存键（`computeLTOCacheKey`）已覆盖导入/导出列表与
   被导入模块的哈希，跨组内联的正确失效由 LLVM 负责。
4. **适用范围**：只用于开发构建（非 `--publish`）。发布构建保持整模块 O2/Os，体积与性能
   不让步。

验收：gui_tabs 改一行用户代码后的重建，优化 + 出目标码阶段降到原来的 1/5 以下；
基准套件（`Zan.Bench`）开发构建性能回退不超过 3%。

### 阶段 3：前端

1. **整构建依赖清单**：复用 `--emit-deps` 记下的实际源文件，加上扫描过的目录清单、
   内嵌资源、驱动清单与环境变量。全部未变时跳过解析和 irgen，直接取对象表，重复构建降到链接耗时。
2. **逐文件解析缓存**：按文件内容哈希缓存 token 流或 AST（需要可重定位的 arena 序列化）。
   gui_tabs 解析的 0.8–2.4 s 大部分花在没改过的库文件上。
3. **包接口元数据**：`genmeta` 已能导出声明面，可作为绑定期的接口缓存，缩短拉入闭包计算。
