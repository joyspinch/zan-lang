# 通用服务端开发规范（V2 草案，供审阅）

**来源与定位**：提炼自用户生产框架（xn.it52.cn，PHP + Swoole 常驻进程 + MySQL，
已实际承载淘宝客工具类业务）的架构经验，目标是产出**真实可落地、对 AI 开发友好**
的通用规范。与 `docs/CODING_STANDARDS.md`（编译器 C11 规范）平行，那份管
`src/`，这份管"用任何语言写服务端业务系统"——包括 Zan 的 `templates/server/*`。

> 一句话总纲：**分层越少越好，每层职责唯一；DB 做存取，内存做智能；
> 样板靠生成，不靠手写；状态分三级，各回各家。**

---

## 0. 为什么这套规范能提高 AI 开发效率

AI 写代码的两大低效源：**泛查找**（不知道该把逻辑放哪，全库翻找先例）和
**再造轮子**（不知道已有封装，重写一份劣化版）。本规范用三条机制直接消灭它们：

1. **层级即导航**：逻辑按"该在哪一层"一查即中，不需要读全库找先例。
   新人（或 AI）拿到一个需求，先问"这是请求解析、业务编排、数据拼装还是存取？"
   答案直接定位到唯一允许的层。
2. **命名即路由**：URL → Controller → Model → 表，名字严格同构
   （`User` 控制器操作 `UserModel` 操作 `user` 表）。看到一处名字就知道全部相关文件，
   glob 一次即中，零泛查找。
3. **样板靠生成**：实体/字段/存取器由 schema 事实源生成，AI 不需要手写
   也不需要读生成的代码——只读事实源就知道全部字段。

## 1. 分层架构：四层，职责唯一，依赖单向

```
请求 → [L1 接入层] → [L2 业务层] → [L3 数据层] → DB/Cache
              ↘ 共享基建（连接池、内存表、日志、配置）↙
```

| 层 | 职责 | 禁止 | 框架实证 |
|---|------|------|---------|
| **L1 接入**（Controller） | 路由解析、鉴权、参数收取、限流、调 L2/L3、组装响应 | 不写 SQL、不做业务规则计算 | `Controller` 基类只做 request/session/auth/tbar 装配；`App::run` 统一做限流/异常/统计 |
| **L2 业务**（Model/Service） | 业务规则、跨表编排、状态机、缓存旁路 | 不碰 HTTP（不读 header/不写 response） | `Model` 基类做 is_delete 注入、时间戳维护、with 拼装、缓存封装 |
| **L3 数据**（Db/Dao） | 参数化 SQL 的存与取、连接池、断线重连 | 不含业务语义、不拼业务字符串 | `Db` 类 20 个方法全部是通用 CRUD 原语；`PdoPo` 连接池 |
| **基建**（Server/Table/Pool） | 进程生命周期、共享内存表、配置热载 | 不含任何业务名 | `Server.php` + `_T(name)` |

**规则：**
- 依赖只允许上层调下层；L3 永远不 import L1/L2。
- **一个业务动作贯穿不超过 3 层**。Controller 调 Model 调 Db 即到头；
  出现 Controller→Service→Model→Dao→Db 五层套娃即违规（本框架实证：无 Service 层，
  业务编排直接在 Model，层越少排查越快）。
- **通用逻辑下沉到基类，业务逻辑只出现在子类**。`update()` 自动补 update_at、
  `delete()` 自动转 is_delete=1、`select()` 自动拼 is_delete=0——这些纪律在基类
  写一次，全项目永不遗漏。AI 评审时只查基类即可覆盖全部子类。

## 2. 命名与路由：名字同构，全局唯一映射

- URL 段 = 目录 = 类名：`/zxadmin/users/users/index` →
  `App/Controller/Zxadmin/Users/Users/Index.php` → `Index::action_Index_PUT`。
  **HTTP 方法进方法名后缀**（`_GET/_PUT/_POST`），同一 URL 不同动词天然分流。
- Model 名 = 表名：`UserAssetsModel` ↔ `zx_user_assets`，控制器里
  `$this->User` 直取模型，靠 `@property` 注释给 IDE 补全。
- 字段名全局唯一字符串常量（Field 类），SQL 里不出现裸字符串列名——
  手打的命名可能不规范，但**机器生成的名字永远一致**。
- 扩展点用**文件即钩子**：`// hook xxx_start.php` 注释点 + 插件目录同名文件，
  `_include()` 编译期把插件代码织入。新增行为不改主文件——这是"开放封闭"的
  低成本实现。

## 3. 数据层规范（细则见 skill `server-db-design`）

核心六条（详细论证与实库证据在 `.agents/skills/server-db-design/SKILL.md`）：

1. DB 是记录存取器：SQL 只做**等值过滤 + 排序 + LIMIT**，JOIN/子查询不进 DB，
   多表数据两段式取回后内存按 key 拼装。
2. 字段 4/8 字节整数优先：全 int unsigned，tinyint/decimal/datetime 禁用；
   金额存分、比率乘标度、时间存 Unix 秒。
3. 主表窄定长 + 1:1 副表放大字段：判据"这列出现在列表页 SELECT * 里吗？"
4. 派生数落列写时维护（reply_num/last_reply_id），列表页永不跑 COUNT/MAX。
5. 分页两段式 + 深页反向。
6. 表结构变更 = 改 schema 事实源 → 重新生成三件套，不手写实体。

**AI 落地动作**：拿到表结构需求先过 skill 里的 8 条评审清单；写列表接口前
先确认"第一遍查询能不能只碰索引列"。

## 4. 状态三级放置：性能问题的九成是状态放错位置

| 状态 | 放哪 | 生命周期 | 框架实证 |
|------|------|---------|---------|
| 瞬时状态（限流计数、并发锁、任务队列位、统计聚合计数） | 进程共享内存表 | 进程内，自动过期 | `_T('current')` 限流、`_T('tmp_lock')` 超时自解锁、`_T('request_stat')`/`_T('sql_stat')` 定时落盘 |
| 热数据（会话、用户资产、配置） | Redis/缓存，cache-aside | 秒~分钟 TTL | `UserAssetsModel::update` 写库后同步 CacheMSet；`GetConfig` 读内存表配置 |
| 事实（业务记录） | DB | 永久 | 全部 CRUD |

**规则：**
- 判据一句话：**"丢了要出事吗？"** 丢了没事→内存；丢了可重建→缓存；
  丢了是事故→DB。把事实放内存=丢数据，把瞬时状态放 DB=自造热点行，
  两个方向的错都常见。
- 热数据读写模式固定为 cache-aside：**先写库，同一调用内同步写缓存**，
  不允许"写库后异步过期"造成的读旧窗口（除非业务明确容忍并写明）。
- 缓存键集中管理（`$this->User->key_assets` 前缀常量），禁止散落字符串拼接键。

## 5. 健壮性基线（每个服务必须内置，不是可选项）

框架已做对的，定为基线；框架做错/欠缺的，定为其反面：

1. **连接池 + 借还 + 断线重试**：所有外部 IO（DB/Redis）经池化封装；
   借出-归还-异常回收三段式封装在基类，业务层无感。判定"断线"按错误消息
   白名单（has gone away / was killed / lost），命中即重试一次。
2. **慢查询日志**：任何 SQL 超过阈值（1s）自动落慢查询日志，按 SQL 指纹
   （参数归一化后的 md5）聚合耗时计数——优化有靶子，不靠猜。
3. **统一异常出口**：框架层 catch Throwable → 按错误码分类响应
   （业务异常带码穿透、HTTP 状态映射、未知异常兜底"服务端异常"不泄内部信息）；
   debug 模式才回传堆栈与现场。
4. **参数化查询是底线**：除批量插入这类确实无法参数化的场景必须走
   白名单转义并写明原因——框架的 `insert_batch` 手拼字符串是**反面教材**。
5. **限流先行**：入口处内存计数限流（进入 incr，finally decr，超阈值快速失败），
   且 get/incr 必须原子——框架"先 get 再 incr"的竞态是**反面教材**。
6. **每请求有账**：请求开始打点（时间、内存），结束回写统计表；
   响应头回带耗时（Use-Tim/Use-Ram），性能回归一眼可见。

## 6. AI 协作纪律（写码前后的固定动作）

- **动手前**：按第 1 节把需求定位到层 → 查该层基类是否已有能力
  （九成"新需求"是已有基类方法的参数差异）→ 查 skill 是否覆盖
  （表结构/列表接口/限流/缓存各有对应章节）。
- **写码中**：新逻辑放唯一允许的层；需要跨层数据就加基类方法，
  不在业务代码里内联 SQL/内联缓存命令。
- **收尾自查**（对应 skill 第 7 节评审清单 + 本规范第 5 节基线）：
  层越权？裸列名？非参数化？COUNT 在列表页？瞬时状态进 DB？每项一票否决。

## 审阅点（请用户裁决）

1. 第 1 节"无 Service 层、业务编排放 Model"——小项目快，大项目会胖。
   要不要给 L2 留一个"超过 ~300 行的 Model 拆 Service"的升级出口？
2. 第 4 节缓存写法默认"同步双写"，是否放宽为"默认同步双写、可配置异步过期"？
3. 第 5.4 批量插入：规定必须走参数化批量语法（MySQL 多 VALUES），彻底禁手拼？
4. 本规范与 `docs/CODING_STANDARDS.md` 的边界（这份管业务服务端）是否认可？
5. 文件名/位置：`docs/CODING_STANDARDS_V2.md` 还是单独 `docs/SERVER_STANDARDS.md`？
