# 服务端开发通用规范

一句话总纲：**分层越少越好，每层职责唯一；DB 做存取，内存做智能；
样板靠生成，不靠手写；状态分三级，各回各家。**

## 一、四层架构：职责唯一，依赖单向

```
请求 → [接入层] → [业务层] → [数据层] → DB/缓存
           ↘ 共享基建（进程生命周期、内存表、连接池、配置）↙
```

| 层 | 职责 | 禁止 |
|---|------|------|
| **接入层** | 路由解析、鉴权、参数收取、限流入口、组装响应 | SQL、业务规则计算 |
| **业务层** | 业务规则、跨表编排、状态机、缓存旁路 | 碰传输细节（读 header、写响应流） |
| **数据层** | 参数化 SQL 的存与取、连接池、断线重连 | 任何业务语义 |
| **基建** | 进程生命周期、共享内存表、配置热载 | 出现任何业务名 |

**规则：**
- 依赖只允许上层调下层；数据层永远不知道接入层的存在。
- **一个业务动作贯穿不超过 3 层**。默认不设独立 Service 层，业务编排放业务层
  （层越少，排查越快）；单个文件超过约 300 行或同一编排出现第二处复用时才拆。
- **通用纪律下沉基类，业务逻辑只出现在子类。** 时间戳维护、逻辑删除注入、
  缓存旁路这类横切纪律在基类实现一次，全项目不再遗漏；
  评审时查基类即可覆盖全部子类。
- 扩展点优先选"不改主文件"的机制（事件、钩子、装饰器），
  而不是往既有流程里继续堆条件分支。

## 二、命名同构：名字即导航

- 外部地址与内部代码严格同名映射：URL 路径段 = 目录 = 类名；
  数据模型名 = 表名；HTTP 动词进方法名后缀，同一地址不同动词天然分流。
- 字段名一律走生成的常量/实体成员，SQL 与业务代码里不出现裸字符串列名。
- 为什么：看到一处名字即可推知全部相关文件，一次检索即中。
  命名与位置对不上，是"泛查找"低效的第一根源——对人和对 AI 都一样。

## 三、状态三级放置：性能问题九成源于状态放错位置

| 状态 | 放哪 | 生命周期 |
|------|------|---------|
| 瞬时状态（限流计数、并发锁、队列位、统计聚合计数） | 进程内共享结构（内存表/字典/原子计数） | 进程内，自动过期 |
| 热数据（会话、用户资产、配置） | 缓存，cache-aside | 秒~分钟 TTL |
| 事实（业务记录） | DB | 永久 |

- 判据一句话：**"丢了要出事吗？"** 丢了没事→内存；可重建→缓存；是事故→DB。
  把事实放内存=丢数据，把瞬时状态放 DB=自造热点行，两个方向的错都常见。
- 热数据固定 cache-aside：**先写库，同一调用内同步写缓存**，键集中管理；
  "写库后异步过期"默认禁止，除非业务明确容忍并注明。
- 瞬时状态操作必须原子（单步 incr 或内存锁保护）——"先读再写"两步在并发下必然超放。
- 由此推论：常驻进程 + 连接池 + 内存状态是高性能的根；
  每请求新建连接、把所有状态都推给 DB，是慢的第一根源。

## 四、健壮性基线（内置能力，不是可选项）

1. **连接池**：所有外部 IO 经池化封装，借出-归还-异常回收三段式收在基类；
   断线按错误消息白名单识别并重试一次。
2. **慢查询日志**：超阈值自动落盘，按 SQL 指纹（参数归一化后）聚合耗时计数
   ——优化有靶子，不靠猜。
3. **统一异常出口**：业务异常带码穿透，未知异常对外只回固定文案；
   内部细节只进日志，debug 开关才放行堆栈与现场。
4. **参数化是底线**：批量插入用多值参数语法，禁止手拼 SQL 字符串。
5. **限流先行**：入口内存计数（进入增、finally 减），超阈值快速失败。
6. **每请求有账**：开始打点（时间/内存），结束回写统计，响应回带耗时
   ——性能回归一眼可见。
7. **异步 handler 必须在派发点 await**：派发循环里漏 await 的 async 处理器
   变成 fire-and-forget 任务，其内异常无人观察——对端表现是连接被硬断
   （reset），服务端日志零痕迹。新增 op 时逐条核对派发点。
8. **应答快照在变更落定之后构建**：先改状态、后取快照。客户端拿应答整包
   替换本地缓存时，变更前取的旧快照就是脏数据，且只在"操作命中"路径复现。
9. **诊断副作用不得打断业务流**：日志/埋点 IO 自己吞错降级（失败置空路径、
   下次重试），绝不向业务调用抛异常——一次瞬时文件锁就能让整个数据目录
   加载失败，症状（空数据）离根因（写日志失败）极远。

## 五、AI 协作纪律（写码前后的固定动作）

- **动手前**：把需求定位到层 → 查该层基类是否已有能力
  （多数"新需求"是已有基类方法的参数差异）→ 查相关 skill。
- **写码中**：新逻辑放唯一允许的层；需要跨层数据就加基类方法，
  不在业务代码里内联 SQL 或缓存命令。
- **收尾自查（一票否决）**：层越权？裸列名？非参数化？列表页跑 COUNT？
  瞬时状态进 DB？限流计数两步写？

## 六、架构评审清单

1. 每个业务动作能说出经过的层吗？超过 3 层吗？
2. 有没有下层反向依赖上层？业务层有没有碰传输细节？
3. 横切纪律是基类一次实现，还是散落各处？
4. 状态各就各位吗（内存/缓存/DB）？
5. 命名同构成立吗？能否按名字一次检索到全部相关文件？
6. 健壮性基线六条是内置的吗？

## 七、服务端模板 e2e 定式（踩坑实锤）

给 master+N worker 的 Zan 服务端模板写自动化 e2e/压测时，这几条都是
踩过坑验证过的：

1. **停服必须杀整树**（Windows：`taskkill /F /T /PID <master>`）。
   只 `terminate()` 主进程，N 个 worker 变成攥着监听套接字的孤儿——
   下一次起服新旧实例混着应答，症状是响应里掺二进制乱码、随机
   connection reset，极易误判成协议 bug。重启前先 `tasklist` 确认清零。
2. **admin 控制器 GET 默认整页 HTML**；要数据片段加请求头
   `X-Fragment: 1`（同族：`X-Requested-With` / `Accept: application/json`，
   见 WebApp.WantsPage）。裸 GET 拿到的是完整后台页，JSON 解析必炸。
3. **checkbox 组必须按 `name[]` 惯例提交**：表单解析只对带 `[]` 后缀的
   重复键合并成逗号串；不带 `[]` 的重复键后值覆盖前值——「绑定角色」
   提交 roleIds=1&roleIds=2 只落最后一个，还报成功。
4. **GenRoute 把 action 名归一成全小写**（RolesSave → rolessave）。
   e2e 写路由前以门生成的路由表为准，别按方法名猜大小写。
5. **长寿命后台 ORM 协程的已知雷**：模板里 `while(true)` 每秒扫库的
   协程与请求并发时，偶发响应被未初始化内存覆盖（A321，A318/A320
   同族）。修复前 e2e 起服用 `ZAN_NO_BG=1` 跳过后台协程（诊断开关
   已在 server-collab main.zan），别把传输层损坏误判成业务 bug——
   判据：同一断言只要响应完整送达即 PASS，红项全部伴随 BadStatusLine
   二进制垃圾 / 10053 / 10054。
