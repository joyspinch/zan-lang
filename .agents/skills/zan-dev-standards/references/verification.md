# 验证与并发纪律——逐坑细节（zan-dev-standards 拆分，按需查阅）

### 原生平台桥接：验证真实消费链与失败边界

- 分别记录宿主状态机回归、目标完整编译单元编译、官方 SDK 链接和设备行为验收。
  宿主 mock 通过不能证明 SDK ABI、服务对象所有权或系统候选框正确；交叉对象编译
  也不能证明链接闭包完整。GUI 曾在原生测试通过后，真实 Zan 消费链仍缺导出符号。
- 平台导入声明与调用必须使用相同目标条件；同时检查目标宏的包含关系，移动平台
  可能也定义桌面系统宏。用真实消费者验证 vtable 带入的整个链接闭包，不能只查
  一个新增函数，或补假成功导出来掩盖不支持的能力。
- Release 回归不得依赖会被 `NDEBUG` 删除的操作或断言；断言式 C 用例应在包含
  `assert.h` 前显式取消它，或改用始终执行的检查。否则协议请求和检查都会消失，
  测试仍可返回成功，外部剪贴板回归曾因此未实际执行。
- IME/事件队列测试直接复用生产状态机，覆盖长文本、队列拒绝后的编辑与重试、
  关闭重开后的迟到回调及跨窗事件顺序；只测短串或另写一份队列会漏掉截断、重放
  和错误删除。异步 selection 还须覆盖有界及无限等待的超时回收。

### 验证是节奏问题，不是力气问题（2026-11-04，机器已落地）

- **"改几行测十几分钟"的三个行为根因（都已机检/成文）**：
  1. **把 ctest 当编辑循环的默认动作**——每改一处就重跑一组。规则：一轮任务
     **收口时验证一次**，编辑循环里只用编译/类型判定 + 探针；重跑只重跑输出
     会变的那条。机检：`scripts/test.ps1` 对同一 `-Match` 组 10 分钟内重复跑
     直接拒绝（`-Force` 才放行）。
  2. **命中面失控**——旧映射给 stdlib 一律 `^conformance_`（1181 条 ≈92 CPU
     分钟），且它匹配不到 `tests/conformance/*.zan` 生成的 `case_*` 用例（名字
     是 `case_<b>`，不是 `conformance_*`——双重错误）。现状：stdlib/packages/
     examples 由 `verify.ps1` 按 **import 依赖现推**最小命中面（最长命名空间
     向短试），其余用已验证前缀；任何档位命中 >80 条 test.ps1 直接拒绝并给
     收窄提示，裸 smoke（≈428 条）同样被拒。
  3. **拉新文件夹复制一堆文件"验证"**——副本不消灭共享状态，只制造漂移和
     重复构建（实测一次多出 2.7 GB 构建树副本）。规则：验证零复制——探针放
     主树 `_scratch/`，主树 `build\zanc.exe --auto-stdlib` 就地编译；测试在
     `tests/` 经 ctest。
- **配套事实**：full 档实测 2860 条 ≈10.6 CPU·h（case_det_ 1189 条孪生每案双
  编译）；单跑一条秒级（缓存失效 6–16s 现编）。单跑一律锚定
  `ctest -R "^case_<name>$"`——不锚定误中 det 孪生把成本翻倍；定向 `-Match`
  已自动排除 `^case_det_`。
- **锁僵死处理**：一颗卡死的 `selfhost_diff` 孙进程让构建锁被占 10+ 小时，
  另一会话在闸里陪等 10 小时没超时。排队前先 `build_gate.ps1 -Status`；持锁者
  进程活着但长时间无进展 = 孤儿，**杀树**（租约按进程存活判定自动失效），
  不要干等 30 分钟超时，更不要另建副本树去躲。

### 隔离发布构建：输出身份、退出码与输入证据

- **构建输出先验路径与链接**：规范化后限定构建根目录，并检查现存父链及
  exe、备份、清单、生成源码等目标的 reparse point；创建目录后再查父链，防
  junction/符号链接把写入引到根外。此检查不等于抵御同权限进程并发换链。
- **完整发布复用官方配方，只隔离产物和版本输入**：备份与依赖清单跟随输出；
  版本默认读权威文件，覆盖值严格校验，生成源码放构建目录并精确排除占位输入，
  避免污染受控源和共享可执行文件。共享中间产物仍须同一把锁；仅已同步的设计
  输入可显式跳过生成，发布验证保留真实 publish 参数，不复制源树另造配方。
- **Windows PowerShell 子进程立即保留 Handle，再等退出取 ExitCode**：
  延迟开句柄可能得到空退出码；空值保留未知，不能推断为零。用自然零/非零退出
  验证捕获；编译预算从实际编译器启动计，看门狗只终止自身拥有的子进程树。
- **构建前后快照按路径并集比较存在性与哈希**：包含新增和删除，分别记录源码、
  生成中间产物、编译器/链接器与共享产物，避免漏删或把响应文件变化误判为源码
  漂移。前后相同仅说明边界一致；事后响应文件不证明精确读时身份，有漂移就保留
  限制，生成版本输入另记哈希，不据产物成功补造稳定性认证。
- **分发清单只收发布产物与实际依赖**：检查 exe 和 native DLL 的导入闭包，
  连同构建报告列出的动态依赖放入干净产物目录，逐文件核哈希并拒链接，避免把
  日志、配置或源码混入更新包。静态闭包不证明按需加载功能或 GUI 启动已通过。
- **发行先验完整 required bundle**：预检 payload 与 GDB support 依赖闭包，实际
  relocation 运行通过后才触旧输出；必需项缺失必须失败，不能 WARN 后成功，也不能
  广扫工具链 bin 补文件，避免缺件或夹带无关依赖。
- **图库按 catalog files 封闭交付**：逐条安全解析，并按大小写一致的实际路径补齐
  stage，收全 catalog 引用闭包；不整体复制 tests，避免遗漏引用或用错误 seed case
  掩盖缺件。
- **stage 身份按哈希与长度判定**：同路径不代表同内容；最终 payload manifest
  必须绑定封存时实际的源→目标映射及文件身份，避免清单与交付内容脱节。
- **SDK 消费核验前后 payload 身份**：严格比较完整文件集合、长度与哈希，新增、
  删除、改写都判失败；协议功能通过不能替代 payload 不变。缓存与日志写入用户
  可写路径，不能落到封存安装目录。
- **项目生成的 package-owner native 库是产物**：Capture 排除这类尚待生成的库，
  Seal 将其归入 Artifact；预置第三方库仍归 NativeInput，避免混淆构建输入与输出。
  LSP 路径回归覆盖可配置 BaseDir 与 ExeDir 不同、严格 override，并对实际 owned
  server 验证正常退出、超时及非零退出时的精确清理，不能只证明解析或握手成功。

### 可恢复文件安装：原件先备齐，提交后只清理

- **发布前固化完整计划与原件**，状态至少区分准备、发布、已提交；原件复制后
  保持不变，逆序回滚可重复执行，新建文件也必须撤销。已提交状态只允许清理，
  清理失败不能把成功安装误报成未提交或在下次调用回滚。
- **恢复只接受调用方明确期望的已认证计划**；日志绑定规范根目录与计划摘要，
  文件目标由已验签清单推导，状态槽位用固定编号。状态是与安装目录同权限的
  本地信任边界，校验和只能检错；清理先检查整个有界目录，拒绝链接和未知子树。
  普通文件 flush 不能当 fsync，进程中断恢复与断电持久性分开陈述。
- **目录拼写不等于文件系统身份**：Windows 用实际目录卷号/文件 ID 绑定日志，
  不能把 GetFullPath 或 ToLower 当身份（大小写/短名别名与大小写敏感目录并存）。
  POSIX 只裁尾 `/`，尾 `\\` 是合法名字；事务状态/锁名保留到任意路径段，防父包
  覆盖嵌套安装锁 inode。验证别名下发布恢复与已提交清理、搬状态到异目录仍拒绝。
  AppUpdate Windows 实跑通过；POSIX 回归已写，交叉运行被现有运行时链接缺符号
  阻断，不能据对象编译成功宣称目标运行通过。
- **签名输入解析保留原始字段表示**，包括摘要与 MD5 的大小写；只在摘要比较时
  归一。否则有效签名会在 Save→Load 或为隔离调用方而复制元数据时失效。
  签名字节的 hex 表示不在签名负载内，计划身份可归一这部分后再绑定。
- **验证跨进程而非只模拟状态**：子进程发布部分文件后直接退出，下一进程经
  生产入口恢复；另测后续文件失败、新文件撤销、调用方旧备份、锁互斥、坏日志、
  已提交清理与签名往返。坑出处：`tests/conformance/app_update.zan`；Windows
  定向用例与最终 `--check-leaks --arc-guard` 实跑通过，父进程 stderr 为空。

### 模板完整链接验收：单项有界、分片留证、产物实存

- **完整链接验收使用源仓库 `tests/run_templates.cmake`**，保留 manifest 的
  EXE/DLL 目标分支，不用统一 `--emit-lib` 的编译门替代 EXE 链接。用 `FILTER`
  按相对模板路径做区分大小写的 CMake 正则筛选（单项 `^game/snake$`、类别
  `^gui/`），零命中必须失败；省略过滤仍全量并包含 `EXTRA_PROJECTS`。
- **每项目设有界超时，不能只依赖整个 batch 的限时**：`COMPILE_TIMEOUT`
  默认 600 秒；超时/非零/启动失败都落盘并使批次最终失败，继续处理其他项目。
  逐项直接保存 stdout/stderr 和 `result.json`，开始时先记 `running`，结束记
  `pass/fail/timeout`，避免整批超时后只剩半棵目录、诊断还困在内存里。
- **rc=0 后仍检查产物存在、不是目录且长度大于零**；清掉本次选中项目的旧目录
  后再编译，防旧产物冒充成功。完整链接通过只证明链接，不证明 GUI/游戏交互。
- **筛选先于清理**：只重建选中项目目录，保留未选项目证据。`WORK/results.json`
  只代表最近一片，`complete` 表示处理完而非全通过；多片报告另存，逐项结果留在
  对应目录。并发分片要用不同 `WORK`，共享编译资源仍按仓库锁规则执行。
- **先用无编译器 harness 验证脚手架语义**：源仓库命令
  `python -I tests/test_run_templates.py`，夹具仅进 `_scratch/` 并自动清理。
  已验证精确/分组/零命中过滤、非零/启动失败/超时及部分输出、rc0 无产物或空产物
  拒绝与有效产物通过、未选目录保留、默认全量和额外项目；无需真实编译、锁或
  CTest。不能把 harness 通过写成真实模板全量通过。

### 私密子进程验收：输出、清理与时限类型

- **按生产者字节协议显式设置 stdout/stderr 解码，并分别等待双流读取完成**：
  UTF-8 管道输出不能依赖宿主 console code page。成功同时要求 exit0、读取完成、
  唯一已知成功行，以及无已知失败行和运行时诊断；零退出码不能替代业务判据。
  授权输出仅在内存分类，报告固定标签、布尔值、退出码与编码元信息，不记录
  原始输出、异常消息、激活码、session、证书或状态文件内容。
- **清理步骤逐项隔离，原始失败与清理失败分开保留**：清环境、逐个 Dispose、
  回收 owned child、删除私密目录和写报告使用独立 try/finally；任一步失败不能
  跳过后续步骤或覆盖 primary failure。未确认退出时保留 owned 句柄供外层有界
  回收，保留仍被使用的状态目录；只在退出确认后删除，清理失败记录固定分类。
- **PowerShell JSON 时间按实际类型归一为 UTC**：兼容字符串、DateTime 和
  DateTimeOffset；拒绝无时区字符串和 Unspecified DateTime，检查过期及剩余
  预算。PS7 可自动转换 JSON 日期，不能先默认 ToString 再 Parse，否则会丢失
  时区；字符串保留显式 Z/offset，DateTime 用 ToUniversalTime，DateTimeOffset
  用 UtcDateTime，比较两端统一 UTC。
- **验证边界分开陈述**：已知文案字节的错误/正确解码、双流与清理异常、时间
  类型/过期拒绝可由无 secret mock 证明；mock 通过仅证明脚手架边界，显式
  UTF-8 修复仍须真实授权进程再次完成业务判据，才能宣称实际验收通过。

### 恢复故障验收：业务、owned 清理与宿主观察分层

- 在真实 SQL/提交成功边界停驻 owned 客户端，确认标记后终止该进程，再由新进程
  先核对持久化故障态、调用生产恢复入口、检查身份/余额/关联/阶段账本；异常回滚
  或同连接重复调用不能替代进程中断恢复，客户端中断也不证明主机掉电持久性。
- 分开记录业务恢复、owned 环境清理和宿主网络观察。服务所有者退出并报告清理后，
  用独立观察确认精确 datadir 不存在、无匹配 owned 服务进程、服务侧端口拒绝；
  Windows `connect_ex` 配置超时后返回 `10035` 属不确定，既不能证明仍在监听，
  也不能证明端口已关闭。精确 `Listen` 状态与监听者归属是另一项只读证据。
- 宿主转发观察采用有界等待，超时保留独立 FAIL/整体非零；只有 owned 环境已确证
  清理且业务完成，才可继续预定有限窗口收集证据。不得以业务成功盖掉清理失败，
  不得通过无限探测、放宽阈值或终止无关监听者追求全绿。坑出处：SQLite/MariaDB
  迁移进程中断验收中，服务/目录均已消失，宿主连接仍由成功转为 `10035` 超时。

### Windows 验收子进程：进程树所有权与运行诊断

- **父 PID 不等于进程树生命周期**：父已退出、后代仍持有 stdout 时，
  `communicate(timeout)` 仍会超时；`taskkill /PID <已退出父PID> /T /F` 无法可靠
  找回后代，`CREATE_NEW_PROCESS_GROUP` 也不能代替 Windows Job Object。
- **先约束、再执行**：创建带 `KILL_ON_JOB_CLOSE` 的 Job，以 `CREATE_SUSPENDED`
  启动子进程，成功 `AssignProcessToJobObject` 后才 resume，防止子进程先派生
  后代的竞态；分配失败则终止挂起进程并报错。正常退出、timeout、`BaseException`
  （含 `KeyboardInterrupt`/`SystemExit`）统一关闭 Job 清后代，收集输出并回收父
  进程后再返回或重抛；POSIX 对应独立 session/process group + `killpg`。
- **退出 0 不是运行通过的充分条件**：Zan 验收运行在合并环境后强制
  `ZAN_RT_HARD=1`，防继承的 `0` 覆盖 `--strict-runtime`；合并 stdout/stderr
  中命中 `memory leak detected`、`runtime error:`、`Unhandled exception`、
  `ARC guard`（大小写不敏感）即失败，JSON 记录诊断，成功标记不能覆盖它。
- **脚手架先自检**：纯 Python 验证父立即退出而子持有 stdout、timeout 杀树、
  中断先清理再重抛、Job 分配失败不执行，以及 exit0+成功 JSON 仍拒绝诊断。
  源仓库 `python -I tests/integration/test_net_interop_harness.py` 已在 Windows
  实跑 15 项通过；POSIX 分支仅 mock 验证，不能写成 POSIX 实测。

### 改了共享底座文件，验证面要自己收窄（验证范围沉淀）

- **`tools/agent/verify.ps1` 对共享底座文件算出的 ctest 命中面会大到不可跑**：改
  `packages/Zan.Net/src/System/Net/Http/Client/HttpClient.zan` 这种被几十个包
  消费的底座，旧映射给出的命中是 **1181 条**（正则 `^conformance_` 全量），照着跑
  就是一次 tier 级的长跑，违反"日常只跑 target 化测试"。
  **做法**：现行 `verify.ps1` 已按 import 依赖自动收窄（如 HTTP 传输层收窄到
  `conformance_(http|https|net_|web_|security_http|ws_)` 55 条），工具给不出
  窄面时再按域手工收窄。改完只跑新增的那条是不够的：
  共享函数（如重定向判定）的签名/语义改动会打到**别的**通道（本次改了
  `RedirectReplay` 的签名，文本通道与字节通道两处调用点都要跟着变）。
- **共享树里别的用例红了，先归因再动手**：同族跑出某个 Web API 文档用例红，
  diff 是布尔渲染从 `1/0` 变成 `true/false`。**归因分两种，处置相反**：
  - 红来自**另一个会话未提交的**编译器改动（在途）→ 不是本次造成的，
    **不要去"顺手修好"**——那是回退别人的在途改动。做法：在交付说明里写清
    归因（哪个文件、哪段 diff、为什么与本次无关），自己的用例单独跑绿作证。
  - 红来自**已提交的行为变更**（某个 commit 改了渲染口径，golden 没跟着刷）
    → golden **就是该跟着刷的**。照"只归因不修"走会留下长期假红，比本次红更糟。
    判据：那次改动**在不在 HEAD**——`git log --oneline -1 <file>` 能看到
    提交号即已提交（看不到就是未提交的在途改动）。
- **"这个用例在 HEAD 上是不是已经红了"用一条命令定案，别一上来就考古**：
  `git show HEAD:<file> | grep <符号>`——看见 `private` 就在 HEAD，读一次文件
  就能定性。此后**只在状态确有差异时**才升级到 `git log` / `git log -L` / blame。
  为什么：一次可见性回归的定性本该一条 `git show` 结束，实际做了七八条
  （log / log -L / show / merge-base 轮着来）才收口——考古工具是二阶手段，
  先用最直接的那个。
- **重跑只跑"输出会变的那条"，不要整组重跑**：改了某条用例的 golden 或某条
  断言，就只跑那一条；整组重跑是习惯不是规则。改共享底座（同一批用例都编译
  它）才值得整组跑一次——那是**一轮**，不是每修一处跑一轮。
- **动手前先查 skill 再写代码**：`base` 是 Zan 保留字（skill 里早有一条），
  本次写 `ResolveLocation` 时用了 `string base = ...` 当局部变量，编译直接报
  "reserved word"，白费一轮构建。保留字清单在 skill 的代码规范一节。

- **GUI 事件与标识纪律：杜绝硬编码号段魔数，必须走 Visual Tree 路由与作用域 Hash 栈**：
  硬编码号段（如 820000、850000、900000、930000、940000 等）在即时模式与保留模式混合时是致命隐患：
  ① **同屏多实例必撞车**：两个文件选择器或两张 DataTable 同屏时 ID 完全重叠，点击事件乱飞；
  ② **步长越界踩踏**：列表按步长分配时，行内控件稍多即踩入下一行号段；
  ③ **组件假互嵌与脏单例**：单例适配器（如 SwitchComp）保留实例字段在多行/多表渲染时状态串扰。
  **正解**：
  - 保留模式控件走真实的 Visual Tree 命中测试（`HitTest`）与标准路由派发（`Control.RouteEvent` 隧穿与冒泡）；
  - 即时模式与池化隔离走作用域 Hash 栈（`WidgetId.Push(name/index)` / `Pop()`），由父级 Hash + 局部序号派生 ID；
  - 槽位状态必须与 `WidgetPoolSlot` 控件实例绑定，单例适配器严禁持有有状态字段。


### 探针测量与脚本改文件的三条硬纪律（排查沉淀）

- **测"超期/耗时"先核对单位与减数**：耗时量是微秒、延时参数是毫秒，`raw - delayMs` 少乘 1000 会把 0.5ms 真超期算成 50ms 假超期（本轮"2× 回归"查了两轮调度器，结果是自己探针的单位错）。测超期一律 `raw - delayMs * 1000`。
- **Stopwatch.GetMilliseconds/GetMicroseconds 是静态单调钟读数（墙钟），不是流逝时间**：拿来当 elapsed 用会打出 1 亿毫秒级的数（探针打出 `build=102483857ms`，误判为计时器坏了）。测流逝要么 `Stopwatch.GetMicroseconds` 前后两次相减，要么 `StartNew` + `ElapsedMilliseconds`。
- **冻结动画仍用独立 raw 单调钟计性能**：性能区间不读可冻结动画钟，parser 拒绝首帧或任一批次缺失时钟声明，避免冻结后耗时假零。
  日志 `surface` 记录实际完整 canvas 的设备尺寸；精确尺寸请求仍受 OS 最小跟踪尺寸约束，须核实际结果，不能以请求值或裁剪区代替。
- **trace 打点必须带绝对时刻，成对相对量串不成时间线**：`late_us` 只能回答"迟了几多"，回答不了"第几段路迟的"；push/fire/park/slept 各打点带 `zan_co_precise_us` 绝对值，一轮就能定位迟滞在停车原语还是派发路径。
- **诊断观测不得推进被观测状态**：跟踪登记或准备失败时只读原始 generation、active
  等标量；先核实查询的真实调用链，若查询会间接退休登记，就不能用于只读诊断。
  日志不得调用登记、Retire、ACK 或准备证明更新，也不得放宽守卫，否则观测会改变故障。
- **脚本批量改文件必须读原文→逐处断言命中→写回→复验大小**：`open(p,"w").write(变量.replace(...))` 里变量不是文件内容时写出 0 字节（本轮两个运行时源文件被截断，靠会话内 grep 证据+HEAD 重建）；写完 `len(...)` 不对就停，别继续跑。

### 用例与环境解耦（内嵌资源、目录枚举与跨包引用）


- **内嵌资源的目录枚举按设计合并磁盘与内嵌**：内嵌根下的目录列表是
  「磁盘优先、内嵌补差」的并集（`stdlib/System/IO/Directory.zan` 的
  `MergeEmbed` / `EmbedChildren`），单文件发布后 `views/` 之类照样能枚举。
  所以**内嵌根名不能与运行目录里的真实目录同名**：conformance 用例的运行目录
  默认是仓库根（`tests/run_case.cmake` 的 `WORKDIR=tests/..`），仓库根上有真实
  的 `assets/`（品牌素材），拿 "assets" 当内嵌根会让 `Directory.GetDirectories`
  数到 {brand, pack} 两个，断言 `Count == 1` 必红——而内嵌功能本身完全正确。
  做法：内嵌根取一个运行目录里不可能出现的名字（本次取 `embedfx`），或者只
  断言内嵌项本身、不对「内嵌+磁盘」的并集总数做等值断言。
- **先分清「语义」和「断言」再决定改哪边**：目录枚举的合并是设计，测试里的
  等值计数是假设。先确认用例量的到底是内嵌树还是并集，再决定是改测试还是改
  运行时；把设计的语义改掉去迁就一条脆弱断言，是拿产品能力换测试绿灯。
- **跨包引用类型必须显式 `using`，编译器不会替你想起来**：某个 SDK 包里
  `Aes.DecryptBlockEcb` 报 "'Aes' is not a known variable, type, or namespace"，
  缺的是 `using System.Security.Cryptography;`——内建成员表里登记过 "Aes"
  只说明编译器知道这个类型的成员签名，不代表它在你的文件里可见。同包的
  另一个文件早就写了那行 `using`，这类"同一个包里一半文件能编一半不能编"
  的报错，先比 `using` 行再怀疑编译器。
- **包与包之间没有依赖清单，A 包 `using` 了 B 包就等于废掉 A 的独立性**：
  `zan.pkg` 的 `dependencies` 段**当前没有任何包在用**（各包清单只有
  name/version/description/author/license）；编译期的可见性来自
  `zan_collect_package_source_roots()` 把**工程里所有**包源根并进来
  （`src/compiler/main.c`）。于是 A 包源码里 `using` 了 B 包的命名空间时，
  在"整仓一起用"（`--package-project zan-lang`、SDK 发布）下能编；一旦用户
  只装了 A 包，A 包自身就编不过。已有先例：`Zan.Ai` 依赖 `Zan.Net`、
  `Zan.Mvc` 依赖 `Zan.Data`。
  **对策**：给包加能力前先问「这个能力在 stdlib 里吗」——**stdlib 是所有包
  都看得见的底座**；非要跨包拿，就走注入（调用方传回调/策略），别让基础包
  硬依赖可选包；真需要共享就评估把最小必要的那部分下沉到 stdlib。
  坑出处：给 `Zan.Net` 接 HTTP 自动解压时，gzip/deflate 编解码器在
  `packages/Zan.IO/src/System/IO/Compression/`，`Zan.Net` 全树零引用；直接
  `using System.IO.Compression;` 就把网络包绑死在压缩包上，压缩包一旦不装，
  网络包连带编译不过。
  **落地形态**（HTTP 内容编码解码）：网络包只留一个注入点
  （`HttpClient.SetContentDecoder`），**实现放在压缩包里**（一个桥类把
  `Content-Encoding` 映射到本包的编解码），两边都不绑死；应用侧一行装配：
  `http.SetContentDecoder(System.IO.Compression.ContentCoding.Decode);`。
- **注入式能力"缺实现"时必须报错，绝不能把"没做"的结果当"做了"交出去**：
  没装解码器又碰上 `Content-Encoding: gzip` 的响应时，客户端要么**抛错**
  （说清缺的是什么），要么明确返回"未解码"标记——**不能默默把压缩字节
  当正文返回**：那样调用方拿到一堆乱码，却没有任何提示，排查时只会怀疑
  服务器。同理，**同一能力的各通道口径要一致**：内存通道解码了，落盘通道
  （下载）不解码的话，落下来的就是压缩过的文件——下载通道要么也解码，
  要么明确报错说"该响应带内容编码，本通道不解码"，不能留一个"看着下完
  了、其实解不开"的文件。
- **协议里"看起来一样"的两种线上形态要按规范判定，不能猜**：`deflate`
  在 HTTP 里有裸 DEFLATE 流和 zlib 包装（2 字节头 + 尾 adler32）两种，
  服务器两种都发过。按 zlib 头判定（`CM==8` 且 `(CMF<<8|FLG)%31==0`）
  决定要不要跳过那 2 字节；猜错就会解出一堆垃圾或直接失败。
- **同名类跨命名空间时，裸名按"成员命中"消歧，落在歧义上要显式限定**：编译器
  解析裸名的顺序是 当前命名空间 → 祖先命名空间 → **本文件**的 `using` →
  成员命中消歧 → 歧义诊断。同名类型多于一个时，`X.M` 这种成员访问先用"谁声明了
  M"筛候选，唯一命中就用它（`Window.GetTickMs()` 命中 `Gui.Backend.Window`）；
  仍然多命中就报 `ambiguous type 'X'; qualify it with its namespace`，这时只能
  写全限定名或调整 import。
  **导入按文件隔离**：别的文件 import 了什么跟你无关（修复前编译器把全工程的
  using 合并成一个列表，任何文件都能被别人的 import 改掉绑定——A438，已修，
  结论在 git 历史）。
  对策不变但**理由变了**：用到哪个命名空间的类型就显式 import 哪个，既让歧义面
  变小也让意图清楚；但不要再把它当绕行手段——编译器已经不串味了。
  坑出处：ddz 加上 `using Game.Cards;` 后 `Window` 绑不到 `Gui.Backend.Window`
  （当时 DataFrame 的 `System.Data.Window` 抢走了裸名，5 个仓库外项目集体编不过）。
- **同名类在"全局命名空间 + using 包"时直接撞车（undefined type，不是绑错）**：
  项目里原本有个全局类 `DataRow`，迁移到包时又 `using Game.Data;` 引入包里
  同名的 `DataRow`，裸名 `DataRow` 就有两个候选，编译器**绑不了**，报
  undefined type（不是"绑到另一个"）。**对策：迁移到包时把项目自研的同名类
  删掉**，别留"适配层"——适配层同样会撞。坑出处：legend 客户端迁 Game.Data
  时，自研的 `Models/DataRow.zan` + `using Game.Data;` 报 127 个 undefined
  type，删掉自研类、改用包里的类型后一次过。
- **做"旧版本对照编译"时别把包源副本放进仓内**：`--package-project <工程根>` 会
  扫工程里**所有**包源根（`zan_collect_package_source_roots()`）。仓内再放一份
  包的源，就变成**两个同名包根** → 同一类型有两个定义 → 凡是提到该类型的文件
  全报 `ambiguous type`，几百条误报把真正的错误淹掉。对照编译要么在**仓外**
  临时目录做，要么直接改工作区源看差异，**不要为了"留个底"往仓里拷包源**。
  坑出处：一次站点 GEO 改造为对照 HEAD 行为，把 MVC 包源解压进仓内 `_scratch/`
  做对照编译，结果 `--package-project zan-lang` 把 `_scratch/` 也当成包根，
  `ZanWeb` 下每个类型都 ambiguous——自己制造的噪声比不做对照更慢，还多花一轮
  清理。
- **把棋类 AI 迁到共享搜索包时，终局分的口径要一起搬**：共享的 alpha-beta
  包（如 `Game.Board.BoardSearch`）对终局只给固定 `±Mate`——只说"谁赢"，不说
  "几步赢"。于是"一步将死"和"四步将死"同分，搜索按走法顺序随便挑一个，
  **AI 会选慢杀**。项目自己那份实现往往带距胜项（象棋旧实现是
  `500000 + depth * 1000`），迁移时把这个项补进适配器的 `Evaluate()`：
  终局分 = `Mate - 已走层数`，并让**游戏侧接管终局判定**（含"无着可走"——
  象棋没有闷杀规则，无着可走就是被将死），否则那条固定 `-Mate` 的分支会
  和带层数的终局分打架。适配器还要把 `Evaluate()` 翻成**当前行棋方**视角
  （包的契约如此），并缓存合法着法列表——合法着法是搜索里最贵的一步，
  终局判定不能再算第二遍。坑出处：象棋项目迁 `Game.Board` 后一度搜出
  "四步将死"，因为终局分没有距胜层数；补上后每层深度都先吃帅。
- **把棋类规则迁到共享包时,三样东西要一起搬**:① 规则语义(禁着/终局/数子口径);
  ② 状态所有权——劫点、停手计数、提子数只能有**一份真相**,放包里,游戏侧读包,
  别再留一份自己的字段(两份真相会在"某处忘了同步"时漂移);③ 表现层钩子——
  包里不碰像素,提子动画靠"包里返回被提子坐标"承接,特效仍由游戏播。
  同时要一条**无副作用试算**接口(`Probe` / `ProbeMove`):否则游戏侧 AI 会
  "存盘→临时落子→算气→还原",那既是两份真相,也是漏还原 ko/pass 计数的老坑。
  坑出处:weiqi 迁 `Game.Board.GoBoard` 时,自研的 `Group`/`TryPlay`/
  `TryPlayRaw`/`Probe`/`Score` 一并删掉改调包,AI 试算换成 `ProbeMove` 一次
  拿全(合法/提子/气数/块大小),项目侧净删 196 行。- **红灯先按层归因，编译错误会掩盖运行期行为**：一条 conformance 用例可能同时
  有编译期错误与运行期行为差异；先把编译错误清掉再重跑看运行期输出——本轮 22 条
  "编译失败"清掉可见性误伤后，有 3 条露出真正的运行期缺陷（X509 的 CN 回退口径、
  MVC 菜单 icon 落空、HTTP/2 帧 API 在仓库里根本不存在）。把编译错误当结论，
  红灯永远查不完。
- **用例要先判定环境能力再断言；"读不到"有两种，别混**。剪贴板、桌面会话这类
  能力在 CI 与 agent 机器上可能不可用，用例应先探测再用，不可用时打印 skip
  理由——否则它在任何无头机器上恒红，把真缺陷淹没在噪声里。但**"写成功、读回
  空"不等于"没有剪贴板"**：Windows 剪贴板是全局独占资源，两个进程同时开会被
  拒，撞上争用时"写"抢到了、"读"没抢到，读回来就是空串。**能力探针（能打开
  就是有）比"读一次看是不是空"可靠**，先量清是哪一种再下结论。坑出处：本轮把
  一次争用误判成"环境没有剪贴板"，登记成环境问题；后来同一会话实测剪贴板完全
  可用、8 条用例全绿，真缺陷（库层不重试）一直躺在"环境问题"里没人修。
- **Windows 全局独占资源（剪贴板）必须退避重试，不能一次失败就返回**。争用是
  瞬时的（复制/粘贴、剪贴板管理器、输入法取词），一次"写-读"往返要开关剪贴板
  十几次，撞上一次整条就红——用户看到的是"复制偶尔没反应"，测试看到的是"用例
  偶发红"。另外它的独占是**按窗口句柄**判的：持有者挂真实窗口（资源管理器/
  IDE 都是）时别人的 `OpenClipboard(NULL)` 会被拒，两边都传 NULL 则互不排斥
  ——所以"造争用"来验证重试时，持有方必须挂真实窗口句柄，否则根本撞不上。
- **红灯先定归属：僵尸基准（源码改了、基准没同步）不是这次改动造成的**。判定
  办法是比对**用例源码**与**基准 .out** 的最后改动时间——基准比源码旧，就是
  僵尸基准（用例加了输出行、基准没跟上），这条红灯在动手前就红着。坑出处：
  `conformance_gui_codeeditor` 的用例在 10-18 加了 "diagnostics and minimap check ok"
  输出，基准停在 9-22，这条用例一直红，差点被当成本次改动的回归。定完归属再
  决定补基准还是修实现，别把别人的锅背到自己改动上。

### 服务端新端点必须标 Perm 位（服务端沉淀）

- **未标注 Perm 的受控 action 一律拒绝授权**：框架启动时打
  `[rbac] N 个受控 action 未标注 Perm，已拒绝授权: …`；请求期的判定是
  `AuthUser.Allow → PermTable.RolesAllow(roleIds, action)`——未标注的
  action 位为 0，普通角色**一律被拒**，只有超级管理员（roleIds="*"）
  用得着。所以"接口写完了、用超管跑通了"**不等于**"普通账号能用"。
- **读标 View、写标 Update/Create/Delete**：与既有 API 控制器一致
  （`[Custom(Perm = PermBit.View)]` / `PermBit.Update`）。新增的屏还要
  管理员在「系统管理 → 角色」里显式授权出去，存量部署不会自动补。
- 坑出处：多维表格（9 个端点）与智能体（2 个端点）漏标 Perm——用超级
  管理员冒烟全绿，客户端换普通账号登录后整页"加载失败"，看起来像接口
  根本没实现。

### 用包做后端：包源必须与应用源一起显式列出（服务端沉淀）

- **属性路由与代码生成器只扫描显式列出的源文件**。纯 `using` 拉入路径下，
  包文件要进编译单元元数据得同时满足两个条件：命名空间目录被访问
  （`using` 触发）、类型名被**按名引用**。而**靠属性发现、从不被按名引用
  的控制器**两个条件都不满足：程序能编译、能启动、静态资产正常，但那些
  控制器的路由**静默缺失（404）**，接口文档里也没有端点——症状像"屏没做"。
- **动作**：构建时把包源与应用源一起列出来
  （`zanc src/main.zan src/**/*.zan <包库根>/<包名>/src/**/*.zan
  --auto-stdlib -o build/app.exe`）。包自己的 README 一般已写明配方
  （"在应用中使用本包"一节），**先查包文档再猜**。
- **判据**：想要的屏 404，先看**路由表**（接口文档页 / 文档 JSON），再怀疑
  action 写错——路由表里没有，就是没进编译图，不是路由声明写歪了。
- 连带坑：包里靠约定合成的成员（ORM 表访问器等）按其依赖类型是否存在
  合成，而那些类型若全仓无人按名引用，就不在编译图里 → 控制器报
  "has no member 'X'"，看着像包的 bug，其实是拉入闭包没闭上。
- 坑出处：企业协同服务端模板按 README 的旧配方构建，管理后台的系统管理屏
  （账号/角色/部门/字典/日志/配置/接口文档）**全部 404**、侧栏无入口；
  包源显式列出后同一份源码全部上线，账号可建可登录。

### 内嵌服务端管理台：别假设区根路由存在（服务端沉淀）

- 管理台的**落地页按账号动态解析**（按该账号可达的菜单挑入口），区根
  （如 `/admin`）常常**故意不注册**。客户端内嵌网页需要一个固定地址，
  要指向**具体的一屏**（仪表盘一类，只要求登录态），不能指向区根。
- 判据：内嵌地址 404 且服务端的其它管理屏都正常 → 多半是区根没有，
  不是服务没起；看路由表确认后改地址。

### 外部安装器自动化：参数失配是零日志的，轮询必须有超时（进程自动化沉淀）

- **官方安装器的命令行解析是朴素的，引号会失配**：自动化静默安装前，
  把最终命令行原样打一条日志（谁拼的参数、带没带引号），失败时第一件事
  就是拿这条日志手动复跑。实测（Firefox 官方 full installer）：
  带引号的 `"/InstallDirectoryPath=..."` 三种引号组合全部失配，不带引号
  才收。
- **收不到静默开关的后果是"进交互模式干等"**：`/S` 缺失或失配时安装器
  弹向导窗口等人工点击，不写任何文件、不报错、零日志。所以自动化轮询
  安装产物**必须设超时**（分钟级），超时报"安装器未产出主程序"而不是
  无限等——表象会伪装成"网络慢"或"反复触发安装"。
- **安装完成的瞬间有瞬态句柄占用**：安装器放下主程序后几秒内可能仍持有
  它的句柄，紧接着第一次 CreateProcess 会失败。这是瞬态不是错误——
  用重试窗口兜底（如 15 秒内每秒重试），别让调用方直接报"启动失败"
  退出（实测：首装完成立即启动 → 失败，重跑就好）。
- **"装上了没有"的判定别做成鸡生蛋**：完成标记（marker 文件）是安装
  流程的最后一步写的，就**不能**把它放进安装流程内部的"是否装上"校验
  ——首装永远差一枚标记 → 判"未装上" → 下次重装。流程内部只验主产物
  本体，标记留给下次运行的外部检测。
- 坑出处：Zan.Gui.Browser 的 Firefox 自举链路，三层表象（反复触发安装）
  对应三层根因（编译器 `List<T>(数组)` 缺陷毁参数 → 安装器交互模式干等；
  marker 鸡生蛋；`GetDirectories` 裸名致缓存检测 miss），每一层都会
  单独复现"重装"表象，修一层以为好了下一层又来。

- **Git Bash 里别用 `cmd //c "x & echo %ERRORLEVEL%"` 取退出码**：`%ERRORLEVEL%` 在整行解析时就展开，恒为运行前的旧值，会把失败报成 0。直接读 `$?`；批量跑窗口用例时同时断言 case 行和结束行，rc=0 不等于跑过（未知 case 名也是 rc=0）。

### ORM 写入谓词：终端选择 IO 路径，mock 超时先分清异常与阻塞

- `Update/Delete.Where(Func<T,bool>)` 只记录黑盒谓词；候选行读取推迟到终端，
  同步终端用 `Query`，异步终端用 `QueryAsync`。异步驱动会直接拒绝同步接口，
  给方法名加 Async 并不能修复构造阶段的同步 IO。SQL 条件先筛候选，委托再取交集；
  大候选集仍有客户端物化成本，明确 SQL 表达式可直接下推。
- 每次终端先快照 SET 值、WHERE 文本与绑定参数、委托列表；UPDATE 候选参数不含
  SET 参数。暂停期间修改构造器不影响在途操作，复用时重新取候选，命中主键不能
  累积回原构造器。零命中固定为假条件；复合键 OR 元组与已有 SQL（含原始 OR）
  都整体加括号后 AND，防第一条 OR 分支绕过委托。保留单主键 IN 绑定与原有
  rowid/复合键 2000 参数限额，超限显式失败，不能分批写入造成部分副作用。
- 判定器使用同步 Query/Execute 均抛错、异步方法实际暂停的执行器，覆盖双谓词、
  SQL 参数、复用、暂停时改 SET/WHERE、零命中、文本/整型复合键和原始 SQL OR。
  源仓库回归：`tests/conformance/orm_async_mutation_predicates.zan`。
- mock 协议先由独立原始字节客户端跑通，再文件打点定位。Main 已抛异常但后台
  Serve/Ticker 仍存活也会表现为 180 秒超时，不能据此推定 reactor 阻塞；watchdog
  只改标志不足以收尾。finally 停池、取消 pending IO、等待 accept/session 清理，
  意外失败给非零退出；限时故障注入验证退出和端口立即可重绑。MySQL 自然 lambda
  原路径与成功 golden 保留在 `tests/conformance/mysql_async_nonblocking.zan`。

### Web 事务提交失败：撤销未发送的成功响应（2026-11-12 实证）

- `HttpContext.Ended()` 只表示响应已准备；JSON、HTML、redirect 可在事务提交前
  填好缓冲。提交返回 false 或抛错后，统一失败出口必须重置未发送的状态、正文、
  字节缓存与成功头，清除 Location、Set-Cookie、Content-Length、附件及业务头，
  再生成错误响应；保留安全/CORS 头，已移交传输所有权的响应不能重写。
- 提交失败保留事务状态供回滚；回滚失败即弃用未知状态的池租约，清理不得重试
  脏连接或以 OnDone/释放异常覆盖原提交错误。转交原异常使用裸 `throw;`，
  避免按基类变量重新抛出而丢失 ApiError 的动态分类。
- 判定器走真实 TCP HTTP、属性路由与 SQLite 事务，覆盖 JSON/redirect/HTML 的
  成功对照、commit false/throw、实际写入回滚、成功头清除，以及 rollback/OnDone
  同时抛错时原提交错误和坏租约弃用。源仓库回归
  `tests/conformance/mvc_commit_response.zan`（38 项断言）；与
  `case_web_response_safety` 精确运行 normal golden/leak/ARC 门通过，不据此宣称
  业务消费者已经重建或端到端通过。


### Windows 运行映像更新：真实 PE 与退出后交接

- **文件同步通过不等于运行映像更新通过**：使用实际安装路径启动真实 PE，分别
  验证运行时外部应用、退出后应用，以及从当前映像启动的自动更新。Windows
  在 GUI 创建前也已加载并锁定 EXE；另启测试进程手动应用、手动启动新版，只能
  证明停机安装，不能替代宿主自动交接成功。新版必须实际启动并核对产物身份。
- **helper 分支放在入口最早处**：在 GUI、注册和后台工作开始前识别内部模式。
  在目标安装目录外运行可信已安装宿主的副本，明确相邻原生 DLL 的部署契约；
  复制可运行产物不等于复制源码树验证。不要执行下载包提供的任意 helper，
  不支持的平台明确报告，不静默退回进程内替换当前映像。
- **握手绑定具体父进程**：helper 打开父进程句柄，联合 PID、创建时间和原始映像
  路径核对身份，防 PID 复用；完成宿主策略预检并确认能等待后才发 ready。
  parent 仅在收到 ready 后正常返回，失败保留暂存并报告；helper 有界等待同一
  句柄退出后才应用，不能用固定睡眠或仅轮询 PID 消失代替交接。
- **固定宿主信任，复用应用 callback**：独立安装配置提供 key pin、产品/平台与
  固定 pending 位置，不能由请求选择公钥或任意目标。切换 helper 工作目录前
  固定配置路径语义；ready 前和实际应用时都重新验证策略、清单快照与签名包。
  公共 bootstrap 负责进程交接，类型化 callback 复用宿主已有事务和管理库存。
  本地请求校验和只绑定快照，不是对同权限写入者的认证；目标须绑定原始宿主，
  重启固定原路径，且须先验证签名库存中的 EXE/DLL 已完整落地。
- **失败与重试分阶段判定**：握手、验签、包校验、快照变化或应用失败不得启动
  半更新程序；未成功消费的 staging 与事务恢复材料保留供同一已认证计划重试。
  已提交后仅重启失败要单独报告，不能误称未安装或盲目回滚。验收至少覆盖篡改
  签名、缺 pin、坏包、交接后快照变化拒绝与恢复后的自动重试，保留旧直接应用
  路径的失败基线；窄 PE 通过不能扩称完整 GUI 或其他平台通过。清理只处理有界、
  已结束的 helper 产物，记录所有自有进程退出、密钥清理与源码/二进制身份。
