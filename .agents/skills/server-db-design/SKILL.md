# 高性能服务端数据层设计准则

来源：用户自研生产框架（PHP + Swoole 常驻进程 + MySQL，xn.it52.cn 备份），
核心思想一句话——**把 DB 当"记录存取器"，把智能放到内存里**。
DB 只做最小粒度的存与取；过滤、拼装、聚合、格式化都在应用内存完成。
瓶颈经常出现在 DB 设计上，而不是代码写法上。

## 一、DB 是记录存取器，不是查询引擎

- 单表读写为主，复杂 JOIN/子查询/存储过程不进 DB。
  需要另一张表的数据时：先查主表拿 id 列表，再 `WHERE id IN (...)` 查副表，
  在内存里按 key 拼装（框架里的 `GetListAuto`/`add_with` 就是这个定式的封装）。
- 为什么：JOIN 让 MySQL 的 buffer pool 命中率被大字段拖垮、让索引选择变复杂、
  让表之间的耦合从代码挪进了无法版本化的查询计划里。定长窄表全在缓存里，
  `IN` 查询等价于内存 hash 拼装，代价远小于 JOIN 扫描。
- 反例对照：Im.zan Chats() 里"全表拉到内存再聚合"不是这个原则——
  那是把 SQL 该做的等值过滤（per-peer 分组）也省了。正确分工：
  SQL 做 **等值过滤 + 排序 + LIMIT**（有索引支撑的），内存做 **拼装 + 格式化**。
- 派生数据（回帖数、最后回复 id、累计阅读）落成主表上的 int 列，
  写时维护（`reply_num`/`last_reply_id`），读时绝不算。
  列表页因此永远不需要 `COUNT(*)`/`MAX(id)` 子查询。

## 二、字段准则：4 字节整数倍，定长优先

- 全部用 `int unsigned`（4 字节），不用 tinyint/smallint。
  布尔、状态、枚举都是 int（0/1/2…）。
  为什么：CPU 与 InnoDB 页对齐按 4/8 字节工作，1 字节字段省的空间换来对齐
  补位与比较开销，得不偿失；全 int 表在内存里是整齐的定长槽位，
  一次预读带出的有效数据最多。tb_one.sql 实库验证：31 个 int 列、0 个 tinyint。
- 时间一律 `int unsigned` Unix 秒（`create_at`/`update_at`），不用 datetime。
- 金额/概率/比率定标成整数存（`charge`/`roi`/`ctr` 全是 bigint/int），
  不用 decimal/float——货币用"分"，比率乘 1e6。
- 大数（成交额、外部平台 id）用 `bigint unsigned`（8 字节）。
- varchar 是给"真正的文本"留的（标题、名字），并且短定长为主
  （`varchar(50)`、`varchar(64)`）；长文本（文章正文）绝不进主表，见下一节。
- 每表标配列：主键自增 id、`create_at`、`update_at`、`status`、`is_delete`
  （逻辑删除，Model 层默认注入 `is_delete=0` 条件）。

## 三、主键关联单表拆分：列表清爽，大字段隔离

- 高频列表查询的表保持"窄 + 定长 + 全 int"：id、外键、统计数、状态位。
  大文本/JSON/长 varchar 拆到 1:1 副表，副表主键就是主表 id
  （`article` 窄表 ↔ `article_info` 副表存 content，PRI 都是 article_id）。
- 为什么：InnoDB 二级索引叶子带主键，主表行宽直接决定索引页能放多少行；
  窄表的列表扫描/计数/分页全是索引内覆盖扫描，副表只在真正点开详情时才查一次。
- 计数型 1:1 拆表同理（`bbs_cate_count` 单独放统计，避免高频 UPDATE 和
  行锁打在主表上）。
- 判据：一列会出现在"列表页 SELECT *"里吗？会→主表；只在详情页用→副表。

## 四、分页与深翻页

- 永远先查索引列（id 列表），再按 id 取整行（两段式）：
  `select(仅 id 列, 排序, 分页)` → `select([id IN 列表], 取全列)` → 内存保持原序。
  深页码（超过总页一半）反向取再数组反转，避免 `LIMIT 100000,20` 的扫过式代价。
- COUNT 也只数索引列（`count($where, $index)`），不数 `*`。

## 五、并发与限流放进程内存，不打 DB

- 常驻进程模型下，限流/并发锁/任务队列状态用进程共享内存表
  （Swoole Table；Zan 对应进程内 Dict/原子计数），DB 只存"事实"不存"瞬时状态"。
  实例：`_T('current')` 并发锁（进入 incr、finally decr，超阈值直接拒绝），
  配置 `limiting=1000`；`_T('tmp_lock')` 带超时自动解锁的互斥；
  `_T('request_stat')`/`_T('sql_stat')` 每 SQL md5 聚合耗时计数，定时器落盘统计。
- 为什么：限流键值每请求读写一次，进 DB 就是自造热点行；内存表纳秒级且天然兜底。
- 由此推论：**常驻进程 + 连接池 + 内存状态**是高性能的根，
  每请求新建连接/无状态进程把所有状态都推给 DB，是慢的第一根源。

## 六、生成式样板：一个 JSON 事实源生成 Field/Entity/Dao

- 从 `SHOW FULL COLUMNS` 一键生成三件套：
  Field（列名字符串常量，供 IDE 补全、杜绝手写列名拼错）、
  Entity（带类型注释的强类型数据袋）、Dao（按 Field 白名单存取的记录袋）。
  表结构变更是"重新生成"，不是"人肉找漏"。
- 为什么值得沉淀：它把"字段准则"变成机器保证——生成器直接读 information_schema，
  类型对不对一眼可见；手写实体类必然漂移。
- Zan 落点：`GenDb.zan` 已按同思想做代码生成；新模板加表时先补 schema 事实源再生成，
  不手写实体。

## 七、评审清单（给一段数据层代码/表结构时按序过）

1. 列表接口是单表索引查询 + 内存拼装吗？有没有混进 JOIN/子查询/函数计算？
2. 每列是不是 4/8 字节整数（或真正的短文本）？有没有 tinyint/decimal/datetime？
3. 大文本拆 1:1 副表了吗？主表 SELECT * 的行宽还在缓存友好范围吗？
4. 列表页有没有 COUNT/MAX/SUM 在跑？派生数落列了吗？
5. 分页是两段式吗？深页反向了吗？
6. 限流/锁/瞬时状态在内存吗？有没有每请求打 DB 的热点行？
7. SQL 只做等值过滤+排序+LIMIT 了吗？（"拉全表内存聚合"与"DB 里做复杂查询"是两个方向的错，都算违规。）
8. 聚合代码里的分组/去重用 Dict 键控结构，不用平行数组 + IndexOf。
