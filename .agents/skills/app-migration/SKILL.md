# 业务程序迁移与复刻规范（以 C# 等强类型业务为主）

适用一切"把现有成熟程序（C#、Web、系统级软件）复刻迁移到 Zan"或"以现有产品为 UX 参照做同族新工具"的场景。核心目标是把返工从"事后发现"挪到"事前确认"，以最小代价产出高保真、纯正原生的 Zan 程序。

## 一、第一纪律：复刻，不创造、不阉割

1. **功能完整度 1:1 对齐**：
   - 动作：原版所有可见的按钮、窗口、菜单、右键项、快捷键、异常提示语、错误码均须完整复刻。
   - 为什么：任何自作主张判定"这个大概没用"并省掉的细节，都会在验收期被彻底打回；每一个凭空自创的控件与交互都会增加用户的认知与迁移成本。
   - 适用边界：允许排版现代化升级（如绝对坐标改弹性流式），但业务功能点与交互分支禁止阉割或自造。
2. **原版业务口径与缺陷原样保留**：
   - 动作：原版算法的循环边界、判断口径、字段取值、数据落盘路径（配置/缓存/DB）必须与原版严格一致。
   - 为什么：迁移者的首要职责是消除行为偏差；若擅自“纠错”，后续对照排查时行为基线会彻底断裂。存疑之处先挂账记录，代码先保持行为等价。

## 二、双账本先行机制（未对齐，不编码）

1. **结构与页面映射账本**：
   - 开工前盘点全部窗体/控制器/模块，建立 `原文件 (如 FormA.cs) ↔ 新文件 (src/.../FormA.zan)` 账本。
   - 新文件头部第一行注释显式声明对应原版类名，方便差距审计与调用追溯。
2. **Schema 与协议契约账本**：
   - 实体字段命名直接照搬底层 DB 或接口原始命名（含大小写），中文仅作为界面展示文案。
   - 严禁在迁移过程中自造中间层别名（如将 `creativeName` 擅改改写为 `title`），第二套命名会导致每次对接接口都必须做二次翻译，迅速失去维护性。

## 三、语义照原版，写法归 Zan（摒弃源语言思维包袱）

1. **严禁平行数组，强制“一行一实体”**：
   - 动作：原版若存在多个 `List<string>` 靠下标隐式对齐的旧代码，迁移到 Zan 必须合并为统一的强类型实体类（`class RowItem { ... }`）。
   - 为什么：平行数组极易因为某列缺失或排序引发静默串行，且无法复用标准表格排序/筛选组件；实体是对接真实数据的前提。
2. **标准库能力优先，严禁手搓影子库**：
   - 动作：实现任何能力前，先用 `zan_api_search` / `zan_example` 查验；只要标准库已有（如网络请求、JSON 编解码、加密哈希、容器集合、异步定时器），严禁在应用层手写底层轮子。
   - 为什么：手造影子库不仅质量缺乏保障，还会带来维护割裂，导致后续维护者重复踩坑。

## 四、C# 业务迁移核心映射规范

1. **类型系统与容器映射**：
   - `class` / `record` $\rightarrow$ Zan `class`，显式强类型字段，存取与加工分离。
   - `List<T>` / `Dictionary<K,V>` / `HashSet<T>` $\rightarrow$ Zan 标准库 `List<T>` / `Map<K,V>` / `Set<T>`。
   - `async Task<T>` $\rightarrow$ Zan `async` 异步函数。
2. **内存模型差异（CLR GC $\rightarrow$ Zan ARC）**：
   - 引用拓扑：父对象（窗口、全局控制器）持有子对象强引用；子对象反向引用父级必须声明为弱引用（`weak`）。
   - 事件解绑纪律：长生命周期的全局事件、通知中心、单例若订阅了短生命周期视图的方法，视图销毁时必须显式解绑。Zan 采用引用计数，遗漏解绑会导致委托强持有该视图，引发 ARC 内存泄漏。
3. **UI 窗体迁移（WinForms/WPF $\rightarrow$ Zan Gui）**：
   - 结构提取前置：先精读原版 `.Designer.cs` 或 XAML，提炼控件树层次与真实事件处理器，禁止盲目看截图抠坐标。
   - 绝对坐标淘汰：彻底弃用 `Point(x, y)` 绝对排版，改用 `Row`、`Column`、`Flex`、`Grow()` 等弹性容器；组件尺寸统一使用系统标准设计 Token。
   - 数据驱动解耦：严禁为了取业务数据而读取 `txtAge.Text`；控件只做展示和输入交互，所有计算必须依托强类型 `PageState` / `Model` 实体。
4. **数据访问与持久层（EF Core/Dapper $\rightarrow$ Zan Data）**：
   - 剥离 EF Core 的隐式行为：移除庞大的上下文跟踪（ChangeTracker）与惰性加载（Lazy Loading），所有查询明确显式化，避免 N+1 慢查询。
   - 遵循三级状态放置：瞬时交互在内存、高频热数据进缓存、事实数据进持久层。

## 五、精读核对四要素（消灭返工在动笔前）

在把 C# 的一个业务方法或事件处理器移植到 Zan 之前，先精读原版对应代码，核对以下四件事：
1. **作用的数据字段名**：从原版 schema/定义处确认字段拼写，不凭记忆猜。
2. **操作的目标行集合**：明确是作用于**勾选集（CheckedRows）**还是**当前激活行（CurrentRow）**。
3. **循环的粒度与层次**：明确是一组执行一次，还是逐行逐项执行一次。
4. **判断所用的数据集合**：明确过滤或校验是对**未过滤的全集**还是**已过滤的子集**计算。

## 六、闭环验证与协作纪律

1. **单模块/单窗体即时编译，严禁积压**：
   - 每写完一个实体或页面，立即执行编译：
     ```bash
     build/zanc <file.zan> --auto-stdlib -o _scratch/verify.exe
     ```
   - 严禁连续改写多个页面却不编译验证一次；编译阻塞时立即停下排查，严禁在未验证状态下继续铺展代码。
2. **算法探针断言先行**：
   - 涉及费率计算、加密算法、报文解析等纯逻辑，在 `_scratch/probe.zan` 中编写单测断言，确保与原版 C# 运算结果逐字节一致。
3. **验证即提交**：
   - 单个模块或窗体编译且冒烟通过后，立即执行 `git commit`（例：`feat(migration): 还原客户管理列表与筛选交互`），不让工作区堆积未提交的半成品。

## 七、逐位一致移植（确定性引擎/仿真/协议栈专用）

当目标是「与原实现**比特级一致**」（游戏引擎确定性模拟、协议栈、编解码、
加密、定点数仿真）时，第三节的"语义照原版"要升级为**逐位照原版**，并额外
遵守以下纪律。这类目标不是"用户可见行为一致"，而是**中间值也一致**。

### 7.1 对照床是唯一真值来源，不许凭读代码"想"出结果

- 动作：把原实现**原样编译成可运行的对照床**（直接 `#include` 真实头文件，
  零转写），让它在合成输入上吐出逐帧/逐步的数值 trace；Zan 侧吐同格式 trace，
  两者 `diff` 必须**逐字节为空**。
- 为什么：数值移植的错误几乎全是"我以为源码是这么算的"。对照床把"想"变成
  "看"，而且一次 diff 就能定位到第一处偏差的帧与字段，比人肉比对快几个数量级。
- 边界：对照床必须**直接包含原实现**，不得手抄一份——手抄那份就是新的漂移源。
  合成数据要够小但覆盖到被移植的路径（空指针/边界/无分支都要能跑）。

### 7.2 场景必须参数化，且两侧共用同一份场景描述

- 动作：把"初始状态"抽成场景描述（位置、目标、参数），**两侧解析同一字符串**，
  对拍脚本遍历全部内置场景。
- 为什么：单场景通过不代表移植对；交叉点、边界、互挤、掉头、静止这些边界
  路径各自暴露不同的语义错误。共用同一份描述杜绝"两边场景其实不同"的假一致。
- 边界：场景描述的**解析代码在两侧各写一遍**（语言不同），但**格式与取值必须
  一一对应**，改一处就要改另一处；发现不一致时优先怀疑解析差异而不是算法。

### 7.3 数值语义要落到"位"，不是落到"数学意义"

- 动作：定点数/宽整型/浮点的每个运算都要确认四件事：**中间量的位宽**、
  **舍入方向**、**溢出是否回绕**、**符号/无符号视图是否改变结果**。
  同一数学意义的两个写法（`x/2` 与 `x>>1`、`a/2u` 与 `a/2`）在位级可能差一位。
- 为什么：这类偏差不会崩程序，只会让结果慢慢偏，最后以"数字不对"的形式
  暴露，定位成本极高。
- 边界：特别核对**字面量后缀与构造函数是否等价**（如 `12_fp8` 与
  `fp8::integer(12)` 差一个移位因子）、**无符号视图下的除法**、
  **复合赋值与二元运算的截断差异**（前者调 `wrap()`、后者不调）。

### 7.4 容器/迭代顺序属于语义

- 动作：原实现里"插入到哪一端/哪一位置"的规则要照抄，包括看起来不重要的
  索引位置；每帧遍历顺序若影响结果，trace 里按原顺序输出。
- 为什么：确定性模拟里，遍历顺序决定谁先动、谁先被挤开，顺序一改结果就分叉。
- 边界：注意"插入到开头"与"插入到第 1 个位置"是**两回事**，后者常被误读成头插。

### 7.5 共享状态机（RNG 等）的调用序列就是状态

- 动作：所有推进全局状态的调用（随机数、累加器、事件队列）按**原顺序**复刻，
  并把"调用次数/最终状态"写进对拍输出的审计行。
- 为什么：少一次或多一次调用，之后所有数值全错，而且症状出现在很远的地方。
- 边界：审计行本身也要两侧同格式，否则"只有审计行不同"会被当成假阳性而忽略。

### 7.6 逐步 trace 床要编译原实现的**打补丁副本**，不许手抄

- 动作：当被移植的函数太大（几百上千行、多个不对称分支），手抄进 trace 床
  必然分叉。做法：用脚本从原源码生成一份**只插了 printf 钩子的副本**，
  trace 床编译这份副本。
- 为什么：手抄版 trace 床自己是新的漂移源——逐步 diff 一致了，只能证明
  "我的 Zan 版等于我的 C++ 手抄版"，不能证明等于原实现。
- 边界：副本要由**脚本从真源码生成**并进版本控制（生成脚本），不能手工维护；
  副本本身通常是巨大的生成物，应进 .gitignore 而不是仓库。

### 7.7 值语义 → 引用语义的移植陷阱：按值传参的 POD 必须显式复制

- 动作：目标语言是引用语义（class）而原实现是值语义（struct/POD）时，
  凡原实现里**按值传参并就地修改**的函数，移植后必须**新建对象逐字段复制**
  再改。原实现按指针/引用传递的实体，改成 class 才是对的。
- 为什么：两条规则方向相反，一起看才完整：
  - 原实现靠**指针传递 + 就地改字段** → 用 class，否则 `list[i]` 拿到副本，
    字段写入静默丢失；
  - 原实现**按值传参 + 就地改** → 即使用了 class，也必须复制，否则改的是
    源对象，源数据被永久污染。
- 症状识别：第一次调用正常、之后所有相关坐标整体偏移一个常量
  （= 膨胀量之和），几乎必然是"expand/apply 类函数改到了源对象"。

### 7.8 "中间目标"不等于"最终目标"：多段式流程要逐段还原

- 动作：原实现里若某层函数**不直接面向最终结果**（例如只算一跳、
  只算前半段、用中间结果当搜索目标），要把它自己的选目标逻辑一并移植，
  不能"简化"成直接搜终点。
- 为什么：简化后的版本**路径仍可能合法甚至更优**，但节点数、展开次数、
  终止条件全对不上；而且外层看起来完全正常（长路径照样对），极易误判成
  "这层没问题"。
- 边界：这类层的输出常与"最终目标"只差几个量级，只能靠对拍暴露——
  所以对拍输出必须包含**中间量**（节点数、展开次数、堆高水位），
  不能只比最终路径。

### 7.9 参照床必须与被测物共用同一份输入规格

- 动作：参照床的地形、初始状态、场景描述**从同一份源**生成（Zan 侧一份
  `Terrain.zan`，C++ 侧从它导出或直接 include），不许在 C++ 床里手抄一份
  地形规则。
- 为什么：床与被测物不一致时，对拍失败会被**误判成移植缺陷**，白白花半天
  查移植代码；反之床写错了也可能让"真缺陷"被当成"床的错"放过去。
- 症状识别：两侧输出**大面积不同**（区域数、路径点数量级差很远）且改动
  只涉及少数几行时，先怀疑床的输入规格，再怀疑移植。
- 附带：床要**用原实现自己的构造函数**造实体，不要手搓结构体——原实现的
  初始化函数会设好一批隐含状态（初始标志位、目标点、当前路点），这些状态
  直接决定第一帧行为，手搓的实体缺一项就会让两侧从起点就分叉。

### 7.10 符号方向要从原语义的定义推，不能从字段名推

- 动作：原实现里凡是 `{-a, b}` 这类**对已有符号再取反**的构造，移植时要照抄
  取反动作，不要按字段名的字面意思写（"from 是起点" ⇒ `pos + from`）。
- 为什么：这类符号错误**只在边界情况下显形**——常规查询全落在合法区间，
  越界分支一次都没被走到；直到某一层开始真正触发该分支才炸。
- 症状识别：新写的对拍用例**全在"正常"数据上通过**，换一批会越界的输入就
  分叉 ⇒ 回头逐个核对符号，而不是加数据量。
- 边界：符号错了但结果仍在合法区间内时**完全不可见**——所以每加一层都要
  补一批**能触发边界分支**的用例，否则上一层遗留的符号错误会一直潜伏。

### 7.11 同一语义只能有一份真相

- 动作：移植后若原实现里的某个状态在目标语言里已经有归属明确的字段
  （例如"移动目标"挂在实体上），路径层/工具层就**直接读那个字段**，
  不要在自己这儿再存一份副本。
- 为什么：两份副本必然有一处不同步；不同步的症状极隐蔽（单位"以为到了
  目标"就停住、"当前目标"指向旧坐标），且会被误判成算法 bug。
- 附带：C++ 里 `const` 容器迭代器有缺陷时，**不要去改原实现的 const 语义**，
  在床里改用非 const 迭代即可——参照床的编译障碍不是移植对象。

### 7.12 编译缺陷要上报，不许绕路

- 动作：移植中撞到语言/编译器缺陷（重载没走、语法不支持）时，做**最小复现
  探针**，登记到语言仓库的缺陷台账（含现象、根因、方向、影响面），**并在移植
  侧用文档化的替代写法**，同时在代码注释里写明"这是编译器缺陷，不是设计选择"。
- 为什么：绕路会让缺陷永远留在编译器里；把绕路写清楚，至少下一个人知道这是
  债而不是规范。
- 边界：绕路只允许是**语义等价且局部**的（改用一个方法调用），不允许是
  "把整个算法重写成另一种风格"——那种会让对拍失去意义。

### 7.13 池化对象：字段会跨生命周期残留，"每次新建"是行为差异

- 动作：原实现若用**对象池/自由链表**复用对象（`new_path()` / `free_path()` /
  `object_pool`），移植时**照抄这个池**，不要"每次 `new` 一个新的"。池化的
  关键在于：`new` 出来的对象**只重置一部分字段**，其余字段**保留上一次的值**。
  要逐字段核对"原实现初始化时写了哪些、没写哪些"，没写的那些就是残留来源。
- 为什么：残留字段是**跨调用**的状态，比算法差异更难查——单看一次调用完全
  正确，只有"前一次调用污染后一次"才显形。症状是"某条信息莫名其妙指向了
  上一次的对象/上一次撞到的东西"。
- 附带：池的**顺序**也是语义（先入后出 / 后入先出），复用顺序不同 ⇒ 拿到的
  对象不同 ⇒ 结果不同。
- 边界：池化常见于"高频分配 + 想避免 malloc"的引擎代码（路径对象、粒子、
  命令缓冲）。判据：**原实现有没有 `free_list` / `pool` / `arena` 这种字段**，
  有就一定是池。

### 7.14 可选参数不是"可有可无"：默认参数往往只在某个调用点成立

- 动作：原实现里带默认值的参数（`bool consider_collision_with_moving_units = false`）
  在**不同调用点取不同值**。移植时**每个调用点都要单独核对**，不要因为"有默认值"
  就统一传默认。同样地，一个函数"看起来等价"的两个重载/两个分支，可能只在
  某个调用点被用到——**漏掉那个调用点**就是漏掉整条行为。
- 为什么：默认参数在原实现里是"多数调用点的取值"，不是"全部调用点的取值"。
  漏传的症状是**该被当作障碍的东西没被当作障碍**，路径直接穿过别人——
  而路径本身仍然合法，肉眼看不出问题。
- 症状识别：两侧的**中间量**（路径点、节点数、目标坐标）不同，但算法步骤完全
  一致 ⇒ 查"传进去的标志位/参数"，不是查算法。

### 7.15 判定顺序是行为的一部分

- 动作：同一个"撞上了 / 不合法"的判定里若有多项检查（原实现用 `a || b` 或
  `a && b` 串起来），**顺序必须逐个照抄**，包括哪一项在前。而且**短路语义**
  意味着顺序还决定了后续项是否被求值（副作用型检查尤其要命）。
- 为什么：`a || b` 与 `b || a` 在纯判定下等价，在**有副作用**或有**返回值差异**
  时不等价。移植常见的错：把"单位碰撞"和"地形碰撞"两个检查按直觉重排，
  结果该滑开的时候没滑开，或者不该撞的时候撞了。
- 附带：不同调用点的顺序可能**本来就不一样**（一个状态单位碰撞在前，另一个
  地形在前）——这看着像原实现的笔误，实际是行为，照抄。

### 7.16 对拍分叉的定位顺序：先比"状态链"，再比"中间量"，最后比"数值"

- 动作：一帧内原实现会跑完多个状态（重试/回退/重规划），只看**帧末状态**
  会漏掉分叉点。对拍输出要包含**每帧的状态序列**（进入状态时记一次），第一
  个不同的帧就是分叉点。然后按"状态链 → 中间量（路径/队列/缓存）→ 数值"
  的顺序逐层收窄。
- 为什么：帧末状态是**多步压缩**的结果，两个不同的中间过程可能收敛到同一个
  末态（也可能一个微小的中间差异被放大成完全不同的末态）。状态链是最早
  分叉的可观测点。
- 三类症状与下一步的对应：

  | 症状 | 去查 |
  |---|---|
  | 某状态多/少跑了一次 | 该状态内部的判定顺序、漏移植的分支、参数漏传 |
  | 状态相同但中间量不同 | 生成器/搜索层：对象池残留、标志位、索引初值 |
  | 状态与中间量都相同但数值不同 | RNG 消耗次数、定点数字面量语义、舍入/回绕 |

- 附带：RNG 的**调用次数**是数值层的第一嫌疑人——原实现一个实体初始化可能
  消耗**多次**随机数（不只是构造时那一次），漏一次就让之后所有随机取值错位。

### 7.17 对照床的输入规格只能有一份，不能"顺手再写一份"

- 动作：新增/扩展对照床时，地形、数据表、场景参数等**输入规格一律从已有的床
  复制**，不许另起炉灶。若各床对同一个概念用了不同的**编号约定**（哪怕语义
  描述一致），派生出来的中间结构就不同，后续一切比对都是噪声。
- 为什么：这类偏差的症状极具误导性——看起来像"移植算法错了"，实际是**输入
  不同**。识别信号：两侧在**最底层**的编号就已经不同（区域编号、瓦片编号、
  节点编号），且差异在"同一个概念"上呈系统性偏移。
- 附带：地形函数一改，所有床一起改；把"地形来源"写成单一文件/单一函数，
  而不是每个床各抄一份。

### 7.18 覆盖不到的状态等于没移植

- 动作：原实现里**只有特殊输入才进得去**的分支（特殊类型单位、特定状态标志、
  特定高度层级），默认的对照场景永远走不到。移植时要**专门为这些分支造场景**
  ——按"能进这个分支的最小输入集"设计每个场景，而不是靠随机参数碰。
- 为什么：这类分支的缺失在测试上完全不可见（所有用例都绿），但线上一定踩到。
  更糟的是有些状态在**调度表**里没有对应项，dispatch 的 default 分支会把它
  **静默吞掉**——行为错了却不报错。
- 附带：造完场景要**核对两边真的进了那个状态**（输出里打状态名），别只 diff
  数值；两边都停在同一个"看起来合理"的状态上，diff 也是绿的。

### 7.19 初始化副作用是行为的一部分

- 动作：原实现创建实体时除了赋值字段，还常有**副作用**：插入空间索引、登记到
  链表、立刻做一次碰撞/重叠检查、消耗随机数、覆盖默认字段。移植和造床时要把
  这些副作用**逐条列出**并照做。
- 为什么：副作用产生的**状态位**（如"碰撞标志"）会改变后续的分支走向，而它既
  不在实体的主字段里、也不在初始化函数的返回值里——照抄字段赋值是发现不了
  它的。症状：差一个状态位，行为整个走向另一条分支。
- 附带：注意**覆盖顺序**。原实现常有"先设默认值、再被上层覆盖"的两段式
  （如精灵默认高度 4 → 随后被单位类型的高度覆盖），漏掉覆盖就是用错值。
  副作用也常带**例外**（某类实体不进索引但仍做检查），别一刀切。

### 7.20 同一个标志被多处改写时，要按"改写顺序"理解最终值

- 动作：一个状态位若被**两处以上**代码改写（一个清、另一个按条件再设），
  移植时必须**按执行顺序**实现，并明确"最终值 = 最后一处改写的结果"。
  不要按"这个标志的语义"去猜它该是什么值。
- 为什么：结果往往是**两处叠加**的产物，看起来"矛盾"（先清后设）却是原样
  的行为。只搬其中一处，得到的是一个"看起来自洽但不是原样"的状态。
- 附带：这类标志常连带改变**别的量**（目标坐标、速度），所以差的不只是标志位
  本身——移植时把"改写点"当成一个整体照抄。

### 7.21 选层要看"依赖闭合"，不是看函数名好不好听

- 动作：挑下一个要移植的模块时，先把它的**调用链**摊开看：链上每一个依赖
  （解释器、图像系统、音频、文件格式、随机表）是不是都还没移植。没移植的
  依赖会把这一层拖成"做不了对拍"的层——因为对照床得把那套依赖也搭起来。
  优先选**依赖闭合**的层。
- 为什么：函数名会骗人。`update_unit_values`（每帧单位簿记）听起来是纯数值
  递减，实际链上是 `set_unit_hp` → 伤害覆盖层 → 图像系统，`stim` 到期还要跑
  iscript 解释器；而 `generate_sight_values`（视距表）看着冷门，实际是纯整数
  掩码运算，一行依赖都没有。
- 附带：先做"依赖闭合"的层还有个副作用——它会把**后续层需要的地基**铺好
  （位掩码语义、坐标约定、表的推导规则），后面几层的坑会少很多。

### 7.22 字段的"默认值"和"显式哨兵"是两回事

- 动作：原实现里同一个字段可能同时承载两种含义：**"没写过"（容器值初始化的
  结果）** 和 **"显式标记为无"（代码里写下的某个特殊值）**。移植时要分开：
  新建对象的字段默认值照抄原版的值初始化结果（通常是 0），而"无"这个标记
  单独用一个值表示。不要图省事把默认值直接设成"无"。
- 为什么：原版常有一个元素**从来没被写过**——它保留了值初始化的结果，
  而这个结果恰好是有意义的（比如中心节点的依赖指针指向自己，索引 0）。
  把它当成"无"来初始化，差的就是整列数据；而且**表的大小和节点数全对**，
  很容易被当成无关噪声。
- 附带：容器（`vector` / `resize` / `clear` 后 `push`）在原版是**值初始化**，
  移植到一个"新对象字段默认 0"的语言里通常正好对上；但如果原版显式写了
  哨兵值（`(size_t)-1`），那个哨兵要单独保留，且**和默认值不同**。

### 7.23 边界检查的整数宽度是语义的一部分

- 动作：原版用**无符号**类型做坐标运算时，负偏移会绕回成一个巨大的正数，
  从而让"越界"判断成立、节点被跳过。移植时若目标语言默认有符号，同样的
  表达式会**漏掉**这个跳过，越界访问就发生了。
- 为什么：这类差异在正常输入下完全不可见（坐标都在图内），只在**贴边**的
  输入下发作，症状是"越界崩溃"或"读到了乱七八糟的数据"——看起来像内存
  错误，不像移植错误。
- 附带：不要照抄那条无符号表达式。把它读成**意图**（"这个格子在图内吗"），
  然后在目标语言里用有符号的显式范围判断写出来。反过来，原版用有符号
  算术的地方也不能改成无符号。

### 7.24 函数名可能与它的实际操作相反

- 动作：遇到"揭开/显示/设置"这类正向命名的函数，先读它的实现，确认它做的
  到底是**置位**还是**清位**。原版常有"名字是 reveal，实现是 `&= ~mask`"
  这种反向设计——因为可见度是从"全员可见"开始、逐帧**扣掉**看不见的人的。
- 为什么：照着名字实现会得到完全相反的语义，而两边如果初值又一样
  （都从 0 开始），差异会被 `&=` 吃掉，**测试全绿但什么都没验到**。
- 附带：所以对照床的**初值必须跟原版一致**。原版 `load_map` 把每个格子的
  可见/已探索都设成全 1，床里设成 0 就等于在两张全黑的纸上做减法。
  规则：对照床的初值抄原版的初始化，不抄"看起来合理"的值。

### 7.25 无符号整数的算术回绕常常是**承重**的

- 动作：原版用 `size_t` / `unsigned` 参与的**减法**要原样保留无符号语义，
  目标语言里用等宽的无符号类型，不要用有符号 int。也不要"顺手修正"看起来
  像 bug 的负值——原版里那些回绕常常正是边界保护的一部分。
- 为什么：经典形状是一个跑动的下标配上同行同列的坐标，回绕时**两者一起
  回绕**，于是"回到上一行"变成一个巨大的下标，边界判断（`y != 0`、
  `x != width - 1`）据此保证不越界。用有符号算术复刻，下标会变成负数 →
  越界；用无符号算术"修正"成负数再判范围，原版的边界语义就没了。
- 附带：**先确认目标语言的无符号类型宽度**。Zan 的 `uint` 是 64 位，
  和 C++ 的 `size_t` 一致；`int` 是有符号的。宽度不一致时回绕点不同，
  差异是**逐条数据**都不同，而不是整体偏移。

### 7.26 随机取元素时，"顺序"和"选法"都是行为

- 动作：原版从容器里**随机**取一个元素时，移植要同时对齐三件事：容器的
  **顺序**（插入是头插还是尾插）、**随机数的用法**（是取下标还是直接当
  随机值、要不要先移位再取模）、**消耗随机数的次数**。
- 为什么：随机数选的是**下标**而不是元素，所以容器顺序不同 → 选中的元素
  不同 → 后续连锁反应不同。症状是"某一帧开始整体分叉"，很难回溯。
- 附带：对照床要**逐条 dump 容器的内容和顺序**（不只是数量），否则这类
  差异验不出来。另外注意原版常在随机值上做位移再取模
  （`(lcg_rand(26) >> 4) % size`），照抄成 `rand % size` 是另一套分布。
- 附带：如果原版用"内嵌在元素里的链表指针"来从节点反查元素，目标语言
  没有内嵌成员指针时，要另设归属（用**下标**，别用对象引用——集合里的
  元素地址通常不稳定）。

### 7.27 工具链变了，之前"绿"的层可能其实一直是错的

- 动作：底层语言/编译器的版本变了之后，**把每一层重新编译一遍**再宣布
  回归通过。旧的绿灯可能来自过期的二进制，或来自编译器当时静默接受的
  非法写法。
- 为什么：编译器收紧检查（例如把"`!` 作用在 int 上"从静默接受变成硬
  错误）时，之前"通过"的那一层其实**当时就没编过**——你只是没重新编译。
  这类潜伏问题不会自己暴露，要靠重新构建逼出来。
- 附带：修的时候按"编译器是对的"处理——把代码改成合法的写法（0/1 的
  int 标志写 `== 0`），不要为了绕过检查把语义改掉。
