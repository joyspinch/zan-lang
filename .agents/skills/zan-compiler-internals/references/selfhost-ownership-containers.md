# 自举闭环专题（四）：数值宽度、所有权、弱引用、协程异常与容器（§115–§148）

返回总索引：[selfhost-closure.md](selfhost-closure.md)

## 115. 字符串实参可以是 char；span 的 float 要显式窄化

- 坑（2026-10-21 实测）：`s.Split(',')` 在自举里发出
  `call i8* @zstr_split(i8* %s, i8* 10)`——clang 直接报
  "integer constant must have integer type"。根因：宿主把"能当字符串用的
  实参"抽象成 `is_string_like_expr`（`src/compiler/irgen_call.c:536`：
  是字符串**或** char），char 先被 `emit_char_to_cstr` 变成一个字符的
  文本；自举只认字符串，把 char 的整数值直接塞进了 `i8*` 形参。
  同样要照顾 char 的还有 Contains / IndexOf / LastIndexOf / Equals /
  StartsWith / EndsWith / Replace（Replace 的两个实参都算）。
- 做法：自举加 `StrArg(e)`——实参类型是 char 时用 `CharToStr` 打包成
  一个字符的托管字符串（作为语句临时值在语句末尾释放），其余原样。
- 顺带修的第二个坑：**span 的元素宽度和值的宽度不是一回事**。span 的
  float 元素在 IR 里是真的 32 位 `float`，而自举的 float 值一律是
  64 位 `double`（`MapType` 把 float 映成 double），所以往 `Span<float>`
  里写必须先 `fptrunc`。原来的判断写的是 `v.ty.sval == "double"`，可值
  本身也可能是 `float`（比如从 `float[]` 里读出来的元素），于是漏掉了
  窄化，clang 报 "'%t33' defined with type 'double' but expected 'float'"。
  判据要改成"这个值是不是浮点值"（`IsDbl`），不是"类型名恰好是 double"。
- 通用教训：**同一个类型名，在"值"和"存储"两层宽度可能不同**。自举的
  模型是"float 即 double"，凡是遇到真实的 32 位存储（span 元素、原生
  内存、FFI 结构体），写入前必须显式窄化；而且判断依据要用"类别"
  （浮点/整数），不要用"类型名相等"——值的声明类型可能是 float 而它的
  LLVM 形状是 double。

## 116. LLVM 的 `null` 实参必须带类型——裸 `null` 不是实参

- 坑（2026-10-21 实测，A484）：自举拼出来的 IR 里出现了裸 `null` 当调用实参，
  clang 报 "expected type"：

  ```
  %p = call i8* @zalloc(i64 24, i8* bitcast (void (i8*)* @zsb_dtor to i8*), null)
  ```

  根因：自举 irgen 的 `ContainerCid()`（`src/selfhost/irgen/irgen.zan`）在"这个类型
  不是内建容器"时返回**裸 `null`**，直接拼进 `@zalloc(size, dtor, cid)` 的第三个
  实参。LLVM 的调用实参必须带类型（`i8* null`）；裸 `null` 只在少数常量位置
  合法。
  - 触发条件很隐蔽：**用户自定义了与内建容器同名的类**（`class StringBuilder` /
    `class List` / `class Dict`）→ `IsContainerType()` 判 false → 走 null 分支。
    普通程序一切正常，差分门 85 个用例一个都没撞上。
- 做法：`ContainerCid()` 的 null 分支返回 `"i8* null"`。
- 通用教训：**自举拼 IR 文本时，任何"空指针"都要带类型**。宿主侧的 IR 一直是
  `i8* null`（参数类型是已知的），自举把参数类型藏进字符串拼接里就容易把
  类型丢掉——而拼出来的 IR 只能靠 clang/llvm-as 验证，肉眼看 `null` 完全合理，
  看不出问题。

## 117. 通用可赋值性检查：先量矩阵，再照着写

- 坑（2026-10-21 实测，A477）：自举的检查器**没有**宿主那种通用的隐式转换检查——
  `int y = "hello";` 在自举里编译通过（IR 照写），宿主报
  `cannot convert 'string' to 'int' in initializer: no implicit conversion`。
  自举原来只有两条 Task 专属规则（`CheckTaskNoResult` / `CheckTaskOnlyHandle`）。
- 做法：
  - **先量，后写**：12 个目标类型 × 17 个值 = 204 组矩阵探针（分块编译，绕开宿主
    100 条诊断的上限），把宿主的判定表**量出来**再照着实现。凭直觉写必错——
    "简单名 vs 限定名"这类区分全被推翻；真正决定判不判的是「目标是不是原始类型」
    +「值是不是已知类型」两件事，而"可空值只能进同种可空槽"这条规则是从矩阵里
    长出来的。
  - `PrimCat()` 把类型名分成 0 其他 / 1 整型 / 2 浮点 / 3 bool / 4 string /
    5 char / 6 枚举 / 7 类实例；`CheckAssignable()` 按这张表判。
  - **宁可漏报，不可误报**：误报会让自举编不过自己的源码、也会拒掉合法程序；
    漏报只是留一条台账。所以三类刻意不判——`double`/`float` 进整型槽（那是宿主
    的**窄化**规则，另一条诊断）、`object` 目标（Zan 的 `object` 不是万物基类）、
    用户类目标（宿主靠类层次判定，自举没有层次）。
  - 字面量的类型也要按后缀分：`5L` long、`5u` uint、`5UL` ulong、`5.0f` float、
    `5.0m` decimal、`0x1FL` long（解析器把进制折进同一个字段，类型后缀取
    `suffix % 8`）——宿主这么分，诊断里点的类型名才一致。
  - 措辞逐字对齐宿主：`cannot convert 'X' to 'Y' in initializer: no implicit
    conversion` / `... in return statement: ...`；`null` 字面量在宿主那里类型是
    `object`，所以诊断里写的是 `'object'` 而不是 `'null'`。
- 通用教训：**两个后端要"逐字一致"的规则，先把对面的行为量成表**。矩阵比对给出的
  三个数（误报 / 漏报 / 措辞差）比任何单条探针都有说服力——而且漏报的每一格都要
  能说清"为什么这次不判"，那才是能进台账的结论。

## 118. 向量层：宿主的每一个运算都在"字节道"上

- 坑（2026-10-21 实测）：自举把 `Vector128`/`Vector256` 当成"两个 64 位槽"来算，
  宿主却是**在字节道上定义每一个运算**（`src/compiler/irgen_expr.c:1995-2436`）：
  值是 `{ i64, i64 }` 结构，运算前转成 `<16 x i8>`（256 位是 `<32 x i8>`），算完再
  转回来。于是自举的 `AddSaturate` / `Average` / `Equals` / `Unpack` / `Shuffle` /
  `ConditionalSelect` / `ExtractMostSignificantBits` 逐字节对不上；`Multiply` /
  `AddFloat` / `SubtractFloat` / `Sqrt` / `MultiplyAdd` 走的又是 `<4 x float>` 另一条道。
- 照抄宿主时踩到的五个具体的坑：
  - `Shuffle`（pshufb）的可移植实现是**逐字节查表**：掩码字节最高位为 1 → 该道清零，
    否则取 `a[掩码 & 0x0F]`（宿主 `emit_pshufb_portable`，`irgen_expr.c:1951`）。
  - `Average`（pavgb）是 `(a&b) + ((a^b)>>1) + ((a^b)&1)`——**向量加法逐道回绕**，
    道与道之间不进位，所以这三步就够了。我们多加了一次 `odd`，答案从 150 变成 0。
  - `ConditionalSelect` 是 `(c&l) | (~c&r)`，取反的掩码是 **0xFF**，不是 1——用 1 会
    得到 `0xFE & r`，答案差一位（42 变成 106）。
  - `UnpackLow/High` 用的是 `shufflevector` **指令**（掩码是 `<16 x i32>` 常量），不是
    intrinsic。`llvm.shufflevector.v16i8.v16i8` 这个 intrinsic 根本不存在，链接期才
    报 `use of undefined value`——IR 文本看着完全合理。
  - `Create(float)` 要先 `fptrunc` 到 float 再进 float 道；自举的 float 值是 double，
    不窄化就发出 `insertelement <4 x float> ..., float %double` 的坏 IR。
  - `Prefetch` 发 `llvm.prefetch.p0`（指针 + 三个 i32 参数），不是调用一个同名函数。
- 通用教训：**照抄宿主的"道"**。宿主把值拆到哪条道上运算，自举必须拆到同一条道；
  先把宿主那段代码（`emit_vector128_call`）读完再动手，别照着 API 名字猜语义。

## 119. 窄化的时机、重载的选择、裸 return：都是宿主行为的一部分

- 坑（2026-10-21 实测），三条"宿主有、自举没有"的规则：
  1. 裸 `return;` 在**非 void** 函数里返回**结果类型的零值**
     （`src/compiler/irgen_stmt.c:1739-1742`），不是 `ret void`。自举一律发 `ret void`，
     生成的 IR 过不了 LLVM 校验（`value doesn't match function result type`）。
  2. `Convert.ToInt32` **不做** 32 位窄化：宿主用 strtoll 解析文本、fptosi 截断浮点、
     整数原样返回（`src/compiler/irgen_call.c:1937-1981`），**窄化发生在值进入有类型的
     位置时**（int 槽是 i32），不在调用里。所以 `Console.WriteLine(Convert.ToInt32(v))`
     打的是完整的 64 位值，而 `int x = Convert.ToInt32(v);` 打的是窄化后的 32 位值。
  3. 自举检查器的重载选择原来只按**名字**取第一个：`Description()` 会撞上
     `Description(string desc)`，`OnMessage(message)` 会撞上 `OnMessage(MessageHandler cb)`
     ——推出来的返回类型是另一个重载的，检查器据此报错（宿主与后端都按**实参类型**
     打分选重载，见后端的 `ScoreCand`）。自举检查器也要按实参类型打分：精确匹配 +4、
     已知不匹配 -1、未知中性。
  4. 顺带：可赋值性检查要认**用户自定义的隐式转换**（`implicit operator T`，解析器
     落成 `op_implicit` 方法），否则 `double d = feet;` 会被误判成不能转换。
- 通用教训：**"逐字一致"不只是诊断措辞**。同一个表达式的**求值时机**（在哪一步窄化、
  谁来选重载、裸 return 返回什么）同样是宿主行为的一部分；照抄时要把宿主那段代码
  读到底，再决定自举在哪一步做这件事。

## 120. 窄化是独立的一条规则：浮点进整型槽、常量越界，措辞还不一样

- 坑（2026-10-21 实测，A485）：宿主判可赋值性时**先**判窄化，窄化有自己的措辞：
  `narrowing conversion from 'X' to 'Y' in <what> needs an explicit cast (C# rules)`
  ——和通用的 `cannot convert 'X' to 'Y' in <what>: no implicit conversion` 是两条
  不同的诊断。自举只学了后者，前者整条缺失。
- 把宿主的判定表量出来（98 组矩阵 + 边界探针），三条结论凭直觉写不出来：
  1. **触发形状只有两个**：浮点值进整型槽（char 槽、枚举槽也算整型槽）、
     整型**常量**越界（`byte b = 300` 报、`byte b = 200` 不报）；
  2. **可空槽不窄化**（`int? x = 5.0` 宿主一声不吭）、**非常量不窄化**
     （`byte b = someLong` 也不报）——只有字面量常量才查范围；
  3. **`decimal` 不是浮点**：宿主有独立的 decimal 类型，`int v = 5.0m` 报的是
     *cannot convert*（不是窄化），`double` 与 `decimal` 互不隐式转换。
- 更贵的坑：**自举把 `decimal` 类型映射成 `double`**（`parser.zan`），AST 里
  `decimal` 目标与 `double` 目标分不出来。第一版按"能区分"实现，结果把
  `decimal d = 5.0m;`（合法程序）判成了错。
- 通用教训：**误报比漏报贵得多**——漏报只是放过一个该拒的程序，误报是拒绝一个
  该过的程序，误报还会让自举编不过自己的源码。当两侧**无法区分**时，宁可把两边
  都放过（记成台账缺口），也不要赌一边。
- 通用教训：**规则要照着"量出来的表"写**。判定表要先用矩阵探针量出来（宿主当
  规格），再照着实现；凭直觉写的规则集在第二版几乎必然要返工。
## 121. 取串路径有"汇合点"：同一个 bool 在四条路径上长得不一样

- 坑（2026-10-22 实测，A441）：同一个 bool 在四条路径上给出三种字符串——
  `Console.WriteLine(b)` -> "true"，`b.ToString()` -> "true"，
  `Convert.ToString(b)` -> "1"，`"x" + b` -> "x1"。
- 原因不是"忘了在某处加分支"，而是**每条取串路径各写各的**：宿主有四处
  （`Convert.ToString` 特判 / `emit_to_cstr_of` 拼接 / `WriteLine` / 插值），
  自举有两处（`ToCStr` / 标量 `ToString`）。
- 通用教训：**先找汇合点，再补分支**。宿主侧的汇合点是 `emit_to_cstr_u`
  （字符串拼接、可空值取串、`string.Format` 的参数全都经过它），自举侧是
  `ToCStr`——在汇合点加一条 bool 分支，四条路径一次对齐；以后新增的取串
  路径也会自动继承。在四个调用点各写一遍，是这种缺口反复出现的原因。
- 通用教训：**两个后端当前一致 ≠ 没问题**。这条里两个后端都输出 "1"，差分门是
  绿的，但两边都与 C# 语义不符——差分门只保证"两个后端一致"，语义缺口要另外
  对着标准（.NET 的 true/false）钉。
- 通用教训：**口径改了要回头看 golden**。旧的 `.out` 里可能把 "1"/"0" 固化了
  （这次是 `string_char_args.out` 的 `eq=0` / `ct=1`），改完必须重跑全量
  conformance，比对哪些 golden 需要跟着更新——别只盯自己新加的那个用例。

## 122. 整数字面量的类型看**进制**：`0xFFFFFFFF` 是 int（值 -1），`4294967295` 是 long

- 坑（2026-10-22 实测，A490）：自举按"值是否超出 int32"给字面量定型，
  十六进制字面量因此被判成 `long` → `int h0 = 0x67452301;` 这类**合法**程序被
  自举拒绝（`narrowing conversion from 'long' to 'int'`），而 packages 里的
  Sha1 / FocusManager / QrCode 全中招 → **整个 packages 编译不过**，
  一大批用例卡在 SELFHOST-REFUSED。
- 宿主是这么定的（`src/compiler/checker.c` 的 `AST_INT_LITERAL -> lit_radix`）：
  **无后缀的 2/8/16 进制字面量，只要值在 uint 范围内就是 `int`**，值取 int 域
  （`irgen_expr.c` 发射时截断成 int32：`0xFFFFFFFF` 是 **-1**）；同样的数值写成
  十进制则是 `long`（`4294967295` 超 int32）。所以 `int x = 0xFFFFFFFF;` 合法，
  `int x = 4294967295;` 是窄化错误——**同一个数值，两种写法，两个类型**。
- 做法：把**进制**也记进 AST（宿主有 `lit_radix`，自举把进制折进 suffix 字段：
  8 = 二进制、16 = 十六进制、24 = 八进制；类型后缀取 `suffix % 8`），定型
  （`IntLitTypeName`）与取值（`IntLitValue`）都按进制裁决。八进制也要折：
  `0o37777777777` = 4294967295 > int32max，不折就会被当成十进制 long 而误报。
- 通用教训：**字面量的类型不只看值，还看写法**。诊断里点的类型名（`'long'` vs
  `'int'`）、窄化判定、运行期值全都跟着写法变；只按值推断类型必然对不上。
- 连带的一条：**窄化规则要照抄整条判定链**，不能只抄"常量是否越界"。宿主
  `checker_check_assignable` 的顺序是：
  ① 浮点进整型槽 → 报；② 整型槽收整型值：先看**值类型的整个范围**能不能装进
  目标范围（int→int、int→long 直接过），**再**看常量本身；③ `nint` 只能进
  `long`/`nint`；④ `ulong` 槽收任何整数字面量。
  只实现 ② 的后半段，就会把 `int x = 0xFFFFFFFF;`（同类型、int 域）误判成越界。
- 通用教训：**"值类型的范围能装进目标"这条捷径在判定链的最前面**——它让"同类型
  赋值"永远不窄化。任何"拿常量值直接比目标范围"的实现，都会在同类型赋值上误报，
  而且误报的规模是"所有 packages"这种量级。
- 补一条：宿主对**超过 int64 的字面量**另有一条规则（`lexer_radix_int_value`）：
  `0xFFFFFFFFFFFFFFFF` 这种值装不进有符号 64 位，就把后缀提升成 **UL**
  （类型是 ulong，值是那个比特模式）；带 `L` 后缀则是错误
  （`integer literal is too large for 'long'`）。自举的词法器没有诊断通道，
  这两条改在**解析器**里报（位置仍是字面量自己的位置，措辞与宿主一致）。
- 又一条：宿主的判定表里有一条**专门的例外**——`-(0x8000000000000000)`（有符号
  64 位的最小值）落进有符号槽是合法的。没有它，`long mn = -0x8000000000000000;`
  会被自举误判成窄化错误。抄判定表时**连例外一起抄**。

## 123. 裸调用要先查**字段**再查方法：静态委托字段是合法的调用目标

- 坑（2026-10-22 实测，A491）：`static CloneTreeFn cloneTree;` 这种**静态委托
  字段**不带限定符直接调用（`cloneTree(root)`）时，自举把它当成方法调用，发出
  不存在的 `@App_cloneTree` 符号 → **链接失败**（不是编译失败，差分门里表现为
  "SELFHOST-BAD-IR"，容易误判成 IR 生成坏了）。
- 原因：裸调用路径只问"这个类里有没有同名方法"，没问"有没有同名字段"。宿主把
  裸名字先按**符号**解析，字段（尤其是委托字段）是合法的调用目标。
- 做法：裸调用路径里，方法没找到时再查静态字段，命中且字段类型是委托，就按
  委托调用发射。
- 通用教训：**名字解析的顺序必须和宿主一致**。宿主"字段优先、委托可调用"这类
  规则，自举往往只实现了"方法"那一半；补的时候要按宿主顺序补，别自己发明顺序。
- 通用教训：**链接失败要往符号名上想**。`@App_cloneTree` 这种"看起来该存在"的
  符号，缺的是**解析规则**而不是发射代码——先查这个名字是谁该发出来的。

## 124. 宿主的 `int` 是 32 位、自举的 `int` 是 64 位：位运算的结果要按 int 域回读

- 坑（2026-10-22 实测，A492）：`BitOperations.RotateRight(0x12345678, 4)` 在宿主里
  是 **-2128007553**（宿主在 i32 上转，返回的是 i32），自举却给 2166959747
  （自举在 i64 上转，`zext` 回来）。这个差异平时被"字面量也按 long 算"掩盖着：
  字面量 `0x81234567` 在自举里是 long（正数），两边碰巧相等；一旦字面量按宿主
  的规则定型成 int（int 域的负数），这个被掩盖的差异就露出来了。
- 做法：32 位路径的结果**用 `sext` 回 i64**（`zext` → `sext`）。宿主里凡是 i32
  上算出来的值，回到 64 位槽都是符号扩展的。
- 通用教训：**自举的值模型比宿主宽**（int 是 i64、float 是 double），凡是宿主在
  窄类型上算出来的结果，自举要**显式回到那个窄类型的域**再比较/打印。忘了这一步，
  差异会被"两边的字面量恰好一样错"掩盖，直到别处改了字面量的定型才暴露。
- 通用教训：**改一个"看起来无关"的规则（字面量定型）会掀出别的差异**。差异一直
  在，只是被巧合遮住；修好一处就要重跑受影响的用例，别只看新用例。

## 125. 显式窄转换要按宿主的宽度截断：byte / short / int 各有各的域

- 坑（2026-10-22 实测，A493）：自举只实现了 uint / ushort / sbyte 三个窄转换，
  `(byte)x` 与 `(short)x` 原样透传 → `unsigned_widths` 的 `(byte)4886718345`
  打印成 4886718345（宿主是 137）、`(short)70000` 打印成 70000（宿主是 4464）。
- 宿主的口径（`src/compiler/irgen_expr.c` 的 `emit_expr_cast_expr`）：先把值
  截到目标类型的宽度，再按目标的符号性回读——byte / uint / ushort **零扩展**，
  sbyte / short / int **符号扩展**，char / long / ulong 保持 64 位不动
  （宿主里 char 是 i64、int 是 i32，所以 `(char)x` 不截断、`(int)x` 截 32 位）。
- 做法：自举的 int 是 i64，于是 `(int)x` 要 `shl 32 / ashr 32`（截 32 位再符号
  扩展）、`(short)x` 是 `shl 48 / ashr 48`、`(byte)x` 是 `and 255`。
- 通用教训：**显式转换的目标宽度就是语义的一部分**。"自举的槽都是 i64" 不能成为
  跳过截断的理由——那会让每个窄转换都返回一个错的值，而且错得毫无规律。

## 126. 原始类型的常量是编译期常量：int.MaxValue / double.NaN / float.Epsilon

- 坑（2026-10-22 实测，A494）：`int.MaxValue`、`uint.MaxValue`、
  `double.PositiveInfinity`、`float.Epsilon` 这些**原始类型的常量**在自举里
  根本编不过（"'int' is a built-in type and cannot be used as a value"），
  于是 `primitive_constants` 整个用例失败，**连标准库都编不过**
  （`stdlib/System/Numerics/MathUtil.zan` 用了 `double.NegativeInfinity`）。
- 宿主把它们折成编译期常量（`irgen_expr.c` 的那张表），程序里的
  `int.MaxValue` 就是个字面量。
- 做法：在成员访问这一层先判"对象是一个原始类型名 + 成员是常量名"，直接给
  常量，**不要去求值那个类型名**（自举原来把类型名当值去求，才报"不能当值用"）。
- 通用教训：**内建类型的成员是常量，不是运行时查找**。常量要在**访问点**截住。
- 通用教训：**一个内建缺失不只是少一个用例**——标准库会用到它，编译期阻塞的
  扩散面比用例大得多（`double.PositiveInfinity` 一个常量就让 math_numerics
  整个用例编不过）。

## 127. 枚举成员的值要按声明顺序折叠：连续规则 + 可以引用早期成员

- 坑（2026-10-22 实测，A495）：自举只认"整数字面量"的枚举成员值，
  `enum Color { Red = -5, Green, Blue = Red + 10 }` 变成 0/1/2（宿主的
  -5 / -4 / 5）。负号、二元表达式、对早期成员的引用，全都不认。
- 宿主的口径（`src/compiler/binder.c` 的 `fold_enum_member_value` +
  `irgen_expr.c` 的枚举成员发射）：成员**按声明顺序**绑定，每个值表达式折叠成
  常量；值可以是字面量、一元 +/-、二元 + - * / & |，或者**引用一个已经折叠过
  的早期成员**（所以 `Blue = Red + 10` = 5）。没有显式值的成员**接着上一个
  继续**（+1），所以 `Green` = -4 而不是 1。发射时值按 32 位**零扩展**。
- 做法：按顺序折叠，前面折好的值放进一张表，标识符只查这张表（后来的成员查
  不到 → 折叠失败 → 报宿主那句 "enum member 'X' initializer must be an
  integer constant expression"）。
- 通用教训：**"顺序敏感"的常量折叠不能只实现最简单的那一支**。序数、连续、
  引用、算术——四种形状都在宿主的折叠表里，抄的时候要连"引用只能指向更早的
  成员"这个方向限制一起抄。
- 通用教训：**枚举成员的值有两个域**：折叠时是有符号 64 位，发射时是 32 位零
  扩展。两个域分开看，`(int)Color.Red` 这类转换才不会算错。

## 128. "能转成字符串"不是白名单：`Convert.ToString` 按**类型种类**拒绝引用类型

- 坑（2026-10-22 实测，A442）：自举侧 `Convert.ToString(<类实例>)` 吐出对象的
  **指针地址**（"140737488xxxx"），宿主侧已经 fail-closed 报
  `cannot convert 'Box' to a string -- call .ToString() on the value instead`。
  同一个源文件，两个后端一个报错、一个输出地址——地址本身也是信息泄露。
- 根因：自举的取串只有"字符串"和"数值"两条路，其余一律落进
  `snprintf("%lld", ptr)`；宿主那边有一张**按类型种类**划的白名单（文本/数值/
  枚举/object/类型参数放行，类/结构体/委托/数组拒绝）。
- 做法：照抄那张白名单，诊断**逐字**照抄（破折号和句点都算），位置指向
  **实参**而不是调用点；数组的名字是**元素**名 + `[]`，不是数组自己的名字。
- 坑：自举的 binder 把**委托**放在 `delegates` 而不是 `types` 里——查类型表
  查不到委托，会漏判。"类型表里查不到就放行"的兜底在这条边界上是错的。
- 通用教训：**"查不到就放行"的兜底在 fail-closed 边界上是反模式**——它把
  "我不知道这是什么类型"变成"那它应该没问题"。两边都判不了时，宁可一起拒绝。
- 通用教训：**两个后端的诊断要逐字对齐，还要对齐位置**（这条指向实参）。
  措辞差一个字，比对就分不出"同一个意思"。

## 129. 枚举的 ToString / TryParse：值→名字的反查按声明顺序，比对用**有符号**折叠值

- 坑（2026-10-22 实测）：自举的 LLVM IR 后端没有枚举的 ToString 和 TryParse——
  `Color.Green.ToString()` 打成数字 10，`Color.TryParse("Blue", out c)` 发出一个
  没人定义的 `@Color_TryParse`，clang 报 "use of undefined value"。
- 宿主的口径（`src/compiler/irgen_call.c`）：
  - ToString：按**声明顺序**依次比对，命中第一个值相等的成员就返回它的名字；
    都不命中就把值按十进制打出来（所以两个成员同值时回答**先声明**的那个）。
  - TryParse：拿文本和成员名字逐个 strcmp（**大小写敏感**），命中就把该成员的
    折叠值写进 out 槽并返回 1，不命中写 0 并返回 0；数字文本（"10"）不命中。
- 关键：**比对用的是有符号的折叠值，成员常量却是 32 位零扩展**。宿主的成员常量
  发成 `(uint64)(uint32)v`，而 ToString 的比对、TryParse 的写回用的是折叠出来的
  int64 值。于是 `enum E { Neg = -5 }`：`E.Neg` 打印 4294967291（常量零扩展，
  比对不上 -5），而 `TryParse("Neg", out c)` 得到的 c 是 -5，`c.ToString()` 回答
  "Neg"（值对上了）。**同一个成员，两条路两个域。**
- 做法：折叠拆成两个域——折叠域（有符号 64 位，比对与写回用）和发射域
  （32 位零扩展，常量用）；ToString 用 select 链**从后往前**建（先声明的成员在
  最外层，于是先声明的赢）；TryParse 同样用 select 链，命中写成员值、不命中写 0。
- 坑：枚举的折叠值在"每次成员访问"时都会重算一遍，诊断也会重复报——宿主在
  bind 阶段只报一次。自举按"成员节点"记住已报过的，重算不再重报。
- 通用教训：**同一个语义量在不同路径上可能活在不同的域里**——常量发射、运行时
  比对、out 参数写回各用各的。照抄宿主要**按路径分别抄**，别用一套值糊过去。
- 通用教训：**自举后端缺一个内建，报错常常出现在链接期**（"use of undefined
  value '@X'"）而不是编译期——这类 undefined value 就是"缺内建"的信号。

## 130. 委托交给原生回调：静态方法组就是**函数指针本身**，不是闭包

- 坑（2026-10-22 实测）：自举把静态方法组包成"闭包 + 带 env 的 thunk"，交给
  extern 时又把闭包里的 fn 字段取出来传过去 → 原生侧按 C 签名调用时**参数整体
  错位一格**（thunk 的第一个形参是 env）：`EnumWindows` 的回调拿到的 hwnd 其实
  是 lParam（恒为 0），窗口标题永远读不出来，而回调本身"跑得好好的"（计数在涨）。
- 宿主的模型（`src/compiler/irgen_expr.c`）：**静态方法引用当委托值时，委托值就
  是那个函数指针本身**（没有闭包记录）。委托值有两种形态，用 tag 位区分：bit0=0
  是"裸函数指针"（按声明形参直接调用），bit0=1 是堆闭包（调用时多传一个记录地
  址）。静态方法组走"裸"这一支——所以它能直接当原生回调用。
- 做法：自举的静态方法组改成直接给**裸函数指针**（bit0=0），带 env 的 thunk 只
  留给实例方法组和 lambda；extern 的委托形参**原样传委托值**（宿主也是原样传），
  不再拆闭包取 fn。
- 坑：委托值在自举里是 i8*，取函数指针要 `bitcast <fnty>* @Target to i8*`——漏了
  "@" 报 "expected value token"，而写成 `bitcast (<fnty>* @T to i8*)`（多一层括
  号）报 "expected type"：函数指针类型只有作**常量表达式**出现时才允许带那层
  括号，作指令的源类型时不能加。
- 通用教训：**闭包 ABI 与 C ABI 不兼容**——闭包把 env 放在第一个形参，原生回调
  按 C ABI 调用就会整体错位。凡是"Zan 委托交给 C 当回调"，交给 C 的必须是**裸函
  数指针**，不是闭包。
- 通用教训：**参数错位是最难查的一类差异**：回调"跑起来了"、计数在涨、没有任何
  报错，只有拿到的值不对（hwnd 变成 0）。看到"回调跑通但参数是 0"，先怀疑 ABI
  错位，别怀疑 Win32。

## 131. 改了**全局**渲染口径，要回头扫全部 golden——差分门只覆盖 92 个用例

- 坑（A441 的余账，2026-10-22 实测）：A441 把宿主的 bool→字符串统一成
  "true"/"false"，我只改了 `tests/conformance/string_char_args.out` 一个
  golden，还写下"现有 golden 里没有把 bool 的 1 固化的用例"。**这条结论是
  错的**：当时只查了 `Convert.ToString` 的 230 处调用，漏了别的取串路径
  （`+` 拼接、插值、`Console.WriteLine(bool)`、`Cpu.Has*` 属性、比较表达式），
  实际有 123 个 golden 把 bool 记成了 "1"/"0"——宿主改了、golden 没改，
  conformance 与差分门一起红。
- 坑的形状：**差分门（92 个用例）只是 conformance（600+）的子集**。"我跑了
  差分门是绿的"不等于"仓库是绿的"；那一轮我只跑了差分门的**子集**（14/14），
  把"子集绿"当成了"全绿"。
- 做法：改全局口径不能靠"顺手改一两个 golden"，要按规则**扫全量**：跑宿主拿
  stdout 与 golden 比，只有当差异**恰好**是 0↔false / 1↔true 的替换时才判定
  为过期并重写；其它差异一律不碰（可能是别人的在途改动）。判据要窄——宽了
  就把别人的行为 bless 掉了。
- 通用教训：**"两个后端一致"和"两边都对"是两件事**；golden 是宿主的快照，
  宿主改了快照就得跟着改，而快照有几百份。
- 通用教训：台账里写下的**验证结论**也要能被复查；写"我查过了，没有"的时候，
  要写下**查的范围**（哪些路径、哪个清单），否则下一个人无法判断它可不可信。

## 132. 整数的运算宽度：变量按声明宽度，字面量是 i64——除零与 MIN/-1 走软失败

- 坑（2026-10-22 实测）：自举把所有整数都当 i64，于是
  - `int a = 2000000000; a + a` 打出 4000000000（宿主是 -294967296）；
  - `int.MinValue / -1` 打出 2147483648（宿主是 -2147483648）；
  - `10 / 0` 直接 SIGFPE 挂掉（宿主报一声 "division by zero" 后继续，x/0 给 x）。
- 宿主的宽度规则（`src/compiler/irgen_expr.c` 与它的 IR）：
  - **int 变量是 i32**（局部、字段、强制转换的结果都是），**int 字面量是 i64**
    （`AST_INT_LITERAL` 发的是 `LLVMConstInt(i64, ...)`）；宿主**不做整数提升**，
    窄类型就按自己的宽度算（byte i8 / short i16 / int i32 / long i64）。
  - 运算取两个操作数的公共宽度：有一个字面量参与 → 整体升到 i64；两个 int 变量
    → i32（**在 32 位上回绕**）。于是 `a * 3` 不回绕、`a * b` 回绕。
  - 常量表达式（`2+3`）折出来也是 i64。
- 除法的软失败护栏（`irgen_expr.c` 的 `TK_SLASH` / `TK_PERCENT`）：
  - 除数为 0 → 报 "division by zero"（**stderr**，`file:line:col: runtime error:`）
    然后**改除以 1** 继续（x/0 → x，x%0 → 0）；
  - 被除数是该宽度的 MIN 且除数是 -1 → 同样改除以 1（MIN/-1 饱和到 MIN，
    MIN%-1 → 0），避开硬件 #DE。
- 做法：自举的算术按"操作数宽度"回绕（int → `shl 32` / `ashr 32`，无符号 → and
  掩码），除法/取模前面加护栏（select 选 1），零除走 `zan_rt_guard_fail3` 报告
  （与宿主同一个运行时函数）。
- 坑：自举的 parser **不给二元表达式记位置**（诊断只能报到 0:0）——宿主记的是
  **运算符**的位置。给二元节点补上运算符的行列，护栏的报告位置才和宿主一致。
- 通用教训：**"两边都是 64 位"是自举的实现细节，不是语言的语义**。语义是"变量
  按声明宽度、字面量按 64 位"，抄宽度规则要把"字面量这个例外"一起抄。
- 通用教训：**软失败契约（报一声 + 给兜底值 + 继续跑）是语义的一部分**：宿主除零
  不是崩溃，自举直接 SIGFPE 就差了一整条契约——而且差的是"程序还活着"这件事。

## 133. 算术结果的"位宽"和它的"类型"是两回事——`(long)x << 24` 的结果宽度是 64

- 坑（2026-10-22 实测）：自举把每个算术结果的**类型**一律标成 `int`（32 位），
  于是
  - `((long)b) << 24` 的结果宽度被当成 32 位，外层 `|` 按 32 位回绕，32 位 CRC
    被**符号扩展**成负数（`0x9F02E328` 读成 -1627200728）；
  - 端到端症状是"WAL 写完重开读回来全错"：CRC 校验不过 → 重放认为尾部撕裂 →
    把日志截断 → 键值全丢。差的只是**一次移位结果的位宽**。
- 宿主的口径（`src/compiler/irgen_expr.c` 的 `coerce_int_pair` / `emit_binary_op_values`）：
  - 运算的**位宽**取两个操作数 LLVM 类型的公共宽度（字面量是 i64 → 整体 i64）；
  - **运算结果保留那个位宽**：`int a; a * 3` 的类型是 `int`，但值是按 i64 算出来的；
  - 类型系统的类型（`int`/`long`）与 LLVM 的位宽是**两套东西**，不能互相顶替。
- 做法：给 `ExprVal` 加一个 `wbits`（值的载体位宽，0 = 从类型推），算术结果把
  运算位宽写进去；父运算看 `wbits` 而不是类型。一元 `-`/`~`/`++`/`--` 同样按
  操作数的位宽回绕（宿主在 int 位宽上算 `++x` 就会回绕）。
- 通用教训：**类型 ≠ 位宽**。凡是"运算结果的类型由宿主决定"的场合，位宽都要
  单独跟踪——把类型当位宽用，实现再"一致"也会在某次运算后被截断。
- 通用教训：**端到端症状离病因很远**：文件读回错 → 根因是一个移位结果的 32 位
  回绕。定位要先做**二分探针**（逐帧打印 plen / 存的 crc / 算出的 crc），把
  "文件 API 有问题"这类猜测挡在门外；第一版探针查了 fwrite/fread、Span、PageFile
  全部正常，第三版探针才落到"读出来的数是负的"。
- 通用教训：**同一段表达式的每个子表达式的位宽都要独立确认**——`(long)x` 是 64 位
  不代表 `<< 24` 的结果还是 64 位，前提是父运算也读同一个"位宽"来源。

## 134. `float` 是 f32：自举的 float 边界要过一次单精度往返

- 坑（2026-10-22 实测）：自举把所有浮点当 double，于是
  - `float e = 0.2f; e + 0.1 == 0.30000000298023224432` 打成 false（宿主 true）；
  - `0.2 == 0.2f` 打成 true（宿主 false）；
  - 向量检索的余弦/L2 断言全线对不上（宿主用 f32 算距离，自举用 f64）。
- 宿主口径（`src/compiler/irgen_expr.c` + LLVM IR）：`float` 是 **f32**，
  - f/F 字面量按单精度取值（`0.2f` = 0.20000000298023224）；
  - 浮点运算在 f32 里做（`0.1f + 0.2f` = 0.30000001192092896）；
  - 打印时把 f32 拓宽成 double 再按 double 的格式输出（`0.1f` 打成
    "0.10000000149011612"，不是 "0.1"）；
  - **LLVM 的 IR 里 float 常量必须恰好可表示**：`float 0.1` 会被 LLVM 拒
    ("floating point constant invalid for type")，宿主因此发的是十六进制位型
    `float 0x3FB99999A0000000`。
- 做法（与原生后端 ngen 的 `NarrowF32` 同一模型）：自举的值仍放在 double 槽位里，
  但**凡是 float 的语义边界都过一次 double→float→double 往返**：
  - f/F 字面量、`(float)` 强制转换；
  - float 类型的运算结果（两个 float、或 float 与整型 → 结果是 float；
    出现 double 就整体升到 double）；
  - float 的槽位：局部、字段、参数、返回值、数组元素、静态字段初值。
  - 字面量用 `fptrunc double 0.1 to float` + `fpext` 取单精度——**不能**直接写
    `float 0.1`（LLVM 拒），也别指望 `fpext float 0.1` 能过。
- 通用教训：**"能跑"不等于"同一个数"**。f32 与 f64 的差别不在量级，在**尾数
  位数**；任何把浮点统一成一种精度的实现，都会在"打印/比较/哈希/距离"这些
  地方整体偏掉。
- 通用教训：**精度边界要照抄宿主的"类型系统"，不是照抄"存储"**：宿主是
  "float 这个类型 = f32"，自举是"float 这个类型 = double 槽位 + 单精度往返"，
  两边对**同一个表达式的值**必须一致。
- 通用教训：**同一个类型有多处"入口"时，抄一处不算抄**：字面量、强制转换、
  运算结果、槽位写入、数组元素、静态初值——少一处就会出现"某个赋值路径上的
  精度不一样"的鬼故事。
## 135. lambda 的临时表是它自己的——别让 `%tN` 泄漏到调用方

- 坑（2026-10-22 实测）：自举编出的委托抛异常程序访问冲突（0xC0000005）。
  症状像"委托/异常对象被提前释放"，但根因在**临时变量表的作用域**：
  - `GenLambda` 生成语句体时**没有重置** `stmtTemps`/`stmtTempTypes`；
  - lambda 里的 `%t4`（异常对象）因此留在**调用方**的临时表里；
  - 调用方随后把这个 `%t4` 当成自己的临时量 `zrelease`——而它其实是闭包的
    **函数指针**，不是对象 → 访问冲突。
- 做法：`GenLambda` 的语句体分支在 `GenStmt(lam.d)` 之前重置
  `stmtTemps`/`stmtTempTypes`（lambda 有自己的临时表），并在 lambda 末尾
  `EmitTempReleases()`（lambda 自己的临时量由 lambda 释放）。
- 验证：p_thr1 / p_thr2 / p_thr 三个委托抛异常探针与宿主**逐字一致**
  （修复前 p_thr1 直接崩溃）；差分门 114 passed / 0 gaps / 27 rejected /
  10 failures（与修复前同档，正式 92 例零回归）。
- 通用教训：**寄存器名是按计数器分配的，计数器的作用域必须和代码块一致**。
  内联/闭包/嵌套函数一旦共用计数器，名字就会撞；撞名的后果取决于"谁负责
  release 这个临时量"，于是表现为远处的释放崩溃，而不是生成期的名字冲突。
- 通用教训：**生成器里的"当前临时表"是隐式状态**：每进入一个独立的作用域
  （lambda 体、委托体、嵌套块）就要成对地保存-重置-恢复，不能只靠"我记得
  这里要重置"。
## 136. 协程的异常：异常不跨帧，处理器要重新武装

- 坑（2026-10-22 实测）：`try { await X(); } catch (E e) { }` 在自举里
  直接崩（退出码 0xC0000028），宿主正常输出 "caught boom / done"。
  这一个症状底下叠了**五个**独立的缺陷，逐个拆：
  1. **longjmp 打进已返回的 invocation**：try 的 setjmp 装在挂起前那次
     调用上，那次调用早已返回，栈是死的。宿主不这么干：它在**每次 resume
     入口**重新武装处理器（`src/compiler/irgen_async.c` 的
     `emit_async_eh_prologue`），挂起时把 EH 深度还原（`emit_async_eh_unarm`），
     于是 longjmp 落点永远在当前还活着的帧里。
  2. **异常不能跨帧**：协程自己没有处理者时，把异常放进**帧**里（宿主：
     `ASYNC_FRAME_EXC`），awaiter 恢复时在自己的上下文里**重抛**。自举原来
     让异常一路 longjmp 穿过挂起的帧 → 必死。
  3. **`_setjmp` 声明缺 `returns_twice`**：longjmp 回来后，跨 setjmp 存活的
     SSA 值在 caller-saved 寄存器里就是垃圾。宿主给 `_setjmp` 挂了
     `returns_twice`（`irgen_builtins.c: add_enum_attr`），自举没挂。
  4. **catch 路径不能从帧里 reload 局部变量**：挂起点之后赋的新值只在栈上，
     帧里是旧副本；reload 会把新值覆盖掉（探针里 `tag = "t"` 变空）。
     宿主没有这个问题，因为它的 async 局部变量**就住在帧里**
     （`emit_async_finalize_slots` 把 alloca 换成帧槽地址）。
  5. **async 方法的 `return` 不跑 finally**：`try { return X; } finally { Y; }`
     在 async 里 Y 从不执行 → 锁没释放 → 下一个 await 永远等不到 →
     调度器空转退出（表现为"输出到一半就没了"，退出码还是 0）。
     非 async 的 return 路径有 `EmitExitFins(0)`，async 的 `GenAsyncReturn`
     漏了。
- 做法（自举侧）：
  - 帧头加两个槽：11=exc_val、12=exc_tid（异常带着走）。
  - resume 入口装**蹦床**处理器（协程的最后一道防线）：异常从蹦床落地时
    写进帧、释放帧持有的引用、唤醒 awaiter。
  - 每个挂起点：还原 EH 深度到本次 resume 的起点（蹦床也随之失效）。
  - 每个恢复点：把**词法上包围该点**的 try 处理器**重新武装**（外层在前，
    内层在栈顶），恢复点因此 longjmp 得到的是当前帧里的活蹦床。
  - await 恢复后检查被等待帧的 exc 槽，非空就在 awaiter 自己的上下文重抛。
  - `_setjmp` 声明加 `#0` + `attributes #0 = { returns_twice }`。
  - async 的 `return` 补上 `EmitExitFins(0)`。
- 验证：p_ae（跨协程）/ p_ae2（同协程、嵌套 try、finally、逃逸异常）两个
  探针与宿主**逐字一致**；`async_generic_method`、`zandb_async_errors`、
  `async_struct_return` 三个用例过门。
- 通用教训：**"异常传播"是三件事**：异常对象去哪、处理器在哪、跳转落点是否
  还活着。少做一件就表现为"随机崩溃"，而不是"catch 没接住"。
- 通用教训：**挂起会杀死调用帧**。任何"在帧上装了状态"的东西（setjmp、
  栈上的局部、锁）都要问一句：帧回来时它还在吗？宿主用"帧住在堆上 + 每次
  resume 重新武装"回答；自举照抄了这个答案。
- 通用教训：**finally 是语义的一部分，不是善后**。漏跑 finally 的表现往往
  不是"少做一件事"，而是"后面某处永远等不到"——症状离病因十万八千里。
  定位这类问题要先怀疑"资源没释放"，再去查释放点。
## 137. 弱引用：弱槽要登记，目标死了要清槽

- 坑（2026-10-22 实测）：`public weak Node up;` 在自举里只是"一个不 retain
  的普通指针"——目标死了以后，槽里还留着野指针：读出来不是 null（宿主读出
  null），继续用就是把已释放的内存当对象。
- 宿主的模型（`src/compiler/irgen_weak.c` + `src/compiler/irgen_arc.c`）：
  - 弱字段是一个**槽**（`void**`）：写进去要走 `zan_rt_weak_store(slot, obj)`，
    它把 (槽 → 目标) 登记进一张 8192 桶的哈希表；
  - 目标死亡时（计数 1→0）先走 `zan_rt_weak_destroy_begin(obj)`：把所有
    指向它的槽清成 null，再回读计数——不是 0 就说明有人在这期间重新强引用
    了，放弃销毁；
  - 持有者自己死的时候，它那几个弱槽要**注销**
    （`zan_rt_weak_store(slot, null)`），否则注册表里留着一个指向已释放
    内存的槽地址；
  - 弱读（`zan_rt_weak_load_retain`）返回的是**加了 1 的强引用**。自举的
    约定不同（生产者不拥有、消费者 retain 时才加 1），所以自举的弱读是
    **普通读**，净效果一样。
- 做法（自举侧）：新增 `src/selfhost/irgen/irgen_weak.zan`，发射一张注册表
  （单链表 + 自旋锁，节点 { next, target, slot }）：
  - 槽统一按 **i64 单元**处理：具体类的指针字段 bitcast 成 `i64*`，擦除后
    的泛型字段（`weak T _target`）本来就是 i64 —— 一套 API 覆盖两种形状；
  - `zan_rt_weak_store(slot, val)`：注销该槽的旧登记 → 写值 → 登记新的；
  - `zan_weak_nil_all_locked(target)`：把所有指向该目标的槽清成 null；
  - `zan_rt_weak_destroy_begin(target)`：清槽 + 回读计数，返回"可以死"；
  - `zrelease` 照抄宿主的口径：**只有计数 1→0 才析构 + 释放**；计数已经
    是 0 或负数 = 超额释放，只把计数再减一，**不再释放第二次**（自举原来
    `nc <= 0` 就 free → 双重释放 → 0xC0000374 堆损坏）；
  - 类析构器里，弱字段要注销自己的槽；
  - 字段写入（`StoreField`）走弱槽登记；弱读是普通读。
- 验证：`weak_field_lifecycle`、`weak_reference_generic` 两个用例与宿主
  **逐字一致**（修复前一个读到野指针、一个 0xC0000374 直接崩）。
- 通用教训：**"弱"不是一个类型修饰，是一个协议**：写进去要登记、读出来不
  拥有、目标死时要清槽、持有者死时要注销。少做一条，表现就是"读到野指针"
  或"释放两次"。
- 通用教训：**引用计数的判断要看"释放前"的计数**。`nc <= 0` 与
  `rc_old == 1` 的差别不是风格问题：前者把"超额释放"当成"最后一次释放"，
  于是同一个对象被 free 两次——症状是堆损坏，离病因很远。
- 通用教训：**同一个后端里"谁拥有一个值"的约定必须前后一致**。宿主是
  "弱读 +1、存进槽不再 retain"，自举是"读不 retain、存进槽才 retain"；
  两套约定混用就会多一次或少一次 retain，表现为对象死活与预期不同。

## 138. 数值转换的守卫：判据要**分两套**，守卫要落在**分派入口**

- 坑（2026-10-22 实测）：自举的 `ToDbl` 对任何非 double 实参一律
  `sitofp i64 <v> to double`——类实例是**指针**，造出 `sitofp i64 i8*`，
  LLVM 校验失败（非法 IR）；`Convert.ToInt32/ToInt` 更狠，无条件
  `call i64 @atoi(i8* <a.op>)`，把**对象指针**当 C 字符串读，静默得到 0。
  宿主侧早已 fail-closed 报人话诊断，两边同款缺陷。
- 关键：**宿主的两个转换入口判的不是同一件事**，照抄时不能混成一张表：
  - `Math.*` 判的是**降级后的值类型**（`math_arg_is_numeric`：整数/浮点算
    数值，字符串/类实例/数组/委托都是指针 → 不算）；
  - `Convert.ToInt32/ToInt64/ToInt/ToDouble` 判的是**静态类型白名单**
    （`type_is_textual_or_numeric`：文本/数值/枚举/`object`/类型参数放行，
    类/结构体/数组/委托拒绝）。
  自举侧只有静态类型，于是 `Math.*` 那套要**按"降级后是什么"重写一张表**
  （可空→struct、数组/字符串/`object`→指针、`decimal`→struct），不能直接
  复用 `Convert.*` 的白名单——`object` 在 `Convert.*` 放行、在 `Math.*` 拒绝。
- 做法：守卫落在**分派入口**（`ToDbl` 与 `Convert.*` 的分派处），不要在
  `GenMathCall` 的每个分支各判一次；诊断**逐字**照抄宿主
  （`Math.<名> requires an int or floating-point argument`、
  `Convert.<名>: cannot convert '<T>' to a number -- pass a string or a
  numeric value`），位置指向**调用点**。
- 坑：枚举走 i64 槽，转换语义与整数相同——按"是不是类/结构体"判会把枚举
  误拒（宿主放行，`Color.Green` → 1）。
- 坑：可空值在 `Convert.*` 路径上宿主给 0（整型路径），自举也必须给 0；
  `ToDouble` 路径宿主会读装箱单元给出垃圾值（实测 2.12e-314），自举给 0.0
  即可——真装箱语义归 A454，别在这条路上"对齐"到宿主的垃圾值。
- 通用教训：**判据不同的两个入口，白名单不能共用一张表**。共用会同时错两次：
  放行了不该放行的，又拒掉了不该拒的。判据先分清，守卫再落。
- 通用教训：**"两边都错"要分清谁对谁错**：宿主把 `bool` 当**有符号**整数
  用（i1 符号扩展），`Math.Sqrt(true)` = NaN、`Convert.ToInt32(true)` = -1；
  自举给 1.0 / 1 才是对的。这种分叉**不要照抄宿主**——照抄会把一个宿主缺陷
  复制成两份，该另立条目在宿主侧修。

## 139. 矩形数组：形状（秩）必须跟着**类型**走，不是跟着创建点走

- 坑（2026-10-22 实测）：自举的 IR 后端把 `int[,]` 当成普通 `int[]`。
  解析器收下了 `[,]`，却只记了"逗号总数"；码生成完全不知道有几维——
  `new int[2,3]` 的额外维度被当成初始化项，`m[1,2]` 只用第一个下标，
  生成的 IR 甚至不合法（把指针存进 i64 槽，clang 当场拒）。
- 关键：**形状是类型的一部分**。宿主把矩形数组建模成"嵌套类型 + 每层
  array_rank"（`int[,]` 是**一个** rank 2 的类型，`int[][,]` 是 `int[,]`
  的数组）；自举原来的扁平模型（`ival` = 层数）表达不了这个，于是给
  类型加了一张**秩列表**（`sval2`："2" = `int[,]`、"1,2" = `int[][,]`，
  外层到内层），索引一次掉一层（`ArrRankDrop`）——元素的类型因此还带着
  内层的形状。
- 做法：**扩展既有布局时，先保住已经在用的那个偏移**。自举 IR 后端的
  数组头是 `[长度][元素]`，长度在 `arr-8`；矩形数组扩成
  `[dim0]...[dim(r-1)][长度][元素]`——长度仍是元素前最后一个字，
  `arr.Length` 一行都不用改，维度 d 在它前面 (r+1-d) 个字。
- 做法：把下标折叠成行主序平铺偏移时，**维度要从数组自己里读**（存在
  头部），不能靠编译期常量——否则 `int[][,]` 这种"锯齿套矩形"在第二层
  就断了。
- 坑：宿主的数组初始化器把嵌套花括号**摊平**：`new int[2,2] { {1,2},{3,4} }`
  是 4 个行主序元素（不是 2 个子数组）。自举照抄即可。
- 通用教训：**"多一个维度"不是"多一个下标"**：形状一旦进了类型系统，
  类型上就必须有"取元素、掉一层形状"这个操作，否则索引处无从知道该折
  几个维度、该读第几个维度。

- 反射元数据从结构化类型读取泛型实参和立即元素。按宿主顺序从内向外显示数组秩，
  保留方括号内的逗号。`reflect_typed_list` 验证不同秩的闭合 List 身份、
  `is` / `as`、`GetTypeArg` 和 `ElementType`。

## 140. 差分门的链接集必须覆盖自举 IR 引用的**全部**硬件助手

- 坑（2026-10-22 实测）：自举为任何 `using System;` 的程序发射整个
  Convert 类，于是 IR 里出现了 `zan_hw_base64_encode` 等 `zan_hw_*` 助手。
  共享构建把 crypto 从 `rt_timer.c` 拆成独立 TU 之后，差分门自己的
  shd 对象集（rt_file/rt_io/rt_sched/rt_timer/rt_decimal/rt_sync/
  zan_embed_api）里就没有这些符号了——**门全线 LNK2019**，一个用例也
  跑不了（不是用例失败，是链接失败，看起来像"自举全崩了"）。
- 通用教训：**门的链接集是门的一部分**：改了运行时的 TU 划分，就必须
  同步门的链接集（或者在门里补一份对应 TU 的对象）。链接失败和用例失败
  要分得清——前者先修链接，再看用例。
- 坑：MSVC 编出来的那份对象带着静态 CRT 的 `___chkstk_ms`，进不了门
  的 clang 链接行；门的 TU 要用 `SELFHOST_CLANG` 编一份同源的。

## 141. 条件表达式的类型：是两支**合并**出来的，不是"第一支"或"第二支"

- 坑（2026-10-22 实测）：自举 checker 的 `InferType` 没有 `AK.Conditional()`
  分支 → 条件表达式的类型恒为**未知**（null）。而周围的兜底分支会把"未知"
  解释成**左操作数的类型**：二元运算里 `rt` 是 null 时整式按 `lt` 定型 →
  `int + (c ? "#s" : "#g")` 被定成 `int`，自举编译器拒收自举源码自己
  （"cannot convert 'int' to 'string' in initializer"），固定点门在
  **gen1 → g2.ll** 这一步就断。宿主（`merge_conditional_types`）正确合并两支，
  接受同一段代码。
- 合并规则要**照宿主的顺序**实现：null → 取另一支；类型参数 → 取它那一侧；
  同形（同名 + 同类型实参 + 同可空标志 + 同数组秩）→ 取该形；两支都是数值 →
  按提升阶梯取宽的（double > float > ulong > long > int）；两支都是引用型 →
  取共同基类（沿基类链找，取不到就是**没有**共同类型）；任一支是枚举 → 取
  枚举那一侧；其余 → **没有共同类型**。
  宿主还多两条自举表达不了的：**可空臂不参与数值提升**（提升的是值种类，可空
  是另一种型）；**decimal 混 float/double 是错误**（自举把 decimal 映射成
  double，判不出来）。
- 关键取舍：**自举侧宁可"判不出"也不误拒**。粗粒度类型模型里判不出共同类型
  时，返回**未知类型**（null）而不产生诊断——误拒宿主接受的程序会打断"自举
  编译自举源码"这条自指链，代价远大于漏报一条诊断。同理，自举**不照抄**宿主
  那句 "cannot apply '?:' operator to operands of type 'X' and 'Y'"：自举说不出
  宿主那两个操作数的准确类型名，硬凑出来的诊断只会误导人。这条差异显式登记在
  台账与差分门的 known-gaps 里。
- 判据（怎么找这类坑）：**报错说的那个类型是"猜"出来的**就是线索——左操作数、
  目标槽、第一分支是三个常见的猜测来源。顺着猜出来的类型往回找，落在"根本没
  定型"的那段表达式上。
- 关联：§131（改了全局渲染口径要回头扫 golden）、§140（门的链接集）。

## 142. 浮点 `!=` 是**无序**比较：有序比较会把 NaN 判成"相等"，有限性检查静默失效

- 坑（2026-10-22 实测）：自举的 IR 后端给浮点 `!=` 发的是 `fcmp one`
  （有序不等），宿主发的是 `une`（无序不等，`irgen_expr.c:4118`）。差分门里
  `zandb_vector` 有 4 条 "Throws" 断言失败——本该抛 `ArgumentException` 的地方
  没抛。根因在向量索引的有限性判定 `value != value || value - value != 0`：
  有序比较下 `NaN != NaN` 为 false，整条判定恒假，异常永远不抛，后面 600 条
  记录的索引因此多出一堆，断言连环崩。
- 宿主口径不是"IEEE 对称"：`==` 用 **OEQ**（NaN==NaN → false），`!=` 用
  **UNE**（NaN!=NaN → true）。这是 C 的语义（NaN 与任何值都不相等，所以 `!=`
  必真）。自举照抄这张表，别"顺手对称"写成 one/oeq 一对。宿主那张表在
  `irgen_expr.c:4113-4131`（OEQ/UNE/OLT/OGT/OLE/OGE），自举的对应物是
  `irgen_expr.zan` 的 `FCmpOp`。
- **两个后端要各自核对**：原生后端（`ngen.zan` 的浮点比较）当时已经是对的
  （`setne` OR `setp` = not-equal OR unordered），IR 后端是错的。同一个语义有
  两套实现，改了一处不能假设另一处也对——这类差异只有差分门才抓得到。
- 判据（怎么找这类坑）：**看到自反式比较就要警觉**——`x != x`、`x - x != 0`、
  `!(x == x)` 这类写法几乎都是 **NaN 哨兵**（IEEE 的 `x != x` 是 NaN 的标准
  判据）。它的正确性完全挂在 `!=` 是不是无序比较上；有序版本不会报错、不会
  崩，只是**永远为假**，于是所有"检测到 NaN 就该报错"的地方静默失效。
- 推论：数值类的**防御性校验**（有限性、范围、除零）在差分门里常常表现为
  "某条 Throws 没抛"，而不是"结果算错了"。看到 Throws 类失败，先量一下
  触发条件那个布尔表达式在自举里的值。
- 关联：§139（形状/秩跟着类型走）、§141（条件表达式的类型合并）。

## 143. 字典键的**比较方式**跟声明的键类型走：非字符串键是不透明的 64 位 token

- 坑（2026-10-22 实测）：宿主给字典调用发一个 `is_str` 标志，只有键类型
  **正好是 string** 时才是 1（`src/compiler/irgen_expr.c:3391`）；其余键类型
  按**身份**比较（不透明 64 位 token）。自举早期一律按字符串比，于是
  `Dictionary<int,V>.Keys` 交回的是字符串指针（`Dictionary<int,Bm25Document>`
  的 `Keys` 被当成 `List<string>`），下游取整数 id 拿到垃圾 → 空指针解引用。
- 修法不是"在调用点判断键是不是字符串"，而是**把宿主那个 flag 机制整体搬过来**：
  运行时的 `zdict_index/set/get/contains/remove` 多一个 `i64 %is_str` 形参，
  字符串键走 `__zan_strcmp0`，其余走 `icmp eq i8*`（token 身份比较）。
- 键的**槽宽**决定怎么把值变成 token：整数键按键类型位宽截断后 `inttoptr`
  成 `i8*`；引用键直接用地址。**判据是槽宽不是类型名**——擦除的类型参数
  （`Dictionary<TKey,V>`）也走 `i64` 槽，早期按 `IsIntLike(类型)` 判断会漏掉
  这一路，门里会报 clang 拒绝 IR（`'%t49' defined with type 'i64' but
  expected 'ptr'`）。
- 坑：`inttoptr` 出来的 token 与真实对象地址不重叠（小整数 vs 高地址堆指针），
  所以身份比较是安全的；但**键 0 会变成空指针**，别把 0 当成"没有这个键"。
- 字符串键必须由字典持有：首次插入 retain，等值更新保留原键，Remove /
  Clear / 析构 release。`Keys` 返回独立拥有字符串的快照；非字符串 token
  不得按字符串释放。键所有权与值的 owns 标记分开。
- 2026-11-18 固定点差异定位：g2/g3 所有共有函数中仅 `__zan_static_init`
  不同，g3 变空且少 51 个初始化函数。`defs[HeadSymbol(line)]` 的临时键在
  `zdict_set` 后被调用方释放，暴露了运行时未保留键的缺口。遇到闭包静默
  丢根，先对照临时键的 ARC 与容器存储契约；不能用永久保活局部变量绕行。
  回归入口：`dict_temporary_keys` 及 canonical fixed point；通过状态以本轮日志为准。
- 判据：字典相关的差异先问"**这个键的比较规则跟宿主一样吗**"，再问"值对不对"。

## 144. 条件表达式的**分支所有权**：分支临时值必须在分支内释放

- 坑（2026-10-22 实测）：三元表达式 `c ? a : b` 的两个分支各自产生一个
  owned 临时（`new` 出来的对象），自举把它们登记成语句级临时槽，然后在
  **合并点之后**统一释放 —— 于是**没走到的那个分支的槽（还是 null）也被
  release 一次** → `zrelease(null)` → 堆损坏（表现为后面的 Access violation，
  崩点随机，跟三元表达式看着毫无关系）。
- 宿主（`src/compiler/irgen_expr.c` 的 `emit_expr_conditional`）的做法是**在
  分支内**把所有权对齐：两分支所有权不一致时，对"不 owned"的那一侧在分支
  末尾 retain，使两侧都是 owned，phi 的结果就是 owned。
- 修法照抄同文件里**已经写对的 `??`**：每个分支用**隔离的临时槽列表**，
  分支内 `retain` 分支值 → 释放本分支自己的临时 → 再合并出 phi；phi 结果
  登记为语句级临时（`AddTemp`），由语句末尾统一释放一次。
- 判据：**"分支"是一个作用域**。任何在分支里产生、在分支外使用的 owned 值，
  它的释放必须发生在分支内；把分支的临时清单泄漏到外层，就等于让没走到的
  分支也参与释放。

## 145. 浮点**容器槽位**与**数组槽位**的 int→float 口径不同（照宿主）

- 坑（2026-10-22 实测）：宿主把整数写进 `float`/`double` **数组元素**时会
  转成浮点（`float[] v; v[0] = 1;` 读回 1.0），但写进 `List<float>`/
  `Dictionary<K,float>` **不转**，原样存位模式（读回 1.401298464324817E-45
  那个 f32 位模式）。两个口径同时存在，是宿主的既定行为。
- 自举早期两边都不转 → `float[] v; v[0] = 1;` 读回 1.4e-45 → 向量索引的
  范数算成 0 → `ArgumentException("Cosine vector norm must be positive")`。
- 修法：数组路径 store 时 `sitofp i64 → double`（float 元素再 f32 舍入）；
  容器路径 `ToSlot` 用 `alloca i64` + `bitcast i64*→float*` + `load float` +
  `fpext` 重解释位。**不能用 `inttoptr`**（那会把值当地址去解引用），
  **也不能 `bitcast i64→float`**（宽度不同，非法 IR）。
- 判据：这类"宿主怪癖"不要凭直觉统一——**宿主是规格**，包括它自相矛盾的地方；
  差分门比的是 stdout 逐字一致。

## 146. 表达式代码生成严禁对子树无条件重复求值（避免 AST 深度指数爆炸）

- 坑（2026-10-23 实测）：自举 `irgen_expr.zan` 在二元运算符 `+`、`-`、`*`、`/`、`%` 上增加了可空数值类型（`int?` 等）的 lifted 运算支持，但在进入前无条件调用了 `ExprVal la = GenExpr(e.a)`。若 `la.ty` 不是可空（99.9% 场景），则直接穿透到后续的普通二元求值路径，并在那里再次执行 `ExprVal a = GenExpr(e.a)`。
- 对于嵌套二元表达式（例如 `n = n + Count(a) + Count(b) + Count(c) + Count(d)`），每增加一层链式加法，左操作树的 `GenExpr` 求值次数翻倍成 $O(2^{\text{depth}})$，导致深层 AST 遍历（如 `CountAwaits`）产生数十亿次递归调用与庞大的重复指令，造成 `fixedpoint_gen2` 在 `g3.ll` 生成时假死超时（>1200s）。
- 修法：在求值前先用 `ArgTypeNode(e.a)` 做无开销的静态类型预判，仅在左臂明确可能为可空时才先求值；若非可空，复用第一次求得的 `la` 或仅求值一次，严禁对同一 AST 节点调用两次 `GenExpr`。
- 判据：IR 生成阶段的所有 helper 必须严格保持单遍（single-pass）发射。任何试探性分支若需求值子表达式，必须将结果缓存传递或确保提前返回，绝不允许穿透后丢弃并重复发射。

- 语义检查同样要复用接收者推断。`InferType` / `CheckCall` 解析成员接收者后，
  把该类型传入 `MethodUpCall`、候选评分与参数目标类型匹配，保留静态调用和泛型替换。
  `mvc_hardening` 的主线程采样曾反复落在 `InferType → MethodUpCall → CallReceiverType`，
  三条 MVC 用例均超过 120 秒；复用后 `mvc_hardening`、`server_mvc_timezone`、
  `web_route_regex` 均在原预算内匹配宿主输出。

## 147. 字符串头与对象 ARC 头不通用：动态调用返回值不能对字符串字面量 `@zretain`

- 坑（2026-11-10 实测）：在泛型容器（如 `List<T>`）的动态反射调用（`InvokeString`/`InvokeObject`）中，对返回指针如果统一调用 `@zretain`，当被反射方法返回的是字符串常量时，由于字符串在只读 `.rdata` 常量区，其对象头布局为 `[-24]=0, [-16]=len, [-8]=magic (TSNZ/1515082580)`，而不是 ARC 类对象的 `[-24]=cid, [-16]=rc, [-8]=dtor`。调用 `@zretain` 会在 `lock incq -0x10(%rcx)` 处尝试原子递增只读段中的字符串长度字段，直接触发 Windows 0xC0000005 写入访问冲突崩溃。
- 当前口径（2026-11-11）：普通 string 已有独立 `[-32]=rc`，`zretain/zrelease` 必须先区分 class/string 再委派 `zstr_retain/release`，不能直接读写字符串的 `[-16]` 长度槽。字面量 rc=-1；TypeInfo 特殊静态头 cid=kind1..8，必须在读 rc 前排除。动态反射返回值的拥有/借用按实际调用契约处理，不能以跳过全部 string retain 掩盖泄漏。完整布局与受测分配闭账见 [selfhost-string.md](selfhost-string.md)。
- 判据：`tests/selfhost/diff_cases.txt` 收录 `reflect_builtin_list` 钉住。

## 148. 重载候选评分必须考虑接口实现与基类继承（子类型实参精准匹配）

- 坑（2026-11-10 实测）：`ScoreCand` 原先只在 `TypeTag(atn) == TypeTag(pt)` 完全相等时加 4 分，其它任何类型不匹配都减 1 分。当调用传入一个具体实现类（如 `SqliteConnection`），而类上重载分别接收接口（`Create(IDbConnection)` vs `Create(IUnitOfWork)`），两者在原先评分算法中得分相同（均为 -1）。平局时按候选列表第一个决胜，导致传入数据库连接却意外绑定到工作单元重载。在后续 `Dispose` 访问字段时，将 `SqliteConnection` 的数据字段解引用当成 vtable 调用直接崩溃（`rcx = 1, mov (%rcx), %rax` 0xC0000005）。
- 连带效应：自举后端在生成非虚/非接口调用时会进行无用代码剔除（tree-shaking），未被解析选中的方法根本不会发射到 LLVM IR，使问题表现为“重载方法丢失/未生成”。
- 修法：在 `irgen_resolve.zan` 中实现 `TypeImplementsOrDerives`，递归沿着 `interfaces` 与基类链查找目标类型。在 `ScoreCand` 中，接口实现或派生匹配给予适中奖励（+2 分），确保当实参类型满足接口契约时，能够压倒不相关的接口或基类，精准选中正确的接口重载。
- 判据：`tests/selfhost/diff_cases.txt` 收录 `data_connectors_hardening`, `data_orm_hardening`, `orm_transaction_scope` 三案钉住。
