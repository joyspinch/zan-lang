# 数据建模与数据布局通用准则

适用一切"程序怎么组织数据"的场景：服务端数据库、桌面软件的本地库与配置、
游戏的存档与资源清单、进程内的实体结构。核心思想一句话——
**把持久层当"记录存取器"，把智能放到内存里**：存取只做最小粒度的存与取，
过滤、拼装、聚合、格式化都在内存完成。瓶颈经常出现在数据布局上，
而不是代码写法上。

## 一、存取与加工分离

- 持久层（DB/文件/存档）按记录原样存取；跨记录的加工（分组、汇总、
  关联拼装）在内存做。
- 边界要拿捏准：这**不等于**"全部读进内存再算"——持久层有索引/游标时，
  等值过滤和范围截断应该交给它，否则是把该它干的活省下来了。
  正确分工：**持久层做定位（过滤+排序+限量），内存做拼装+格式化**。
- 关联另一份记录时：先取主记录的键列表，再按键批量取副记录，内存按键拼装。
  键控批量取等价于内存 hash 拼装，代价远小于逐条取或全量 JOIN 式扫描。
- 派生数据（计数、最后一条 id、累计值）落成记录上的整数列，
  **写时维护，读时绝不算**——高频列表路径因此永远不需要现场聚合。

## 二、字段准则：4 字节整数倍，定长优先

- 整数一律 4 字节起步（int32/int64），不用 1/2 字节的"节省型"类型。
  布尔、状态、枚举都是整数（0/1/2…）。
  为什么：CPU 与存储引擎都按 4/8 字节对齐工作，1 字节字段省下的空间换来
  对齐补位与比较开销，得不偿失；全 int 记录在内存与磁盘页里都是整齐的
  定长槽位，一次预读带出的有效数据最多，也天然可 memcmp、可二分、可整块换入换出。
- 时间用整数 Unix 秒/毫秒，不用本地化时间格式。
- 金额/比率/坐标定标成整数存——货币用"分"，比率乘固定标度，
  游戏内坐标/属性能用整数就不用浮点（浮点只留给渲染插值）。
- 定长字符串优先；变长文本（正文、描述）绝不进高频访问的主记录，见下一节。
- 每类记录标配：主键 id、创建时间、更新时间、状态位、逻辑删除位。

## 三、主记录窄定长，大字段按键拆分

- 高频路径访问的记录保持"窄 + 定长 + 全整数"：id、外键、计数、状态位。
- 大文本/大 JSON/长数组拆到 1:1 或 1:N 的副记录，副记录主键就是主记录 id。
  判据：这个字段会出现在"列表页/每帧/每行"的访问路径上吗？
  会→主记录；只在点开详情/加载单个对象时用→副记录。
- 为什么：行宽决定一次 IO 能带出多少条有效记录、决定索引/目录页能放多少项；
  窄记录的扫描、计数、翻页全是覆盖式访问，大字段只在真正需要时付一次 IO。
- 高频写（每帧/每请求都会改）的计数字段单独拆放，
  避免它的写放大拖累主记录的读缓存。

## 四、状态三级放置

| 状态 | 放哪 | 生命周期 |
|------|------|---------|
| 瞬时状态（限流计数、互斥锁、任务队列位、统计聚合计数、当前选中/窗口状态） | 进程内存（共享表/字典/原子计数） | 进程内，自动过期或随会话 |
| 热数据（高频访问、可重建） | 缓存层/内存驻留 | 秒~分钟 TTL |
| 事实（业务记录、存档、配置事实） | 持久层（DB/文件/存档） | 永久 |

- 判据一句话：**"丢了要出事吗？"** 丢了没事→内存；可重建→缓存；是事故→持久层。
  把事实放内存=丢数据；把瞬时状态写进持久层=自造热点。
- 游戏对照：存档落持久层的是"事实"（等级、物品、进度）；当前 buff 剩余帧、
  临时开关、UI 状态是"瞬时"，重开可丢；热更资源表可重建，属"缓存"。
- 桌面对照：用户文档是事实；窗口布局/最近列表可重建；剪贴板、拖拽态是瞬时。
- 瞬时状态操作必须原子——"先读再写"两步在并发/多输入源下必然超放或丢更新。

## 五、聚合与索引的数据结构

- 按 key 分组/去重/查重，用**键控结构**（字典/hash 映射/索引数组），
  禁止平行数组 + 手写线性查找（多份列表靠下标对齐是隐性契约，一处 Add 漏掉
  全体静默错位，且每加一个字段要同时改多处）。
- 内存聚合一遍成型：先在键控结构里完成聚合，再统一序列化/渲染；
  不要"边聚合边生成输出"导致第二遍回填。
- 需要按序访问时，键控结构 + 有序键或排序列表，不要为省一个结构退化成每次全表扫。

## 六、生成与单一事实源

- 实体类/字段常量/存档结构这类纯样板，由 schema 事实源生成，不手写：
  结构变更是"重新生成"，不是"人肉找漏"。
- 价值两条，与语言无关：① 字段名等字面量收拢为生成物，引用处不出现裸字符串
  ——手写必然漂移，生成物与 schema 恒一致；② 有静态类型的栈直接生成带类型
  的实体，没有的栈用轻量包装达到同目的。生成是手段，
  **"字段定义单一事实源"才是原则**。

## 七、持久化引擎/文件格式的验证：内存参照模型差分对拍

- 写存储引擎、序列化层、存档格式时，把**固定种子的伪随机操作序列**
  （LCG 即可，禁止时间做种——崩了必须能原样重放）同时打到被测实现和
  一个几十行的内存参照模型（原生 Dictionary 即可），每步对拍数量与取值，
  结尾全量扫描比对，再"关闭→重开加载→再比对"，且重开循环要跨**所有
  持久化档位**各跑一遍。为什么：覆盖顺序、删除墓碑、恢复水位这类状态
  缺陷在单点测试里全绿，只在第 N 步后的状态漂移里显形；实测一轮对拍
  同时抓出归并后墓碑复活、重开序号从 0 起算被恢复水位当陈旧帧跳过、
  以及一个编译器数组字面量 ARC 悬垂（元素串值）三处单测漏掉的缺陷。
- 参照模型只准用最朴素的原生结构，禁止复用被测层的任何旁路设施。
  为什么：参照模型若与被测层共享同一有序结构/编码器，同一缺陷两边
  同时存在，对拍恒绿、形同虚设。
- 对拍失败的定位顺序：先固定种子缩到最小失败前缀，再二分操作序列。
  为什么：300 步里第 280 步才漂移时，全量日志没法肉眼归因；最小前缀
  才能给出可复现、可归因的最小证例。

## 八、评审清单（给一段数据层代码/表结构/存档格式时按序过）

1. 高频路径是窄定长记录 + 键控批量取吗？有没有混进现场 JOIN 式扫描或全量读入？
2. 每个字段是不是 4/8 字节整数（或真正的短文本）？有没有 1/2 字节节省型、
   该定标的浮点、本地化时间格式？
3. 大字段拆副记录了吗？主记录的行宽还在覆盖式访问的友好范围吗？
4. 高频路径有没有现场聚合（COUNT/MAX/逐条累计）？派生数落列了吗？
5. 状态三级各就各位吗？瞬时状态有没有写进持久层？操作原子吗？
6. 聚合/去重用键控结构了吗？有没有平行数组 + 线性查找 + 第二遍回填？
7. 样板实体是 schema 生成的吗？字段定义有单一事实源吗？
