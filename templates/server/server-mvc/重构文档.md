> 目标：按参考框架 `D:\project\soft`(Swoole/PHP) 的标准，把 zan 模板 `templates/server/server-mvc`

## 总纲 · 统一架构原则（所有改动服从这 6 条）

> 现状根子问题：**封装散落、各写各的，缺一条贯穿主线**。本次重构先立总纲，后面每一步都必须服从；
> 任何新增代码若违反其一即视为不合格。

1. **单一真源（Single Source of Truth）**：每类信息只有一个出处。
   - 路由属性 `[Route]/[Http*]/[Custom]/[Description]` = 路由 + 权限 + 菜单 + 统计 key + 接口文档 的唯一来源；
   - 运行配置只在 `Cfg`；站点设置只在 `sys_setting`；字符串常量集中在 `SettingKeys/Routes/Codes`。
   - 杜绝「属性派生 + 手写 seed」这类两套并存会漂移的结构。
2. **约定优于配置**：目录 = 路由 = 菜单分组 = 视图路径；类 = 控制器、方法 = 动作。不靠任何手写映射表。
3. **分层职责单一**：`Controller`(取参/鉴权由网关/组织响应) → `Service`(业务规则，复杂时才有) → `DAO`(SQL) → `Model`(纯数据)。DB 只存取，业务在 zan。DAO 不含业务、Controller 不写 SQL。
4. **跨切面集中在框架入口一层**：鉴权、限流、统计、错误捕获、控制流、日志——全部在 `WebApp` dispatch + 基类里做一次，控制器**不重复**写。
5. **统一基类树**：`AppController`(连接/事务/取参) → `AdminController`(后台外壳) / `ApiController`(JSON) / `FrontController`(前台)。共性只定义一次，子类只写差异。
6. **统一响应/控制流/错误码/分页**：一套 `HttpError` 受控异常 + 顶层出响应；一套错误码表；一套 `ListQuery/Pager`。全站行为一致，调用处无样板 `return`。

> 落地检查：重构后随便点开一个控制器动作，应当只剩「取参 → 调 DAO/Service → 交给基类出响应」三步，鉴权/菜单/统计/错误一行都看不到（都在框架层）。

## 0. 参考框架的标准（已通读，作为对齐基准）

| 维度 | 参考框架做法 | 关键文件 |
|---|---|---|
| 鉴权 | cookie token→`check_token()`→`{uid,gid}`；`gid==1` 超管绕过；基类构造自动 `UserAuth()` | `App/Controller/Controller.php` |
| 授权 | **节点 node=路由**；`@auth/@login/@menu/@rank/@title` 注解 → 反射 `getMethodList()` → upsert `zx_menu`（**绝不手写**）；角色授权 `zx_role_auth{role_id,node,status}`；启动灌入共享表 `_T('auth')`，请求期只查内存 | `Server/Func/Misc.func.php`、`System/Config/Menu.php`、`Model/Sys/{Menu,RoleAuth}Model.php` |
| 菜单 | `zx_menu(is_menu=1)`，非超管按 `zx_role_auth` 过滤，按 `parent_node`(=目录层级) 建树 | `System/Config/Menu.php::action_User_GET` |
| 统计 | `_T('request_stat')[route]={count,ms}` 按接口聚合；`_T('workers_stat')` 每 worker；`_T('current')` 并发；`zx_stat_visit` 每分钟 task 落库 | `Server/Libs/App.php`、`Common/Tick.php` |
| 错误 | `xn_log($msg,'php_xxx_error')` 始终落文件；`debug` 只控制是否把 trace 返回客户端 | `Server/Libs/App.php` catch |
| 控制流 | `response()`=`throw Exception($body,$status)`，顶层 try/catch 统一出响应，**调用处无 return** | `Server/Libs/Controller.php` |
| DB 风格 | 表前缀；大量 int 字段、按常规长度设计；`$table/$index`；软删 `is_delete`；**无外键**，关联存 `*_id` 内存 join | 各 `Model` |

**结论**：zan 框架 stdlib 其实已内建这套（`[Custom(Authorization/IsMenu/MenuGroup/Rank/Icon)]` + `RouteTable`(共享内存) + `MenuBuilder.ForUser`(属性出菜单+resolver 过滤) + dispatch 里 needsLogin/needsAuth 网关）。**问题全在 app 层（Schema/Rbac/各控制器）画蛇添足地手写入库 + 硬编码。**

## 2. 目标架构

> **总原则**：命名标准化（不照搬参考表名）；**权限/菜单禁止任何手动维护，100% 由属性配置派生**，DB 只存「角色→路由 action 授权」这一份运营数据。

### 2.1 授权/菜单（零权限目录表，纯属性驱动，禁止手动维护）
- **唯一模型：路由 action = 权限节点。** 由 `[Custom(Authorization=Login/Auth/ApiAuth, IsMenu, MenuParent, Rank, Icon)]` + `[Description]` 声明，编译期进 `__AttrRoutes` + 运行期进 `RouteTable`(共享内存)。**加一个控制器/动作=加属性即可，不需要也不允许改任何 seed/DB。**
- **删除** `Permission`/`RolePermission` 目录表、`SeedPermissions`/`SeedRoles(授权部分)`/`SyncRoutePermissions`、`AdminMenu.zan`。
- **保留唯一真实数据**：`sys_role`(角色) + `sys_user_role`(用户→角色) + `sys_department_role`(部门→角色) + 新 `sys_role_grant{role_id, action}`(角色→路由 action)。
- **鉴权含部门维度**（对齐你现在的 check_token）：token 只带 `uid`+版本、**不带 gid**；一个用户的角色集 = 直配角色(`sys_user_role`) ∪ 其部门角色(`sys_department_role`)；授权 = 该角色集在 `sys_role_grant` 是否含 `action`；超管(`is_super`)绕过。worker 内存缓存(已有)。
- 菜单：直接用 stdlib `MenuBuilder.ForUser(app, uid, path)`（属性出条目 + `app.Allow` 过滤 + 分组/层级）。
- 角色授权页 `Roles.Grant`：可授权项**来自路由元数据**(`app.router.All()` 里 needsAuth 的 action，按 MenuGroup/MenuParent 分组)，勾选后写 `sys_role_grant`。不再读 `Permission` 表。

### 2.2 Controller 路径规划（目录=路由=菜单层级）
```
Controller/
  Index/       /            Index, Live
  Account/     /account/*   Login, Register
  Admin/
    Dashboard.zan   /admin
    System/    /admin/system/*    Users, Roles, Departments, Dicts, SiteConfig, Logs, Docs
    Content/   /admin/content/*   Articles, Categories, Comments
    Monitor/   /admin/monitor/*   Monitor, Data
    Dev/       /admin/dev/*       Coder, Assistant
  Api/         /api/*       Auth, Data, Index
```
- 路由模板按目录：`[Route("admin/system/[controller]/[action]")]`；`MenuGroup`/层级由目录段自动派生（删手写字符串，禁止手动维护菜单）。
- 视图目录跟随：`views/Admin/System/Users.Index.html` 等。
- 删除 `Admin/Permissions.zan`（权限目录页，无意义）。

### 2.3 Framework 瘦身
- **删**：`AdminMenu.zan`、`Rbac.zan`(逻辑并入 `Auth.zan`)、`Model/Sys/Permission.zan`、`RolePermission.zan`。
- **砍**：`Schema.zan` 只留 `SyncStructure` 表清单 + bootstrap 超管；其余 seed 删。
- **移出到 `src/Feature/`**：`Ai/Gen/Coder`；**归各自模块**：`Mailer/VerifyCode/Presence/Prose/Settings`。
- **保留 Framework 核心**：`Db/DbContext/Cache/CacheContext/AppServices/Cfg/Auth/AppController/AdminController`。

### 2.4 代码质量 · 对齐参考控制流
- 新增 `HttpError`(受控异常)；`Fail/Need/Guard/校验` 一律 **throw**，由 WebApp 顶层 try/catch(已加) 捕获→按 code/status 出 JSON；**非 ajax 出 302 跳登录**(Accept/X-Requested-With 区分，对齐参考 0401/0402)。→ 调用处删掉全部 `if(!...){...return;}`。
- 常量化：`SettingKeys.*`(设置 key)、`Routes.*`(路径)；删裸字符串。
- 参数获取：类型化 `this.In<T>/Need/InInt`(已有) + 上传走 `this.Upload().Path/.Size`；删 `ctx.state.Get("字符串")`。
- 鉴权统一走网关：给 admin 基类/动作补 `Authorization=Login`，删控制器内手写 `Guard(code)`。

### 2.5 统计/错误（阶段 5，方向已定）
- 按接口分组(已) + 按 worker + 并发量 + 访问统计定期 task；长连接(SSE/WS)不计时长、按通讯(帧/消息/字节)计量(已修 SSE 排除)。
- 聚合粒度：内存里按**分钟**聚合桶（时间桶×接口：count/耗时/成败）。
- 落盘：独立 `metrics.db`(WAL)，后台协程异步批量 upsert，**定时+定量触发，默认间隔 1 分钟、可配**（`[metrics].flushSeconds` 默认 60、`[metrics].flushRows` 行数阈值），绝不每请求刷盘；内存环形上限防暴涨。
- 历史查看页 + CSV/JSON 导出（有大小上限、参数校验、脱敏）。
- 错误：始终落盘 + 后台可查页；控制台仅 debug、后台可开关（已加基础，待接后台查询页 + 异步批量）。

### 2.6 DB 命名与字段规范（标准化，不照搬参考表名）
- **命名标准化**：表 `snake_case` 前缀分域（`sys_*`/`blog_*`/`gen_*`），字段 `snake_case`，关联一律 `*_id`，主键 `id` int 自增；**不复制参考的 `zx_*` 表名**。
- 大量用 **int**：状态/开关/类型→`tinyint`(0/1)；时间戳→`int`(秒)；金额→`int`(分)；关联→`*_id int`。
- 字符串按用途给合理 `StringLength`，不撑大。
- **禁止**：外键、存储过程、触发器、视图、级联；关联在 zan 侧按 id 查/内存 join。
- 系统表：`sys_user / sys_role / sys_user_role / sys_role_grant / sys_department / sys_department_role / sys_dict_* / sys_operation_log / sys_login_log / sys_setting`；业务表 `blog_*`；生成器 `gen_*`。

## 4b. 全代码审计发现（臃肿/低效/不合理封装）

> 按「问题→定位→为何不合理→改法」，量化数据来自全 src 扫描。

### F1. 授权双轨 + 硬编码 code（最普遍）
- **量化**：`Guard("sys:...")` 40 处/9 文件；`Layout(...,"sys:...")` 14 处/12 文件。
- 定位：`AdminController.May/Guard/Layout(code)` + 各控制器手写 code；同时 dispatch 又有 `[Custom(Authorization)]` 网关（`WebApp.zan:435-446`）。
- 不合理：同一件事两套判定、code 字符串手写易漂移、和路由 action 是两个真源。
- 改法：删 `May/Guard/Layout(code)`，鉴权全部走网关（action=路由）；菜单走 `MenuBuilder`。

### F2. 控制流啰嗦（Fail 不中断 → 满地 return）
- **量化**：`this.Fail(...)` 106 处/21 文件；裸 `return;` 82 处/22 文件。
- 不合理：参考是 `throw`（顶层统一出响应，0 个 return）；现在每次校验/鉴权失败都要手动 `return;`，漏一个就继续执行。
- 改法：`HttpError` 受控异常 + 顶层 try/catch；`Fail/Need/Guard` 改 throw，删掉 82 处 return 里的错误分支。

### F3. 魔法字符串（设置 key / 路径）
- **量化**：裸设置 key `"site.|auth.|ai.|mail.|..."` 82 处/12 文件；裸路径 `"/admin|/login|/register"` 59 处/22 文件；`ctx.state.Get("...")` 2 处。
- 改法：`SettingKeys.*` / `Routes.*` 常量；上传等中间件产出走类型化访问。

### F4. Settings 用「字符串大 blob + IndexOf」存取（低效/脆弱）
- 定位：`Settings.Blob()` 把所有设置拼成 `name\tvalue\n...`，`Get()` 每次 `"\n"+blob` 再 `IndexOf`，还要 `OneLine/Restore` 转义换行。
- 不合理：每次读一项都要 O(n) 扫整串 + 字符串重建；换行转义脆弱；一个页面 `Apply()` 连读 10 项=10 次全串扫描。
- 改法：缓存**类型化 map**（一次装载 Dictionary），`Get` O(1)；键常量化。

### F5. DTO 过度封装（Java 式样板）
- 定位：`Ai.zan` 的 `AiAgent/AiVendor` = 私有字段 + `Of()` 工厂 + 每字段一个一行 getter（`Code()/Name()/...`）。
- 不合理：zan 支持 `{ get; set; }` 自动属性（`Attributes.zan` 已在用）；纯数据类写十几个 getter 是无谓样板，几百行里一大半是这个。
- 改法：改自动属性，删工厂 + getter 样板。

### F6. 冗余/重复抽象
- `AdminMenu.zan`(224 行) 与 stdlib `MenuBuilder` 重复 → 删。
- `Rbac.zan`(181 行) 的 code↔routeAction↔permissionId 三层间接 → 只留 role→action → 并入 `Auth.zan`。
- `Schema.zan`(565 行) 一半是手写 seed → 砍到表清单 + 超管。
- `Permission/RolePermission` 模型 → 删；换 `sys_role_grant`。

### F7. Framework 混入业务
- `Ai/Gen/Coder`(业务功能) 混在 `Framework/` → 移 `src/Feature/`；`Mailer/VerifyCode/Presence/Prose` 归各自模块。Framework 只留基类+基础设施。

### 审计小结（预计削减）
- 删除文件：`AdminMenu.zan`、`Rbac.zan`、`Model/Sys/Permission.zan`、`RolePermission.zan`、`Controller/Admin/Permissions.zan`（≈700+ 行）。
- 大幅缩减：`Schema.zan`(565→~180)、`Ai.zan`(getter 样板)、各控制器（删 40 Guard + 106 Fail-return 分支）。
- Framework 从 19 文件回到「核心 ~10 文件」，业务功能独立成 `Feature/`。
