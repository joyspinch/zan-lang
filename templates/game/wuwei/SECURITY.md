# 安全与资源保护

## 存档加密（Save.zan）

- 算法：AES-256-GCM（认证加密），密钥 `SaveStore.Key`，AAD `wuwei-save-v1`。
- 落盘格式：`WUW1|nonce|ct|tag` 的 Base64 信封；nonce 每次写入随机生成
  （12 字节），tag 校验失败即视为存档损坏，拒绝载入而不是带着被改过的
  数值继续跑。
- 玩家可见文本（角色名等）不加密——加密的对象是数值表状态。

## 数值表加密（tools/pack_data.py）

发布构建时 `build.ps1` 先把 `data/*.csv`（除 `source_tables.csv` 外的全部
运行时表格）加密成 `wuwei-data` 内嵌进 exe：

- 同一套 AES-256-GCM 信封（`WUW1|…`），游戏启动时解密到内存，
  不落明文盘。
- 开发模式（`-Development`）不做加密，表格明文随行，方便改表。

## 威胁模型（诚实版）

密钥随客户端分发，因此这套保护挡的是：随手用记事本改表改档、
分享“修改器”、破坏存档格式——它不宣称能挡住有心人的逆向。单机游戏
做不到绝对防破解；这里的目标是让篡改需要刻意为之，而不是打开即改。

## 无网络

游戏不发起任何网络请求：不更新、不上报、不联机。exe 旁出现的
`libssl`/`libcrypto` 来自标准库 GUI 的图片 HTTP 能力在发布时的静态链接，
本作不调用它们。

## 发布校验

`build.ps1` 在发布输出目录发现散装的 `data/`、`assets/` 或 `skins/`
目录会直接失败——内嵌失败必须是硬错误，而不是带着明文资源“看起来
也能跑”。`tools/test.ps1` 对产物做同样的检查，并用
`File.EmbedExists` 探针在运行中的游戏里确认资源确实来自内嵌。
